## RAG 隔离（KB / 部门）能否用评测 JSON 测
- 隔离模型（上传即定）：`/upload`(rag_upload.py:323) 收 `kb_id`+`department` 两 Form 字段，文档物理存于 `DOCS_DIRECTORY/{kb_id}/{department}/`。`KNOWLEDGE_BASES`(knowledge_base.py) 分两类：① 业务知识库 biz_inventory/biz_order/biz_product/policy_hr/policy_finance，各自 `owner_depts` 限定可选部门；② **通用公共知识库** policy_general（企业公共制度知识库），`owner_depts=["all"]` 对所有部门开放。
- 部门过滤在检索层**完全支持**：indexer 把 department 写入每个 chunk 的 metadata(indexer.py:569) 并存 chunk_store/doc_registry；pipeline `_prepare_context`(pipeline.py:441) 拼 `mf` dict（kb_id + QueryAnalyzer 的 doc_type/business_domain）→ `RequestContext.metadata_filter`；ChunkLevelRetriever(retrievers.py:162) 把整个 mf 当 Chroma `where`（多 key=AND），hybrid._filter_by_metadata(hybrid.py:18) 对 BM25 也做全 key AND。所以 mf 里多带 `"department"` 即按库+部门同时过滤，**无需改检索器**。
- KB 级隔离**已接入评测**（runner 注入 kb_id）。部门隔离**架构可测但当前未接**：① runner 只注入 kb_id、没注入 department；② 当前 live 数据 rag_test_kb(21)/policy_general(3) 全部 department='general'（因这俩 owner_depts=all、上传默认 general），无部门多样性；③ eval 无"跨部门泄漏"判定。
- 让部门隔离可随 JSON 测需三步：① 准备带真实部门的索引数据（如 policy_general 下 hr/finance 各放文档，或启用业务 KBs）；② runner 注入 `{"kb_id":..,"department":..}` 并加泄漏判定（retrieved chunk 的 department 不在 allowed 集合→fail）；③ JSON 用例加 `expected.allowed_departments/forbidden_departments`，expected 为 schema-free dict 不改模型。
- ⚠️ doc_id 协议隐患：indexer.py:1354 开发者自注 `md5(basename)[:10]` **跨目录同名文件共享 doc_id（当前部署可接受）**。上传去重在 `get_by_path`(按全路径) 不撞；但 doc_registry 级 `get_by_doc_id` 返回单行、评测 `relevant_docs` 按 doc_id 引用——若不同(kb,dept)放同名文件，relevant_docs 会歧义。测试数据须保证 (kb,department) 内文件名唯一。
