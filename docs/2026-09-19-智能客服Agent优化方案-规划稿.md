## 一、假设与待确认问题

在未确认前，后续计划按"默认假设"执行；确认结果只调整指标或范围，不改变总体架构。

| 编号 | 待确认问题 | 默认假设 |
|---|---|---|
| Q1 | 生产峰值流量、同时在线 SSE/WS 数量是多少？ | 20 请求/秒、200 个 SSE、50 个坐席 WS 连接 |
| Q2 | 正式可用性和时延 SLO 是什么？ | 月可用性 ≥99.9%；RAG 完整回答 P95 ≤8 秒；业务查询 P95 ≤2.5 秒 |
| Q3 | 退款、退货、改址是否已有真实写接口？ | 暂无；继续使用明确标识的演示沙盒，禁止显示为真实成功 |
| Q4 | 客服是否需要租户隔离？ | 单租户，但所有数据仍按 user_id 强隔离；若为多租户，所有唯一键与查询需增加 tenant_id |
| Q5 | 对话、附件、审计的保留周期？ | 对话 180 天、附件 30 天、审计 365 天；支持用户删除请求 |
| Q6 | 是否支持外语客服？ | 第一阶段只验收简体中文；其他语言统一转人工 |
| Q7 | 管理端 cs 聊天页及专用组件的删除是否为有意收敛？ | 视为有意删除重复入口，保留 /cs/conversations、/cs/handoff、/cs/stats |
| Q8 | CS Checkpointer 是否计划在生产开启？ | 默认关闭；跨轮恢复必须依赖 PostgreSQL 业务状态，开启/关闭都要通过验收 |
| Q9 | 灰度发布是否允许按会话稳定分桶？ | 允许，按 5%→20%→50%→100% 放量 |
| Q10 | 多模态优先级是什么？ | 核心文本链路稳定后，只先做图片/截图；语音和视频不进入本期 |

> **Q 确认记录（2026-09-19）**：
> - Q3 = 暂无真实写接口，用演示沙盒（= 默认假设）。
> - **Q4 = 多租户（≠ 默认假设，实质性范围变更）**：所有新增客服业务状态表（案件快照、确认、工单、事件、附件）的唯一键与查询必须携带 `tenant_id`；权限模型按租户维度校验；JWT tenant claim → 网关注入链路（WP-A 已建）作为租户权威来源。P1/P2 表结构设计与迁移据此执行。
> - Q5 = 对话 180 天 / 附件 30 天 / 审计 365 天（= 默认假设）。
> - Q7 = 确认为有意收敛删除，13 项删除可随 WP-D 提交（保留 /cs/conversations、/cs/handoff、/cs/stats）。
> - Q1/Q2/Q6/Q8/Q9/Q10 继续按默认假设执行；后续确认只调整指标或范围，不改变总体架构。

## 二、当前项目判断

现有系统不需要推倒重写，正确方向是"收敛并补齐闭环"。

| 能力 | 当前基础 | 主要缺口 |
|---|---|---|
| 输入门禁 | 已有 NFKC 规范化、注入/有害输入检测、CS 专用 Guard | normalized_query 未作为下游唯一处理文本；全局 Guard 与 CS Guard 职责重叠；无统一实体、缺失槽位、情绪契约 |
| 路由 | 主图三层 Router、CS 预过滤、20 个细粒度意图、规则优先 | 评测集仅 20 条；当前 CS Runner 直接以空 cs_route 调子图，未完整覆盖入口预过滤和 CSRouter |
| Agent 决策 | 客服 9 节点子图、5 专家、循环上限 5、递归上限 20 | Supervisor 仍存在边界 LLM；简单请求和复杂任务的成本口径未形成质量门禁 |
| 记忆 | 已有 L1 短期窗口、L2 摘要、L3 长期记忆、Token 裁剪 | 缺少客服专属的结构化案件快照；订单号、已确认事实、未解决项仍分散在消息和多个状态对象中 |
| 状态可靠性 | 已有确认、转人工、审计、Redis 事件、Celery 清理任务 | ConfirmationStore 部分路径仍允许 L1 内存先成功、DB 写失败后仅告警，与"PG 唯一事实源"冲突 |
| RAG | 已有混合检索、Rerank、EvidenceGate、引用生成 | 客服评测未系统覆盖错别字、冲突政策、金额、时效、版本失效和低证据拒答 |
| 人工接管 | 队列、认领、回复、关闭、WS/轮询、事件补发均已有实现 | 需要真实故障演练；缺少明确的等待 SLA、情绪升级标准和全链指标 |
| 多模态 | 消息模型已有 attachments 字段 | 没有上传入口、文件安全、OCR/视觉理解、附件权限与生命周期闭环 |

## 三、目标与成功标准

以下为上线门禁，不满足即不得进入 100% 流量。

| 目标 | 可检查的成功标准 |
|---|---|
| 路由正确 | 客服黄金集不少于 300 条；意图 Macro-F1 ≥0.92；退款、投诉、显式转人工召回率分别 ≥0.98；非客服转主图精确率 ≥0.95 |
| 简单请求低成本 | FAQ、订单/物流查询不得调用 Planner；确定性可判定样本中 Supervisor LLM 调用率 ≤10%；同一评测集平均输入 Token 比基线下降 ≥25% |
| 实体和槽位正确 | 订单号、物流号、金额、动作类型、商品实体的精确匹配率 ≥0.95；订单号与金额错误改写为 0/500；缺必填槽位时发起澄清率 100% |
| 回答可信 | 需引用的知识问答引用率 100%；受证据支持的声明比例 ≥0.95；无证据场景拒答/澄清召回率 ≥0.95；伪造订单状态、金额、退款结果为 0/500 |
| 状态一致 | 20 个并发确认请求只允许 1 次状态认领；20 个并发坐席认领只允许 1 个成功；PostgreSQL 故障时高风险写操作成功数必须为 0 |
| 权限安全 | 跨用户读取、评分、确认、消息查询、工单操作共不少于 100 个越权用例，拒绝率 100%；未经确认的高风险执行数为 0 |
| 上下文稳定 | 20 轮对话中已确认槽位保持率 ≥0.95；跨会话、跨用户事实泄露为 0/500；所有模型请求不超过配置 Token 上限 |
| 实时恢复 | SSE/WS 各执行 100 次随机断线；恢复后消息丢失数为 0、重复展示数为 0、事件顺序错误数为 0 |
| 人工接管 | 显式转人工工单创建成功率 ≥99.9%；工单在坐席队列可见 P95 ≤2 秒；waiting_human/human_active 状态下 AI 抢答次数为 0 |
| 性能 | 首个 status 事件 P95 ≤300ms；确定性业务查询完整响应 P95 ≤2.5 秒；RAG 首个回答增量 P95 ≤2 秒、完整响应 P95 ≤8 秒 |
| 业务效果 | 标记为 self_service=true 的黄金集自动解决率 ≥80%；能力缺口转人工率 ≤10%；累计有效评价 ≥100 后平均评分 ≥4.2/5 |
| 稳定性 | 月可用性 ≥99.9%；服务端错误率 <1%；Redis、Worker 重启不丢失业务状态；PG 恢复后无双执行 |

## 四、范围边界

### 做

- 保留主图 8 个核心节点及现有客服 9 节点子图。
- 统一输入规范化、实体/槽位、情绪、风险和路由结构。
- 让规则、状态机和权限系统控制最终动作，LLM 只处理边界识别和文本生成。
- 将客服结构化上下文、确认、转人工、动作和审计收敛到 PostgreSQL。
- 补齐 SSE/WS 恢复、故障演练、评测集、质量仪表盘和灰度门禁。
- 保持 APISIX 为 API、SSE、WebSocket 唯一入口。

### 不做

- 不新增第二套 Router、Supervisor、Store 或编排系统。
- 不修改主图核心节点数量和固定命名，不把客服节点手写进主图 Builder。
- 不把同步 /chat/stream 放入 Celery。
- 不在真实业务写接口缺失时实现真实退款、付款、改址或账号修改。
- 不把模拟结果包装成真实执行成功。
- 不在核心文本链路通过验收前上线语音、视频或情绪声学识别。
- 不把全部请求交给 LLM 分类，也不以提示词调优代替权限、事务和规则校验。
- 不对无关 RAG、旅游、选品、SQL、认证链进行重构。

### 停止条件

任一条件出现即停止当前阶段并回滚到上一灰度版本：

1. 出现 1 次跨用户数据访问。
2. 出现 1 次未确认高风险动作或重复业务执行。
3. PostgreSQL 写失败后仍向用户返回"成功"。
4. 数据库迁移不可降级，或生产演练中锁表超过 30 秒。
5. 核心意图召回率低于 0.98，或整体 Macro-F1 低于 0.92。
6. 相对基线错误率增加超过 0.5 个百分点，或 P95 时延增加超过 20%。
7. Redis/Worker/应用重启造成 1 条业务消息或状态永久丢失。
8. 待改文件与当前未提交改动重叠且无法确认所有权。

## 五、总体做法

推荐采用"增量收敛"，不新建平台副本。

```
APISIX
  → 全局 Input Guard：清洗、安全、脱敏标记
  → CS Prefilter：是否进入客服域
  → CSUnderstanding：意图、实体、槽位、情绪、风险、置信度
  → 客服子图确定性分派
      ├─ Knowledge → RAG + EvidenceGate
      ├─ Query     → 订单/物流/账户 Service
      ├─ Action    → 资格检查 → 确认 → 幂等执行
      ├─ Complaint → 工单/安抚/升级
      └─ Handoff   → 人工队列
  → Output Guard + 规则校验
  → PostgreSQL 持久化 + Redis 事件
  → SSE/WS 交付与断线补发
```

统一理解契约至少包含：

```json
{
  "raw_text": "...",
  "normalized_text": "...",
  "domain": "AFTER_SALES",
  "intent": "as_refund",
  "confidence": 0.96,
  "entities": {"order_id": "ORD-1001"},
  "missing_slots": [],
  "sentiment": "angry",
  "urgency": "high",
  "risk_level": "high",
  "next_action": "propose_refund",
  "decision_layer": "rule"
}
```

原文只用于审计和展示；路由、检索、实体提取使用规范化文本。订单号、物流号、金额、邮箱和手机号不得被纠错器改写。

## 七、依赖与风险

| 依赖/风险 | 可检查影响 | 控制措施 |
|---|---|---|
| 当前工作区存在大量未提交改动 | 目标文件发生覆盖或错误归因 | P0 输出文件级所有权清单；未确认重叠文件不得编辑 |
| 真实退款/改址接口缺失 | 无法验收真实写操作 | 本期仅验收 proposal、确认、幂等和沙盒结果；真实写接口单独立项 |
| 身份与租户口径未确认 | 唯一键和权限模型可能返工 | Q4 未确认前不得新增正式业务状态表 |
| 当前 CS 数据集仅 20 条 | 路由准确率无统计意义 | P0 扩至固定 300 条并锁定版本 |
| LLM/Embedding 网络波动 | P95、错误率不可重复 | 分离模型耗时与业务耗时；设置硬超时；使用固定输入跑 3 轮取中位数 |
| 知识库政策版本无业务负责人 | 旧政策可能被正确检索但业务上错误 | 每份政策要求 effective_at/expires_at/owner/version；缺字段不得进入生产 KB |
| 情绪识别误判 | 普通用户被错误升级或降权 | 情绪只影响语气和转人工优先级，不直接触发业务写操作 |
| Redis/事件补偿不完整 | 多进程消息漏发 | PostgreSQL 事件表为补发来源；Redis 只承担通知，不作为事实源 |
| 长期记忆保存敏感信息 | 隐私泄露 | 资金、密码、证件、完整地址禁止进入 L3；通过 100 个 PII 用例验证 |
| 坐席数量和服务时间未知 | 转人工 SLA 无法成立 | Q1/Q2 未确认前只承诺"入队可见 ≤2 秒"，不承诺接通时间 |

## 八、验收清单

- [ ] 客服黄金集 ≥300 条，数据分布符合 P0 步骤 2。
- [ ] 意图 Macro-F1 ≥0.92，退款/投诉/转人工召回率均 ≥0.98。
- [ ] FAQ 和标准查询不调用 Planner。
- [ ] 所有金额、订单号、业务状态来源可追溯到 DB 或知识证据。
- [ ] 未确认高风险动作执行数为 0。
- [ ] 并发确认和并发认领各只有一个成功者。
