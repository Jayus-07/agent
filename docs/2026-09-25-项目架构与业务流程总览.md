## 一、项目定位与技术栈

**电商 RAG + Multi-Agent 平台**：以 PostgreSQL + pgvector 为唯一存储底座、LangGraph 为编排核心的多域智能体系统，含客服、旅游（规划/商务/预订）、选品漏斗、SQL 分析、RAG 知识问答等业务域。

| 层 | 技术 |
|---|---|
| 网关 | APISIX `:9080`（**唯一入口**）：JWT 验证 → 注入 X-User-Id 等身份头（Bearer 优先于 X-API-Key）→ 路由/SSE/WS |
| 应用 | FastAPI（`app` 容器 `:8000`）+ LangGraph（主图 + 域图，postgres checkpointer 可选） |
| 异步 | Celery 五队列（Redis 兼 broker/result backend），状态权威在 PG |
| AI | DeepSeek（langchain-openai 兼容接口）；嵌入 bge-m3 + reranker-v2-m3（硅基流动） |
| 数据 | PostgreSQL 18 双库：`agent_business`（业务）/ `agent_memory`（元数据/幂等账本/checkpoint），docker `agent-postgres-1` 宿主映射 **5433** |
| 前端 | Next.js 14 ×3：用户端 `:3100`、管理端 `:3200`、客服坐席工作台 `frontend-cs:3300` |
| 服务化 | rag-service `:8090`（检索/mcp `:8091`）、oa-auth-service（Java，登录链路经 APISIX `/api/auth/**`） |

## 二、系统分层架构

```text
┌─ L5 网关层 ────────────────────────────────────────────────┐
│ APISIX :9080  JWT 验证 / 身份头注入 / SSE·WS / 网关鉴权插件  │
├─ L4 编排层 ────────────────────────────────────────────────┤
│ GraphRunner（Input Guard → memory.start_session → graph）   │
│ 主图 8 核心节点 ｜ 5 域图（自注册，不改 builder.py）         │
├─ L3 能力层 ────────────────────────────────────────────────┤
│ Planner(Capability DAG) → 12 Skill → 28+ Tool → 4 Workflow  │
│ 方向铁律：上层调下层；Tool 不得 import Skill                │
├─ L2 服务层 ────────────────────────────────────────────────┤
│ rag-service:8090 ｜ MCP 2 server·5 tool ｜ providers        │
│ （travel live/fake 七态契约 + booking 三能力 profile）      │
├─ L1 数据层 ────────────────────────────────────────────────┤
│ PG:5433 双库（业务 7 schema×18 表 + 元数据/账本）           │
│ Redis（共享热状态/降级队列/事件通知）｜ Celery 5 队列        │
└────────────────────────────────────────────────────────────┘
```

### 主图 8 核心节点（顺序与命名不得改动）

```text
POST /chat/stream → GraphRunner 门禁 → START → router ─┬─ 客服域锁/CS 预过滤 ──→ cs_graph_node → END
                                                        ├─ 旅游预过滤 ──────────→ travel_graph_node → END
                                                        ├─ 选品预过滤 ──────────→ 选品漏斗域图 → END
                                                        ├─ 预订 prefilter ──────→ booking 域图 → END
                                                        ├─ 商务 prefilter ──────→ commerce 域图 → END
                                                        └─ 三层 Router(rule→vector→LLM) → route_selector
                                                             ├─ direct   → skill_executor（跳过 Planner）→ reporter → END
                                                             ├─ workflow → workflow_executor → reporter → END
                                                             └─ plan     → planner → critique → supervisor(Send 并行) → reporter → END
```

**预过滤优先级：客服 > 旅游 > 选品 > 预订 > 商务**（交易意图不得降级为 search）。三条域开关 `CS_ENABLED` / `TRAVEL_ENABLED` / `SELECTION_FUNNEL_ENABLED` 代码默认全关，由根 `.env` 决定；`TRAVEL_COMMERCE_ENABLED` / `TRAVEL_BOOKING_ENABLED` 同理。守护用例：`tests/orchestration/graph/test_router_prefilter_order.py`。

### 四层模型与注册铁律

- **Planner** 只拆解（禁调 Tool/DB）→ **Critique** 规则优先（仅 anomaly 调 LLM）→ **Supervisor** 纯规则 DAG 调度 → **Skill** 业务封装（不碰外部系统）→ **Tool** 无状态原子操作 → **MCP** 是 Tool 的第二出口。
- **G1-G4**：声明式注册、启动期派生、fail-fast；`capabilities.yaml` 是 capability→Skill→节点映射唯一事实源（G2 禁手抄）；谁定义谁注册（G3）；例外必须登记台账（G4）。
- 新增资产接线点速查：Tool 2 处 / Skill+capability 5 处（漏 `capabilities.yaml` = 永远路由不到）/ Workflow 3 处 / MCP 2 处 / 域图 5~7 处（prefilter 必须插进 `router_node.py`）。

## 三、业务流程

### 3.1 统一聊天入口（SSE 流式）

`POST /chat/stream` 同步执行、不经队列：Input Guard 门禁 → `memory.start_session` → `graph.stream` → 节点 status/log + LLM delta 汇入 `merged_q` → SSE 帧序 `meta → status/log/delta → done/error`。上下文预算防线（L1-L5）贯穿每次模型调用；trace 全链贯穿（request_id 可关联 conversation/message/trace/action/task）。

### 3.2 客服域流程（`backend/customer_service/`）

```text
窗口锁域（domain_hint=cs，跳过判域/灰度）或全局入口 CS 预过滤（灰度 CS_ROLLOUT_PERCENT）
  → 子图 9 节点：state_loader → pending_handler → cs_supervisor（handoff 拦截/循环上限/LLM 兜底）
      → 5 专家（knowledge/query/action/complaint/handoff）→ 回 supervisor → cs_reporter
```

- **转人工**：显式/情绪/低置信触发 → 工单入队（P95 ≤2s 可见）→ 坐席 WS 实时推送；WS 断 >30s 自动降级轮询、恢复自动切回；`after_seq` 事件回放补齐；AI 抢答禁止。
- **动作确认链**（退款/退货/换货/改址等高风险动作）：动作专家资格检查 → 确认卡（PENDING）→ 用户确认 → **原子条件 UPDATE 认领**（并发 20→1）→ 幂等执行。三层防线：①业务实体唯一守卫（051 partial unique：同租户+动作+实体+语义指纹的 active 操作全局一行，并发由唯一索引决胜）②Phase2 side-effect ledger（owner CAS + IN_DOUBT 阻断）③provider 幂等键。执行未知（`SideEffectOutcomeUnknown`）一律转 `verifying` 对账态，绝不谎报成功/失败。

### 3.3 旅游规划流程（`backend/travel/`）

```text
slot_filler（槽位补齐）→ travel_supervisor（纯规则）→ poi/transit/budget/risk 四专家
  → travel_validator（时间/地理/体力/预算四轴，纯规则零 LLM，只判定不修改）
    → 未通过 → travel_repair（局部修复，用户点名条目永不被静默丢弃）→ 回 supervisor
  → travel_reporter
```

跨轮续订：brief 指纹变化触发 planning_reset；上下文存 Redis 分布式仓库（WATCH→mutation→MULTI 原子写，进程内 dict 仅降级/单测）；thread 前缀 `travel:{conv}` 防与 CS 共表覆盖。

### 3.4 旅游商务与预订流程（STOP K/L，`backend/travel/commerce/` + `backend/travel/booking/`）

```text
「帮我订大阪10月3日梅田广场酒店」
  → booking prefilter（TRAVEL_BOOKING_ENABLED）→ 2 节点域图（零 LLM）：
     booking_resolver（新预订/确认/状态查询）→ booking_executor
  → Quote 不可变快照（DB trigger 级守卫 + sha256 指纹 + 双时钟 expiry）
  → 显式确认 gate（绑定指纹：quote/金额/币种/provider/租户/用户/过期）
  → 价格库存复核（Decimal 精确比较；变化→阻断并强制重新确认）
  → 幂等执行（intent/merchant_order_id 确定性派生；复用全局 PG 账本 +
     Provider 三模型决策矩阵：A=同 key 重放 / B=先查再重试 / C=IN_DOUBT 人工）
  → 状态机集中 CAS + status_version 单调（QUOTED→…→BOOKED/FAILED/IN_DOUBT）
  → Webhook Inbox（HMAC 签名/重放窗口/去重/未知订单隔离）
  → Reconciliation（查询事实 ≠ 重试）+ Recovery 扫描（maintenance beat）
```

9 类故障场景（双击/HTTP 重试/worker 重跑/provider 超时/成功后本地崩溃/webhook 重复/乱序/价格改变/DB 短暂故障）全部有探针钉死：不悄悄多订、不把未知说成成功、也不把未知说成失败。

### 3.5 RAG 问答链路

改写 → MultiQuery → 混合检索（pgvector 向量 + BM25）→ 同文档扩展 → Rerank → **EvidenceGate**（证据不足拒答/澄清）→ 带引用生成 → META 尾拒答判定。客服知识问答受同一套 EvidenceGate 与引用纪律约束。

### 3.6 异步任务流（`backend/tasks/`）

```text
入队 → QueueRouter（单一事实源，未登记 fail-closed）→ 5 物理队列：
  interactive_agent ｜ rag_index ｜ metadata_shadow ｜ report ｜ maintenance
执行：PG 任务行状态权威 + 租约 execution_id + fencing（失权写拒绝）
语义：at-least-once；错误分类学（业务终态不重试）；SIGKILL → visibility_timeout 恢复
自愈：pending_recovery（主动 CAS 认领）/ zombie_reconcile / stale_execution_recovery / idempotency_retention
```

### 3.7 SQL 分析子系统

`SQLSkill → SQLAgent → Router → Generator → Validator(6层) → RowSecurity → Executor(连接池) → PG`。六层安全：SELECT 校验 / 表白名单 / 敏感列拒绝 / 函数黑名单 / LIMIT 强制 / agent_readonly 只读角色。

## 四、数据架构

- **agent_business**：7 schema × 18 表（product / order / inventory / customer / crawler / finance / ai）。
- **agent_memory**：`tasks`（任务权威）、`ai.idempotency_records`（幂等账本，031/047）、`ai.tool_approval_requests`（审批单，007）、confirmations（051 补 tenant_id + semantic_fingerprint）、CS conversations/events（028 outbox）、`travel.*`（052：booking_quotes / booking_orders / booking_webhook_inbox / booking_events）、langgraph checkpoints、记忆三层表。
- 迁移只走 `backend/sql/migrations/`（000→052），新迁移必须登记 `MIGRATION_TARGETS`（未登记 init_db 即报错）；金额 DECIMAL、时间带时区。

## 五、安全与可靠性机制（横切）

| 机制 | 落点 |
|---|---|
| 写操作审批门 | 副作用工具执行前 `tool_approval.ensure_approved()`，管理员 `/api/approvals` 批准后同指纹放行 |
| 身份链 | 登录（Java auth-service）→ JWT（py 自建 issuer=agent-platform）→ APISIX 验证并注入身份头 → 服务端重解析 tenant/user（前端不可信：金额/provider 一律服务端重读） |
| 租户隔离 | JWT tenant claim → 网关注入 → 全部新增业务表唯一键/查询带 tenant_id |
| 幂等三层 | 技术幂等（PG 账本）→ 业务实体唯一守卫（语义指纹）→ provider 三模型矩阵 |
| 上下文预算 | L1-L5 防线 + Redis CAS + semantic pin；模型请求永不超配置窗口 |
| 可观测 | trace 全链贯穿、Prometheus（multiproc 四 worker）、travel_booking_* / cs_* 低基数指标 |
