## 一、总体说明

### 1.1 当前平台可复用能力

两个方案均可在现有平台基础上扩展，不必从零搭建：

| 现有能力                         | 方案 3 复用点                    | 方案 4 复用点                       |
| ---------------------------- | --------------------------- | ------------------------------ |
| **Multi-Agent 编排**           | 5 节点编排上层兴趣挖掘 / 下层场景推荐 Agent | 抓取 → 清洗 → 抽取 → 分析 → 报告 Agent 链 |
| **RAG 6 段流水线**               | 商品知识库、SOP、用户画像文档检索          | 竞品公开资料、行业报告检索                  |
| **Web 抓取 Skill**             | 补充外部商品/价格信息                 | 核心数据入口                         |
| **Report Skill + Jinja2 模板** | 推荐效果日报 / 用户画像报告             | 竞品分析报告、策略建议                    |
| **Workflow 引擎**              | 推荐模型定时训练、效果反馈重算             | 定时抓取 → 分析 → 报告推送               |
| **SQL Agent + PostgreSQL**   | 用户行为数仓查询、AB 实验指标            | 竞品价格/库存数据查询                    |
| **Trace + Metrics**          | 推荐链路 latency / 转化率观测        | 抓取成功率 / 报告质量观测                 |

### 1.2 两个方案的本质差异

| 维度           | 方案 3：多 Agent 电商推荐系统                 | 方案 4：Agent 竞品分析系统          |
| ------------ | ----------------------------------- | -------------------------- |
| **系统性质**     | 在线实时推荐服务（影响核心转化）                    | 离线/近实时分析系统（决策支持）           |
| **延迟要求**     | 极严格（端到端 < 200ms）                    | 宽松（分钟/小时级）                 |
| **数据依赖**     | 高度依赖内部用户行为数据质量                      | 依赖外部公开数据源                  |
| **业务风险**     | 高（推荐策略直接影响 GMV）                     | 中低（报告辅助决策，不直接改链路）          |
| **技术复杂度**    | 高（需特征工程、召回、排序、在线服务）                 | 中（爬虫 + LLM 抽取 + 报告）        |
| **与现有平台契合度** | 中（Agent 适合解释/策略，但实时 ranking 需传统 ML） | 高（几乎完全匹配现有 Skill/Workflow） |

## 二、方案 3：多 Agent 电商推荐系统

### 2.1 方案概述

根据截图，系统分为两层：

```
上层：用户理解与兴趣挖掘
  用户行为采集 → 兴趣挖掘 Agent（推理分析） → 用户画像 Agent（标签体系）
                              ↓
下层：场景匹配与推荐决策
  场景识别 Agent（场景理解） → 场景匹配 Agent（策略匹配） → 商品推荐 Agent（排序推荐） → 效果反馈 Agent（效果评估）
```

核心目标：多智能体协同挖掘用户偏好，结合实时场景精准推荐商品，提升转化率。

### 2.2 实施步骤拆解与排序

#### Phase A：数据基座（第 1-4 周）

| 步骤 | 任务         | 关键产出                               | 备注                     |
| -- | ---------- | ---------------------------------- | ---------------------- |
| A1 | 业务场景与数据源盘点 | 推荐场景清单、现有行为事件表                     | 明确首页/详情页/购物车/搜索无结果等推荐位 |
| A2 | 用户行为事件埋点补齐 | 点击、曝光、加购、下单、收藏、搜索词事件               | 若已有埋点则做质量校验            |
| A3 | 用户画像特征仓库   | user_profile 表 / Redis 特征缓存        | 人口属性、偏好类目、价格带、生命周期     |
| A4 | 商品画像与索引    | product_feature 表 + ChromaDB 向量索引  | 类目、属性、卖点、价格、库存、销量      |
| A5 | 场景上下文定义    | context_schema（页面、设备、时间、地理位置、会话轨迹） | 作为场景识别 Agent 输入        |

#### Phase B：上层 Agent：兴趣挖掘与用户画像（第 3-6 周）

| 步骤 | 任务         | 关键产出                                     |
| -- | ---------- | ---------------------------------------- |
| B1 | 兴趣挖掘 Agent | 基于近期行为的 LLM 推理模块，输出兴趣标签与权重               |
| B2 | 用户画像 Agent | 标签体系管理、画像更新策略、画像解释生成                     |
| B3 | 画像存储与更新机制  | 批量日更 + 实时增量更新                            |
| B4 | 画像可解释性接口   | `/recommendation/user_profile/{user_id}` |

#### Phase C：下层 Agent：场景匹配与推荐决策（第 5-10 周）

| 步骤 | 任务             | 关键产出                                          |
| -- | -------------- | --------------------------------------------- |
| C1 | 场景识别 Agent     | 输入 context，输出场景类型（如「闲逛」「明确购买」「比价」「补货」）        |
| C2 | 召回层建设          | 多路召回：协同过滤、内容相似、热门、新品、向量相似、规则兜底                |
| C3 | 场景匹配 Agent     | 根据场景选择召回策略组合与粗排权重                             |
| C4 | 商品推荐 Agent（排序） | 精排模型 + Agent 解释生成；初期可用轻量模型（LR/GBDT），后期上深度模型   |
| C5 | 效果反馈 Agent     | 实时收集曝光/点击/转化，回流模型训练                           |
| C6 | 推荐服务 API       | `POST /recommendation/recommend`（< 200ms P99） |

#### Phase D：前端集成与实验体系（第 9-14 周）

| 步骤 | 任务       | 关键产出                   |
| -- | -------- | ---------------------- |
| D1 | 推荐位前端组件  | 推荐卡片、瀑布流、猜你喜欢组件        |
| D2 | AB 实验平台  | 分流、指标看板、显著性检验          |
| D3 | 灰度发布     | 5% → 30% → 100% 流量逐步放量 |
| D4 | 推荐效果运营后台 | 规则干预、黑名单、冷启动策略配置       |

#### Phase E：持续优化（第 13-16 周及以后）

| 步骤 | 任务    | 关键产出                    |
| -- | ----- | ----------------------- |
| E1 | 模型迭代  | 引入序列模型 / 双塔模型提升 CTR/CVR |
| E2 | 多目标优化 | CTR、CVR、GMV、多样性平衡       |
| E3 | 实时化升级 | Flink 实时特征、在线学习         |

### 2.3 关键里程碑及时间节点

| 里程碑                | 时间      | 验收标准                                         |
| ------------------ | ------- | -------------------------------------------- |
| **M1：数据基座就绪**      | 第 4 周末  | 行为事件可稳定入仓；用户/商品画像表可用；特征覆盖率 > 80%             |
| **M2：画像 Agent 上线** | 第 6 周末  | 兴趣标签可解释；画像更新延迟 < 1 小时；接口响应 < 500ms           |
| **M3：推荐服务内测**      | 第 10 周末 | 推荐 API P99 < 200ms；多路召回 + 精排打通；Agent 可输出推荐理由 |
| **M4：AB 实验上线**     | 第 14 周末 | 至少 1 个推荐位灰度至 30% 流量；CTR 提升 > 5%（置信区间 95%）    |
| **M5：全量发布**        | 第 16 周末 | 核心推荐位 100% 流量；效果反馈闭环跑通；运营后台可用                |

### 2.5 潜在风险识别及应对措施

| 风险                 | 影响               | 概率 | 应对措施                                                      |
| ------------------ | ---------------- | -- | --------------------------------------------------------- |
| **实时 latency 不达标** | 推荐位卡顿，影响用户体验     | 高  | ① Agent 只做策略/解释，排序用轻量模型；② Redis 缓存用户画像；③ 召回预计算；④ 异步生成推荐理由 |
| **用户行为数据稀疏**       | 冷启动效果差，推荐不准      | 中  | ① 新用户走热门/规则兜底；② 基于商品内容相似；③ 快速收集偏好问卷                       |
| **推荐负向影响 GMV**     | 推荐策略反而降低转化       | 中  | ① 严格 AB 实验；② 设置熔断规则；③ 保留原策略作为兜底                           |
| **画像标签解释不可信**      | 运营/用户不信任推荐理由     | 中  | ① Faithfulness NLI 校验；② 人工抽检；③ 标签置信度阈值过滤                  |
| **多 Agent 协作失败**   | 某 Agent 失败导致推荐中断 | 中  | ① 每步设置超时 + fallback；② 降级到简单规则推荐；③ Supervisor 卡死检测         |
| **数据隐私合规**         | 用户行为收集越界         | 低  | ① 仅采集必要行为；② 匿名化存储；③ 符合个人信息保护法                             |

## 三、方案 4：Agent 竞品分析系统

### 3.1 方案概述

根据截图与文字描述，系统分为三层：

```
数据抓取层：全网数据源 → 爬虫 Agent → 数据存储
解析层：数据清洗 → 信息抽取 → 竞品拆解 → 优劣分析
报表输出层：可视化报表 → 策略建议 → 竞争研判报告
```

核心目标：自动全网抓取竞品数据，智能拆解优劣，输出市场策略与竞争研判报告，几乎无需人工参与。

### 3.2 实施步骤拆解与排序

#### Phase A：需求与数据源规划（第 1-2 周）

| 步骤 | 任务     | 关键产出                        |
| -- | ------ | --------------------------- |
| A1 | 竞品清单确认 | 核心竞品 5-10 家、监测 SKU/类目范围     |
| A2 | 数据源清单  | 官网、新闻站点、社交媒体、公开数据库、电商平台     |
| A3 | 数据字段定义 | 价格、促销、新品、评价、品牌动作、市场声量等字段    |
| A4 | 合规评估   | robots.txt 检查、网站服务条款、数据使用范围 |

#### Phase B：数据抓取层（第 2-5 周）

| 步骤 | 任务          | 关键产出                                 |
| -- | ----------- | ------------------------------------ |
| B1 | 爬虫 Agent 框架 | 基于现有 `web_crawl` Skill 扩展，支持定时/增量/全量 |
| B2 | 多源适配器       | 官网、电商详情页、新闻 RSS、社交媒体 API 适配器         |
| B3 | 反爬与稳定性      | 代理池、请求频率控制、User-Agent 轮换、验证码兜底       |
| B4 | 数据存储        | 原始页 / 结构化数据表 / 变更历史表                 |
| B5 | 抓取调度        | APScheduler / Workflow 引擎定时触发        |

#### Phase C：解析层（第 4-7 周）

| 步骤 | 任务         | 关键产出                       |
| -- | ---------- | -------------------------- |
| C1 | 数据清洗 Agent | HTML 去噪、编码统一、重复检测          |
| C2 | 信息抽取 Agent | 基于 LLM 抽取价格、SKU、促销、卖点、评价情感 |
| C3 | 竞品拆解 Agent | 产品矩阵、价格带、渠道、目标人群分析         |
| C4 | 优劣分析 Agent | SWOT 分析、与本品牌对比、价格竞争力评分     |
| C5 | 数据校验规则     | 价格异常检测、字段完整性校验、置信度评分       |

#### Phase D：报表输出层（第 6-9 周）

| 步骤 | 任务         | 关键产出                        |
| -- | ---------- | --------------------------- |
| D1 | 报告模板设计     | 日报 / 周报 / 专题报告 Jinja2 模板    |
| D2 | 可视化报表      | 价格趋势图、市场份额图、情感分析图           |
| D3 | 策略建议 Agent | 基于分析结果生成定价/促销/产品策略建议        |
| D4 | 报告生成服务     | Markdown + 图表 → PDF/邮件/前端查看 |
| D5 | 人工审校入口     | 关键结论人工确认、异常标记               |

#### Phase E：调度与运营（第 8-12 周）

| 步骤 | 任务          | 关键产出                                                 |
| -- | ----------- | ---------------------------------------------------- |
| E1 | Workflow 编排 | `competitor_monitor` workflow：抓取 → 解析 → 分析 → 报告 → 邮件 |
| E2 | 告警机制        | 价格突变、新品上线、负面舆情实时告警                                   |
| E3 | 前端仪表盘       | 竞品看板、报告库、告警中心                                        |
| E4 | 效果复盘        | 报告被阅读/采纳率、决策辅助价值评估                                   |

### 3.3 关键里程碑及时间节点

| 里程碑                   | 时间      | 验收标准                            |
| --------------------- | ------- | ------------------------------- |
| **M1：数据源与合规确认**       | 第 2 周末  | 竞品清单、数据源清单、合规评估报告               |

### 3.5 潜在风险识别及应对措施

| **抽取准确率不足**  | 报告结论错误，误导决策     | 中  | ① LLM + 规则混合抽取；② 置信度评分；③ 人工抽检；④ 关键字段二次校验     |
| **数据时效性**    | 竞品动态已变，报告仍是旧数据  | 中  | ① 高频增量抓取核心字段；② 报告标注数据更新时间；③ 异常波动实时告警         |
| **LLM 幻觉**   | 策略建议不可信         | 中  | ① 基于结构化数据生成；② Faithfulness NLI；③ 人工审校入口      |
| **目标站点完全封闭** | 核心竞品数据无法获取      | 中  | ① 购买合规第三方数据；② 聚焦公开渠道；③ 人工补充                  |

### 4.3 优先级建议

**建议：优先落地方案 4，同步筹备方案 3。**

#### 理由

1. **更快验证 Agent 平台价值**  
   方案 4 几乎完全复用现有 `web_crawl` Skill、RAG、Report Skill、Workflow 引擎，12 周内可产生可阅读、可分发、可辅助决策的竞品报告，快速证明 Multi-Agent 在业务场景中的落地价值。
2. **风险更低、业务侵入性更小**  
   方案 4 是离线分析系统，不改动核心交易链路，失败不会影响 GMV。方案 3 作为在线推荐服务，任何策略失误都可能直接造成收入损失。
3. **为方案 3 积累关键能力**  
   方案 4 实践中会打磨：Agent 编排稳定性、LLM 抽取准确率、报告生成管线、Workflow 调度、人工审校闭环。这些能力后续可直接复用到方案 3 的「兴趣挖掘 Agent」「推荐理由生成」等环节。
4. **数据与合规先行**  
   方案 4 涉及外部数据抓取，可提前建立合规流程、代理池、反爬策略、数据质量校验机制，为后续方案 3 引入外部商品/价格数据做准备。
5. **资源投入更合理**  
   在 Phase 3 平台化（鉴权/RBAC/多租户）尚未完成的情况下，不宜同时启动高风险的实时推荐项目。方案 4 对平台化依赖较低，可独立跑通。

#### 落地节奏建议

```
第 1-12 周：方案 4 全面落地
  ├─ 同步补齐方案 3 所需的数据埋点与画像基础
  └─ 产出：竞品日报/周报自动化、看板、告警

第 8-16 周：方案 3 预研与基座建设
  ├─ 行为事件埋点、用户画像仓库、商品向量索引
  └─ 产出：画像服务、候选召回 demo

第 16-28 周：方案 3 试点上线
  ├─ 非核心推荐位 AB 实验
  └─ 产出：单场景 CTR 提升验证

第 28 周以后：方案 3 规模化 + 与方案 4 联动
  └─ 例如：结合竞品价格动态调整推荐策略
```
