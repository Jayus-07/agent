## 1. 目标与成功标准

**目标**：会话实体从 Redis `auth:session:{userId}:{jti}` 改为 DB `auth.sessions` 一行
（= 一次设备登录 = refresh token family）。access token 只作会话内短期凭证，携带
`sid` claim；refresh 轮换归入同一 `session_id`；`/security` 列表与强制下线按 session 聚合。

| 编号 | 成功标准 |
|---|---|
| S1 | 同 device_id 登录一次 → 活跃 session 行数 = 1 |
| S2 | 连续 refresh 5 次 → sessions 行数不变、session_id 不变、last_active_at 单调 |
| S3 | 两个不同 device_id 登录 → 活跃 session 行数 = 2 |
| S4 | 同 device_id 二次登录 → 旧 session revoked_at 非空（revoke_reason='replaced'），活跃仍 1 |
| S5 | 已吊销 refresh 重放（超宽限期）→ 401 + 整 session 吊销 |
| S6 | 并发同 hash 刷新在 60s 宽限期内均成功、同一 session_id、不触发整吊销 |
| S7 | 按 session 强制下线 → revoked_at 非空 + refresh 全吊销 + Redis jti 键删除 + 后续请求 401 |
| S8 | Redis 不可用时 /security 列表仍返回 DB 数据 |
| S9 | access token 含 sid；APISIX/业务鉴权回归通过 |
| S10 | 存量未吊销 refresh_tokens 中 session_id 为空的行数为 0 |
| S11 | `pytest backend/tests/security --no-cov` 退出码 0，新增用例覆盖 S1-S8 |
| S12 | 前端 /security 按 session 渲染，字段完整，下线按 session |

## 3. 总体做法

- 数据库做台账：`auth.sessions` 一行 = 一次设备登录；`auth.refresh_tokens` 逐 token 保留、`session_id` 归组。
- Redis 只做在线闸门：键格式/TTL 不变；管理面不依赖 Redis scan。
- access token 加 `sid` claim（APISIX/业务鉴权不感知）。
- 登录=创建或替换 session；刷新=继承 session；重放=撤销 session。
- `/security` 列表/强制下线切 DB 口径。
- Redis 新增 `auth:session_idx:{uid}:{sid}` 集合记录活跃 jti，强制下线 O(1) 定位删键。
- 存量先 dry-run 再归组回填；无法归组行吊销。

## 5. 依赖与风险

| 编号 | 风险 | 缓解 |
|---|---|---|
| R1 | 多标签并发 refresh 竞态误登出 | 60s 宽限期同 hash 幂等 |
| R2 | 重放检测误判 | 仅超宽限期的已吊销 token 触发整吊销 |
| R3 | 同设备重登登出其他标签 | 用户已接受（Q6）；必要时前端提示 |
| R4 | 存量归组错误 | dry-run + 无法归组吊销（重新登录兜底） |
| R5 | session_idx 与 jti 键不一致 | 写侧同事务语义 + 一致性校验脚本 |
| R6-R9 | revoked_at 缺失 / deviceId 缺失 / 停 Redis / claim 兼容 | 分别对应 1.4 / 2.1 / S8 / S9 |
