# 安全、幂等、预算与反馈闭环实施规划

任务类型：架构级改造。
本计划只描述实施路径，不修改代码、不创建文件、不运行测试。
建议拆成 6 个可独立验收的工作包，按顺序交付，禁止一次性合并上线。

## 一、假设与待确认问题

### 1. 当前假设

1. B1 决策拍板 API、T3 通用任务恢复 API 已存在，本次只做回归验证，不重建、不改接口语义。
2. 统一错误协议仅统一“失败结果”；成功结果保持现有业务契约。
3. 错误码采用给定的 9 个通用码；示例中的 TOOL_TIMEOUT 归一为 TIMEOUT，通过 source="tool" 区分来源。
4. Redis 用于原子占位、用量预占和短期状态；PostgreSQL 是幂等结果、预算策略、用量、反馈及评测候选的权威存储。
5. 写操作在现有 ensure_approved() 审批通过后、实际副作用发生前申请幂等键。
6. Redis 或预算存储不可用时，副作用操作和受硬预算约束的模型调用默认拒绝执行，不允许静默降级。
7. 首批语义后置校验覆盖所有写操作及存在多候选选择的 Tool；纯只读、单候选且输出契约明确的 Tool 只做结构校验。
8. 用户负反馈、纠错内容只能生成待审核评测候选，不能自动进入生产 golden set。
9. 语义缓存、OTel 导出、B1/T3 重建均不在本次范围。
10. 所有测试编写前必须加载项目要求的 test-quality-guard skill；如果执行环境中找不到该 skill，停止测试开发并先解决技能可用性。

## 二、目标与成功标准

### 目标

在不重复建设已有 B1/T3 能力的前提下，交付统一失败协议、全局幂等、Tool 语义后置校验、请求及用户/租户预算、反馈到评测候选闭环，以及对应测试和 Prometheus 观测。

### 成功标准

| 编号 | 成功标准 | 检查方式 |
|---|---|---|
| S1 | Tool、Skill、HTTP、SSE、Celery 失败结果均包含 code、retryable、handoff_available、message、trace_id | 每种传输边界至少 1 个契约测试；JSON Schema 校验全部通过 |
| S2 | 生产路径不向客户端返回 Python 类名、堆栈或本地文件路径 | 扫描 API/SSE/Celery 错误响应测试输出，敏感模式命中数为 0 |
| S3 | 同一租户、同一幂等键、同一请求体并发提交 20 次，只发生 1 次副作用 | 集成测试断言外部适配器调用次数等于 1 |
| S4 | 同一幂等键配合不同请求体返回 IDEMPOTENCY_CONFLICT，副作用次数不增加 | 冲突集成测试通过 |
| S5 | FC 失败且存在多个候选时，不再执行候选首项 | 测试断言 Tool 调用次数为 0，结果为澄清或人工转接 |
| S6 | 请求预算在每次模型调用和 fallback 前检查；超过任一限制后没有新增模型调用 | 边界值与超限值测试均通过 |
| S7 | 每条 LLM/Embedding/Rerank 用量都有 user_id、tenant_id、trace_id、request_id、组件和调用类型 | 数据库检查缺失归属记录数为 0 |
| S8 | 用户或租户达到预算 80% 产生一次预警，达到 100% 阻断后续调用 | 日/月四组集成测试通过 |
| S9 | 负反馈或纠错可关联到同租户 Trace，并生成 pending 评测候选 | API、越权和数据库集成测试通过 |
| S10 | 未经人工审核的候选不能进入 golden set | 审批状态机测试证明 pending/rejected 无法 promotion |
| S11 | 9 个新增指标均可被 Prometheus 抓取，且标签不包含用户、租户、trace、request 或幂等键 | /metrics 测试及标签白名单检查通过 |
| S12 | 项目指定注册一致性测试、分层测试和新增专项测试全部退出码为 0 | 保存测试命令及退出码作为验收证据 |

## 三、范围边界

### 做

- 定义统一的内部错误模型及各传输边界适配器。
- 建立 Redis 原子 claim、PG 最终结果持久化的幂等执行器。
- 接入已确认的副作用 Tool、客服写操作和 Celery 任务提交。
- 删除“FC 失败后默认执行候选首项”的行为。
- 增加输出结构校验、能力匹配校验和需要澄清/转人工的决策。
- 增加请求级预算、用户/租户日月预算、用量归属和硬阻断。
- 扩展反馈模型，关联 Trace，建立人工审核和评测候选状态机。
- 增加契约测试、单元测试、集成测试、并发测试、权限测试和指标。
- 更新接口契约、数据库迁移说明、运维告警规则及回滚说明。

### 不做

- 不重建 B1 决策拍板 API。
- 不重建 T3 通用任务 resume API。
- 不实现语义缓存。
- 不实现 OTel exporter。
- 不自动把反馈写入生产 golden set。
- 不新增与现有 capability 重复的近义 capability。
- 不把 trace_id、user_id、tenant_id、request_id 或幂等键放入 Prometheus label。
- 不重构与本次六个工作包无关的图节点、RAG 链路或前端页面。
- 不改变已有成功响应，除非消费方与服务端在同一提交中完成适配。

### 停止条件

满足任一条件即暂停对应工作包：

1. 无法确定副作用操作清单。
2. test-quality-guard skill 不可用且任务进入测试编写阶段。
3. 数据库迁移存在不可逆数据丢失风险。
4. 无法从认证上下文可靠取得 user_id 或 tenant_id。
5. 找不到可审计的模型价格表却准备启用成本硬熔断。
6. 幂等存储故障时系统仍能绕过执行副作用。
7. 外部客户端尚未完成错误协议兼容性清点，却准备强制切换协议。
8. Trace 查询不能执行租户隔离，却准备开放反馈关联。
9. 关键专项测试未通过，却准备进入下一阶段或生产放量。

## 四、总体做法

采用“契约先行、基础设施集中、业务逐项接入、观察后强制”的顺序：

1. 先冻结错误、幂等、预算、反馈四类契约及数据库状态机。
2. 建立集中基础组件，业务 Tool 不自行实现 Redis、PG 或预算判断。
3. 先接入一条代表性链路验证，再按清单扩展到全部目标。
4. 新行为先以观测模式运行，收集 7 天数据；数据满足门槛后再启用硬阻断。
5. 每个工作包独立测试、独立审查、独立提交；上一包未验收不得开始依赖它的下一包。
6. B1/T3 只增加“不被重复建设、不被破坏”的回归检查。

## 六、依赖与风险

| 依赖或风险 | 影响 | 控制措施 | 可检查门槛 |
|---|---|---|---|
| 副作用操作清单不完整 | 重复写仍可能发生 | registry、审批点、客服域图三方对账 | 三方差集为空 |
| Redis claim 后 Worker 崩溃 | 长期卡在 running | lease、heartbeat、过期恢复和 PG 对账 | 故障测试在规定 lease 后可恢复 |
| 外部系统不支持幂等键 | “已成功但回包丢失”无法完全证明 | 保存外部请求 ID；重试前查询外部状态；无法查询时转人工 | 不允许自动重复副作用 |
| 错误协议破坏客户端 | 前端或调用方解析失败 | 兼容期、契约测试、客户端清点 | 已知客户端通过率 100% |
| 路由分数不可比较 | 固定阈值产生误判 | 多候选 FC 失败直接澄清；阈值仅用于已校准模型 | 校准集误执行数为 0 |
| 并发配额超卖 | 超预算后仍调用模型 | Redis 原子预占、实际结算、PG 审计 | 并发测试实际使用不超过额度 |
| 模型价格变化 | 成本计算失真 | 价格表版本化并记录生效时间 | 每条成本记录可追溯价格版本 |
| 用量无租户归属 | 无法审计或错误计费 | RequestContext 强制校验 | 缺失归属记录数为 0 |
| Trace 越权关联 | 泄露其他租户内容 | 服务端从认证上下文取身份，不接受客户端覆盖 | 跨租户用例全部返回 403 |
| 反馈污染 golden set | 回归基线失真 | 人工审核、状态机、promotion 幂等 | 未批准候选进入数为 0 |
| Prometheus 标签高基数 | 监控系统内存增长 | 禁止身份、Trace、请求和幂等键标签 | 标签白名单检查通过 |
| 测试只验证 mock | 假阳性 | 只 mock 外部边界，Redis/PG 使用真实集成环境 | 关键状态机均有集成测试 |
| 一次上线改动过大 | 难以定位回归 | 六个工作包独立合并，分级灰度 | 每包可独立回滚 |

建议初始告警阈值：

| 告警 | 触发条件 |
|---|---|
| 幂等冲突激增 | 10 分钟内冲突率 >10%，且请求数 ≥20 |
| Tool 语义不匹配 | 10 分钟内不匹配率 >5%，且执行数 ≥20 |
| 预算超限异常 | 15 分钟内超限率 >1%，且请求数 ≥100 |
| 负反馈升高 | 1 小时负反馈率 >20%，且反馈数 ≥20 |
| 失败后未转人工 | 5 分钟内计数 >0 |
| 审批或幂等存储降级 | 连续 2 分钟状态为 degraded |
| token 无归属 | 5 分钟内缺失归属计数 >0 |
| fallback 异常 | 15 分钟 fallback 比例 >20%，且 LLM 调用数 ≥50 |
