## 二、唯一实锤缺口：满意度评价闭环（需求 ⑥ 后半句）

**现状证据（全链路无一处实现）：**
- 后端 `customer_service/` 全域 grep `满意度|satisfaction|rating` 零命中（仅其他域如 selection_funnel 命中）
- `cs_admin.py` 8 个路由（list/detail/traces/queue/ws-ticket/close/claim/agent-messages/messages）无 stats、无 rating
- 用户端 `frontend/src/components/cs/` 10 个组件无评价组件；无评分 API 调用
- 管理端 `frontend-admin/src/app/cs/`（page + conversations + handoff）无统计 tab

**建议实施（P0，三步闭环）：**

1. **后端**（`customer_service/`）
   - `conversation_store` 增 rating 字段迁移（PostgreSQL `ALTER TABLE cs_conversations ADD COLUMN rating SMALLINT, rating_comment TEXT, rated_at TIMESTAMPTZ`，sql/migrations 下新增迁移文件，注意 java 写权模式：rating 属于元数据写，仍走 Python 侧或经 business_client 透传，需按 `CS_WRITE_SOURCE` 开关对齐）
   - 新接口：`POST /cs/conversations/{id}/rating`（用户端评分）；`GET /cs/admin/stats`（聚合：评分均分/1-5 分布/评价率/按意图分布/转人工率）
2. **用户端**（`frontend/src/components/cs/`）
   - 新组件 `CSSatisfactionCard.tsx`：星标 1-5 + 选填备注；展示时机 = 会话关闭（/close）或人工会话结束；复用 `fetchRaw` 提交
3. **管理端**（`frontend-admin/src/app/cs/`）
   - page.tsx 增「统计」tab：5 张统计卡（总 会话/消息/均分/评价数/转人工率）+ 满意度分布条形图 + 意图分布条形图（意图数据现成，`cs_route` 已随 turn 落库，见 `conversation_store.record_cs_turn` 的 `cs_route` 参数）

## 三、次级差距（P1/P2，建议排在 P0 之后）

1. **P1 统计汇总接口缺失**：管理端目前只能逐会话看，无任何聚合视图（会话量趋势、意图分布、转人工率）。做 P0 满意度时顺带补 `GET /cs/admin/stats` 一并解决。
2. **P2 用户端客服会话双体系疑点（待核实）**：`useCSChat.ts` 的 `persistSession` 走通用 `/api/chat/messages`，而 CS 域自有 `conversation_store`（含 trace 关联）。两条持久化链路是否重复落库、会话 ID 是否同一命名空间，建议下一步实测确认（本报告不下结论，遵循「不确定先查代码」）。
3. **P2 转人工等待体验**：`CSHandoffCard` 已有状态卡片 + 坐席轮询同步，但无「队列位次/预计等待」提示（`cs_admin.py:214` 队列接口数据现成，前端补展示即可）。

## 四、验收路径（P0 实施后）

1. 用户端 `/agent?cs=1` 对话 → 结束会话 → 出现星标评分卡 → 提交
2. 管理端 `/cs` 统计 tab → 均分/分布/意图分布/转人工率出数
3. 评分数据落 PostgreSQL `cs_conversations` 表（rated_at 可查）
