## 二、P1：前端 dev 链路所有 API 404（阻断级）

### 现象

```
POST http://127.0.0.1:3200/api/auth/login   → 404 {"error_msg":"404 Route Not Found"}
POST http://127.0.0.1:9080/api/auth/login   → 400 {"code":400,"message":"用户名或密码错误"}
```

同一请求直连网关能到后端（400 = 业务正常响应），经前端 dev server 则是 APISIX 的 `404 Route Not Found`。

### 根因：两层剥 `/api` 前缀，剥重了

- `frontend/next.config.js:26` 与 `frontend-admin/next.config.js:26`：

  ```js
  source: '/api/:path*',
  destination: `${process.env.API_URL || 'http://127.0.0.1:9080'}/:path*`,   // ← 剥掉了 /api
  ```

- `apisix/apisix.yaml`：网关路由只认 `/api/*`（`app-fallback` uri 为 `/api/*`，再由 `proxy-rewrite` 剥 `/api` 转上游）。

前端先把 `/api/auth/login` 剥成 `/auth/login` 发给网关 → **网关没有任何 `/auth/*` 路由** → 404。

该写法在「前端直连后端 8000」时代是正确的（后端路由无 `/api` 前缀），切流到 APISIX 后语义反了：网关需要 `/api` 前缀才能命中路由。属切网关时的回归。

### 影响面

- 两个前端配置完全相同 → `frontend`(3000) 与 `frontend-admin`(3200) **同时受影响**
- 登录/刷新/注册等 `/api/auth/*`、所有业务接口全部 404，**前端实际不可用**
- 仅 `/api/health` 例外：剥成 `/health` 恰好命中网关 `sys-health` 路由（`apisix.yaml` 的 `/health`），所以健康检查看起来是通的，容易掩盖问题

### 修复建议

```js
destination: `${process.env.API_URL || 'http://127.0.0.1:9080'}/api/:path*`,
```

副作用已评估：修复后 `/api/health` 走网关 `app-fallback` → 无 Bearer 时按 `X-API-Key` 通道放行（前端带 `NEXT_PUBLIC_API_KEY`），后端 `/health` 在 `_SKIP_AUTH_PREFIXES` 白名单内 → 仍 200。调用方仅 `frontend-admin/src/app/page.tsx:130`。

## 三、P2：审计页指标区恒降级（PromQL 拼错）

### 现象

`GET /api/observability/gateway-auth?hours=6` → `200` 但 `available=false`：

```
error: Client error '400 Bad Request' for url '.../api/v1/query?query=
  sum+by+%28code%29+%28increase%28apisix_http_status%7Bjob%3D%22agent-platform-apisix%22%7D%7Bcode%3D~%22401%7C429%22%7D%5B6h%5D%29%29'
```

### 根因

`backend/app/api/routes/observability.py`（`/gateway-auth` 端点）拼出两段并列花括号：

```
apisix_http_status{job="agent-platform-apisix"}{code=~"401|429"}
```

直连 Prometheus 9090 验证：

| 查询 | 结果 |
|---|---|
| 当前实现（双花括号） | `400 bad_data: 1:72: parse error: unexpected "{" in aggregation` |
| 修正写法（逗号分隔 `{job="...",code=~"401|429"}`） | `200 success`，1 条 series |
| 对照：`apisix_gateway_auth_denied_total{job="..."}` | `200 success`，**9 条 series（有数据）** |

### 放大效应

该端点用 `asyncio.gather` 并发四个查询，**任一抛异常就整体降级**为 `available=false`。所以即使 `gateway_auth_denied_total` 有 9 条 series 的真实数据，也因 status_codes 这一条查询失败而全盘不可用。

后果：管理端 `/observability/gateway` 页面上部的「认证拒绝汇总卡 / 拒绝趋势 / 拒绝原因分布」**永远显示「Prometheus 数据源不可用」启动指引**，只有下半部的「访问审计明细」（独立 PG 数据源）正常。

### 修复建议

1. 必需：`{job="..."}{code=~"401|429"}` → `{job="...",code=~"401|429"}`
2. 建议：`asyncio.gather(..., return_exceptions=True)` 或逐项 try，单点失败不再拖垮整个接口

## 四、P3：仅凭前端公开 API Key 可匿名读审计明细（安全）

### 现象

```
GET /api/observability/gateway-access-logs?hours=6
X-API-Key: <前端 NEXT_PUBLIC_API_KEY>      （无 Authorization / 无 JWT）
→ 200 {"available":true,"total":71,"logs":[...完整审计明细...]}
```

`GET /api/observability/gateway-auth` 同样 200 可读。

### 链路分析

1. 网关 `gateway-auth.lua`：无 Bearer 但有 `X-API-Key` → 打标 `X-Auth-Type: api-key` **直接放行**（网关不校验服务级 Key，注释明示由下游负责）
2. 后端 `app/api/middleware/auth.py`：只做 `X-API-Key` 常量时间比对 → 通过
3. `/observability/*` **无任何角色闸**：网关 `ROLE_GATE_PREFIXES` 只列了 `/api/approvals`(write=admin) 与 `/api/prompts`(write=editor)；后端该路由也无角色校验
4. 该 Key 是 `NEXT_PUBLIC_` 前缀 → **编译进浏览器 bundle，等于公开值**

另测：viewer 角色的普通登录用户同样 200 可读全部审计明细。

对应 `docs/未完成功能进度汇总-2026-09-16.md` 的 **A3（四组敏感接口收口：observability / evaluation / rag / schedules）**，文中实测 `grep SENSITIVE_API_GUARD_MODE backend/` 为 0 命中 —— 本次复测确认仍未做。

### 修复建议（按成本递增）

1. 网关 `ROLE_GATE_PREFIXES` 增加 `/api/observability` 的 read 闸（如 read=admin），与后端分工一致
2. 或后端给 `/observability/*` 接入 `resolve_operator_role()` 校验
3. 根本项：不要把服务级 Key 下发到浏览器（现 `NEXT_PUBLIC_API_KEY` 设计本身即隐患）
