### 真实调用链与当前契约

1. `POST /travel/plan` 与 `POST /travel/plan/stream` 接收当前 `TravelPlanRequest`（message/session/conversation/client_run/source），各自准备图输入并通过共享有界 `RequestExecutor` 调用旅游 LangGraph；REST 与 SSE 的执行准备逻辑仍有重复。
2. `_seed_cross_turn_base()` 从 `PlanVersionService`/`PlanVersionStore` 恢复最近版本的 brief、parent version 与指纹，供 Checkpointer 缺失时跨轮自愈；读账异常目前软降级。
3. 旅游图通过 `TravelIntent`、slot filler、supervisor、专家节点、validator、repair/partial-replan、reporter 执行。局部改单已有 `travel_partial_replan`，交通查询已有 `live_search_service`（含治理执行适配），工具事件基础封装已有 `run_travel_tool` 与 tool failure policy。
4. 图结果经 `_record_plan_version()` 进入 `PlanVersionService`；现有 `record_plan_result()` 对规划与改单统一记录为 `waiting_confirmation`。确认通过版本比较与数据库 CAS；账本读写失败目前可能软失败，不能据此向用户声称版本已持久化。
5. 版本账本在 `agent_memory.travel_plan_versions`；`active_version()` 当前在无 confirmed 版本时回退 latest，存在把草案当正式版读取的语义风险。`discard_draft` 目前只写决策审计，不改变版本生命周期，草案存在刷新后复活风险。
6. SSE 使用 `run_id`/`seq`；已有工具事件缺少稳定的 `turn_id/task_id/tool_call_id` 关联。前端 reducer 主要按工具名寻找运行中项目，同名工具并发/重复调用无法可靠归属。
7. 旅游页表单把结构化字段拼成自由文本，未提交 `mode=plan` 与结构化 `brief_input`。桌面/移动端复用 `TravelChatDrawer`，但消息在组件本地 state；响应式卸载/重挂会丢失当前消息。
8. 现有 Prompt Registry 已有 `travel.llm_intent`、`travel.slot_enrichment`、`travel.clarification_renderer`；Reporter 当前为确定性模板。新增理解或回复能力应复用 Prompt Registry、模型治理、token/trace 归因与降级机制。

### 优先复用模块

- 请求执行与图：`backend/travel/request_runtime.py`、`backend/travel/graph_builder.py`、`backend/travel/core/graph_state.py`、`backend/travel/core/plan_service.py`。
- 版本与安全：`backend/travel/core/plan_store.py`、现有 confirm/CAS、diff、restore 与 `backend/travel/core/decision_store.py`；任何新状态须采用向后兼容迁移。
- 语义/工具：现有 intent、slot enrichment、clarification renderer、`live_search_service`（GovernanceRuntime）与 travel tool event/failure policy；避免重复 LLM 抽取或绕过治理。
- 前端：`frontend/src/api/travel.ts`、`travelRuntime.ts`、`planState.ts`、`TravelChatDrawer`、`TravelPlanList` 和既有 REST/SSE 入口。
- 会话消息：优先核验并复用 `chat_sessions`/`chat_messages` 与 `MemoryService`，不得未经身份/租户校验复用不安全的通用写端点，也不另造重复消息表。

### Phase 0 风险清单

| 风险 | 当前证据 | 施工要求 |
|---|---|---|
| 表单结构被降格成自由文本 | `/travel` 提交使用 `composePlanMessage` | 扩展向后兼容 API/TS 契约，表单传结构化 Brief 和 `mode=plan` |
| 单一 Intent 无法承载组合任务 | `TravelIntent` 只有单值；计划与交通任务分离 | 建立结构化主动作+修改指令+附加任务决策，复杂语义才调用 LLM |
| 正式版/草案混淆 | active fallback latest；放弃仅审计 | 明确 Active/Draft、持久化失败 fail-closed、放弃为持久状态、基准版本冲突返回 409 |
| 重复/并发工具事件错配 | 前端按 tool 名归属 | 贯通 turn/task/tool call 标识并复用现有工具事件/治理出口 |
| 双端消息和首轮结果不一致 | drawer 内存状态，表单与聊天路径不同 | 抽共享会话状态，统一首轮消息、版本引用和断点恢复 |
| 数据库与异步基线不稳定 | 正确 Docker DB 缺 `ai.question_ledger`；60ms 执行测试受同步准备影响 | 先修复测试隔离/环境迁移证据，再推进数据库实机验收；不连接 5432 |
| 真实部署误操作 | 本机开发服务正在运行，端口已有占用 | 重启/替换前复查 PID、容器、端口归属；只操作本项目服务 |

- `/travel/plan` 与 `/travel/plan/stream` 兼容旧 body，并接受 `mode`、基于现有 `TravelBrief` 的 `brief_input`、`base_plan_version`、`ui_context`、`action_payload`；这些字段进入 `TravelGraphState`，不被 LangGraph schema 过滤。
