### 真实调用链与当前契约

1. `POST /travel/plan` 与 `POST /travel/plan/stream` 接收当前 `TravelPlanRequest`（message/session/conversation/client_run/source），各自准备图输入并通过共享有界 `RequestExecutor` 调用旅游 LangGraph；REST 与 SSE 的执行准备逻辑仍有重复。
2. `_seed_cross_turn_base()` 从 `PlanVersionService`/`PlanVersionStore` 恢复最近版本的 brief、parent version 与指纹，供 Checkpointer 缺失时跨轮自愈；读账异常目前软降级。
3. 旅游图通过 `TravelIntent`、slot filler、supervisor、专家节点、validator、repair/partial-replan、reporter 执行。局部改单已有 `travel_partial_replan`，交通查询已有 `live_search_service`（含治理执行适配），工具事件基础封装已有 `run_travel_tool` 与 tool failure policy。
4. 图结果经 `_record_plan_version()` 进入 `PlanVersionService`；现有 `record_plan_result()` 对规划与改单统一记录为 `waiting_confirmation`。确认通过版本比较与数据库 CAS；账本读写失败目前可能软失败，不能据此向用户声称版本已持久化。
5. 版本账本在 `agent_memory.travel_plan_versions`；`active_version()` 当前在无 confirmed 版本时回退 latest，存在把草案当正式版读取的语义风险。`discard_draft` 目前只写决策审计，不改变版本生命周期，草案存在刷新后复活风险。
6. SSE 使用 `run_id`/`seq`；已有工具事件缺少稳定的 `turn_id/task_id/tool_call_id` 关联。前端 reducer 主要按工具名寻找运行中项目，同名工具并发/重复调用无法可靠归属。
7. 旅游页表单把结构化字段拼成自由文本，未提交 `mode=plan` 与结构化 `brief_input`。桌面/移动端复用 `TravelChatDrawer`，但消息在组件本地 state；响应式卸载/重挂会丢失当前消息。
8. 现有 Prompt Registry 已有 `travel.llm_intent`、`travel.slot_enrichment`、`travel.clarification_renderer`；Reporter 当前为确定性模板。新增理解或回复能力应复用 Prompt Registry、模型治理、token/trace 归因与降级机制。

### Phase 3 — Supervisor 任务执行与局部重排（P0）

- 新增唯一 `travel_auxiliary_tasks` 节点，复用现有 `run_checked` / Tool Failure Policy 执行车次、天气、景点与酒店查询；不为每种 Tool 复制规划图，也不在 slot_filler 中发起实时 Tool IO。
- Supervisor 在问答出口和规划专家链前调度未完成的附加任务；每轮最多 4 个任务、任务类型不可重复、checkpoint 状态重新按 `TravelAdditionalTask` 校验；成功、空结果、需补槽、拒绝、超限和降级分别落入 `task_results`。任务按 id/type 去重，失败仍视为本轮已执行，不被 supervisor 重试循环放大。
- 每轮由 slot_filler 清空 `task_results`；全局 planning reset 同样清空任务结果与工具失败账。多项可选 Tool 的失败记录增量合并，不能互相覆盖，亦不产生硬依赖阻断。
- `TravelGraphResult`、`travel_context` 与 REST/SSE 的既有 `ui_payload/done.result` 契约透传任务结果。Reporter 展示真实天气/地点摘要；纯车次问答由辅助节点执行后直出，仍跳过五个规划子 Agent。工具事件的稳定 task/tool-call 关联字段留待可观测性收口阶段。

### Phase 4 — 行程版本及对话状态收口（P0）

- 首次成功规划直接成为 `confirmed` Active；基于现有 Active 的改单写成 `waiting_confirmation` Draft。`active_version()` 只读 confirmed，不再在没有 Active 时把最新草案冒充正式版；放弃是持久化终态，重复放弃幂等，已放弃草案不可复活。
- 版本读写按 tenant/user/conversation 隔离；事务 advisory lock 与版本 CAS 串行化并发写。确认、放弃、恢复均核对当前版本；草案必须先持久化才能返回可应用状态。版本账本读写失败时 API 清除 itinerary 并返回失败，不把生成结果伪装成已保存。
- `_seed_cross_turn_base()` 以 confirmed Active 重建 Brief，Draft 只作为版本链 parent，不污染正式规划基底；问答/失败轮不创建版本。历史列表及恢复投影只认 confirmed Active。

### Phase 6 — Reporter LLM 与可观测性（P0）

- Reporter 在确定性结构化结果与模板完成后，可通过 Prompt Registry 的 `travel.reporter` 生成单行短回复；模型仅使用主模型角色、温度 0、最多 220 tokens、超时 2.5 秒。模型调用、Prompt 渲染、JSON/内容校验或计量任一失败均不重试，回退到原模板，不更改 `itinerary`、版本状态或 Tool 结果。
- 新增 Prompt 默认 YAML `backend/prompts/defaults/travel_reporter.yaml` 与 Registry 项。Reporter 输入是受限摘要：当前问题、主动作、已解析变更、Brief、版本/草案状态、附加任务及降级状态；数值必须与模板中的完整数字 token 一致，高风险事实词也必须已出现在模板中，结构化 Tool 摘要不能单独成为聊天气泡的新事实来源。此校验不等于完整语义事实验证，仍需真实模型评测。禁止应用/持久化/预订成功声明。前端仅当 `reporter_meta.source=llm` 时在聊天气泡采用短回复；模板来源和旧后端继续显示原有状态提示。

### Phase 7 — P1 体验增强与回归

- **P1-02 草案期间继续问答**：增加 `read_only` 请求模式和独立无 checkpoint 图。只读门仅允许事实问答/白名单查询任务；明确改单在 slot filler 与 supervisor 双重拦截，不进入规划 Agent、局部重排或版本写入。只读路由严格加载当前用户/租户的 Active 与 Draft，Draft 只作为回答上下文；Reporter 以确定性事实模板为基底，原计划不变。已验证草案中问预算、安排原因与只读查询，不生成 itinerary 或新版本。
- **P1-01 跨设备消息恢复**：新增 `/travel/conversations/{conversation_id}/messages` GET/PUT，复用既有 `chat_sessions/chat_messages` 与 `MemoryService`，不新建表、不跑迁移。存储会话键与 owner 均由网关身份中的 user/tenant 及 conversation id 派生；由于共享消息表无 `tenant_id` 列，owner 使用不超过 64 字符的稳定散列，避免通用记忆会话列表因同 user_id 跨租户而泄露标题。PUT 在单事务内替换最多 100 条消息快照，重试不会追加重复行；替换时同步清除过期 L2 摘要水位线。GET 缺失会话返回空消息、不泄露内部 session 是否存在；未认证 401，基础设施故障 503。
- 前端在切换/恢复 conversation_id 时先读现有 sessionStorage，再拉服务端历史；服务端已存在时避免无意义删写。若请求期间本地产生新轮次，会将新尾部合并保留并补写服务端；服务端恢复的历史助手回复不播放打字动画。同步故障会提示用户，当前设备快照仍保留。跨设备恢复的消息字段受既有表限制，只持久化 role/content/时间与 DB 行 ID，UI rationale/tag/tone/turnId 不随服务端恢复；turnId 会在恢复时重建。
