# RAG 验收剩余项实施方案（企业做法）

> 依据：`docs/reports/2026-10-04-RAG上传检索验收清单.md`（下称「清单」）。
> 范围：四~十六章中仍为 ⬜ 的 **103 项**（117 项中 11 项二轮已验、3 项补登 L2/L3/L7），外加 5 张缺陷修复任务卡（D-2~D-5、K1/D-1）。
> 执行原则：**准入检查 → 带证据执行 → 缺陷分级处置 → 七行证据回写 → 路径限定提交**；每批独立会话窗口，批末清单打钩+提交，不做「Demo 跑通式」验收。
> 日期：2026-10-04 ｜ 基线：`a1af6d4`（清单列结构修正后）

## 一、总体策略

1. **按依赖与风险排序，六批串行**（共享栈不并行压测）：
   修复卡先行（D-3/D-4 是后面取证的依赖）→ 生命周期/契约 → 权限缓存 → 解析索引（顺带 K1）→ 检索质量 → 故障/容量（需窗口）→ 评测集（产出型专项）。
2. **证据分级**：能实机的必须实机（经 APISIX 9080 自签 JWT）；实机不可达的（如 PG 拔线级故障）降级为**代码级故障注入测试**并在清单注明「实机不可达，以单测为准」，禁止谎报 ✅。
3. **缺陷分级处置**（批内新发现一律走此流程）：
   - **P0**（数据错误/安全/崩溃）：阻断本批退出标准，当批修复+回归测试；
   - **P1**（功能缺陷有绕行）：登记 D-xx，当批或下一批修复；
   - **P2/P3**（体验/口径）：登记缓修台账（清单 §十八），不阻断。
4. **门禁对齐**（清单 §十七五门禁）：Batch 1~4 产出对应 `RAG_UPLOAD_GATE` / `RAG_RETRIEVAL_GATE` / `RAG_OBSERVABILITY_GATE` 的证据；Batch 6 产出 `RAG_QUALITY_GATE`；全部批次完成后才能宣布 `RAG_PRODUCTION_READY` 候选。
5. **窗口纪律**（多会话共享栈，来自仓库避坑纪律）：Batch 5 动容器/杀进程前必须 ①`docker ps` 留证 ②向用户报告影响面 ③确认无会话在跑全量 pytest；批后恢复现场并复核容器状态。

### Batch 1：生命周期一致性 + API 契约（13 项，1 天）

前置：D-2 已合入；`docker ps` 快照留证。

| 项 | 方法 |
|---|---|
| L1 上传幂等 | 同一文件 2 线程并发上传（`concurrent.futures`），核对单版本提交、无重复 doc/chunk；同 `upload_id` 重放受理响应 |
| L4 三方一致 | 上传/覆盖/删除三时点分别 psql 对账：`doc_registry.chunk_count` vs `SELECT count(*) FROM rag_vectors WHERE doc_id=…` vs BM25（经 rag-service 检索命中数/日志），零孤儿 |
| L5 chunk 原子切换 | 大文档（50MB）覆盖期间后台线程连续 ask（每 2s），断言检索结果无新旧标志词混用 |
| L6 索引失败回滚 | 实机：对 `rag_test_kb` 临时改错 embedding key 触发批量失败（窗口内还原）；单测：monkeypatch embedding 抛异常断言不误标 active。两条腿取其一必须留证据 |
| L8 orphan chunk | SQL：`SELECT count(*) FROM rag_vectors v WHERE NOT EXISTS (SELECT 1 FROM doc_registry r WHERE r.doc_id=v.doc_id AND r.status='active')` = 0 |
| L9 pending/failed 清理 | 停 rag-index-worker → 上传滞留 → 起 worker 恢复；人工造解析失败文件 → 终态 failed 非永久 indexing |
| L10 重启恢复 | indexing 中 `docker restart agent-rag-index-worker-1` → 任务恢复或安全 failed，向量无重复写（与 I4 同源取证） |
| API1 | 缺 file/kb/department、非法 enum → 4xx + 稳定 error_code（断言响应体 code 字段） |
| API4 | 401/403/404/409/5xx 语义矩阵：逐端点探（无凭证/越权/不存在 doc/重名冲突/内部错） |
| API5 | detail DTO 全字段断言脚本（summary/doc_type/version/status/chunk_count/metadata_route/processing_status…对照 `sanitize_doc_row`） |
| API6 | OpenAPI diff：`git stash` 前后 /openapi.json 比对，已上线字段零删除/改名；前端 contract 测试跑通 |
| API7 | 同一上传的 request_id/upload_id/processing_run_id/trace_id 四元串联回放（trace tags + processing-runs 端点） |
| N2 | 同文件并发 2 上传（与 L1 同脚本），文件锁/幂等生效 |

### Batch 2：权限安全 + 缓存（10 项，0.5 天）

前置：D-5 合入；C6 需临时停 `agent-redis-1`（报告后 5 分钟窗口）。

| 项 | 方法 |
|---|---|
| S1/S2 租户与部门隔离 | 先核 TD-13 状态（`git log --grep TD-13` + 客服线清单）；**未修则按现行语义实测并挂账**：受限 KB 矩阵 viewer(hr/finance/general) × (policy_hr/policy_finance/biz_order) search+ask 交叉，越权必须 403；travel=all 为对照组 |
| S4 admin 代部门 | admin 上传指定部门 → op log/audit 落 operator+target_department（psql 查操作日志表） |
| S5 metadata 注入 | 请求体/表单手工塞 `tenant_id/permission_scope=finance` → 上传后 detail 回读为鉴权上下文值 |
| S6 doc_id 越权 | viewer(hr) 猜 policy_finance 文档 doc_id → detail/preview 404（与不存在同形，不泄露存在性） |
| S7 citation 越权 | 无权限用户直造 `/documents/{id}/file` URL → 404/403（快照二次鉴权，快照线已有裁决代码，实测确认） |
| S8 删除权限 | viewer/editor/admin × DELETE 矩阵（403/403/200） |
| S9 审批权限 | viewer 调 `/pending/{id}/approve` → 403（require_rag_editor） |
| S10 审计日志 | 上传/覆盖/审批/删除/reindex 五动作后逐一查操作日志表，actor/tenant/kb/doc/action/result 全留痕 |
| C4 权限变化失效 | 同题 ask 两次，第二次改 viewer 权限头（permission_scope 变）→ 缓存键 scope 维度变化不命中旧值；叠加撤权场景说明 |
| C6 缓存降级 | `docker stop agent-redis-1` → ask/search/upload 三链路可用（缓存旁路）→ start 恢复；全程 ≤5 分钟并报告 |

### Batch 3：解析切分 + 索引治理（21 项，1 天）

前置：`d:/tmp/rag-samples/` 造样本集（PDF/DOCX/MD/TXT/GBK 编码/空文件/纯图 PDF/50MB 大 MD/Markdown 表格/H1-H3 多级/POI 结构文档各 1）；全部实验走 `rag_test_kb`，验后删除。

- **P1** 四格式各传一样本 → active + chunk 非空 + 关键词抽查。
- **P2** 空文件/纯空格/纯图无 OCR → 明确拒绝或 error，零空 chunk。
- **P3** 50MB 样本 → 不 OOM、有超时/限流、终态明确（观察 app 内存 `docker stats`）。
- **P4** GBK/BOM 文件 → 中文无乱码或明确 error_code。
- **P5** 表格样本 → chunk 行列语义抽查（表头+数据同行）。
- **P6** H1-H3 文档 → chunk metadata `section_title` 含层级路径。
- **P7** Parent/Leaf → `chunk_store` SQL 抽查 leaf 的 parent 指针可回溯。
- **P8** 全库 chunk 长度分布 SQL（min/p5/p50/p95/max vs 策略阈值），过短/超长占比报告。
- **P9** 相邻 chunk overlap 抽查（重复片段长度 vs 配置 CHUNK_OVERLAP）。
- **P10** 乌塔/三坊七巷词条边界抽查（infobox 不与正文串味；D-6 的结构性旁证）。
- **P11** `data/quality_records/<kb>/<doc>.json` 含 removed/统计与版本（二轮已见实例，补全字段核对）。
- **P12** registry `pipeline_version/metadata_route` 非空可溯源。
- **I1** registry `embedding_model` 列非空（done 帧已见 qwen3.7-text-embedding，补 SQL 留证）。
- **I2** 模型升级隔离：`rag_test_kb` 切第二 embedding 模型重索引 → 维度/collection 隔离，检索不混（读 pgvector_store 核验 + 实测检索）。
- **I3** reindex API 单文档/单 KB 可用（不重传源文件）。
- **I4** 连续 reindex 两次 → chunk/vector 数量不翻倍。
- **I5/I6** 与 L4 同一 SQL 对账脚本，全库跑一遍出报告。
- **I7** embedding 异常：临时用错误 key 上传 → 受控 retry 后 failed，不无限重试（窗口内还原 key）。
- **I8** partial batch：造含非法字符的混合 batch → 重试不重复不遗漏（chunk 数守恒断言）。
- **K1/D-1 修复卡**（批尾）：改 `metadata_taxonomy.yaml` filename_hints 补 `福州-景点-` 等爬虫命名 → **必须先过 V9 分类评测样本集**（与本批共建 30 条）→ 重传抽样 15 篇误分类文档核对改判 + Structure 切分生效。

### Batch 4：检索质量 + 证据门 + 引用溯源（20 项，1 天）

前置：D-3（trace 可查）、D-4（span 计数）已合入；复用二轮探针脚本与自签 JWT 配方（附录 A）。

- **Q1-Q3** 三类 query（FAQ 短问/专有名词/多问复合）各跑 → trace 取 `tier/mode/reason`（Q2 用「崇妙保圣坚牢塔」现成样本）。
- **Q4** 同 query ×5 route 基本稳定（容忍 embedding 抖动，允许 ±1 tier 内漂移并记录）。
- **Q5/Q6** 构造多路命中同 chunk → 结果唯一且 score 合并正确（D-4 计数佐证）。
- **Q7** 同文档扩展上限（parent/sibling 扩 K 配置核验 + trace 候选数封顶）。
- **Q8** 越权 KB filter 前置：viewer 查受限 KB → rerank 前候选=0（trace 候选数对比，不能是 rerank 后才被滤）。
- **Q9** top_k 边界：search 固定 10 核验；ask 内部 top_k 异常值（0/负/超大）不拖垮服务。
- **Q10** 空结果 → `no_evidence` 稳定码 + 话术（R4 已证，补 trace reason 字段）。
- **Q11** rewrite 质量：错别字/口语/省略主语样本 10 条改写前后对比，意图与实体保持。
- **Q12** rewrite 失败降级：rewrite LLM 超时（限流模拟）→ 降级原 query 检索非 500。
- **E1** rerank 阈值标定：相关/弱相关/无关样本各 10 条 → 分数分布报告（**只出报告不改默认 0.3/0.35**，改阈值走变更门+回归）；D-6 乌塔样本纳入。
- **E2** rerank 超时降级：timeout 注入 → 降级 recall score + trace `gate_degraded` 标记。
- **E3** 最低证据数：0/1 个弱 chunk 场景 → 不强答，稳定 answer_status。
- **E4** 数字证据：价格/数量/日期问题 ×10，答案数字必须可在 evidence 中找到（脚本比对）。
- **E5** 时效证据：v1/v2 不同日期（与 L3 同场景）→ 只用当前版本日期。
- **E6** 冲突证据：造两篇冲突文档 → 明确冲突提示或按权威规则裁决，不静默任选。
- **E7** citation 一致：answer 引用 `[E1]` 与 sources 一一对应（脚本比对）。
- **E8** 大召回上下文预算：多文档命中 → input_budget 封顶 + trace 可见裁剪。
- **A2** 快照内容 = evidence 内容（file preview 与引用 chunk 比对）。
- **A3** 覆盖后打开旧回答 citation → 明确版本失效提示。
- **A4** PDF 页码/MD section 定位（用 Batch 3 的 PDF 样本 + 现有 md 语料）。
- **A6** 幻觉回归：语料外事实 ×10（含「于山」）→ 全部拒答或明确缺证据。
- **A7** 部分可答：混合多问句 → 可答部分正常 + 缺证据部分明示。

### Batch 5：故障恢复 + 容量并发（16 项，1 天，**窗口批**）

前置（缺一不开工）：
1. 向用户报告并确认窗口；
2. `docker ps -a` 快照留证，确认无其他会话活动（含全量 pytest）；
3. 验后逐容器恢复并复核 healthy。

- **T1** 全程帧序脚本断言 `received→parse→clean→chunk→embed→index→done` 单调不倒退（F14 部分证据的补全）。
- **T2** SSE 断线：中途 kill 客户端 → 重连（Last-Event-ID）→ 不丢终态不重复执行（代码核验 `rag_upload.py` 流实现 + curl 模拟）。
- **T3** embedding 阶段 `docker stop agent-rag-index-worker-1` → 任务恢复或明确 failed，重启后不重复写。
- **T4** 停 `agent-redis-broker` → indexing 期间不产生 active 假状态，恢复后可续。
- **T5** PG 中断：实机不可达（不拔权威库）→ 单元级故障注入（connection 抛异常）断言 fail-closed 不产生孤儿向量，清单注明口径。
- **T6** vector 中断：同上单测口径 + upsert 异常不误标 active（与 L6 复用注入点）。
- **T7** 各阶段 timeout 配置核验（parser/embedding/rerank/search 独立超时非叠加放大）+ 慢注入实测一例。
- **T8** retry 分类：429/timeout 可重试，400/schema 永久失败直进 failed（用错误参数与限流各造一例）。
- **T9** poison task：持续失败文件 → 达 retry 上限进 dead/failed，不再消费。
- **N1** 10 并发上传（不同文件）→ 无串写/死锁/重复索引。
- **N3** 并发 ask：10 并发 ×5 轮 → p95/p99 计时报告（对照企业评审 P95 目标）。
- **N4** indexing 期间持续检索 → active 文档正常服务，半成品不可命中。
- **N5** 大 KB（rag_100_docs/scale 语料）检索延迟对比 travel 库 → 非线性恶化证据。
- **N6** context budget：大召回 → trace `input_budget` 封顶可见（09-30 已有 L2 压缩实证可复验）。
- **N7** backpressure：超 `MAX_CONCURRENT_REQUESTS=5` → 503+retry-after（09-30 实机证据在案，复验留证即可）。

### Batch 6：离线评测集建设（10 项，1~1.5 天，产出型专项）

1. **V1 Golden Set ≥50 条**：从 travel 38 篇语料出题——POI×20、美食×10、路线/交通×8、无答案×8（含「于山」）、权限负例×4；格式 `question/expected_doc/expected_answer/type`，入库 `backend/datasets/` 固定版本（提交评审）。
2. **V2-V5** 跑离线 retrieval eval：Recall@5 / MRR / NDCG / Top-1，**首次结果冻结为基线**写入本清单与 ROADMAP（后续只升不降，降则阻断发布）。
3. **V6** 无答案子集：拒答率必须 100%，不许为 recall 强答。
4. **V7** 权限负例：越权召回率必须为 0。
5. **V8** Regression Gate：核对 `rag_smoke.yml`（PR 8 条）与 `rag_regression.yml`（每日 02:00）触发路径覆盖 parser/chunker/taxonomy/retrieval 参数变更；缺口补工作流触发条件。
6. **V9** 分类评测集（30 条 doc_type 样本，Batch 3 K1 修复的门禁）→ `travel_guide` 独立准确率指标。
7. **V10** Faithfulness：答案关键事实逐条对 evidence 的支撑抽测（20 条人工+脚本混合）。

## 四、证据与留痕纪律（每批相同）

1. **七行证据格式**（每项写进清单状态列）：修改内容 / 影响文件 / 验证命令 / 测试结果 / 未验证项目 / 已知风险 / 回滚方式。
2. **清单回写**：当批完成即打钩+证据，禁止攒批；⚠️ 部分通过必须写明缺口。
3. **提交**：`git add -A -- <paths>` + `git commit -- <paths>` 双重限定；测试代码与修复同提交；混线文件不提交（沿用二轮纪律）。
4. **造数清理**：所有测试文档/KB 用 `rag_test_kb` 或 `ZZZ-` 前缀命名，批末删除并 psql 复核零残留（二轮 ZZZ 残留教训）。
