## 3. 冻结的施工边界

- 原位改造现有 `StateLoader → PendingHandler → Supervisor → 五个客服子 Agent → Reporter`；不新增客服系统、第二套状态机或图节点。
- Sandbox 为唯一业务来源。组合退款必须先用服务端订单/物流事实完成权限、条件和资格判断，再由现有 ActionExpert 建 Proposal；用户确认后仍由 ConfirmationFlow 执行。
- Pending 期间只允许 Knowledge/Query 受控只读；每轮只执行一次。`waiting_human`/`human_active` 由 Handoff 权威状态优先，排队期间不触发 AI 查询、回复或写操作。
- PostgreSQL 迁移向后兼容；确认副作用需版本绑定、租户/用户/Proposal 绑定、持久原子认领和幂等键。
- 代码、Prompt、Token/Cost 和 Trace 复用统一治理链；前端复用现有 `CSDrawer`、`useCSChat`、store、SSE 和确认卡。
- P0 全绿前不切换本机运行代码；不做灰度、影子双跑，不接真实 Java。

## 4. 改造前后主链路

**当前结构：** `StateLoader → PendingHandler（确认优先）→ Supervisor → Knowledge / Query / Action / Complaint / Handoff → Reporter`。

## 7. Graph、契约与状态矩阵

唯一客服执行链不变：StateLoader → PendingHandler → Supervisor → Knowledge / Query / Action / Complaint / Handoff → Reporter。没有新增客服图节点或第二套副作用执行链。

| 当前事实 | 本轮允许路径 | 写操作门 | 验收 |
|---|---|---|---|
| 无 Pending、无 Handoff | 既有 Supervisor 正常分派 | Action 仍需 Proposal 和后续确认 | 自动化通过 |
| Pending + 明确确认/取消 | 原 ConfirmationFlow | PG 校验身份、tenant、proposal/version、目标、期限、handoff 和 client_action_id | API/PG 自动化通过；浏览器只实测取消 |
| Pending + Knowledge FAQ | Pending 白名单只放行 Knowledge，一轮后 Reporter | 不调用 Action，不改 confirmation 行 | 实机通过；确认行保持 pending/version=1 |
| Pending + 订单/物流查询 | Pending 白名单只放行 Query，一轮后 Reporter | 不调用 Action，不改 proposal | 实机只读查询通过；物流语义未通过 |
| Pending + 新写操作或模糊确认 | 冲突说明或澄清 | 不覆盖旧 Proposal、不把疑问当确认 | 自动化通过；未做全套实机矩阵 |
| waiting_human / human_active | 以 PostgreSQL Handoff 权威状态优先；排队说明/人工状态同步 | 禁止 AI Query、Action、新 Proposal 和 AI 确认；读取失败 fail-closed | 状态机自动化通过；未实机接入坐席 |
| need_info + FAQ | Knowledge 路径，不消耗补槽重试 | 保留原 need_info/Pending | 实机 FAQ 通过 |
| need_info + 候选/订单槽补充 | 按服务端候选及原上下文继续 | 真实订单必须由服务端授权查询 | 自动化通过；本次浏览器只测单订单补槽 |

### CSTaskPlan / CSTaskResult

CSTaskPlan 固定 schema_version=1，primary_intent 与 tasks 经 Pydantic 验证；能力白名单仅含 query_logistics、query_order_status、propose_refund。每项 task 含 task_id / capability / depends_on / optional condition。DAG 拒绝重复 ID、循环/错误依赖、超量任务、任意 SQL/代码/URL/Tool；条件只接受固定事实字段、比较操作和枚举值，缺失或未知事实为 false。模型提供的订单号不替代服务端查询结果。

图 state 使用 task_plan / task_cursor / task_results / current_task。每个 CSTaskResult 含 task_id / status / facts / source / error_type。TaskPlan 只调既有 Query/Action Expert；用户请求、Sandbox 事实、退款资格和权限必须共同满足后，才生成 Proposal；确认继续走原 ConfirmationFlow。任务计划/条件/unknown/multi-order 自动化通过，本次未在 HTTP Sandbox 实机跑完 true/false/unknown 三分支。

### Confirmation API

请求体新增并要求：session_id、decision、proposal_id、expected_version、client_action_id。服务端绑定认证 user、tenant、conversation、当前 pending Proposal、版本与目标；过期、人工接管、失配、数据库 claim 失败均拒绝副作用。响应保留 status / answer / confirmation_state / action_result。浏览器真实测试生成 version=1 的退款待确认申请并取消；没有在浏览器触发确认执行或并发重复确认。
