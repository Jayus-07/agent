## 3. 冻结的施工边界

- 原位改造现有 `StateLoader → PendingHandler → Supervisor → 五个客服子 Agent → Reporter`；不新增客服系统、第二套状态机或图节点。
- Sandbox 为唯一业务来源。组合退款必须先用服务端订单/物流事实完成权限、条件和资格判断，再由现有 ActionExpert 建 Proposal；用户确认后仍由 ConfirmationFlow 执行。
- Pending 期间只允许 Knowledge/Query 受控只读；每轮只执行一次。`waiting_human`/`human_active` 由 Handoff 权威状态优先，排队期间不触发 AI 查询、回复或写操作。
- PostgreSQL 迁移向后兼容；确认副作用需版本绑定、租户/用户/Proposal 绑定、持久原子认领和幂等键。
- 代码、Prompt、Token/Cost 和 Trace 复用统一治理链；前端复用现有 `CSDrawer`、`useCSChat`、store、SSE 和确认卡。
- P0 全绿前不切换本机运行代码；不做灰度、影子双跑，不接真实 Java。

## 4. 改造前后主链路

**当前结构：** `StateLoader → PendingHandler（确认优先）→ Supervisor → Knowledge / Query / Action / Complaint / Handoff → Reporter`。

**目标结构：** `StateLoader → Handoff 权威检查 → PendingTurnDecision → Supervisor（一次只读守卫或有限 TaskPlan 调度）→ 原有 Expert → FactSet 投影 / Response Composer / OutputGuard → Reporter`。确认执行仍为 `POST /api/cs/confirm → 持久化版本 claim → ConfirmationFlow → Sandbox`；不建立第二执行链。

本节记录 Phase 0 目标，不代表实现已经完成。后续各阶段 commit 与真实 Graph/SSE/浏览器验证结果见本文增补。
