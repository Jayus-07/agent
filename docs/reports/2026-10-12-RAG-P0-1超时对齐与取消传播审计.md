## 1. 结论摘要

- 修复：`rag.search` 策略超时 15s → **45s**（`backend/core/tool_runtime/policy.py`，单值 + 注释依据），`.env.example` 示例同步。复用既有 Tool Runtime 全套治理（Deadline 检查 / Retry / Bulkhead / CircuitBreaker 均未改动）。

- 取消传播：`asyncio.wait_for` 超时后 `asyncio.to_thread` 线程不可取消，rag-service 无取消接口，子任务必然跑完（httpx read 300s 兜底）——本轮**不改动**该机制（改动即平行取消系统），以超时线对齐消除常态相撞，长尾保留既有对账证据链。
- 实机对照：复现 1 同款 query（客服审核时间）在 45s 线下 **9.1s 全链成功**；15s 回滚口径下同 query 13.2s 仅 1.8s 余量擦线（P90 形态实锤）；「现货商品发货」极端 query 在两口径下均复现「父超时 → 子生成完整答案（107 字，带引用）→ 答案丢弃 + $0.0019 费用留痕」。

## 2. Deadline 审计（四环）

| 环节 | 现状 | 证据 |
| --- | --- | --- |
| 请求入口（主图 runner） | `RequestDeadline.started_now()`（BUSINESS 30s / WORKFLOW 25s / reporter 5s，全局 env 可配）随 RequestContext 进图 | `runner.py:660`、`request_context.py:61` |
| BaseSkill | 从 state 取 `rc.deadline`，透传 governance/executor | `skills/base.py:494,531,546`、`base.py:819-830` |
| workflow 引擎（rag_agent 所在） | `call_skill` → `_build_state` 只构造 plan/step_results 最小 state，**无 RequestContext → deadline=None**；`scheduler.py`/`skill_adapter.py` grep deadline 零命中（唯一直调 executor 的 sql.query 也不传） | `skill_adapter.py:68-83,89-130,177-185` |
| executor | deadline=None 时有效超时 = policy 值原样；deadline 非 None 时 = `min(policy, 剩余 workflow 预算 − reserve − margin)` | `executor.py:190-218`、`deadline.py:148-178` |
| 子端 rag client | 同步 httpx，read=300s，与父端超时完全解耦；rag-service 无取消接口 | `rag/client.py:22-23,70-74` |

**推论**：P0-1 的复现证据（workflow=rag_agent，父子错位 57%）全部在 deadline=None 路径——15s policy 线是唯一约束。因此**只调 policy 单值即可在该路径全额生效**，不需要（也不应该）在本轮把 Deadline 接入 workflow（接入反而会把 45s 压回 ~17-20s，属于批 3 联动机制的域级预算设计问题）。

主图路径（客服等 agent 域）预算压缩事实由测试锁定：`test_main_graph_deadline_compresses_policy_timeout`——默认 30/25/5s 预算下 45s 被压到 min(45000, 25000−5000−250)=19750ms，仍宽于旧 15s 线（P95 形态同样被覆盖），但 RAG 若常态化逼近 20s 需批 3 做域级预算联动。

## 3. 取消传播审计

超时后的实际行为链（`executor.py:227-229,307-323`）：

1. `asyncio.wait_for` 超时 → 取消 `_invoke` 协程 → `TimeoutError` → `map_exception` → `ToolStatus.TIMEOUT` → `cb.record_failure()`（连续 5 次熔断 OPEN 30s）；
2. 但 `asyncio.to_thread` 的工作线程**不可取消**，httpx 同步 read（300s）继续等 rag-service；
3. rag-service 无取消接口，完整跑完 检索→rerank→LLM→Evidence Gate，子 trace=success、llm_usage 照记；
4. 父侧已走降级话术，答案丢弃。

本轮取舍：**保留该机制**。理由：a) wait_for+to_thread 是统一执行边界，改造成可取消 HTTP 属平行取消系统（用户红线）；b) 45s 对齐后正常负载（P90=16.3s/P95=19.1s + 前置排队）不再触发超时取消，错位率从 ~57%（慢 query 段）降到长尾；c) 父子证据链保留完整——父 span `metrics.child_trace_ids` 预留挂链（`client.py:102-118`），子 trace 完成后可对账（§5 实机即用此链取证）。

「线程钉死」量化（实机）：超时后 `asyncio.run` 收尾 join 默认线程池，A 场景 wall 28s（15s 线+13s join）、B 场景 wall 97s（45s 线+52s join）——钉死窗口 = 子任务剩余耗时，随超时线上调而变长，但仅在触发超时的长尾请求上发生，且生产常驻 loop 无 join 语义（`test_regression_rag_180s.py:83` 注释）。
