## 1. 结论摘要

- 修复：`rag.search` 策略超时 15s → **45s**（`backend/core/tool_runtime/policy.py`，单值 + 注释依据），`.env.example` 示例同步。复用既有 Tool Runtime 全套治理（Deadline 检查 / Retry / Bulkhead / CircuitBreaker 均未改动）。
- 审计实锤：`rag_agent` workflow 路径（`skill_adapter._build_state` 不含 RequestContext）**Deadline 系统未接入**，policy 超时是唯一约束——45s 在该路径（P0-1 证据所在路径）全额生效；主图路径被 RequestDeadline(30/25/5s) 预算压缩，45s 只是名义上限（已用测试锁定该事实，联动调优属批 3）。
- 取消传播：`asyncio.wait_for` 超时后 `asyncio.to_thread` 线程不可取消，rag-service 无取消接口，子任务必然跑完（httpx read 300s 兜底）——本轮**不改动**该机制（改动即平行取消系统）。
- **容器间直连严格配对（GPT 补验 1）**：同一 query、同输入、容器 DNS 直连（无宿主端口转发噪声），rag-service 实际处理 ~23s（15-45s 区间）——**15s 口径 TIMEOUT（答案生成后丢弃，$0.0025 费用照记）；45s 口径同耗时成功返回完整答案**。
- **治理语义量化（GPT 补验 2）**：单请求治理窗口 = policy timeout（retries=0 不叠加）；bulkhead 槽位超时后立即回收（重复/后续调用可进入，不 TOOL_BUSY）；**to_thread 残留线程存活 = 子任务剩余在途时长（生产上限 client read 300s）**；连续 5 次超时 → 熔断 OPEN 近零延迟快速失败。**因此「请求最大耗时 45s」的说法不成立**，准确表述见 §3。

| --- | --- | --- |

## 3. 取消传播审计与治理语义量化（GPT 补验 2 答复）

超时后的实际行为链（`executor.py:227-229,307-323`）：

1. `asyncio.wait_for` 超时 → 取消 `_invoke` 协程 → `TimeoutError` → `map_exception` → `ToolStatus.TIMEOUT` → `cb.record_failure()`（连续 5 次熔断 OPEN 30s）；
2. 但 `asyncio.to_thread` 的工作线程**不可取消**，httpx 同步 read（300s）继续等 rag-service；
3. rag-service 无取消接口，完整跑完 检索→rerank→LLM→Evidence Gate，子 trace=success、llm_usage 照记；
4. 父侧已走降级话术，答案丢弃。

**耗时语义（不得宣称「请求最大耗时 45s」）**，定向测试 `test_timeout_residual_bulkhead.py` 4 例锁定（等比缩放 0.5s:1.5s ↔ 45s:300s，同一 executor 执行路径）：

| 维度 | 事实 | 证据 |
| --- | --- | --- |
| 治理窗口 | 超时即返回，≈ policy timeout；retries=0 治理层不叠加 | `test_residual_thread_outlives_governance_window`（治理返回先于子任务完成） |
| bulkhead 槽位 | 超时返回后**立即回收**；重复调用/后续调用正常进入真实执行，不 TOOL_BUSY | `test_bulkhead_slot_released_after_timeout_later_call_enters`、`test_repeated_call_after_timeout_not_blocked` |
| to_thread 残留线程 | 存活 = 子任务剩余在途时长，随子任务完成自然结束，**不永久泄漏**；生产上限 = client read 300s | 同上（done 事件 wait 到位）+ 实机 wall 22.7s = 15s 判死 + 7.7s join |
| 熔断 | 连续 5 次超时 → OPEN；第 6 次近零延迟 CIRCUIT_OPEN 快速失败 | `test_five_timeouts_open_circuit_then_fast_fail`（<50ms） |
| 并发放大面 | 20 并发满载超时场景：槽位逐个回收不占死；线程池（asyncio 默认 executor，min(32, cpu+4)）被残留线程按子任务剩余时长占用 | 等比测试 × 机制推导；生产 20 并发全真 45s 验证未执行（成本），按等比口径登记 |

本轮取舍：**保留该机制**。理由：a) wait_for+to_thread 是统一执行边界，改造成可取消 HTTP 属平行取消系统（用户红线）；b) 45s 对齐后正常负载（P90=16.3s/P95=19.1s + 前置排队）不再触发超时取消；c) 父子证据链保留完整——父 span `metrics.child_trace_ids` 预留挂链（`client.py:102-118`），子 trace 完成后可对账（§5 实机即用此链取证）。

## 7. 未关闭风险（挂账，P0-1 不标记完全修复）

**本轮定性为「超时缓解」**：15s→45s 消除的是「15s 线 vs 端到端常态」的结构性相撞（常态负载下父子错位大幅下降），以下风险保持未关闭：

1. **子任务取消传播缺失**：超时后 to_thread 线程不可取消、rag-service 无取消接口，子任务必然跑完（§3）。极端长尾（>45s）仍会出现「父失败、子在途」。
2. **远端工作继续计费**：超时被丢弃的请求，rag-service 侧 LLM/rerank/embedding 费用照记（§5.1 实锚：单次 $0.0025、1020 token 答案白烧）。费用归属（P1-8 归因断链）与「超时请求费用告警」均未建设。
3. **Deadline 一致性**：workflow 路径无 RequestDeadline、主图路径预算压缩 45s（§2 表）——三处超时（policy/workflow Deadline/client 300s）联动机制未建（批 3）。
4. **LLM 耗时波动**：同 query 实测 11s~48s（§5.1），45s 线对波动上限无控制力；>45s 长尾回落到「父超时子成功」形态。
5. **client read 300s 保持**（沿用批 1 决策）：作为极端长尾外层兜底；收敛需 rag-service 内部超时先收敛（批 3）。
6. **to_thread 不可取消 / rag-service 无取消接口**：结构性问题，改造属平行取消系统，超出本轮；对账靠 child_trace_ids + llm_usage 证据链。
