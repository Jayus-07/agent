# 客服域 LLM 语义层与自然回复改造 · Phase 0 审计报告

> 日期：2026-10-08｜分支：feat/cs-acceptance-p0｜审计范围：backend/customer_service/ 全量 + 治理面（prompt/模型/记账/trace/metrics）
> 结论先行：**客服域现有 5 处 LLM 全部已走统一治理（PromptService + LLM 代理 + 线程级超时 + 白名单降级），无绕行；但 LLM 分布零散、无统一理解层、无自然回复层、trace/metrics 不可归因**——本轮按任务书收口。

---

## 1. TL;DR

| 维度 | 现状 | 与任务书差距 |
|---|---|---|
| LLM 调用点 | 6 处（supervisor 兜底 / query 分解 / complaint severity+仲裁 / chat_fallback / knowledge RAG / agent_assist） | 零散，缺统一 Understanding Layer 入口 |
| Router | 纯规则零 LLM（DomainDetector→Coarse→Fine） | 规则 miss → unknown → 低置信 finish，无 LLM intent fallback |
| 理解层 | 纯规则版 `context/understanding/`（CSUnderstanding 契约，2026-09-29 B5/B11） | 无 LLM slot enrichment（自然引用无法解析） |
| 回复层 | Reporter 纯模板组装 + OutputGuard 收尾 | Query/Complaint 回复生硬，无 Response Composer |
| 治理面 | 8 个 prompt 键已注册；llm 代理记账（component=customer_service 自动归因） | 缺 3 个新键；trace 无 cs_llm_* 字段；metrics 缺 understanding/response 计数器 |

## 2. 逐项审计（对照任务书第四节 A–G）

### A. Router（真实文件：`router/cs_router.py` + coarse/fine/domain_detector/intents/types）

```
DomainDetector(domain_detector.py, 规则词表判定 is_cs)
  → CSCoarseRouter.classify()   # 关键词+正则计票；优先级: 质量投诉→售后政策问句→配送政策问句→计票≥2(0.6+)→hint_fallback(0.5)→UNKNOWN(0.0)
  → CSFineRouter.classify()     # 域专属关键词映射 intent；未命中落 DOMAIN_DEFAULT_INTENT(conf=0.6)
  → CSRouteResult               # confidence=(coarse+fine)/2；300s 进程内缓存
```

- **每层均零 LLM**：rule=yes、confidence=规则计票、fallback=hint/域默认意图、LLM=无。
- 意图单一事实源：`router/intents.py::INTENT_PROFILES`（22 键，含 domain/requires_auth/requires_action/risk_level/route_path/kb_ids 画像）——本轮 LLM intent fallback 的白名单从这里动态派生，不维护第二份。
- 已存在规则理解层接线：主图 router_node → `orchestration/graph/routing/cs_understanding.py::_enrich_with_understanding`（纯规则 CSUnderstanding 结果写 `cs_route.metadata`：entities/missing_slots/sentiment/urgency/risk_hits，decision_layer 写 trace tags）——**本轮 LLM 语义层的接线点即此处之后**。

### B. Supervisor（`supervisor.py`，837 行）

- v2 七层固定优先级（`_decision_v2`，CS_DECISION_V2 默认 true）：L1 handoff 拦截 → L2 pending 确认 → L3 风险信号兜底+P0 投诉直通 → L4 循环预算 → **L4.5 分诊直出**（寒暄→chat_fallback 一次 LLM 人设；出域→固定话术零 LLM）→ L5 意图路由（conf≥0.6 直派）→ L6 低置信无历史 → L7 LLM 兜底。
- `_llm_decision()` 实测口径：
  - **输入**：PII 掩码后的 user_message[:200] + intent + expert_history（经 `render_prompt("customer_service.supervisor")`）
  - **输出**：单个 expert 名（纯文本）
  - **白名单**：`ExpertType` 枚举 5 值 {knowledge, query, action, complaint, handoff}，不在白名单返回 None
  - **是否影响业务状态**：不影响——只产出 RUN_EXPERT 决策；`cs_supervisor_node` 按 `graph_state.EXPERT_NAME_TO_NODE` 查表 goto；无 FINISH 契约、无状态写权限（confirmation/handoff 状态机不经 supervisor LLM）
  - **Schema Validate**：无 JSON schema，等效于「纯文本 + 枚举白名单校验」（比 JSON 更严格）
  - **timeout**：CS_SUPERVISOR_LLM_TIMEOUT_MS=800，`sync_call_with_timeout` 线程级限时（config={"timeout"} 实测不生效是既有结论）
  - **fallback**：None → 规则降级（不重复派发刚执行过的 expert；decision_layer 如实标注）
- 度量：`record_cs_supervisor_decision(layer, action)` 已有（layer: 1=rule/2=combination/3=llm）。
- **收口点**：LLM 决策后无独立 guard 二次验证环节（前置七层已保证 pending/handoff 不冲突，因 L7 位于 L1/L2 之后）；本轮补 `cs_supervisor_decision_source` trace 打点。

### C. QueryExpert（`experts/query.py`）

- `_compound_suspected()`：`vocab.QUERY_SERVICE_KEYWORDS` 命中 ≥2 个服务域才触发（规则预判控成本）。
- `_llm_decompose_intents()`：CS_QUERY_LLM_DECOMPOSE_ENABLED（默认 true）→ PII 掩码 → `render_prompt("customer_service.query_intent")` → llm 代理 → 3000ms 线程超时 → **输出白名单 = `_INTENT_SERVICE_MAP` 5 意图**（t_order_status/t_logistics/t_ticket_status/as_repair/as_quality_issue），非数组/无效意图全部丢弃，空则 None 降级单意图。
- 查询结果全模板格式化（`_format_order_list/_format_logistics/_format_ticket_list`），零 LLM。

### D. ActionExpert（`experts/action.py`，736 行）

- 真实链路：intent → order slot（`resolve_order_slot`：cs_route.metadata 注入值 > 当前轮显式实体；**缺则 need_info 结构化追问 + 退款候选点选（2026-10-08），禁止 fallback "latest" 红线在** `_SLOT_ORDER_INTENTS`+`_ask_missing_slot`）→ permission（`PermissionChecker.validate_user_identity`）→ proposal（refund/after_sales/account service build_*_proposal，含 Business Guard 幂等判重）→ 确认状态机（`confirmation_flow.process_confirmation` 唯一实现：`claim_for_execution` 原子认领 + PG durable ledger 幂等）→ simulate_execute → audit。
- **写操作在任何情况下没有被 LLM 直接执行：确认。全链路零 LLM，全模板话术。**

### E. ComplaintExpert（`experts/complaint.py` + `service/complaint_service.py`）

- 级联：`COMPLAINT_PATTERNS` 规则计数（0 命中→非投诉；1→medium；≥2→high）→ 规则 0 命中时 LLM 兜底（`detect_with_llm_fallback`：CS_COMPLAINT_LLM_ENABLED + PII 掩码 + `customer_service.complaint_assess` + 3000ms + 输出白名单 `{is_complaint:bool, severity∈low/medium/high}`，无效回规则结果）。
- 2026-10-08 三级分流已落地：非投诉（LLM 兜底也否认）不建单；medium 灰区 `llm_escalate_arbitration` 仲裁（`{escalate:bool}`，**fail-safe 偏人工**）；high/重复命中直接升级。
- **severity 判断**：LLM 只出 candidate（白名单三值），**是否创建工单/是否转人工由规则矩阵决定**（`escalate = severity∈{high} ∪ collect_count≥1 ∪ 仲裁 escalate`；priority 经 `_severity_to_priority` 规则映射，未知值落 medium）。无「LLM 说 critical 直接当 critical」路径（LLM 词表无 critical）。
- **收口点**：severity 来源（rule vs llm_fallback）无 trace 溯源。

### F. Reporter（`reporter.py`）

- 组装优先级：direct_reply（分诊直出）> handoff 拦截固定话术 > pending proposal_text > expert response_draft（+evidence 引用列表）> action_result 模板格式化 > 失败原因映射话术 > 兜底。**纯模板/直接转发，零 LLM**；唯 Knowledge 的 draft 是 RAG LLM 产物。
- OutputGuard（`security/output_guard.py` 五层过滤：内部信息/未授权承诺/他人信息/handoff 内部/投诉内部）在 `_run_output_guard` 最后执行——**P0-20 的「OutputGuard 在 Response Composer 之后」现状已满足，本轮 Composer 接线必须保持此序**。

### G. Prompt / Model / Accounting

- 客服 LLM 全部走统一链：`prompting.render_prompt`（= `prompt_service.render_sync`）→ `backend.infra.llm llm` 代理（限流/韧性/llm_usage 记账）→ `sync_call_with_timeout` 线程级限时。**未发现绕过治理的调用**（chat_fallback 曾有裸实例零记账问题，已于 2026-10-05 G7 收编走代理）。
- 记账归因：`proxy._usage_component()` 按 trace.tags["cs_target"] 自动归因 component="customer_service"，主图=llm——新 LLM 调用点在 CS 链路内自动正确归因，无需额外接线。
- Prompt 键现状 8 个已注册：system/answer/query_intent/complaint_assess/complaint_escalate/supervisor/redirect_main/chat_fallback（`prompts/defaults/*.yaml` + `registry.py`）。
- 开关全集（`config/customer_service.py`）：CS_SUPERVISOR_LLM_ENABLED(T)/CS_COMPLAINT_LLM_ENABLED(T)/CS_QUERY_LLM_DECOMPOSE_ENABLED(T)/CS_CHAT_FALLBACK_ENABLED(T)/CS_REDIRECT_MAIN_LLM_ENABLED(**F**)/CS_AGENT_ASSIST_ENABLED(T)。

## 4. 缺口清单（本轮施工范围）

1. **G1 无统一 Understanding Layer**：意图 LLM fallback 缺失（router 规则 miss → unknown → 低置信 finish，自然语言复杂句无法补判）；无 LLM slot enrichment（「昨天买的耳机怎么还没到」只有规则实体抽取，product_reference/time_reference 类语义引用无解析）。
2. **G2 无 Response Composer**：Query/Complaint 回复全模板（生硬）；任务书要求 Knowledge/Query=LLM preferred、Action/Handoff=Template、Complaint=LLM+policy guard。
3. **G3 观测不可归因**：trace 无 cs_understanding_source/cs_llm_*/cs_response_* 字段；metrics 缺 cs_understanding_llm_total/cs_slot_llm_*/cs_response_total 计数器；complaint severity 无溯源。
4. **G4 确认语义候选**：模糊确认（「行」「嗯就这样」）词表已覆盖 P0 案例（CONFIRM_KEYWORDS 含「可以/嗯/好的」，CANCEL 含「算了/不要」+疑问句守卫）；规则 NONE 时的 LLM semantic candidate 缺失（任务书第十三节「可以」项，做成开关默认关）。
5. **G5 prompt 缺 3 键**：intent_understanding / slot_enrichment / response_composer。

## 5. 施工方案（Phase 1/2/3 落点）

```
新增 backend/customer_service/understanding/（LLM 语义层；规则层保持 context/understanding/ 不动）
  contracts.py            CSUnderstandingResult + CSSlotCandidate（Pydantic 白名单）
  llm_intent_fallback.py  规则 miss/低置信 → intent candidate（INTENT_PROFILES 动态白名单）
  llm_slot_enrichment.py  自然语言 → 语义槽位候选（禁真实 ID）
  llm_confirm_candidate.py 确认词表 NONE → {decision: confirm|cancel|unknown}（开关默认关）
  validator.py            白名单校验 + 真实 ID 字段拒绝 + severity validator
  semantic.py             编排入口（Rule First → LLM Fallback 一次 → Schema 校验 → 软降级）

新增 backend/customer_service/response/
  contracts.py            CSResponseContext + CSRenderedResponse（只允许 answer 字段）
  composer.py             按 Expert 策略（knowledge/query=LLM, action/handoff=template, complaint=LLM+guard）

接线（最小改动）
  orchestration/graph/routing/cs_understanding.py   规则 enrich 后追加 semantic enrich（LLM intent/slot）
  customer_service/supervisor.py                    L7 补 cs_supervisor_decision_source 打点
  customer_service/experts/complaint.py             severity 溯源打点（severity_source）
  customer_service/reporter.py                      OutputGuard 前接 Response Composer
  customer_service/confirmation_flow.py             规则 NONE → LLM candidate（开关关）
  config/customer_service.py                        5 个新开关
  observability/metrics.py                          5 个新计数器
  prompts/defaults/ + registry.py + prompts.lock.json  3 新键
```

### 命名说明（对任务书建议结构的偏差）

任务书建议 `understanding/service.py`；该文件名已被迁移 B11 的 import 兼容 shim 占用（`understanding/service` → 规则层 `context/understanding/service.py::build_understanding`，测试与 routing 按 shim 路径消费）。新编排入口命名 `semantic.py` 避让，职责等价。`understanding/__init__.py` shim 的 5 个子模块映射保持不变。

### 红线落实（任务书第三、十、十二、十三、十四、十六节）

- LLM 只出 candidate：intent ∈ INTENT_PROFILES 白名单（prompt 动态构造）；slot 白名单字段集（语义引用类）；真实 ID 字段（order_id/refund_id/ticket_id/user_id/tenant_id/handoff_ticket_id/confirmation_id）在 validator 层**键名拒绝 + 值形态拒绝**双保险，只丢弃不消费。
- 真实对象解析仍由 ContextResolver（`resolve_turn_reference` 序数/回指）+ 业务服务（真实 user_id）完成——LLM slot candidate 只做 ContextResolver 的**输入增强**，不替代。
- confirmation/handoff 状态机零改动（LLM candidate 仅在规则 NONE 时提供白名单 decision，经既有 `ConfirmationIntent` parser 消费）。
- 全部新 LLM：PII 掩码进、一次调用、线程级超时、软降级（绝不 500/断流/空回复）、trace+metrics+prompt 版本治理。
