## 已实施的边界修复

- `frontend/src/app/travel/page.tsx`：示例使用同一结构化表单生成请求，日期按点击当天动态计算；运行句柄保护重复提交、取消和迟到结果。
- `backend/app/api/routes/travel.py` 与 `backend/travel/request_runtime.py`：REST/SSE 共用有界执行器、同会话互斥、租户/用户限额、deadline、协作取消和超载响应；同步图不再占用事件循环。
- `backend/orchestration/graph/travel_graph_node.py`：独立旅游入口的 checkpoint namespace 始终包含 tenant/user（缺省用 `-` 占位），两个用户同会话 ID 不共享状态。
- `backend/providers/travel/live/resilience.py`：Provider 执行槽有界，超时不提前释放；single-flight key 在调用结束后回收；节点和 Tool 边界检查取消。
- compose 生产默认 `TRAVEL_ADMISSION_BACKEND=redis`；Redis admission 故障关闭，避免多副本各自放行。

## 上线阻断和并发风险

1. P0：尚未在独立环境经 APISIX/JWT 和真实供应商逐一执行三个示例。
2. P1：同步 Provider 已运行时不能被 Python 安全强杀；当前通过 Provider 槽、请求许可和真实完成后释放控制资源，仍需慢供应商故障注入验证。
3. P1：多副本容量取决于 Redis、PostgreSQL、供应商配额和实例 CPU/内存；100 是 admission 默认上限，不是实测吞吐。
7. 火车票 MCP 的项目契约明确为非官方学习研究源、无 SLA、不商用。生产需关闭该源或更换可商用的数据源；界面不能承诺真实车票能力而缺少可用的生产 Provider。

## 建议实施路线

优先选择保留现有旅游图和 SSE 接口，补齐独立入口身份隔离、首屏日期与运行状态、可配置有界并发、deadline、取消与指标；复用现有 Provider 治理。单纯增加 uvicorn workers 会放大供应商调用与进程内限额，不能替代这些控制。异步任务队列适合未来长时批量任务，当前交互链路不整体迁移到 Celery。

第一阶段：已完成首屏、双用户隔离、重复提交、动态日期、取消和迟到事件修复与回归。

第二阶段：已完成入口资源控制、同会话冲突、Provider 有界等待和统一请求 deadline 的代码接线；需补 queue_wait、TTFT 生产看板和压测校准。

第三阶段：在独立环境部署同一提交，经 APISIX 和正常 JWT 逐一执行三个首屏示例；执行真实小流量供应商验收、确定性故障注入与隔离容量压测。共享本机不直接进行高负载压测。

## 暂定验收基线

用户并发和硬件需求待确认，暂按 100 个同时进行的规划请求评估，不代表已支持该容量。建议目标：正常依赖条件下成功交付率至少 99%，p95 首个有业务意义的事件不超过 2 秒，p95 全程不超过 60 秒；超载快速拒绝、用户间零状态串扰、取消后不提交新结果，30 分钟稳态运行无持续线程、连接与内存增长。心跳帧不计为业务首事件；降级交付与完整真实数据交付分别统计。低于目标时按瓶颈和配额调整执行许可或容量，而不是虚报达标。

最终上线需附：部署提交号、配置摘要（不含密钥）、三个示例的 Trace/结果、压测并发模型与资源曲线、失败/降级分布、回滚步骤。
