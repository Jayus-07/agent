# 智能客服子系统企业级演进分析（2026-10-03）

> 视角：客服业务子系统（非平台整体）。与同日《企业级架构评审报告》（平台生产就绪视角，P0 止血已立案为 41 任务卡施工书）互补：那份回答「平台为什么还不算准生产」，本份回答「客服域如何从功能闭环演进到企业级标准」——知识库运营 / 渠道 / 工单 / 人工协作四块补齐路线 + 保留/替换裁决。
> 口径：真实活跃用户 ≈3、单租户 default、1 人 + AI 会话协作、零专项预算、全栈私有化、学习演示用途但按可服务真实企业的标准设计。所有「现状【事实】」均可在代码/数据库复核。

---

## 1. 阶段定位

**一句话：功能闭环已完成的单租户内测系统（Internal Beta+）——客服域「问、查、办、转、检」五环全部搭通且治理面超出多数企业实践，但知识供给侧（索引覆盖 13.1%）、渠道接入面（仅 Web）、人工协作面（演示级）三大支柱仍是原型水平；缺的不是功能，是供给侧与运营闭环。**

成熟度五级标尺（L0 Demo / L1 内测 / L2 准生产 / L3 生产可承诺 SLA / L4 规模化多渠道）：

| 维度 | 级别 | 依据 |
|---|---|---|
| 功能完整度 | **L3** | 意图/多轮/知识问答/任务办理/转人工/工单/质检全链闭环，含坐席辅助 |
| 工程治理 | **L2.5** | 模型角色化 DB 唯一来源、契约 lock、审批门、Prompt pin、预算 CNY——超配；但「建成 ≠ 运行」（监控停摆 6 天、TTFT 失效） |
| 知识供给 | **L0.5** | 覆盖 13.1%、拒答 63.5% 未分流、无知识运营机制——功能最完整支柱上最大的洞 |
| 渠道 | **L0** | 仅自建 Web |
| 人工协作 | **L1** | handoff + WebSocket 认领制 + AI 辅助有骨架，无 ACD/SLA/技能组，工作台演示级 |
| 评测运营 | **L1.5** | 框架+smoke 有，客服域黄金集与数据回流闭环缺失 |

综合：**L1+（内测后期）**。要到 L2 准生产，先做施工书 P0（平台止血）+ 本报告 Phase 1（知识供给）；要到 L3，补人工协作企业化与渠道。

## 2. 现状盘点

### 2.1 现有做法（客服域全链）

- **接入**：APISIX 唯一入口 + JWT + 限流；双入口——客服窗口 `domain_hint` 锁域直进 / 全局入口规则预过滤 + 灰度放量
- **编排**：LangGraph 客服域图 `state_loader → pending_handler → cs_supervisor → 5 子 Agent → cs_reporter`；域主 Agent 纯规则调度（handoff 拦截/循环上限/LLM 兜底）；PG checkpointer 断点续跑
- **NLU**：词表（热更）+ 规则 + LLM 三层，词表代码单一事实源
- **追问**：缺失槽位主动追问，同问去重 + 会话封顶 2 次防循环
- **知识问答**：复用平台 RAG——改写→MultiQuery→混合检索（pgvector+BM25）→同文档扩展→Rerank→EvidenceGate（拒答分权限话术）→带引用生成→META 尾拒
- **业务服务**：订单/退款/物流（轨迹）/售后/账户/投诉 6 服务，投诉可建案可查
- **转人工**：handoff 子系统 + WebSocket 坐席工作台（认领/收发）+ 坐席辅助（AI 实时推荐回复，置信度门控、异步不阻塞）
- **写操作**：敏感操作二次确认链（与工具级审批门独立双链）
- **质检**：Celery 日聚合（会话量/转人工率/AI 独立关闭率/满意度/FRT 60s 达标率/意图 Top10/坐席维度/工单 48h 超时），幂等可重跑，写库 + Prometheus
- **出域**：非客服诉求识别引导转出

### 2.2 资产裁决：保留 / 替换 / 不做

**保留（企业级资产，是演进的地基不是包袱）**

1. LangGraph 域图 + 域主 Agent/子 Agent 编排——对话引擎核心
2. RAG 检索链全套（混合检索 + Rerank + EvidenceGate + 引用）——检索面完整，问题全在供给侧
3. 模型角色化治理（12 角色 DB 唯一来源 + 热刷新 + 发布门）
4. Tool/Skill 四层 + 契约 lock 门禁 + 写操作审批门
5. 三层意图 + 词表单一事实源热更
6. 双确认链设计（业务确认 ≠ 工具审批，分离正确）
7. **质检日聚合 + 事件 outbox**——outbox 模式是渠道/工单对接的天然挂点，当时设计的前瞻性正确
8. 追问防循环守卫（同问去重 + 会话封顶）
9. Prompt 请求级版本 pin + 预算 CNY 本位币治理
10. 坐席辅助「异步生成不阻塞消息主链路」的架构决策

**替换/升级（方向对、水平不够）**

1. 坐席工作台：架构保留（WebSocket + 认领制），交互与 ACD 策略全部升级
2. 内部模拟业务数据：演示保留，但服务层重构为**适配器接口**让真实外部系统可插
3. 纯文档知识形态：**补 FAQ 双轨**（FAQ → 文档 RAG → LLM 兜底三段式），不是替换
4. FRT 口径 60s：收紧到 30s（企业级常见值）
5. 词表热更新无评测守护：补词表变更评测门

**明确不做（避免过度工程）**

1. 不引入 Rasa 等传统 NLU 框架（与 LLM 时代架构不匹配）
2. 不自建电话语音栈（接 SaaS 或「未接来电→短信→工单」最低成本闭环）
3. 不做微服务拆分（单机 Compose 模块化够用，按 L3 前不需要）
4. 不做面向非开发者的可视化流程编排器（1 人团队维护灾难）
5. 不先做多租户（单租户已拍板）

## 3. 企业级智能客服参照架构

### 3.1 业务架构（能力域）

```
渠道层      Web / APP / 小程序 / 微信生态 / 电话 / 邮件 / 开放 API
交互层      机器人会话 ｜ 坐席工作台 ｜ 管理后台 ｜ 知识运营台
智能服务层  意图识别 · 多轮对话 · 知识问答 · 任务办理 · 主动服务
人工服务层  ACD 排队分配 · 坐席辅助 · 质检(AI 全量+人工抽检) · 工单
知识供给层  知识生产 → 审核 → 发布 → 运营(缺口分析/效果回收/盘点)
数据智能层  会话数据 · 标注数据 · 评测集 · 模型调优
支撑层      租户权限 · 监控告警 · 安全合规 · 成本治理
```

### 3.2 应用架构

- **渠道网关**：渠道适配器（协议归一化：inbound 消息 → 统一消息模型；outbound 回执/主动消息）、渠道用户 ↔ 统一 visitor_id 映射
- **会话服务**：会话状态机（机器人 ↔ 排队 ↔ 人工 ↔ 结束）、跨渠道会话合并、上下文管理
- **对话引擎**：NLU → DM（槽位/策略）→ 执行（工具/检索）→ NLG；任务型与问答型分流
- **知识服务**：FAQ 精准匹配层 + 文档 RAG + 知识生命周期管理
- **ACD/工单服务**：排队、技能组、SLA 计时、工单生命周期
- **质检服务**：全量 AI 质检（话术合规/情绪/流程）+ 人工抽检
- **集成层**：业务系统适配器（OMS/CRM/物流），防腐层

### 3.3 数据架构

| 数据域 | 内容 | 现状对应 |
|---|---|---|
| 会话事实 | 消息明细、事件流、会话快照 | cs schema 会话/消息表 ✅ |
| 知识数据 | FAQ、文档、向量、BM25、版本 | doc_registry + rag_vectors ✅（覆盖失真）+ FAQ ❌缺 |
| 业务数据 | 订单/物流等（只读集成） | agent_business 模拟库 ⚠️ |
| 运营数据 | 指标、报表、成本 | 质检报表 + llm_usage ✅（归因列空） |
| 标注/评测 | 黄金集、badcase 池、定标集 | 评测框架有、客服域集 ❌缺 |

关键闭环：**badcase → 标注 → 黄金集 → 评测门禁 → 拦截回归**；**拒答/转人工/差评 → 缺口清单 → 知识生产 → 效果回收**。两条回流管道是企业级与 Demo 的分水岭。

### 3.4 技术架构（典型形态）

渠道 webhook/WebSocket → 消息队列削峰 → 对话引擎（无状态×N）→ LLM/RAG → 业务集成（熔断降级）→ ACD/工单 → 数据分析回流。私有化部署、灰度发布、多副本 + 会话亲和解除。

**对本项目的映射**：APISIX ≈ 渠道网关位（缺渠道适配器）；GraphRunner ≈ 对话引擎（同步 SSE 单副本，扩展路径已建未演练）；rag-service ≈ 知识服务（缺 FAQ 层与生命周期）；handoff ≈ ACD 雏形（缺排队/SLA/技能组）；质检报表 ≈ 质检服务（缺会话级 AI 质检）；outbox ≈ 集成层雏形（缺适配器）。

## 4. 技术栈分块建议

每块按「现状 → 建议 → 替代方案 → 优先级」。

### 4.1 渠道接入

- **现状**：仅自建 Web 窗口（SSE）。
- **建议**：先抽**渠道适配器抽象**（接口：消息归一化 inbound/outbound + 渠道 ack + 幂等去重 + visitor 映射），然后按国内电商优先级落：
  1. **企业微信「微信客服」API**（首选）：可挂公众号/小程序/视频号入口，机器人可注册为接待人员，回调 API 完整、免费；
  2. **微信服务号客服消息**：48h 窗口期限制、被动回复 15s 超时重试语义，需幂等去重（微信 5s 无响应会重推 3 次）；
  3. **APP**：不自研原生 SDK——H5 会话组件（复用现有 Web 窗口）+ WebView 嵌入，1 人团队唯一务实解；
  4. **电话语音**（最后）：不自建。最低成本闭环 =「未接来电 → 短信引导 → 文字渠道/工单」；若必须语音，接 SaaS（智齿/合力亿捷/容联）做人工语音 + AI 文字辅助，或 ASR+LLM+TTS 按分钟付费——按量成本最高，明确 P2/暂缓。
- **替代方案**：SaaS 客服平台托管（美洽/智齿/Udesk 只做机器人接入）——与私有化+学习目标冲突，仅作对照不采用。
- **优先级**：**P1**（渠道抽象 P1，微信渠道 P1，APP H5 P2，语音 P2/暂缓）。
- **关键坑**：微信是「推」模式且断线重推 → 消费端必须幂等（msg_id 去重表）；主动消息窗口期；回调验签。

### 4.2 会话网关

- **现状**：APISIX + SSE 同步单副本；F2 SSE resume 已建；无跨渠道会话归一。
- **建议**：保留 APISIX 不换。补两件事：①**visitor 统一身份**（channel_user_id ↔ visitor_id 映射表 + 会话合并策略，转人工与多渠道的前提）；②**WebSocket 长连接通道**——人工对话与渠道推送必须真正双向，现有坐席工作台 WS 可复用扩展为「用户侧双通道」：SSE 管机器人流式、WS 管人工/渠道事件。多副本时 SSE resume + 状态在 PG/Redis 已解会话亲和。
- **替代**：Nginx/自研网关——无理由替换 APISIX。
- **优先级**：visitor 映射 P1（随渠道走）；WS 双通道 P1（随人工协作走）。

### 4.3 对话引擎

- **现状**：LangGraph 域图完整，域主 Agent 规则调度 + LLM 兜底开关化，防循环守卫，PG checkpointer。
- **建议**：**保留不动**。增量：①把追问话术/转人工阈值/灰度比例从代码常量收敛为「客服运营参数表」+ 管理端可调（变更走评测门，非自由编辑）；②多副本前验证 Send 并行与 checkpoint 写竞争（评审 P1-5 已含）。
- **替代**：Temporal（重、无收益）；Dify/Coze 类编排（不可控、私有化受限）——都不换。
- **优先级**：P1（参数收敛）。

### 4.4 NLU / LLM

- **现状**：词表+规则+LLM 三层；主模型 doubao-seed-2.0-mini，12 角色化治理。
- **建议**：三层保留。增量：①**意图/分诊黄金集**（300 条：每意图 ≥20 正例 + 边界负例 + 出域样本）作为词表/规则任何变更的评测门——这是「词表热更无守护」的直接补法；②判域 LLM 调用（实测 2.9s 串行）小模型化或本地 embedding 分类器前置（CoarseIntentClassifier 已存在，评审 L2 已列 P2 优化）。
- **替代**：Rasa/传统 NLU——否。
- **优先级**：黄金集 **P1**（评测痛点 6 的客服域落点）；判域提速 P2。

### 4.5 RAG 知识库（最大瓶颈的系统性解法）

检索链保留，**要补的是供给侧**。三个子块：

**a. 数据面修复（= 施工书 P0，不重复展开）**：索引收敛 Job 三方对账、265 份补索引、804 积压处置、parsing 看门狗、上传闸。出口：覆盖率 ≥99%、对账 14 天零不一致。

**b. FAQ 双轨（新增，客服域特有）**：
- FAQ 结构：`question / variants(问法变体) / answer / 知识文档引用 / 生效渠道 / 有效期 / 审核状态`；
- **三段式检索**：FAQ 精准匹配（embedding 相似度超阈值 → 直接返回答案，不进 LLM 生成：TTFT 从秒级降到 <500ms、成本≈0）→ 未命中进文档 RAG → 仍未命中 LLM 兜底。电商客服「查订单地址/退货政策/发货时效」类高频问题 80% 该走 FAQ 层；
- FAQ 来源：从现有文档蒸馏高频问答对 + 坐席人工答复回流自动成候选。
- **优先级：P1（知识侧最高性价比新能力）**。

**c. 知识运营机制（用户痛点「谁维护/怎么更新/怎么验收」）**：
- **谁维护**：角色化——知识运营（编写/更新）与知识审核（发布门）分离；1 人团队也要双角色走流程（自己左手写右手审），保证企业级机制真实运转而非纸面；
- **怎么更新**：生命周期 `draft → in_review → published → deprecated` + 变更审计 + 时效性知识（活动/政策）强制带过期时间 + 季度盘点；
- **怎么验收**：新知识上线 7 天效果回收（相关问题的拒答率/命中率前后对照）+ 引用准确率抽检 + 命中的 badcase 回流；
- **缺口来源管道**：拒答日志聚类 + 转人工会话坐席答复回流 + 差评会话 → 自动生成「待补知识清单」（管理端知识运营页）；
- **EvidenceGate 定标**（= 评审 P1-2）：200 条定标集（应答/应拒各半），假拒 <10%/漏拒 <5%，阈值实验台替代散落硬编码。
- **优先级**：生命周期+缺口管道 P1；效果回收 P2。

### 4.6 Agent / 工具调用

- **现状**：39 Tool + 12 Skill + 契约 lock + 审批门 + 七分类错误口径——治理超配。
- **建议**：保留全部。增量：①客服高频工具（订单/物流查询）加**结果缓存 + 降级预案**（业务系统不可用时客服返回「系统繁忙+已记录+转人工」而非卡死——熔断降级语义）；②工具错误七分类看板已有（M2/M3），补客服域视角告警（订单查询错误率突增 = 业务系统故障的先导信号）。
- **优先级**：降级预案 P1；看板告警 P2。

### 4.7 业务系统集成

- **现状**：6 业务服务查的是**自己库里的模拟数据**——这是「演示」与「企业」的分水岭之一。
- **企业级做法**：集成层 = 适配器模式（防腐层）：客服域定义 `OrderProvider / LogisticsProvider / TicketSink` 等接口，内部实现（模拟库）与外部实现（真实 API）可插拔切换；外部适配器必须带超时/熔断/缓存/凭据治理（复用 domain-service-map 的五行登记）。
- **落地路径**：先接一个真实外部源验证模式——**物流轨迹 API（快递100/菜鸟，免费额度可用）是最现实的第一刀**（低敏感、只读、高频）；订单侧保留模拟库。
- **工单对接**：**outbox 已有是最大优势**——补「对外同步适配器接口」（REST + webhook 双向、状态映射表、冲突仲裁以对方为准），用 GitHub Issues 或 Jira 做对接示范验证接口完备性，真实工单系统来了换适配器即可。
- **优先级**：适配器接口抽象 P1（随工单走）；物流真实源 P2；工单外部对接 P2。

### 4.8 数据与评测

- **现状**：9 套件评测框架 + PR smoke 门禁；客服域黄金集缺、回流闭环断。
- **建议**：客服域三套黄金集：①意图分诊集 300 条；②转人工时机集 50 条（明确要求/情绪激动/连错 2 次/敏感投诉/贵重订单边界）；③拒答定标集 200 条（与评审 P1-2 共用）。**badcase 回流管道**：质检报表差评 + 人工纠错 + 拒答样本 → 标注队列 → 黄金集/定标集 → CI 门禁。客服域 smoke 8 条进 PR 门禁（对齐 rag_smoke 模式）。
- **优先级**：三套集 P1；回流管道 P1（轻量起步：一张标注表 + 管理端页）。

### 4.9 运维与安全

- **现状**：监控栈停摆 6 天（施工书 P0 救活）；四类安全埋点在工作；审计完整。
- **客服域特有增量**：
  1. **PII 脱敏进 LLM**：手机号/地址/姓名在进入 prompt 前脱敏或 tokenization（占位符替换 + 回复时还原）——个保法视角的必做项，当前未做；
  2. **AI 身份告知**：会话开场显著标识「AI 智能客服」+ 转人工入口常驻（生成式 AI 管理办法 + 电商平台惯例）；
  3. **消息留存策略**：留存期限 + 用户删除权接口（当前只增不减）；
  4. **承诺类话术锁定**：退款金额/赔偿等 LLM 不得自由生成，模板化锁定（幻觉风险最高的合规点）。
- **优先级**：PII 脱敏 **P1**；AI 告知 P0.5（一行话术，立即可做）；留存策略 P2。

## 7. 演进路线（四阶段）

**Phase 0（0-2 周，进行中）——平台止血 = 知识修复地基**
= 施工书 41 任务卡 P0：索引覆盖 ≥99%、监控救活、TTFT 修复、备份演练、积压处置。
出口：覆盖率 ≥99%、监控连续 7 天、TTFT 有数据。

**Phase 1（2-6 周）——知识供给侧企业化（痛点 1 根治）**
1. 知识生命周期（draft/review/published/deprecated + 过期时间 + 审计）+ 双角色流程；
2. FAQ 双轨：FAQ 表 + 三段式检索（FAQ→RAG→LLM）+ 从文档蒸馏首批 100 条高频 FAQ；
3. 缺口管道 v1：拒答日志聚类 + 转人工答复回流 → 管理端「待补知识清单」页；
4. 客服三套黄金集（意图 300 / 转人工 50 / 定标 200）+ 词表变更评测门 + 客服 smoke 8 条进 PR 门禁；
5. EvidenceGate 定标实验台（承接评审 P1-2）；
6. AI 身份告知 + PII 脱敏进 LLM。
出口：拒答率 63.5% → 15-30%（定标口径假拒 <10%）；FAQ 层命中占比可测；新知识 7 天效果回收有报告。

**Phase 2（6-12 周）——人工协作企业化（痛点 3/4 后半）**
1. ACD：排队队列 + 技能组（按意图分类路由坐席）+ 负载均衡 + 坐席状态机（在线/小休/离线）+ SLA 计时催单 + 离线留言；
2. 坐席工作台升级：排队台（等待量/最长等待）+ 会话转移/升级 + 快捷回复库 + 服务小结 + 满意度邀请；
3. 工单生命周期：状态机（升级链/超时升级/回访）+ 对外同步适配器接口（outbox 出站 + 状态映射）+ GitHub Issues/Jira 对接示范；
4. badcase 标注回流管道 v1（标注表 + 管理端页）。
出口：排队/SLA 指标可测（排队放弃率、首响 ≤30s 达标率）；工单可双向同步到外部系统。

**Phase 3（3-6 月）——渠道与真实集成（痛点 3 前半）**
1. 渠道适配器抽象 + 企业微信微信客服渠道（回调 + 幂等去重 + visitor 映射）；
2. APP H5 会话组件（WebView 嵌入方案交付）；
3. 物流轨迹真实 API 适配器（快递100/菜鸟，验证防腐层模式）+ 高频工具熔断降级；
4. 会话级 AI 质检（合规/情绪打分）+ 效果回收制度化；
5. 多副本演练（承接评审 P1-5，DIST 门 + SSE resume 跨副本）。
出口：微信渠道端到端真实对话；外部物流 API 故障时客服可降级应答；两副本 P95 不劣化。

**暂缓（显式不做）**：电话语音、多租户、可视化编排器、原生 APP SDK。

## 8. 成本、风险、合规、核心指标

### 8.1 成本

- **LLM API**：现状 7 天 ¥17.79（54% 在入库侧）；修复归因后按域记账已有治理。增量预估：FAQ 层上线后高频问题成本≈0（不过 LLM），整体问答成本**下降**；意图黄金集评测跑批属于低成本批处理。建议设月度预算上限（预算门已有，补一条客服域额度）。
- **渠道**：企微/微信 API 免费；短信引导（电话兜底）按条 ~0.045 元；电话语音若上 SaaS 按坐席/分钟计费（数百元/月起）——暂缓理由成立。
- **基础设施**：单机现有硬件 + 电费，Phase 3 前无新增。
- **人力**：1 人 + AI 会话——**最大成本是自己的时间**：Phase 1 约 4 周 × 50% 投入，Phase 2 约 6 周。按此排期需接受 Phase 3 顺延。

3. **生成内容风险**：承诺类话术（退款金额/赔偿）模板锁定，禁 LLM 自由生成；
4. **数据出境**：全栈私有化天然满足；
5. **知识版权**：外部引入语料（如维基百科 CC BY-SA）保留出处（已有先例）。
