## 〇、总览（先读这个）

智能客服域的**骨架是健康的**：域图拓扑、确认三段式、派单并发控制、坐席 WS、落库隔离、checkpointer 纪律都是真实且扎实的实现，**不存在需要重写的架构**。真正阻塞「收口上线」的是六类问题：

1. **四个端点裸奔（IDOR，已实测坐实）**——任何登录用户可读全库会话列表/统计/他人会话详情/trace 关联；
2. **租户字段三处缺口**（写路径恒 default、查询无 tenant 过滤、WS 广播无租户）；
3. **「停止」只停在节点边界**——CS 整图是主图单节点，点停止后子图（含全部 LLM 调用）继续跑完；
4. **RAG 答案缓存命中会被 CS 拒答门强制顶替为拒答话术**（`.env` 中 `RAG_ANSWER_CACHE_ENABLED=true`，已实弹）；
5. **人工接管生命周期不自愈**——坐席中途退出后 `human_active` 会话永久滞留，无超时、无重派 UI；
6. **handoff 状态一致性裂缝**——跨进程 L1 缓存漂移 + `handoffs`/`conversations.handling_mode` 双表分叉 + 幽灵状态 `initiated`。

其余为重复层收口（supervisor v1/v2、两级同源正则、shim 兼容层、tickets/cs_case 双写）、工具治理域外特区、测试断层（真 PG 验收不在默认绿色基线内）与前端死代码体量问题。

## 三、CS Graph 真实拓扑

`backend/customer_service/graph_builder.py`（:126-171）实测定论：

- `add_node` 9 个：cs_state_loader / cs_pending_handler / cs_supervisor / cs_reporter（4 个编排节点包 `wrap_cs_node` 打 span）+ 5 个 expert（Span 由 CsExpertHooks 负责，:137-138 注释）。
- `add_conditional_edges` **零条**——路由全部由 `Command(goto=...)` 完成（supervisor.py:810-818、pending_handler.py）。
- 接线：START→loader→pending_handler；5×(expert→supervisor) 静态回边；reporter→END。
- 真实拓扑：

```
START → cs_state_loader → cs_pending_handler ─┬─(无 pending)──────────────→ cs_supervisor ⇄ 5×expert
                                              └─(补槽 pending)→ 转发 action expert ┘
cs_supervisor ──Command(goto)──→ expert ──静态边──→ cs_supervisor（循环）
cs_supervisor ──(FINISH/PENDING/HANDOFF)──→ cs_reporter → END
cs_pending_handler ──(确认/取消/超时终态)──→ cs_reporter → END
```

| 节点 | 输入 | 输出 | LLM | Tool/DB | 副作用 | 下一跳 |
|---|---|---|---|---|---|---|
| cs_state_loader | 主 state 输入 | PG 业务快照（status/mode/handoff/confirmation/pending）+ 执行态重置 | 否 | PG（StateTransitionService.load_snapshot）| 无 | pending_handler |
| cs_pending_handler | pending_action | 处理确认/取消/超时（委托 confirmation_flow 唯一实现）；补槽转发 | 否 | PG（confirmation_store）| 确认消费（一次性 claim）| reporte / action expert / supervisor |
| cs_supervisor | cs_route + 信号 + 历史 | CSSupervisorDecision（Command goto）| 仅 L7 兜底（800ms 限时，默认开）| 无 DB | 无 | 5 expert / reporter |
| cs_knowledge_expert | question+kb_ids | RAG 回答+置信三档 | 是（rag.qa）| RAG pipeline + ai.cs_faq | 无 | supervisor |
| cs_query_expert | intent+槽位 | 订单/物流/工单查询结果 Markdown | 少量（多意图分解/精确查单）| PG agent_business / HTTP business-mock | 无 | supervisor |
| cs_action_expert | intent+槽位 | proposal / 确认处理 / **模拟执行** | 否 | confirmation_store + PG ledger | proposal 落库；执行全 simulated | supervisor |
| cs_complaint_expert | 信号 | 工单+必升级转人工 | 是（严重度兜底，3s 限时）| tickets + cs_case + handoff | 工单落库 + WS 通知 | supervisor |
| cs_handoff_expert | 触发词/自动 | waiting_human 入池 | 否 | handoff store + tickets | handoff 落库 + WS | supervisor |
| cs_reporter | supervisor_decision + expert 结果 | final_answer | **否** | 无 | OutputGuard 后直出 | END |

十问回答：

1. **Command(goto)?** 是，supervisor 与 pending_handler 均返回 `Command(goto=target, update=...)`，无条件边 [代码 supervisor.py:810-818]。
2. **expert 为何回 supervisor?** 静态边回边（graph_builder.py:159-163），每次回都重新过七层裁决（handoff 拦截/pending/风险/循环/分诊/路由/低置信），支持一轮内多 expert 协作。
3. **最大循环次数**：`CS_EXPERT_MAX_LOOPS=5`（config/customer_service.py:116）+ 同 expert 连续 2 次即 FINISH（supervisor.py:622-628）+ 图级 `CS_GRAPH_RECURSION_LIMIT=20`（:169）。三重守卫。
4. **FINISH 条件**：路由置信度达标派完 expert 返回后（`is_finished`）、循环超限、重复检测、分诊直出、专家无输出兜底。
5. **HANDOFF 条件**：handoff 拦截态（INTERCEPT_STATES，handoff.py:117-119）、P0 直通后 complaint 必升级、显式转人工触发词、低置信拒答自救走到必转时机。
6. **PENDING 条件**：action expert 产出 proposal（`requires_confirmation`）或缺槽追问（need_info）。
7. **Reporter 只负责展示?** 是——纯模板组装零 LLM；唯一"决策"是按 `supervisor_decision.direct_reply` 直出（消费 supervisor 已做的决策，不自做决策）。
8. **Reporter 有无偷偷做业务决策**：无。七级组装优先级都是消费上游产物。
9. **Expert 可否直接执行高风险副作用**：**不能**。所有执行走 `_simulate_execute` 三类型全部只构造 `AgentActionRecord(status="simulated", data.simulated=True)`（refund_service.py:102-121 等），无 DB 写无 HTTP 写；真实副作用 Phase 6 未接入（confirmation_flow.py:223-227 文案自证）。
10. **Confirmation 挡在副作用前?** 是，且链路完整：proposal 落库（语义指纹唯一守卫 051 索引）→ 用户确认（卡端点/文本关键词共用 `process_confirmation`）→ `claim_for_execution` 原子认领（条件 UPDATE pending→confirmed RETURNING，rowcount 决胜）→ durable 幂等账本 `cs.action.execute` → 模拟执行。**全项目最扎实的部分**。

## 四、是不是「Router 太多了」

真实决策层全图：

```
【Domain 层（进不进 CS）】
runner CS Input Guard（锁域提前门禁）
  ↓
router_node：cs_rule_hits_of（第 1 级正则计数，domain_detector.cs_rule_hit_count）
  ↓
cs_prefilter：detect_cached → DomainDetector.detect（第 2 级完整正则检测，同词表同源）
  ↓
CSRouter.route = CSCoarseRouter（域，计票）+ CSFineRouter（意图，规则映射）   ← intent 唯一判定点
  ↓
route_selector → DomainGraphRegistry（查表，无判定）
  ↓
【CS 域内（选哪个 expert）】
cs_supervisor：七层裁决 = handoff 拦截 → pending → 风险信号门 → 循环 → L4.5 分诊直出 → L5 查表映射 → L6/L7 低置信(LLM)
  ↓
【工具层】
无 Tool Selector（CS 不经过）
```

逐层结论：

- **两层正则同源冗余（真实存在，官方自认）**：`router_node.py:78-79` 注释明写「1) 与 3) 现在同源（都走 _rule_channel 正则），属可收拢的冗余」。锁域路径下第一级结果仅剩 redirect 判定用途（:137），而 `CS_WINDOW_STANDALONE=true` 下该分支恒 None。**没有两个组件同时判 intent**（CSRouter 唯一），**没有两个组件同时选 expert**（supervisor 查表唯一）。
- **出域/寒暄双判定（受控重叠）**：router 层 `detect_cs_redirect` 与 supervisor 层 `_triage_direct_reply` 语义重叠，靠同一开关互斥对齐——是设计选择而非漂移，合并需改判定语义，**不建议本轮动**，补单一事实源注释即可。
- **枚举映射已收口**：P2.2 改造后权威表在 `graph_state.py:35-73`（ROUTE_PATH_TO_EXPERT_NAME / EXPERT_NAME_TO_NODE / DOMAIN_TO_EXPERT_NAME / ROUTE_PATH_TO_CS_TARGET / CS_TARGET_TO_EXPERT 派生），supervisor.py:61-67 注释确认此前三处硬编码已统一；无活跃的第二套映射。
- **低置信处理单一**：supervisor L6（知识类放行例外）/L7（LLM 兜底）唯一；coarse/fine 只出 confidence 不处理低置信。
- **risk/handoff 无重复裁决**：规则原语单源（`should_intercept`/`is_p0_escalation`/signals.py），v1/v2 只是分支双写（见 §五）。
- router/ 目录 6 文件全部有产线或门禁调用方，**无废弃死模块**（域检测向量通道已于 3f88b4f 删除）。

```ini
CS_ROUTING_SINGLE_RESPONSIBILITY=false   ; 因两级同源正则冗余 + 出域双判定受控重叠
CS_ROUTING_DUPLICATION_FOUND=true        ; 但均为「可收拢冗余」级，非职责混乱
```

**最小改动**：锁域路径让第一级直接复用 `detect_cached(query).rule_hits`（检测结果与 session 无关、已有 TTL 缓存），或锁域跳过第一级；改动面 = router_node 约 5 行。

## 六、三套状态生命周期（以代码为准）

### 6.1 Conversation（state_machine.py）

```
status: open ⇄ pending / → resolved / → snoozed；pending→open|resolved；resolved→open；snoozed→open
mode:   ai → human|waiting_human；human → ai；waiting_human → human|ai
不变量：resolved 必须 mode=ai；mode=human 必须有 assigned_agent_id（:90-100）
```
- 执行者：`transition()/apply()`（:103-137，只校验/原地改），落库在 ConversationManager（conversation_manager.py:112/155）。

### 6.2 Confirmation（confirmation.py:22-60）

```

confirmed → executing；executing → success|failed|verifying；verifying → success|failed
```

### 6.3 Handoff（handoff/handoff.py:30-65）
