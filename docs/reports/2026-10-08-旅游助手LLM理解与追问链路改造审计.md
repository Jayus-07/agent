## B. clarification 生成次数 → **DUPLICATE_CLARIFICATION_GENERATION = true**

| 生成点 | 位置 | 触发条件 |
|---|---|---|
| ① | `slot_filler.py:304` `_requirement_agent.build_clarification(brief, message)` | 每轮都算，写入 `state.clarifications` |
| ② | `reporter.py:461` `build_clarification(brief, state.get("user_message",""))` | supervisor 转 REPORT 且 `brief_missing` 时**从 brief+原话重新推导一遍** |

两点当前输出一致（同为纯模板、同输入），但违反单一事实源；本轮收口为：
slot_filler 为唯一生成点（ClarificationPlan → Renderer），reporter 只消费
`state["clarifications"]`，不再 import `build_clarification`。reporter 保留
**纯模板**应急兜底（state 无 clarifications 的历史状态/checkpoint 异常态），
零 LLM、零重判。

## C. llm_intent_service 现有契约

- 输出：`family ∈ {query, modify, out_of_scope, unknown}` → 仅映射
  `query_dynamic / modify / out_of_scope`（**无 plan 映射**，防止 LLM 跳过补槽）。
- 三条铁律：只在词表返回 None 时触发；只产枚举不碰字段；失败回落 None。
- 槽位抽取零参与 —— **保持单一职责，本轮不往里塞槽位补全**（新服务独立文件）。
- 已知存量缺口（登记不在本轮修）：`_build_llm_for` 直构调用未补
  `record_llm_result` 计量（llm_usage 无该路径记录）。

## E. LLM 构建方式与计费

- 构建出口（旅游域先例 llm_intent_service，2026-10-04 实机甄别）：
  `model_roles.resolve_effective("main")` 取 DB 绑定名 →
  `backend.infra.llm.proxy::_build_llm_for(model_name)`（唯一带 DB 托管凭据
  解析的构建出口；`get_llm_for_role`/全局 proxy default 通道在本库解析为
  无凭据构造）。
- 限时：`backend.infra.async_utils.sync_call_with_timeout`（线程级超时，
  ChatOpenAI 的 config timeout 实测不生效）。
- 计费：绕过 `_LLMProxy` 的直构调用必须补
  `proxy.record_llm_result(response, duration_ms=…, model_name=…)`
  （rag/preprocessing/llm_enrichment.py 的既有模式）→ 进 llm_usage →
  pricing 唯一入口 `price_usage()` 统一计价。
- 归因：`backend.observability.llm_context.llm_attribution_scope(agent_domain="travel")`
  包裹调用，llm_usage 落 agent_domain 维度。
- 禁止事项核对：不自建 ChatOpenAI ✅｜不读 API KEY ✅｜不另起计费 ✅。

## F. 前端契约（复用，不改前端）

- `PlanResponse.clarification`：追问正文（Markdown 纯文本即可）。
- `PlanResponse.clarification_options: {label, days:number|null, message}[]`：
  点击 = `send(message)`；`days===null` = 聚焦输入框。
  → destination 选项**不带 days 键**（undefined ≠ null → 走重发通道）✓
  → days 选项维持既有「按 3 天参考规划 / 自己填天数」两枚（存量测试锁定，
     且快捷接受+自由输入优于 2/3/4 硬枚举）。
- C 端不展示 prompt 版本/LLM 状态（管理端/Trace 专属）。
