## 3. 改造后架构

```
用户消息
 ↓ router_node（锁域/全局命中/兜底三入口）
 ├─ _enrich_with_understanding      规则理解层（零 LLM，CSUnderstanding）
 └─ _enrich_with_semantic           ★新增 LLM 语义层（Rule First 编排）
     ├─ 规则强命中 → LLM 0 次（source=rule）
     ├─ rule miss/低置信 → LLM intent 补判（INTENT_PROFILES 动态白名单）
     │    → validator → 画像派生改写 cs_route（固定保守置信度 0.65）
     └─ 意图需要业务对象且无显式订单号 → LLM 语义槽位候选
          → validator（键名白名单+真实 ID 形态拒绝）→ metadata.semantic_slots
 ↓ CS Supervisor（七层守卫不变；L7 补 decision_source 打点）
 ├─ ActionExpert  ★semantic_slots → 真实订单解析（唯一绑定落穿 proposal /
 │                多候选点选追问 / 服务故障如实说不可用）；状态机红线不动
 ├─ QueryExpert   ★semantic 唯一匹配 → 精确查单；既有 latest 兜底保留
 ├─ ComplaintExpert ★severity 溯源打点（rule/llm_fallback）；validator 收口
 ├─ HandoffExpert（零 LLM，归因词表补「不想跟机器人」）
 ↓ CS Reporter
 ├─ _assemble_answer（模板组装，不变）
 └─ ★Response Composer：knowledge=直通(llm) / query=complaint=LLM 转写
    （一次调用+订单号守卫）/ action=handoff=模板直出 / 失败回模板
 ↓ OutputGuard（五层过滤，仍在最后——P0-20）
用户
```

## 4. Understanding Layer（Phase 1）

`backend/customer_service/understanding/`（7 文件）：

| 文件 | 职责 |
|---|---|
| contracts.py | `CSUnderstandingResult`/`CSSlotCandidate`/`CSUnderstandingSource` 契约；SLOT_NAME_WHITELIST 7 字段；FORBIDDEN_SLOT_NAMES 10 个真实 ID 字段 |
| validator.py | 意图/槽位/severity/confirm 四类白名单校验；真实 ID 值形态拒绝（订单号连字段/工单前缀/UUID）；`extract_json_object` 容错解析 |
| llm_runtime.py | LLM 公共边界：PII 掩码进、llm 代理、线程级限时、一次调用失败返 None（禁止自动 retry） |
| llm_intent_fallback.py | 规则 miss/低置信补判；白名单从 `INTENT_PROFILES` 动态构造进 prompt |
| llm_slot_enrichment.py | 语义槽位候选（product/time/ordinal/attribute…）；SLOT_TARGET_INTENTS 5 意图族 |
| llm_confirm_candidate.py | 确认语义候选（`CS_CONFIRM_LLM_CANDIDATE_ENABLED` 默认 false；疑问句永不进入） |
| semantic.py | Rule First 编排：`enrich_semantic_understanding()`；槽位段独立 try 不连累 intent 采纳 |

命名说明：任务书建议的 `service.py` 已被迁移 B11 import 兼容 shim 占用（→ 规则层 `context/understanding/service.py`），编排入口命名 `semantic.py` 职责等价。

## 5. Slot Enrichment（Phase 2）

- LLM 只产语义指称候选；真实 ID 唯一出口 = `context/semantic_slots.py::resolve_semantic_slots`（用真实 user_id 查 `order_service.list_recent_orders_with_products` 新方法，商品名包含匹配 + 时间窗口缩小）。
- 语义：唯一匹配 → `metadata.order_id` 权威 referent（query 精确查单 / action 落穿 proposal，资格校验照常）；多候选 → 点选追问（`_ask_missing_slot` 新增 `candidates_override`，退货/换货同样获得点选能力，话术按动作类型渲染）；无匹配 → 不猜。
- 补槽阶段（`_handle_slot_fill`）同样接语义解析：用户以「就耳机那个」类自然引用回答追问时可唯一绑定。
- 红线核对：LLM 输出永不直接当 ID 消费（validator 键名+值形态双保险）；服务故障上抛 DatabaseError 由专家层译成「业务服务暂时不可用」（STOP C 口径），不伪装成「没有匹配」。

## 6. Supervisor LLM 收口

`_llm_decision` 行为零变化（ExpertType 白名单 + 800ms 线程超时 + None 降级）；新增 `cs_supervisor_decision_source` trace tag（layer=3 时区分 `llm` 与 `fallback`——reason 含「LLM 决策不可用」即规则降级；其余 layer=rule）。Guard 时序：L7 位于七层守卫（handoff/pending/风险/循环）之后，LLM 只产出 RUN_EXPERT 且经 `EXPERT_NAME_TO_NODE` 查表 goto——结构上不存在 LLM 改状态/跳守卫路径（P0-05/06/13）。

## 7. Complaint LLM 收口

- `_llm_assess` 的 severity 改经 `validator.validate_severity`（low/medium/high 白名单，词表外整体丢弃回规则——LLM 词表本无 critical，越权输出无处落地）。
- `cs_severity_source` trace tag（rule/llm_fallback，按 matched_patterns 判定）。
- 建单/转人工仍由规则矩阵执行（severity∈high ∪ 收集计数≥1 ∪ 仲裁 escalate，fail-safe 偏人工）——LLM 只出 candidate。

## 8. Response Composer（Phase 3）

`backend/customer_service/response/`（contracts + composer）：

| Expert | 策略 | LLM 次数 |
|---|---|---|
| knowledge | LLM_UPSTREAM 直通（RAG 链已是 LLM 组织+证据门禁） | 0（不二次烧模型） |
| query | LLM_PREFERRED：结构化事实+模板初稿 → 自然语言 | ≤1 |
| complaint | LLM_WITH_GUARD：安抚话术自然化 | ≤1 |
| action / handoff | TEMPLATE 直出（高风险话术禁 LLM 改写） | 0 |

- Reply Contract：输入 `CSResponseContext`（facts 白名单化，剥离 audit/pending/身份字段）；输出 `CSRenderedResponse` 只允许 answer。
- **P0-18 守卫**：输出中订单号集合 ⊆ 输入基线（draft+facts）集合，出现未知订单号即拒绝回模板；日期形态（10-10）不误杀（订单号正则要求含字母）。
- 降级：超时/异常/非法 JSON/守卫拦截 → 模板初稿原样返回，source=llm_fallback，绝不 500/断流/空回复；一次调用无重试。
- OutputGuard 仍在 reporter 最后执行；guard 结果写 `cs_response_guard_result`（filtered:<reasons> 优先）。

## 9. Action 安全边界（本轮未放松任何一条）

缺 order_id 禁止猜 latest（`_SLOT_ORDER_INTENTS` + 结构化追问）→ 语义解析唯一绑定**不跳过** proposal/确认（写操作链路 Intent→Slot→Permission→Proposal→Confirmation→Execution→Audit 每层原样）→ Business Guard 幂等判重 → 原子认领 → durable ledger。全链路零 LLM。存量 action/confirmation 回归 147 条全绿。

## 10. Confirmation / Handoff 状态机

- confirmation：状态机/原子认领/幂等 ledger 零改动；新增 LLM candidate 仅在规则 NONE 时提供 confirm/cancel 白名单值，经 `ConfirmationIntent` parser 消费；疑问句在 candidate 前硬短路（「退款多久到账？」永不定表态）；开关默认 false（词表已覆盖 P0 案例 6/7）。
- handoff：状态机/lifecycle 唯一入口零改动；仅补 `_HANDOFF_PATTERNS` 归因模式「不想跟机器人说了」类表达此前落 auto_trigger（转人工链路正常但归因失真为能力缺口），现正确归因 explicit_request。

## 11. PII

全部新增 LLM 调用（intent/slot/composer/confirm）经 `llm_runtime.mask_for_llm`（shared/pii_mask 单一实现）掩码后进模型、掩码后不还原（E4b 口径）；composer facts 白名单额外剥离 user_id/tenant_id；Prometheus label 全部低基数枚举（无 user_id/order_id/手机号/原文）。

## 12. Prompt Governance

新增 4 键全部走 `prompts/defaults/*.yaml` + `registry.py` 注册（category=customer_service, risk_level=high, agent=customer_service）：

```
customer_service.intent_understanding / slot_enrichment /
customer_service.confirm_candidate / response_composer
```

全部经 `render_prompt`（PromptService）渲染，模块零硬编码 production prompt。版本随 `record_prompt_version` 统一落旁路；composer/semantic 打 `cs_response_prompt_version`/模型/耗时 tag。`prompts.lock.json` 为 DB 发布状态镜像——4 键尚未发布到 PG，lock 无变化（发布走管理端门禁后重新生成）。

**并行会话在途说明**：registry.py 同时含另一会话的 2 个 travel 键（STOP 1/4 在途，其 YAML 已落盘未提交），按多会话纪律 registry.py 与 `test_registry_defaults.py`（断言 51→57）**留工作区未提交**，待该会话落定后一并入库；期间本域 4 键经 defaults 路径完全可用（render_sync YAML 兜底，version=None）。

## 13. Token/Cost

全部新 LLM 调用走 `backend.infra.llm llm` 代理（`llm_invoke_once` 唯一出口）——限流/韧性/llm_usage 记账自动生效，component 经 trace.tags.cs_target 归因 customer_service（G7 口径，对账合并主图无需改）。成本结构（任务书 §三十三）：规则强命中请求 0 次新增 LLM（Rule Fast Path）；复杂自然语言请求 intent+slot ≤2 次理解 LLM + ≤1 次回复 LLM；action/handoff/knowledge 路径零新增。

## 14. Trace/Metrics

Trace tags 新增：`cs_understanding_source`（rule/rule+llm/llm_fallback/unchanged）、`cs_llm_intent_used`、`cs_llm_slot_used`、`cs_llm_slot_candidate_count`、`cs_llm_slot_accepted_count`、`cs_llm_slot_rejected_count`、`cs_llm_slot_fallback_reason`、`cs_supervisor_decision_source`（rule/llm/fallback）、`cs_severity_source`、`cs_response_source`（template/llm/llm_fallback）、`cs_response_model`*、`cs_response_prompt_version`、`cs_response_latency_ms`、`cs_response_guard_result`。

Metrics 新增（`observability/metrics.py`）：`cs_understanding_llm_total{status}`、`cs_slot_llm_total{status}`、`cs_slot_llm_fallback_total{reason}`、`cs_response_total{source}`、`cs_response_llm_fallback_total{reason}`。*cs_response_model 由 llm_usage 行（component=customer_service）按 call 关联，trace 不重复落模型名（低基数纪律）。
