# 旅游助手 Tool 失败降级与容错修复验收报告

> 日期：2026-10-07 ｜ 分支：feat/model-billing-closure ｜ 任务书：STOP A–K 全条目
> 冻结契约：**Tool Failure ≠ Workflow Failure；External Provider Failure ≠ Internal Planning Failure；Optional Data Missing ≠ Task Impossible；DEGRADED ≠ SUCCESS/FAILED；FAILED ≠ BLOCKED**

---

## 1. 原始故障

浏览器实机（旅游页 `/api/travel/plan/stream`）：规划「福州」行程时 景点检索 ✅ / zhihu ✅ / **12306 车票查询 ❌**，报 `RuntimeError: asyncio.run() cannot be called from a running event loop`；随后 transit 专家 failed → 无 itinerary → 前端整页「行程未能生成（排程阶段未产出结果）」+「本轮共 3 个 Tool · 执行失败」。

实机日志（agent-app-1，trace 41c7ecd8c349 / b1e60d96b003）证实：**12306 与知乎真实调用都曾报同一错误**——知乎平时「成功」是 ToolCache 命中掩盖（`[ToolCache] 命中 zhihu_search_tool:...`），缓存未命中即炸。

## 2. 12306 根因（STOP A）

调用链：`transit_expert_node → run_travel_tool → PlanningAgent.search_trains → live_search_service._invoke → GovernanceRuntime.execute_sync → SafeToolExecutor._invoke → travel_train_search_tool → mcp_client.call_tool → asyncio.run(_call_async)`。

**根因是治理层引入的嵌套事件循环，不是上游 12306 故障**：

1. `GovernanceRuntime.execute_sync()`（`core/tool_governance/guard.py`）用 `asyncio.run(self.execute(...))` 驱动治理门——在 worker 线程上启动事件循环 L1（2026-10-06 Tool Governance Runtime 落地后旅游域改经此路径，属回归）；
2. 协程 `execute()` 内部**同步调用** Tool 闭包——此时 L1 正在运行；
3. MCP 系 Tool（12306/知乎）内部的同步桥 `mcp_client.call_tool` 再调 `asyncio.run()` → 撞运行中的 L1 → `RuntimeError`。

为何只有 MCP 系 Tool 中招：地图系 Tool 走同步 httpx（无内嵌 asyncio）；知乎平时走两层 TTL 缓存（`mcp_client` 缓存 + `travel/services/tool_cache.py`）提前短路，真实调用（缓存未命中）才触发。宿主侧复现补丁验证：修复前 `ENVELOPE_STATUS: failed`（上游调用失败），修复后 `success`。

## 3. 修复调用链

三层修复（不 nest_asyncio、不吞 RuntimeError、不临时 loop 绕过）：

| 层 | 文件 | 修法 |
|---|---|---|
| 执行器（治本） | `core/tool_runtime/executor.py::_invoke` | 同步 `call` 一律 `asyncio.to_thread` 移出 loop 线程（与 BaseSkill 既有 `lambda: asyncio.to_thread(fn.invoke, …)` 模式同规）；附带收益：`wait_for` 超时对同步 Tool 真正可生效（此前同步阻塞卡死 loop 线程、超时永远不触发）；ContextVar 随 to_thread 复制，归因/会话上下文不丢 |
| Tool 边界（防御） | `infra/mcp_client.py::call_tool` | 改经 `infra/async_utils.run_async`：调用线程无 loop → `asyncio.run`；已在运行中 loop 内被调 → 显式跳独立线程执行（明确的 sync/async 边界适配层，异常语义不变）。另加 `ExceptionGroup` 根因解包（anyio TaskGroup 不再把真实错误包死） |
| 治理适配器（契约） | `core/tool_governance/guard.py::execute_sync` | docstring 冻结边界契约：事件循环只属于治理+执行器机器，用户 Tool 代码恒在工作线程；异步调用方必须走 `await execute()` |

## 4. Tool Failure Contract

**复用既有契约，未建第二套模型**（任务书 §4 审计结论）：平台已有 `ToolResult`（`core/tool_runtime/models.py`，8 态 `ToolStatus` 含 `DEGRADED`）+ `ToolCriticality`（REQUIRED/IMPORTANT/OPTIONAL）+ `SafeToolExecutor`（熔断/隔离舱/Deadline/保守重试）+ `error_mapper`（异常→状态唯一出口）+ `error_taxonomy` 七分类。本次**扩展** `ToolResult` 四字段：

- `degraded_reason: str`——降级原因（用户可读短语）
- `fallback_provider: str`——降级后实际供数 Provider（与 `fallback_used`（策略名）分工）
- `blocking: bool`——对**当前用户目标**是否硬依赖；True = 上层 Workflow 应终止
- `criticality: ToolCriticality | None`——依赖级别回显（trace 自包含）

任务书 BLOCKED 语义落位：per-call 层不加新枚举（`ToolLifecycle.BLOCKED` 已存在于治理门拒绝）；工作流级 BLOCKED = `ToolResult(FAILED, blocking=True)` + state `blocked_tools` 账本，由 supervisor/reporter 消费。

## 5. Error Classification

- 复用 `error_mapper`（TIMEOUT/UNAVAILABLE/RATE_LIMITED/INVALID_REQUEST/UNAUTHORIZED/FAILED + retryable 判定）与 `error_taxonomy.unify_tool_status` 七分类——**未造第四套词表**；
- 域内新增两个语义码：`provider_degraded`（外部源失败降级继续）、`hard_dependency_unverifiable`（硬依赖无法验证，阻断）；
- 用户可读话术与开发者诊断分离：SSE/前端只见 `user_message`（`tool_failure_policy.user_safe_message/realtime_disclosure/blocked_disclosure`）；异常类型/上游地址/堆栈只进 trace span（`tool.error` 事件 + `error_code`）与 `tool_failures` 状态账。

## 6. Retry Policy

复用 `SafeToolExecutor` 既有保守重试（默认 `retries=1`、100ms jitter 退避、写操作强制零重试、熔断 5 连失败 OPEN/30s 半开、Deadline 预算判定跳过），既有回归测试锁定：`tests/tool_runtime/test_governance.py`（`test_502_503_retryable` / `test_connect_error_retries_once_max` / `test_business_error_no_retry` / 熔断与隔离舱用例）。**域内裁决层不做第二次重试**（避免双层重试叠加尾延迟）。

## 7. Fallback Policy

| Tool | fallback 链 | 依据 |
|---|---|---|
| POI（腾讯 LBS） | 全败 → **高德景点类目源顶上做主候选**（真实已有 Provider，`source=amap` 留痕） | `poi_service._build_live_candidates` F1 分支（新增） |
| POI（两路全败） | 本地攻略语料源（需腾讯补坐标，腾讯挂则不可用）→ 空 → BLOCKED | F3/F4，存量种子回退仍由 `TRAVEL_POI_FALLBACK_SEED` 显式门控 |
| 12306 | **NO_FALLBACK_AVAILABLE**（项目无第二实时铁路源）→ 降级为「无实时班次」模式继续 | 保留出发/到达/本地交通估算；具体车次/票价/余票一律不伪造 |
| 知乎攻略 | 三主题+全网逐路独立降级（error 封套），全败也只是披露 | `research_agent.search_guides` 存量 + 本次 fixture 修复后 16 测试锁定 |
| 天气 | 区县级→城市级回退（存量）→ 全不可用则跳过检查+披露 | 存量 §44 路径 + 本次 E2 强化 |

禁止项落实：无 Fake Provider、无「失败返空数组假装成功」（失败封套不缓存、降级必披露）、无捕异常后伪造 12306 成功。

## 8. Dependency Level（动态判定，禁止静态配死）

`travel/services/tool_failure_policy.py::resolve_transport_dependency(brief, user_message)`：

- **REQUIRED**：`必须|一定|务必|得|要 … X点前 … 到/抵达` **且** `否则|不然|…就` 终止语义同时命中（「必须找到 10 月 8 日上午 9 点前抵达泉州的高铁，否则不要给我行程」）→ 12306 失败即 BLOCKED；
- **IMPORTANT（=PREFERRED）**：有出发地+出发日期的常规查询（「帮我做泉州 3 天游」）→ 失败降级继续；
- **OPTIONAL**：无城际交通诉求（调用方 `_needs_train_search` 短路）；
- 「9 点前到」但无终止语义 → 只是到达时间事实（`brief.arrival_time` 承接排程），不构成硬依赖（测试锁定，防误阻断）。

## 9. Degraded / Blocked 语义与状态账

新增 state 键（`travel/graph_state.py`，均入 schema、planning_reset 跨轮清空防污染下一轮）：

- `degraded_tools: [{tool, provider, dependency_level, reason, note}]`——实时数据未验证但行程继续；reporter 渲染「实时信息核验情况」⚠ 段；
- `blocked_tools: [{…, user_message}]`——硬依赖无法验证；supervisor 见账即 REPORT 终止；
- `tool_failures: [{…, error_code, error_message}]`——原始失败账（排障/管理端，不给用户）。

transit 专家实现要点：账本持有在节点外层闭包（`run_expert_safely` 对 failed 收口会清 `data`，闭包持有保证阻断账不丢）；BLOCKED 时 transit 直接 failed、**不产出 itinerary**（不假装满足约束）。

## 10. Supervisor 改动

`travel/supervisor.py::decide`：在步数上限之后、专家派发之前插入阻断检查——`blocked_tools` 非空 → `REPORT("硬依赖无法验证（…），停止规划并如实披露")`。排在 `finished` 判定之后：上一轮 blocked（finished=true）后下一轮社交回复正常 DONE，不被残留账本误终止（测试锁定）。原「任一专家失败且无产物 → report」护栏不变（内部失败的收口路径）。

## 11. Validator 改动

**零改动（设计结论，非遗漏）**：四轴（时间/地理/体力/预算）+ 覆盖度校验的输入是排程产物与 brief 硬约束，**实时数据缺失从来不是校验轴**——「火车信息缺失 ≠ 行程非法」在现有结构下天然成立。VALID_WITH_WARNINGS 语义即既有 error/warning 分治（warning 不推翻交付）。天气证据过期（SOURCE_STALE）判「引用的数据是否过期」，无证据 ≠ 过期，降级不会误报。

## 12. Reporter 改动

- 新增 BLOCKED 分支（排在候选池为空之前）：输出 `blocked_tools[0].user_message`（「目前无法验证满足该交通条件的实时信息，因此没有继续生成可能不成立的方案。」）+「可以稍后重试，或去掉该硬约束」；内部异常细节零透出（测试断言无 RuntimeError/Traceback 字样）；
- 行程单新增「## 实时信息核验情况」段：逐条 ⚠ 降级披露（「12306 实时班次暂时无法查询，已继续生成行程；相关实时信息未经验证，出行前请通过官方渠道确认。」），绝不渲染成「全部已核实」；

## 13. SSE 改动

复用既有 `tool.started/tool.result` 事件骨架（`travel/core/events.py` 同一出口），扩展三个取值/字段，**未另造第二套协议**：

- `tool.result` 新增 `status: degraded | blocked` 与 `user_message`（用户可读话术）；
- 新增 `tool.degraded` / `tool.blocked` 事件（provider + dependency_level，供前端/审计直接订阅）；
- run 级失败帧语义不变：只有 BLOCKED/内部致命才 `run.finished status=failed` / `error` 帧；Tool degraded 不产生 run 失败帧（图级集成测试断言事件序锁定）。

## 14. 前端改动

- `travelRuntime.ts`：Tool 状态扩为 `running|success|degraded|failed|blocked`；**解除「Tool 失败 → 整轮 error」联动**（原 `tool.result failed` 与 `stage.finished failed` 均直接置 `status='error'`——这是前端「整页红」的直接原因）；现在仅 `blocked` / `error` 帧 / `done failed` 才置轮次失败；
- `ToolProcessRows.tsx`：降级行琥珀色 ⚠（「实时查询暂不可用 · 已继续生成行程」+ user_message 正文），阻断/失败行红色；技术 stack 不渲染；
- `TravelChatDrawer.tsx`：汇总「本轮共 N 个 Tool · X 成功 · Y 降级 · Z 失败」+ 降级横幅「部分实时信息未验证（Y 个数据源降级），行程已继续生成」；
- 验证：`tsc --noEmit` 0 错误；travel 组件 70 测试全绿（含 3 条新语义用例）。

## 15. Trace
