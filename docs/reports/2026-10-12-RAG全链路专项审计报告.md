## 1. 架构与执行时序

### 1.1 上传与索引链路

```
POST /rag/upload (require_rag_editor)
 └─ rag_upload.py: upload_document
     ├─ RagAuthorization.build（fail-closed）→ can_upload_to（kb∈可见集 且 department=主体部门）
     ├─ 扩展名/MIME 白名单 + Content-Length 预检(50MB+16KB) + 流式字节计数硬限
     ├─ 暂存流式写盘(data/rag/tmp/staging) + 流式 SHA256 + 空文件/魔数(PDF/OOXML/NUL) + 扫描件预检
     └─ _dispatch_index_with_idempotency（幂等 ledger：同键同内容附着 / 异内容 409）
         ├─ IndexRunStore.create_run（status=claimed，记 base_generation）
         ├─ create_index_task_record（tasks 表）
         └─ execute_index_task.apply_async → rag_index 队列
SSE 进度：Worker 只写 Redis 镜像 upload:{id}（TTL 600s）；API 轮询消费；断线重连读镜像
Worker：run_with_task_state（租约 CAS→admission→心跳 fencing→节点边界 pause/cancel）
 └─ _do_index_sync（rag_upload.py）
     ├─ 终态幂等短路（published→done；failed/superseded→拒绝）
     ├─ 暂存存在性+SHA256 比对；duplicate 检测（registry 同 path+active+同 hash→直接标 published）
     ├─ 同逻辑文档互斥（FileLockedByOtherError）
     └─ 候选期（generation 隔离）：parse → ChunkStrategyRouter(parent 2000/leaf 500 tok)
         → UnifiedMetadata/DecisionEnvelope → EmbeddingStage(批 32、重试 5 次降级逐条、embed_cache)
         → 候选 collection「{main}::cand:{gen}」+ BM25 staging-{gen}
发布 publish_candidate（文件锁 30min TTL）：
     a mark publishing → b registry.register_published（CAS，提交点：active 或 pending_review）
     → c 候选向量晋级主 collection（单语句 UPDATE）→ d BM25 快照切换（逐文件 os.replace）
     → e os.replace 暂存→正式 → f chunk_store flush → g/h 旧版本清理 → i mark published
     提交点前失败→cleanup_candidate；提交点后失败→保持 publishing 等续跑
兜底：Sweeper(6h 五路一致性) + 每日 reconcile(REPEATABLE READ+advisory lock) + parsing 看门狗(15min)
```

```
POST /chat/stream → MultiAgentSystem.stream_events（producer 线程 + asyncio.Queue）
```

## 3. 四项复现结论

### 3.1 父 Trace 超时 / 子 Trace 成功（必须复现 1）——已复现【实测】

- 样本：父 `8b8b67f75bf1`（status=degraded，34765ms）/ 子 `38cb6ec125b7`（status=success，11213ms，parent_id 指向父）。
- 时间轴：父 rag span `10:49:52.385`→`10:50:07.360`（14975ms 判 error=15s 线）；子 trace `10:49:56.375`→`10:50:07.597`。**请求发出到 rag-service 接入耗时 ~4.0s**（前置排队/建链），内部检索 4.26s（含 rerank 0.43s）+ LLM 6.45s，收尾比父判超时晚 237ms。
- 子 trace 答案实际生成成功：「客服的审核时间为 1-2 个工作日 [E1]」（faq 引用相关度 0.97），费用 rerank $0.000115 + llm $0.00163 + 6 次 query embedding，**全部白烧**。
- 频率：本地库 workflow=rag_agent 子 trace 7 条全部 success，其中父 degraded 4 条（**57%**）；RAG 子 trace 全量 P90=16.3s、P95=19.1s（627 条），超 15s 线的请求约 10%+。
- 结论：这不是偶发抖动，是「15s 工具超时 vs 端到端常态」的**结构性必然相撞**；前置 4s 排队 + 检索 + LLM 的耗时构成使 15s 线在正常负载下即会被击穿。

### 3.2 RC-039 检索失败（必须复现 2）——已定位：丢失阶段=语料供给层【实测】

- CI artifact per_case/RC-039.json：status=fail，stage1_top_docs=[baseline_purchase, baseline_employee_handbook, baseline_faq, baseline_qc_sop, baseline_supplier]，**目标文档 legal_采购合同.md 不在 Stage1 候选内**，doc_recall@5=0，retrieved_docs 仅 finance_员工报销制度.pdf / purchase_采购流程.docx。
- 根因：`backend/evaluation/dataset/fixture_catalog.py` 加载的 baseline fixture_set 共 **16 份**，逐一核对**没有 legal_采购合同.md**（16 份均为 FAQ/制度/手册/SOP，无合同/法律类）；而 cases.jsonl 中 RC-039 的 ground truth 三条付款节点全部来自 legal_采购合同.md。
- 漂移量化：regression suite 29 案中 required_docs 不在 baseline 语料的有 RC-039、RC-032 两案；RC-032 靠部分命中 recall@5=0.5 擦线 pass，RC-039 recall=0 必败。
- 佐证：本地库存在 `/app/data/docs/rag_eval_kb/general/legal_采购合同.md` 的 **deleted** 残影（2026-10-11 12:35，另一条导入通道），说明曾有人为跑通该案例手动补灌过语料后删除——但 CI 每次全新环境，补库救不了门禁。
- 结论：RC-039 不是检索算法缺陷（Stage1 在 16 份语料中排序属正常行为），是**评测案例与语料 catalog 的资产漂移**；它使 CI 通过率的理论上限=28/29。

### 3.3 上传同名覆盖/重复内容/中途失败一致性（必须复现 3）——既有契约成立，崩溃窗口存在缺口【实测+代码确认】

- 既有测试实证（本机 5433 专用测试表，32 例全绿）：
  - `test_candidate_publish.py` 8 passed：发布 happy path 提交+旧版清理、CAS 冲突→SupersededCandidate 清理、提交点后失败保持 publishing。
  - `test_doc_registry_pg.py` + `test_delete_consistency.py` 24 passed：registry 版本/状态机/并发（4 进程×25 文档）、删除级联对称性。
- 同名覆盖路径（代码确认）：同名同内容→duplicate 终态不重复索引；同名不同内容→新 generation 候选→CAS 提交，doc_version=old+1，旧 chunk 向量按 id 精确删（失败仅 warning→P2-11）。源文件在 os.replace 前全程不被触碰。
- 中途失败缺口：P1-1（提交点后崩溃→dedup 假成功）与 P1-2（BM25 切换非幂等→续跑必败）见 §2；两者组合使「发布段崩溃」的三种落点（b 前/b-c 间/c 后）中两种无自愈。
- 实机旁证：rag_index_runs failed 样本含「索引运行已终态(failed)，拒绝重跑」×2（终态语义生效）、「暂存源文件缺失」×2（GC 与任务竞争）、「BM25 与向量库文档集合不一致」×6（一致性前置校验拦截生效，但说明漂移确实发生）。

| Gate/口径 | EVAL_GATE=legacy、lexical 语义评分 | 生产配置 |

- 同一案例检索结果不同源实例：RC-001「现货商品的发货时间」在 CI 靠 baseline_faq 得 recall@5=1.0；本地业务库该文档为 pending_review，/retrieve 因 P0-2 无过滤照样命中（若经 ask 链路会被过滤剔除）——**两侧同库异态，指标不可互推**。
- 结论：CI 96.5% 是「512 维本地模型 + 16 份固定语料 + 无生成」环境下的检索指标，不能当作生产全链路通过率；生产质量需以同模型/同语料口径的评测为准。
