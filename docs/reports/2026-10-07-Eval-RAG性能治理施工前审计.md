### 1.5 RAG Daily Regression 连续失败 5 天 — 根因已实锤（与任务书猜测不同，见 §7）

- 证据：`gh run list --workflow=rag_regression.yml` → 10-01～10-05 连续 5 次 `failure`。
- 真实报错（run 37390584335 失败日志）：
  ```
  ValueError: Suite 'regression.json' 声明的 cases_hash b4c28d9e3288fc4b
  与当前 canonical 内容 hash 87c0ee4098f9d7c0 不一致
  ```
- 根因链（逐环验证）：
  1. `cases.jsonl` 自 09-19（`6cfc3fb`）未再变更；suite 的 `cases_hash` 10-04（`cd1f08f`）更新为 `b4c28d9e`。
  2. `.gitattributes` 给 `manifest.json`/`suites/*.json` 加了 `text eol=lf`，**漏了 `*.jsonl`** → `git ls-files --eol` 显示 cases.jsonl `i/lf w/crlf`（本机 core.autocrlf=true）。
  3. suite 声明的 hash 是 **Windows CRLF 字节**的 sha256（`b4c28d9e`，261053 字节）；CI Linux checkout 得到 **LF 字节**（`87c0ee40`，260784 字节）——`git show HEAD:… | sha256` 已复算证实。**两边永远不相等，与内容无关。**
  4. `backend/evaluation/datasets/rag/manifest.json` 的 `content_hash` 同样被 CRLF 污染（声明 b4c28d9e ≠ LF 实际 87c0ee40）。
- 次要发现：失败发生在 fixture 导入**之后**（CI 白跑 init_db+import ≈4 分钟才在 `load_dataset` 内 fail）；`import_fixture` 期间 QuestionGen LLM 报 ChatAnthropic ValidationError 但规则降级，不阻断（噪音，另行记录）。

## 2. RAG 检索现状

### 2.1 Executor 拓扑（CURRENT_RAG_EXECUTOR_TOPOLOGY）

```
请求线程 (SSE worker / to_thread[rag.search])
 │ RAGPipeline.ask_result → RAGChain.ask → gate → rerank 包装 → MultiQueryRetriever
 ├─〔触发改写〕submit ×3 变体 ──────────────► retr-inner(6)  multi_query.py:386
 │    每变体在 inner 线程同步跑 ChunkLevelRetriever → hybrid_retrieve：
 │      ├─〔enhanced 默认开〕submit rule/dense/sparse ×3 ─► retr-outer(4) enhanced:92-104
 │      │    inner 线程阻塞 .result() 等 outer，无超时
 │      ├─〔enhanced 关闭/全空 fallback〕submit vector+bm25 ─► retr-inner(同一池!) hybrid.py:477
 │      └─〔vector_only〕submit vector ──────────────────► retr-inner(同一池!) hybrid.py:368
 │    adaptive 扩展（retrievers.py:906）：在 inner 线程再同步跑 1~3 轮完整 hybrid
 └─〔未触发改写〕请求线程直接跑（父在池外，无自嵌套）
```

**Starvation 实锤**：MQ 把 3 个父任务放进 retr-inner(6)；fallback/vector_only/enhanced-全空三条路径的子 leg 又 submit 回**同一个 inner** 并阻塞等待——父占坑等子。当前仅因 `MULTI_QUERY_COUNT=3 < 6` 单请求未死锁；**2 个并发 MQ 请求 × 3 变体 = 6 父占满 inner，若都走 fallback 路径即经典线程饥饿死锁**。另存在 inner→outer→inner 跨池排队放大。
