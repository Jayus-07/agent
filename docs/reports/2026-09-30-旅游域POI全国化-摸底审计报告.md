## 二、本轮实测事实（活服务探针，非推理）

探针命令（key 取自根 `.env`，不落日志、不写入任何文件）：

```bash
KEY=$(grep -m1 '^TENCENT_LBS_KEY=' .env | cut -d= -f2- | tr -d '\r' | tr -d '"' | tr -d "'")
curl -s "https://apis.map.qq.com/ws/place/v1/search\
?keyword=%E6%99%AF%E7%82%B9&boundary=region(<城市>,0)&page_size=3&key=$KEY"
```

### 2.1 覆盖广度（同一把 key，全部 `status: 0`）

| 城市 | 返回条数 | 首条类目示例 |
|---|---|---|
| 福州 | 1473 | `旅游景点:风景名胜` |
| 丽江 | 931 | `旅游景点:世界遗产` |
| 敦煌 | 236 | `旅游景点:世界遗产` |
| 哈尔滨 | 1447 | `旅游景点:风景名胜` |
| **理塘县**（四川县级） | **60** | `旅游景点:风景名胜` |

→ **县级也覆盖，全国覆盖成立。** 城市数不是瓶颈。

### 2.2 可用类目前缀（做筛选的依据）

`旅游景点:世界遗产` / `旅游景点:国家级景点` / `旅游景点:风景名胜` /
`旅游景点:其它旅游景点` / `文化场馆:博物馆` / `文化场馆:展览馆`

### 2.3 两个已踩到的坑（施工时必须处理）

1. **`filter=category=旅游景点` 单独使用报 `status 348`**（"参数错误，以下参数不合法：boundary"）
   → 必须与 `keyword` 同时传，不能只靠类目筛选。
2. **关键词检索会混入非景点**：搜「鼓山」返回的第一条是
   `地名地址:热点区域:商圈类` 的「鼓山」，第二条才是 `旅游景点:国家级景点` 的「鼓山旅游景区」
   → **必须加一层 `category` 前缀过滤 + 重排**，不能把原始结果直接当景点候选。

### 2.4 配置现状

根 `.env` 中 `TENCENT_LBS_KEY` / `TENCENT_LBS_ENABLED` / `QWEATHER_API_KEY` **三项均已配置且有效**。
即：天气与路线两条数据面**已经是真实第三方在跑**，「旅游域全是 fake」的笼统说法不成立。

## 三、根因定位（代码级）

### 3.1 种子库的城市白名单作用（比"录得少"更要紧）

| 位置 | 事实 |
|---|---|
| `backend/tools/travel/poi_seed.py:73` | `CITY_ALIASES` 仅 3 城（福州/厦门/杭州 + 中英别名） |
| `backend/tools/travel/poi_seed.py:98` `all_cities()` | 由 `_CATALOG` 键集派生 → 恒为 3 城 |
| `backend/tools/travel/poi_seed.py:103` `load_city()` | 未知城市返回 `[]` → 上层降级 |
| `backend/tools/travel/poi.py:27-48` `resolve_city()` | **城市归一只认种子城市**：非三城 → `None` |
| `backend/tools/travel/poi.py:110-113` | `resolve_city` 返回 `None` → `search_poi` 直接 `return []` |
| `backend/travel/services/requirement_service.py:17-30` | `KNOWN_MAJOR_CITIES`（33 个知名城市 + 11 个境外）|
| `backend/travel/agents/requirement_agent.py:327` | `extract_unsupported_city()`：点名了但不支持 → 明示「暂时无法规划」 |

**机制性结论**：用户问「丽江三日游」不会崩、也不会漏回主 Router ——
`travel_prefilter.is_travel_request()` 在 P2 已做城市解耦（`travel_prefilter.py:56-62`），
非种子城市仍进旅游域，由 `slot_filler` 明确告知「暂不支持该城市」。
**缺的不是"优雅降级"，是"这座城市根本没有可用的候选池"。**

### 3.2 腾讯 POI 的两个真实缺口

| 位置 | 事实 |
|---|---|
| `backend/providers/travel/poi.py:81-114` | `TencentPOIProvider` **只实现了点名解析 `resolve()`** |
| `backend/providers/travel/poi.py:111-114` | `search()` 是**空实现**：直接 `return []`，注释写「城市级候选仍由种子池承担」 |
| `backend/providers/travel/live/router.py:29` | `poi.search: ("seed",)` —— 唯一源 |
| `backend/providers/travel/live/router.py:16-17` | 注释把城市级 live 源记为「**BLOCKED 台账**」 |

⚠️ **定性复核（沿用上轮结论，维持）**：`router.py:17` 的「城市级 live 源 BLOCKED」**偏重**。
按 `resilience.py` 的 `BLOCKED` 语义（合同/凭据类阻塞），这活实际是**未接线**，不是**未采购**。
真实缺口是：① 城市级检索没写；② 类目过滤没做；③ 城市归一白名单没解耦。

### 3.3 一个必须记住的架构事实：链账目前只是"声明"

`providers/travel/live/router.py:8-17` 明确写着：`PROVIDER_CHAINS` 是**声明事实源**，
执行语义（fresh → stale-if-error → 七态失败）**内嵌在各 adapter 内部**，Router 不重写降级。

推论：**POI 这条链除了 seed 之外没有任何执行器**。
`weather` 之所以能"腾讯挂了自动换和风"，是因为存在 `FallbackWeatherProvider` 这个具体组件
（`router.py:62-80`）。POI 想接腾讯，同样要**新写一个组合/回退组件**——
没有"改一行链账就自动多源"这回事。

## 四、关键架构发现

### 四.0 本报告初稿的两处定性修正（重要）

| # | 初稿写法 | 代码事实 | 修正 |
|---|---|---|---|
| 1 | 「seed 营业时间/票价 = **人工整理，可信**」 | `poi_seed.py:4-6` 自声明：坐标/营业时段/闭馆星期/票价/建议时长**均为示例值，不可作为真实出行依据**；`poi_service.py:80-83` 将其定档为 `SEED / 0.5`；`contracts.py:102` 消费档 = **`needs_confirmation`** | ❌ 撤回。seed 的营业时间/票价在系统里的定性是**「需确认」**，不是「可信」 |
| 2 | 「直接换腾讯会让三城数据**变差**」 | 腾讯给权威坐标但营业时间/票价为契约默认占位值（统一 `09:00-17:00`、票价 0）；seed 给的是**有变化的示例值**（08:30–22:00、有闭馆日、有票价档） | ⚠️ 部分撤回。退化的是**排程输入的信息量与校验轴的可计算性**，不是"可信度" |

**为什么这条修正重要**：它直接决定了你那个问题的答案（§四.3）。

### 四.1 两者的真实能力对照（修正版）

| 能力 | 腾讯位置服务 | seed 种子库 |
|---|---|---|
| 城市覆盖 | 全国（县级亦覆盖） | 仅 3 城 |
| 坐标 · 名称 | **权威**（LIVE 源） | 示例值 |
| 营业时间 · 票价 | 契约默认占位值（统一 09:00–17:00、票价 0）**← 实测确认无此字段** | **示例值，但成体系**（有变化/闭馆日/票价档） |
| 评分 · 标签 · 建议时长 | 无 | 有（示例值） |
| 时效标注 | `unverified` + `observed_at` | `SEED` 档，`expire_at=None` |
| 消费档（reporter 渲染） | 坐标 trusted / 字段 needs_confirmation | needs_confirmation |

### 四.2 为什么简单链式 fallback 会坏（修正版理由）

| 排法 | 结果 | 判定 |
|---|---|---|
| `("tencent", "seed")` | seed 永不参与 → 丢失 ①离线兜底 ②测试夹具对齐 ③**排程/校验轴的可用输入**（三城全部退化为统一占位值，`providers/travel/poi.py:111-112` 原话：「打满 unverified 的候选池会让校验轴全部失真」） | ❌ 能力退化 |
| `("seed", "tencent")` | 覆盖问题能解决，但 ①三城内仍用**示例坐标**（seed 坐标同为示例值）→ 通勤折算与折返检测带偏差；②链账没有执行器，**仍需新写回退组件**（§3.3），并不更省事 | ⚠️ 可行但劣于方案 A |

**结论**：链账的「降级」语义表达不了「**合并/增强**」。必须引入合并，而不是排序。

### 四.3 「人工整理种子库是不是太麻烦」——正解

#### (1) 量上：不可持续

全国 5A/4A 景区 + 博物馆**上万**，每条 5 个字段（营业时段、闭馆日、票价、建议时长、评分）。

**更致命的是这些数据会腐烂**：票价每年调整、博物馆改周几闭馆、景区季节性变更营业时间、临时闭园。
一套没有回访机制的人工数据集，半年后一半是错的——**而你不知道是哪些**。
这正是数据供应商存在的原因（他们养团队常年做这件事），不是个人开发者该接的活。

#### (2) 性质上：投入产出比最差

`poi_seed.py:4-6` 自声明这些字段是**示例值**；系统按 `SEED → 0.5 置信 → needs_confirmation`
（`poi_service.py:80-83`、`contracts.py:31-37/102`）消费。

意味着：**你人工录 1000 个城市，它们全部仍显示为「需确认」档**，用户看到的还是"仅供参考"。
用最高的人力成本，产出最低可信档的数据 —— 这是最差的一笔投入。

想让数据真的"可信"，路径是让 **LIVE 源（腾讯，基线 0.95）** 来供，而不是人工补录。

#### (3) 设计意图上：方向相反

`poi_seed.py:11-12` 原文：

> 接入真实数据源（地图 / 票务 MCP）后，**应替换本模块的数据供给**，
> 并把 source 改为具体 provider 标识；Poi 契约本身不变

即：种子库从第一天起就是**临时脚手架**，项目原计划是**替换它**，不是养大它。
（`requirement_service.py:8-10` 同款措辞：「过渡安排，禁止继续向本模块堆积通用知识资源」。）

#### (4) 那它该扮演什么？（三个真实身份 + 一个终点）

| 身份 | 依据 | 要不要变大 |
|---|---|---|
| ① 测试夹具 | `poi_seed.py:12-13` 故意覆盖周一闭馆/收费/超长停留/全天开放四类边界 | ❌ 不要。多了只拖慢测试 |
| ② 离线兜底 | 无网时链路仍可跑通 | ❌ 不要 |
| ③ 排程/校验的确定输入 | 排程需要营业时段与建议时长才能算时间轴；腾讯不提供（`providers/travel/poi.py:111-112`） | ❌ 不要 |
| ④ **终点：被真源替换** | `poi_seed.py:11-12` 自述 | 方向是替换 |

#### (5) 所以正确的分工是

| 要什么 | 谁供 | 怎么得到 |
|---|---|---|
| 哪里有什么景点（全国覆盖） | 腾讯 LBS | 自动、实时 **← 要干的是这个** |
| 坐标（权威） | 腾讯 LBS | 自动 |
| 排程可计算性 / 离线 / 测试 | seed（36 条） | **保持不动** |
| 城市识别 | 不能靠 seed 白名单 | `resolve_city` 解耦 + 腾讯城市检索 |
| 营业时间 · 票价 | **腾讯给不了**（实测）；高德/百度可给营业时间 | 见 §四.4（本批次标 `unverified`） |

### 四.4 营业时间 / 票价：到底能不能从地图拿（实测后修正）

#### (1) 三家地图厂商的字段实测对照

| 厂商 | 营业时间 | 价格类字段 | 评分 | 依据 |
|---|---|---|---|---|
| **腾讯**（你在用的） | ❌ **没有** | ❌ 没有 | ❌ 没有 | **本报告活服务实测**：`place/v1/search` 与 `place/v1/detail` 返回条目**恒定 8 个键** —— `id / title / address / tel / category / type / location / ad_info` |
| **高德** | ✅ `business.opentime_today`（今日）、`business.opentime_week`（周描述） | ⚠️ `business.cost` = **人均消费**，非门票挂牌价 | ✅ `business.rating`（餐饮/酒店/景点/影院类） | 高德开放平台「搜索POI 2.0」文档，端点 `restapi.amap.com/v5/place/text` |
| **百度** | ✅ `detail_info.shop_hours` | ⚠️ `detail_info.price` = **商户价格**，非门票挂牌价 | ✅ `detail_info.overall_rating` | 百度「地点详情检索」文档，需 `scope=2` |

**为什么你在 App 里看得到**：App 用的是各家自有完整数据（商户申报 + 用户纠错 + 第三方票务跳转），
**与开放 API 是两个产品，API 字段是收窄的**。腾讯收得最干净，高德/百度留了口子。

#### (2) ⚠️ 但这条路有五个坑，别高兴太早

1. **覆盖率不保证**：文档原文「不同类型 POI 对应不同类别详情数据」。百度官方示例里
   `shop_hours` 直接就是空字符串 `""` —— **大多数 POI 很可能没有这个字段**。
2. **你不知道它何时核实的**：这是第三方维护字段，没有"最后核实时间"。你抓到的时间可能是三年前的。
3. **坐标系不一样**：腾讯/高德 = GCJ-02，百度 = BD-09，**两者差几百米**。混用必须转换，
   否则通勤折算与折返检测直接偏。
4. **额度可能不够**：高德个人认证约 **1 万次/月 + 2 QPS**。旅游助手单次规划要打几十次调用
   → 一个月只够跑几百次规划。**腾讯现在没这个问题。**
5. **票价基本还是拿不到**：两家的 `cost` / `price` 都不是景区门票挂牌价。真要门票价，还得票务源。
6. **合规同腾讯**：免费/试用额度不得商用。

#### (3) 五条路（修正版）

| 选项 | 做法 | 成本 | 备注 |
|---|---|---|---|
| ① **标「待核实」**（本批次推荐） | 搜到即展示，时间/票价如实说"出发前请核实" | 0 | 与 Phase 4 可信标签一致，符合"没有就说没有" |
| ② **会话现场采集** | 用户在对话里说"这个馆周一闭"→ 记录，仅本次行程生效 | 低 | **唯一可扩展的人工路径：由使用现场产生，不由你预先录** |
| ③ 类目先验兜底 | 用"博物馆 09:00–17:00 周一闭馆"这类行业惯例填空 | 低 | ⚠️ 必须标 `ESTIMATE/needs_confirmation`，且**只能放规则层**——provider 层纪律是「只搬运事实、不做推断」（`providers/travel/poi.py:12-14`） |
| ④ **接高德当"营业时间补充源"** | 高德 v5 取 `opentime_today/week` + `rating`，只补营业时间，**不补票价** | 中 | ⚠️ 必须：带 `observed_at` = **我方抓取时刻**；**不得标 LIVE/0.95**（它只是"第三方说的时间"）；排程仍按"可能变化"档处理。**且要另加一把 key + 坐标系转换** |
| ⑤ 采购权威源 | 接票务/景区数据供应商 | 高 | 等有流量再谈 |

#### (4) 我的建议

- **本批次不接**（选 ①）。理由不是"拿不到"，而是：**排程是按营业时间算时间轴的，
  接一个"可能有、可能过期、可能为空"的时间源，比没有时间更危险**——
  它会把行程排到闭馆时段，而你们 Phase 4 的校验器会拿这个错值当"事实"去校验。
- **要做的话按 ④ 的规矩做**，且放在 Phase 8 统一接（那时接线点最干净）。

**⚠️ 两条必须先澄清的事实（否则目标态会建在误解上）**：

1. **「高德有价格」只对一半。** 高德返回的 `cost` 字段是**人均消费**（餐饮 / 商户维度），**不是景区门票挂牌价**。
   - ✅ 「美食店的人均消费」——高德有
   - ❌ 「景点门票多少钱」——高德**没有**，百度也没有（那个 `price` 同样是商户价格）
   - 营业时间要看 `opentime_today` / `opentime_week`，这个是真的有
2. **腾讯 ↔ 高德可以直接切，不用转坐标。** 两家都是 **GCJ-02**，属于同一个坐标系；只有百度是 BD-09，混用会差几百米。
   这条是好消息：降级切换不需要坐标转换层，`PROVIDER_CHAINS` 的链式降级能直接套用。

**关于「腾讯备用」的一个设计后果（须写进施工方案）**：
腾讯接口**实测无营业时间 / 价格字段**。所以主源（高德）挂掉降级到腾讯时，**这两个字段会整块消失**。
这不是缺陷，但**必须在契约上如实表达**——靠 Phase 4 已建成的可信标签机制标成「暂不可用 / 待核实」，
**绝不能让降级后的空值被当成「确定信息」**（这正是 Phase 4 要防的事）。

**额度提醒（事故风险，非省钱问题）**：高德个人认证配额约 **1 万次/月 + 2 次/秒**。
本助手**一次规划就要打几十次 POI / 路线调用**，一个月只够跑几百次行程。
所以切高德之前要先想清楚：**演示能不能撑住、要不要保住腾讯作为并行的第二源**（而非仅作降级备胎）。
