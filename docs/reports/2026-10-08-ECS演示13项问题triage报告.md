## 1. 预算状态圈不动 + 额度来源要中文名

**机制链路实测是通的**：ECS `LLM_BUDGET_MODE=enforce`、账本在累加（user 5/6/7 各有 ¥0.0006~¥0.011 用量、时间戳新鲜）。"不动"是**展示层三件事叠加**：

1. **金额太小**：doubao-mini 一轮对话 ¥0.001~0.01，日限 ¥10（tenant_default:default 模板）→ ratio≈0.01% → `Math.round(ratio*100)` 恒 "0%"（`frontend/src/components/chat/BudgetRing.tsx:57,78`）。
2. **新用户无账本行**：注册不建预算记录（设计口径：模板共享、账本惰性生成，`backend/infra/llm/quota.py:3-7`），首聊前 used=0。
3. **纯 60s 轮询**（`useBudgetStatus.ts:28-31`），聊完不等下一个周期不刷新；401/503 时整圈消失（403 改密门禁也会命中这条）。

**额度来源英文**：后端 `quota.py:499-502` policy_source 只有 scope_type/scope_id，从不发 label → 前端恒走 `${scope_type}:${scope_id}` 回退（BudgetRing.tsx:103-107），显示 `tenant_default:default`。

**改造落点（后端为主）**：
- `backend/infra/llm/quota.py` policy_source 加 `label`（user=用户策略/tenant=租户策略/tenant_default=租户默认策略/platform=平台默认策略+scope_id）——**一处改，用户端+管理端两处受益**。
- 前端 `frontend/src/api/budgets.ts:84-89` scopeLabels 补 tenant_default/platform；`frontend-admin/.../budgets/page.tsx:209` 同步（前端组件在验收线占领区，等混线或协调）。
- **产品拍板**（真正的"预算治理改造"）：日限 ¥10 对 mini 模型永远显示 0%。选项：A. 调低 platform/tenant_default 默认日限（如 ¥1）；B. ring 用分位/两位小数展示（"已用 1.2 分"）；C. 聊天后事件驱动刷新。建议 A+C。

## 5. 客服端（:8082）登录「有问题」

**实测登录链路本身是通的**：网关与 cs-web BFF 登录均 HTTP 200 + 有效 JWT（账号 18250164938 存在、密码正确、roles=[viewer, agent]）。

**根因（实锤）**：该账号 `must_change_password=true`（auth.users 实查，是全库唯一临时密码账号）→ JWT 带此 claim → 后端 `must_change_password_gate`（`backend/app/api/middleware/auth.py:198`，P6.3）对**除改密/登出/刷新/基本信息外的一切 API** 返回 403 `{"error":"MustChangePassword"}`（实测 /prompts、/budgets/me 均 403）→ cs-web 登录页对该码**零处理**（frontend-cs grep 无命中）、也**没有改密页**（frontend-cs/src/app 下无 change-password，主前端有）→ 登录「成功」即被全站 403 弹回 = 「登录有问题」。

**解法**：
- 立即：用该账号在主前端（:80）登录 → 走 /change-password 改密 → 8082 恢复正常。或给会话一个新密码代执行 `/api/auth/change-password`。
- 中期（可实施，frontend-cs 未被占领）：cs-web 登录后识别 `mustChangePassword` → 跳主前端改密页或内嵌改密卡。

**数据层全健康（实测）**：prompts=48 行、prompt_versions=48 行、10 个白名单 key 全部存在（含 6 个 customer_service.*）；后端代码与 main 无差异（不含旧缺陷）。

## 10. /alerts 库存告警中心「没有数据」

机制：**不是 Celery beat**，是 app 内 APScheduler 每天 08:00 跑 `inventory_alert` 工作流（server.py:608，日志实测已注册、APScheduler 已启动）。两层断点（均实测）：

1. **阈值规则 0 条**（inventory_threshold_rules 实查=0）：无规则 → 工作流判 NORMAL 永不产 case（`orchestration/inventory/state.py:115-127`）。没有任何自动 seed 入口。
2. **工作流实际运行即失败**：trace 实测昨天 08:00 的 run `failed (0 steps)`，最后一个 span=`sql.guard` `decision=deny` `reason_code=SQL_PERMISSION_DENIED`（1ms 秒拒）——定时任务无用户上下文、无 sql.read 权限 → SQL 步骤被 6 层守卫拒绝 → 整个 workflow abort。同根证据：用户聊天里数据查询 8 次 sql.guard 全 deny（viewer 角色无 sql.read）。
3. 库存数据在（6 SKU，product1 安全库存 100>现货 20，配好规则必出告警）。

**修复路径**：① 给演示账号授 `sql.read`（或用 super_admin 查数据页）；② **设计决策**：定时工作流的 SQL 执行需要一个服务身份（service account + sql.read）或调度器上下文豁免用户级权限检查——这是权限模型的正经缺口，不是配置手滑；③ 配一条 global 阈值规则（`POST /api/inventory/thresholds {"rule_type":"global","min_qty":50,...}`）+ `POST /api/demo/run/inventory_alert` 手动触发验证。

## 11. /observability/alerts「全是错误 tool」

**反直觉实锤：降级事件流本身是空的**——`logs/degradation.jsonl` 在 app 容器不存在（LLM 熔断/worker 超时等降级事件从未发生，文件惰性创建）。用户看到的红色全部来自同页「能力健康度」卡（GET /api/observability/skill-health，聚合最近 trace span），它把**四种性质完全不同的东西**画成同一种红：

| 红色项 | 实测真相 | 性质 |
|---|---|---|
| zhihu_search 18/18 错、global_search 5/5 错（昨日 14:46-15:07） | **现在实调 initialize+tools/call 全通**、返回真实搜索结果 | 时段性故障（限流/网络窗口），已自愈 |
| sql.guard 8/8 错 | `SQL_PERMISSION_DENIED` 秒拒 | **安全机制正常工作**（权限拒绝），不该画红 |
| rag:rag.search 5/5 错（30ms） | 快败待查（疑 KB 权限 fail-closed） | 真问题，需查 |
| trace 里旅游「追问补槽」被记 status=error | 正常澄清流程 | 状态语义污染 |

再加一个可观测缺口：**span 的 last_error 全是空串**——span 不记错误消息，页面无法判型，只能看到红。

**治理方案**：① skill-health 区分三色（deny/not_configured→中性蓝灰、真故障→红）；② span 记录错误摘要（reason_code 已有，把 message 带上）；③ not_configured 类不进告警流（error_taxonomy 增 not_configured 分类，四文件贯通清单已探明）；④（可选）trace 状态把 clarify/answered 与 error 分开。落点：`skills/validation.py:297-305`、`observability/error_taxonomy.py`、`skills/base.py:429-434`、`frontend-admin/.../alerts/page.tsx`。
