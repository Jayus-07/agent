# 路由层企业级改造验收清单

> 目标：验收请求是否已经按“入口门禁 → 域判断 → 意图分类 → 候选能力解析 → 统一决策策略 → RouteDecision → 执行分支”运行。
>
> 适用提交：`RoutingEngine` 收口改造及其后续意图阶段改造。
>
> 说明：`execution_mode` 继续兼容下游的 `direct / workflow / plan`；`route_mode` 是对外完整路由归宿，补齐 `clarify / domain_graph / general_chat`。

## 二、架构顺序验收

### 1. 入口门禁

- [ ] `GraphRunner` 先执行 Input Guard，再创建并运行 LangGraph。
- [ ] `BLOCK` 不进入 Router、Planner、Tool 或域图。
- [ ] `CLARIFY` 只进入受控澄清出口；客服人工接管的豁免有明确条件和 Trace。
- [ ] Router 层不重复实现 Input Guard，不绕过 Guard 直接接收外部请求。

证据位置：

- `backend/orchestration/graph/runner.py`
- `backend/security/input_guard/`

### 2. 域判断

- [ ] `DomainRouter` 只输出 `DomainDecision`，不执行 Tool/Skill/Workflow。
- [ ] 域 prefilter 顺序仍为客服优先，再按项目冻结顺序处理旅游、选品、预订、商务。
- [ ] 客服窗口 `domain_hint=customer_service` 的锁域语义没有被主路由覆盖。
- [ ] 低置信或 `unknown` 不强行猜域。

证据位置：

- `backend/orchestration/router/domain_router.py`
- `backend/orchestration/graph/router_node.py`
- `backend/orchestration/graph/routing/prefilter_chain.py`

### 3. 意图分类

- [ ] `IntentRouter` 是显式阶段，位于域判断之后、候选能力解析之前。
- [ ] `IntentRouter` 只输出可序列化的 `IntentDecision`，不执行下游业务。
- [ ] 强规则意图可被统一策略采纳；弱规则只能作为候选提示，不能直接执行。
- [ ] 复合意图识别为 `composite`，默认进入 `plan`。
- [ ] `unknown` 或无法可靠确认的意图进入 `clarify`，不把空候选伪装成普通 `plan`。
- [ ] `intent_decision` 写入 LangGraph 状态，便于 checkpoint、Trace 和验收排障。

证据位置：

- `backend/orchestration/router/intent_router.py`
- `backend/orchestration/router/models.py`
- `backend/orchestration/state.py`

### 4. 候选能力解析

- [ ] `CapabilityRouter` 只在已经确定的工具域内解析候选。
- [ ] `general / clarify / domain_graph` 不做无意义的能力向量解析。
- [ ] 候选结果包含名称、分数、来源，且不等于已经执行。
- [ ] 向量索引不匹配不会在请求线程同步重建索引。

证据位置：

- `backend/orchestration/router/capability_router.py`
- `backend/orchestration/router/vector_router.py`

### 5. 统一决策策略

- [ ] `ExecutionModeResolver` 是唯一的执行方式策略出口。
- [ ] 规则、向量、LLM 只能提供证据，不各自维护一套最终分支逻辑。
- [ ] 强规则、域图、普通工具候选、澄清分别有明确策略优先级。
- [ ] 策略失败能够区分业务不确定性与基础设施故障。

证据位置：

- `backend/orchestration/router/execution_mode.py`
- `backend/orchestration/router/engine.py`

### 6. RouteDecision

- [ ] 所有主路由结果都由 `RoutingEngine` 组装为 `RouteDecision`。
- [ ] `RouteDecision.route_mode` 能表达：`direct`、`workflow`、`plan`、`clarify`、域图模式、`general_chat`。
- [ ] `execution_mode` 保持下游兼容：`direct / workflow / plan`。
- [ ] `query_understanding` 只提供复杂度/实体等消费元数据，不再二次改写 `route_mode`。
- [ ] `routing_meta.stage_order` 固定为：

```text
entry_gate → domain → intent → capability → policy → route_decision
```

- [ ] `routing_meta` 至少能看到域、意图、候选能力、最终归宿、fallback 原因和缓存状态。

## 三、分支场景验收

| 场景 | 期望 `route_mode` | 期望行为 | 结果 |
|---|---|---|---|
| 普通单能力问题 | `direct` | 进入 `tool_selector / skill_executor` | ⬜ |
| 已注册工作流强信号 | `workflow` | 进入 `workflow_executor` | ⬜ |
| 多能力复合问题 | `plan` | 进入 Planner → Critique → Supervisor | ⬜ |
| 意图或域不明确 | `clarify` | 澄清，不执行 Tool，不把空候选送 Planner | ⬜ |
| 旅游/客服等有状态域命中 | 对应域图模式 | 进入域图，保留跨轮状态 | ⬜ |
| 寒暄/能力咨询 | `general_chat` | 主 LLM 直答，不进 RAG/Planner/Tool | ⬜ |
| Input Guard BLOCK | 无路由分支 | 在 Router 之前结束 | ⬜ |

建议最少回放以下问题：

- `查本月库存多少`：应为 `direct`，候选应包含 `sql.query`。
- `每天生成经营日报`：应为 `workflow`。
- `查询库存，并说明员工报销制度`：应为 `plan`，至少包含两个能力候选。
- `帮我看看这个`：应为 `clarify`。
- `你好，你能做什么`：应为 `general_chat`。
- 旅游规划或客服订单问题：应进入相应域图，不能被普通 capability 路由抢走。

## 四、故障与降级验收

- [ ] 域分类器不可用：`fallback_reason=domain_classifier_degraded` 或具体异常原因，进入受控 LLM fallback。
- [ ] 向量索引模型不匹配：`fallback_reason=vector_index_mismatch`，不在请求中重建索引。
- [ ] 向量服务不可用：记录 `vector_unavailable`，不伪装成普通低置信结果。
- [ ] LLM fallback 失败：`llm_failure` 可观测，最终结果仍是可序列化的安全决策。
- [ ] 缓存读取失败：继续实时决策，不阻断请求。
- [ ] 缓存只按版本、manifest、模型和稳定身份作用域隔离；不能把动态会话摘要造成错误命中。
- [ ] 降级结果不被长期缓存，避免一次基础设施故障放大成持续错误。

## 五、旧架构清理验收

- [ ] 主流程不读取 `ROUTING_ARCHITECTURE`、`ROUTING_SHADOW_MODE` 决定实现。
- [ ] 生产主路由不再调用 `route_legacy()`。
- [ ] `Router` 仅是兼容 facade，内部委托 `RoutingEngine`。
- [ ] 域图 prefilter 未放行时回到同一个 `RoutingEngine`，不跳到第二套路由。
- [ ] 不存在旧 Router 反向持有向量解析器的循环依赖。
- [ ] 不存在“规则一套最终决策、向量一套最终决策、LLM 又一套最终决策”的并行出口。

建议命令：

```powershell
rg -n "ROUTING_ARCHITECTURE|ROUTING_SHADOW_MODE|route_legacy" backend/orchestration backend/config backend/app
rg -n "get_router\(|from backend\.orchestration\.router\.router" backend/orchestration
```

预期：第一条无生产代码命中；第二条最多命中兼容 facade 本身及明确的迁移兼容调用，生产主路径不得出现第二套路由决策。历史审计/归档文档中的旧术语不作为生产代码命中。

## 七、面试时可以这样解释

这次不是在旧 Router 上继续堆判断，而是把路由改成一条固定流水线：先由入口门禁拦风险，再判断业务域，再识别用户意图，再解析候选能力，最后由一个统一策略决定走直连、工作流、计划、澄清还是域图。每一步只负责一种判断，结果都落成结构化对象，故障、缓存和降级都有明确原因；以后新增域或能力主要接入对应阶段，不需要复制一整套路由逻辑。
