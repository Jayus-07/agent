## 本机真实链路验证（实机驱动：建号→APISIX 登录→/chat/stream SSE，domain_hint=cs 域锁）

### 第一轮：暴露两个真缺陷 + 一个环境问题

| 场景 | 结果 | 结论 |
|---|---|---|
| 普通查询（订单物流） | ✅ SSE 全链 12s，查无此单→引导语义正确 | 链路通 |
| 风险请求（查别人的订单） | ✅ Input Guard 图前拦截「您只能查询和操作自己的数据」 | 主防线生效 |
| P0 投诉直通 | ❌ 图级兜底话术「客服系统暂时不可用」 | **缺陷①** |
| P0 后续消息 | ✅ handoff 拦截，AI 零抢答 | — |
| 退款缺单号（need_info） | ✅ 结构化追问「请提供订单号」 | — |
| pending 期间插无关问题 | ❌ 图级兜底「系统繁忙」；②c「算了，取消」仍被追问 | **缺陷②** |
| 知识问答 | ⚠️ rag-service /ask 503 | **环境问题③** |

**缺陷①（B5 引入、v2 层序显性化）：P0 直通死循环 → GraphRecursionError**。
宿主机最小复现坐实：P0 信号是**静态的**（同一轮 metadata 不变），直通分支位于第 3 层、先于第 4 层循环守卫裁决 → complaint 执行后 supervisor 再直通 → 幂等返回 → 再直通……撞 CS 图递归上限（20），整轮打成兜底话术。v1（B5 原位：pending 后、2b 重复检测前）存在同缺陷——B5 的单条件测试测不出，真实链路暴露。
**修复（6d56ac6）**：直通加「本轮 complaint 未执行过」防重入（v1/v2 同修）；修后流程 = 直通 1 次 → 真实执行 → 存量语义二次派发（幂等）→ 重复检测 FINISH。回归门 **1273 passed / 0 failed**。

**缺陷②：need_info 阶段取消意图无消费者**。「算了，取消」在补槽路径被当答非所问继续追问，违反设计方案场景 4「取消 pending，语义不残留」。**修复**：`_handle_slot_fill` 入口接 `detect_confirmation_intent`（复用 confirmation 单一取消词表源，含疑问句保护），CANCEL → `store.clear(final_state="cancelled")` + 审计 + 平铺键清理；语义与 proposal 阶段既有取消行为对齐（既有用例 test_j 的混合消息「算了，帮我查保修政策」随之按新语义归入取消场景，该用例改用纯新问题消息锁定「不吞掉→继续追问」原意）。

**环境问题③（非本迁移引入，记录待办）**：rag-service /readyz 503 —— `runtime 模式只读索引不可用：BM25 与向量库文档集合不一致`，知识链路降级路径工作正常（503 被接住出降级话术不崩），但 B9 的 live 验证（有答案/无答案/错误召回）需先重建 RAG 索引。属 RAG 工作流（rag_eval_kb 重 ingest），不在客服域迁移范围内自行修复。

## B7：审计异步化 —— 边界核对后结案（无可安全异步项，维持同步）

按委托方边界逐项核对现状审计条目：`_persist_audit_records`（cs_graph_node）落库的对象只有两类——①`action_record` 走 `insert_action_idempotently` 同事务幂等（=幂等相关审计+退款执行审计，委托方红线：必须同步）；②`cs_audit_entries` 全部为写操作/状态变化类（complaint_ticket_created / handoff_timeout_recovered / pending_cancelled / 动作审计），属「状态变化审计必须同步」类。**不存在「普通行为日志/非关键运营日志」类的现役审计条目**——trace 日志本就已异步（Redis streams）。

结论：**不做 fire-and-forget 异步**（「不要为了性能破坏审计完整性」）；同步成本 = 有审计轮次的一次 PG 往返（实测轮内占比 <5%）。附带发现记录不阻塞：①容器 JSON 日志 formatter 丢弃 `exc_info`（堆栈不可达，本次排障被迫宿主机复现）；②审计走 cs-db 专用 loop 时偶发「event loop 已切换，重建 engine」warning（跨 loop 亲和问题，根治属跨模块改造）。B7 以「边界核对结案」入档，未改代码。
