# 待复核流程修复

## 触发条件

文档进入索引流水线的元数据阶段后，会计算 MinHash，并与注册表中除自身外的所有存量文档比较。相似度严格大于 `near_dup_similarity_threshold`（默认 `0.85`）时，写入 `near_dup_id`，注册表状态为 `pending_review`。当前实现中，低置信度、质量分数或业务域字段本身不会单独触发待复核；管理端卡片展示这些字段用于人工判断。

待复核文档的向量、BM25 与 chunk 可能已经生成，但检索侧会按注册表状态软过滤，避免审核前被业务查询命中。

## 正确处理流程

```text
上传/重建索引
  -> MinHash 近重复检测
  -> near_dup_id 非空
  -> pending_review（检索过滤）
       |-- approve -> rag-service 本地 registry: active -> 清理过滤缓存
       |-- reject  -> rag-service 本地清理向量/doc/chunk/BM25
                      -> 回读确认无残留
                      -> 删除源文件
                      -> registry: deleted
```

管理端 app 在 `RAG_MODE=remote` 时只负责鉴权和转发，审核动作通过 rag-service 的内部接口执行。拒绝清理失败时保持 `pending_review`，返回错误与警告，不再返回假成功。
