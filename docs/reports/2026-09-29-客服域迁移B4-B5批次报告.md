## B4：Context Manager 落地（差异点 D4）— 提交 edf3210

**范围收窄说明（相对设计方案 §4.1 全量五项上下文）**：审计后确认「三处重复解析」在现状代码的真实剩余形态是——①实体抽取包装循环 ×2（query `_extract_order_no` / action `_extract_order_id_from_message`，P1 收敛后均已委托 understanding.entities，但 6 行循环各抄一份）；②「预过滤注入 > 当前轮显式实体」优先级拼接 ×2。身份解析的三种语义（query/action 强校验 PermissionChecker、complaint 匿名兜底、action `_resolve_tenant` 可信租户链 = STOP D §67 冻结语义）是**有意差异而非重复，不收敛**；query 物流分支的 `injected > latest` 有注释锁定「保留原行为」，不动。§4.1 的其余上下文项（pending/handoff 状态）已由 state_loader 装载进 state，独立节点只做搬运，故本批以纯函数组件形态落地，图拓扑零变更。

**改动**：
1. 新建 `backend/customer_service/context_manager.py`：`extract_order_entity`（规范化→understanding 抽取→ORDER_ID，空串兜底）+ `resolve_order_slot`（注入优先级单一实现，空白注入视同未注入）；纯函数、零 LLM、零 IO。
2. `experts/query.py`：t_order_status 分支调用点改 `resolve_order_slot(...) or None`（列表语义等价）；`_extract_order_no` 收敛为单行委托（保留 None 契约与测试导入面）。
3. `experts/action.py`：`_resolve_order_id` / `_extract_order_id_from_message` 收敛为单行委托（保留空串契约；缺槽追问语义不变，缺陷6.2）。

**验证**：新增 `test_context_manager.py` 9 条（优先级/空白注入/None route/缺槽空串契约，夹具取自既有已验证用例）；`test_order_ref_resolution` 等委托路径继续覆盖抽取行为；**CS 域全量 1025 passed / 0 failed（580s）**。评估集 offline sanity 不受影响（纯数据集结构校验，数据集未变）。

**回滚**：revert edf3210（无开关——等价重构，全量回归门证明等价）。

## B5：understanding 信号接入 Supervisor 决策（差异点 D5）— 提交 aeb95ea

**问题（审计 §1.5/§6.3）**：`build_understanding` 每轮产出情绪/紧迫/风险信号，但 `_enrich_with_understanding` 只把实体/槽位/规范化文本搬进 `cs_route.metadata`，**信号被丢弃**——产出无决策消费者，只进 Trace。设计方案 §4.2 L1 要求「安全拦截」、§9.1 介入点④要求情绪升级自动化。

**改动（全部确定性规则，零 LLM，带开关 `CS_SIGNAL_GATE_ENABLED` 默认开）**：
1. `understanding/signals.py`：新增 `P0_ESCALATION_MARKERS = ("12315","曝光","报警")`（既有 `_ANGRY_MARKERS` 高危子集，**不新增词条**——词表扩充归 B8）+ `is_p0_escalation(hits)` 判定helper。
2. `orchestration/graph/router_node.py::_enrich_with_understanding`：`sentiment` / `sentiment_hits` / `urgency` / `risk_hits` 四字段随 metadata 进 CS 图状态；trace 补 `cs_sentiment` / `cs_risk_hits` tags。CS 域锁与全局两条入口都过此处（已核）。
3. `supervisor.py::make_supervisor_decision`：新增「Layer 1 信号兜底」段，**插在 2a pending 之后**（确认等待中的会话不被改道），两个分支：
   - **风险兜底拦截**：`risk_hits` 非空 → FINISH（拒答+转人工建议）。定位是 Input Guard 图前主拦截的兜底位（实测「查别人的订单」在 prefilter 即被 guard 拦截，本门只接漏网流量）；确定性拒绝优先于一切执行类分支。
   - **P0 投诉直通**：命中监管/舆情子集 → 强制派 complaint expert（防重入+升级转人工为该专家既有链路），**不依赖路由置信度**（低置信时的 P0 信号此前会走降级/知识兜底而漏掉投诉）。
4. `config/customer_service.py`：`CS_SIGNAL_GATE_ENABLED`（默认 true；关闭=回到接线前行为，只影响这两个兜底分支）。

**有意不做（记入 B12 范围）**：非 P0 情绪（ANGRY/DISSATISFIED）的 P1/P2 分级消费需要 cs_case 案件体系与 SLA 分级支撑，本批不接——避免愤怒但诉求明确的合法消息（如「垃圾快递太慢了」查物流）被错误改道投诉。

**验证**：新增 `test_supervisor_signal_gate.py` 12 条（P0 判定 4 + 风险兜底 5 + P0 直通 3，含：风险拒绝压过 P0 直通、pending 压过风险门、开关关闭还原、无 metadata 向后兼容、低置信仍直通）；`test_router_understanding.py` 补信号 enrichment 3 条（其中风险信号用例直测 `_enrich_with_understanding`——越权类消息实测在图前即被 Input Guard 拦截，恰好验证了主防线/兜底分层）。定向 79 条全绿；回归门=CS 全量 + orchestration/graph（结果见提交信息）。

**回滚**：`CS_SIGNAL_GATE_ENABLED=false` 一键关闭（无需回滚代码）；或 revert 本提交。
