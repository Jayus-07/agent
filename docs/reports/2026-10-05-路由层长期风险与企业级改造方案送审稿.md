## 1. 背景

### 1.1 项目概况

电商 RAG + Multi-Agent 平台（FastAPI + LangGraph，PostgreSQL/pgvector，单机 Docker 部署，单人开发 + 多 AI 会话协作）。主链路：`POST /chat/stream` → GraphRunner → Router → 域图/Skill 执行 → SSE 返回。当前规模：12 Skill / 17 capability / 39 Tool / 5 域图（客服、旅游、选品、预订、商务）。

### 1.2 路由层架构现状

路由分两级，加一个出口选择器：

**第一级：编排级 Router 节点**（`orchestration/graph/router_node.py`）——8 步短路链，任何一步命中即返回：

```
空 query → plan
① CS 廉价规则预判（纯正则）
② 域锁判定（客服窗口消息带 domain_hint=cs，锁域跳过灰度/其他 prefilter）
③ 非锁域时依次：旅游 pending 补槽 → 预订 pending 续填 → 会话延续判定 → 寒暄直答
④ redirect_main 出域判定（CS 锁域但命中旅游/选品强信号时转出）
⑤ CS 完整预过滤（总闸 + 灰度放量）
⑥ 域 prefilter 四连：旅游 → 选品 → 预订 → 商务（各自纯规则正则）
⑦ CS 兜底完整检测
⑧ L1 弱命中追问（差一个槽位就进域的输入 → 追问卡片，带防循环守卫）
```

**第二级：三层 fallback Router 本体**（`orchestration/router/router.py`）——①~⑧ 全未命中才进入：

| 层 | 耗时 | 拍板条件 | 实现 |
|---|---|---|---|
| Rule | ~1ms | confidence ≥ 0.8 | 正则强信号（workflow 词 / SQL 词 ≥3 个 / 竞品词等） |
| Vector | ~30ms | ≥0.85 拍板；0.6~0.85「中置信采纳」跳过 LLM | pgvector 语义匹配：capability 的 example queries 预嵌入 `rag_vectors`（collection=router_index） |
| LLM | ~3-5s | 必拍板（兜底） | qwen 本地模型，超时 `ROUTER_LLM_TIMEOUT` 默认 6s |

决策结果按 `版本号 + 排序后 context + query` 缓存 300s；路由异常整体兜底为 `route_mode="plan"`。

**架构开关**：`ROUTING_ARCHITECTURE` 二选一——`legacy`（上述三层）或 `hierarchical`（粗分类 CoarseIntentClassifier → 域内 FineToolRouter）；另有 `ROUTING_SHADOW_MODE`：legacy 拍板执行的同时 hierarchical 零 LLM 并行计算，记录 `legacy_tool / hierarchical_tool / is_match` 供双轨评估。两套架构并存维护。

**出口选择器**（`route_selector`）：`direct → skill_executor ｜ workflow → workflow_executor ｜ plan → planner→critique→supervisor ｜ clarify → 追问 ｜ general_chat → LLM 直答 ｜ 域名 → domain_graph_registry 动态查表 ｜ 兜底 → planner`。

**治理现状**：域开关（CS/TRAVEL/SELECTION_FUNNEL_ENABLED 等）已迁 sys_config，DB 覆盖免重启热改；`capabilities.yaml` 是 rule 关键词与 vector examples 的单一事实源（G2）；每层路由判定结果落 trace span event + Prometheus 指标（`record_router_decision`）。

### 1.3 已有的正确设计（避免评审误判为需要全盘重写）

- 三层递进 + 全链路异常兜底（宁可多跑不拒答）；
- 域优先级顺序有守卫测试锁定（`test_router_prefilter_order.py`）；
- 关键词/examples 单一事实源（`capabilities.yaml`），VectorRouter 启动按 manifest 对账、数量不符自动重建；
- shadow 双轨对比、QueryRouter 纯规则 plan→direct 降级、声明式域注册（新域不改 router 代码）。

**结论预告：本方案是治理化改造，不是重写。**

## 2. 问题清单（按发生确定性 × 影响面排序）

### A 类：规则资产腐化（确定性最高，代码内已有征兆）

**P1. 正则词表只会线性增长，且存在隐式顺序耦合。**
Rule 层与四连 prefilter 全是关键词/正则表。上线后每次误路由事故的标准修法是"加一个词"，词表单调增长；真正的麻烦是**优先级依赖隐式且相互耦合**——`rule_router.py` 已有注释："需在 SQL 段之前判断，否则『竞品价格多少』会被 SQL 关键词抢走路由"。每加一组关键词需人脑回归所有既有组。`travel_prefilter.py` 为排除业务时间窗使用三重负向后顾断言（`(?<![\d近])(?<!过去)(?<!前)\d{1,2}\s*[天日](?!气)`），每出现新时间窗说法就要再叠一层，每次改动可能击碎别的匹配。
**长期后果**：词表不可维护、路由行为不可解释、回归成本 O(n²)。**当前预警手段**：无（词表变更无评估门，见 P9）。

**P2. 阈值（0.8 / 0.85 / 0.6）为拍定值，从未对真实流量校准。**
三个魔法数字直接写在代码里，没有对应任何标注测量。examples 随 capability 增长后分数分布漂移，"0.85"的含义随时间失真。
**长期后果**：误路由率缓慢爬升而无人察觉。**当前预警手段**：无。

### B 类：静默退化（影响面最大）

**P3. 换 embedding 模型 → 路由索引失配 → 全量静默掉进 LLM 层。**
平台模型角色是 DB 热管理的（管理端可切换、15s 热刷新），而 VectorRouter 的 `vector_router.py` 明确注释："embedding 模型更换（维度变化）后必须重建（运维操作）；**维度不符时写入/查询会报错并静默降级 LLM Router**"。即：管理端切换 embedding 角色 → 路由向量查询全部报错 → 每条消息走 3-5s LLM 兜底 → p95 延迟翻倍、成本上涨，系统不报错。hierarchical 模式的粗分类（embedding 域心）同样中招。
**当前预警手段**：仅日志与计数指标，无告警。

**P4. 路由缓存命中率机制上趋近于零。**
缓存键设计假设"context 是预留键位，当前决策只依赖 query"（`router.py` 注释自述"同值不影响命中率"）。但编排层实际传入的 context 含 `active_domain / last_intent / last_action / brief_summary / pending_question` 等**每轮会话都在变的字段**，全部进入缓存键。结果：同一用户同会话连问两句相同的话，第二轮 active_domain 已变 → 键不同 → miss。legacy 路径三层（rule/vector/llm）**根本不消费 context**，这些字段只是白白加宽键。
**长期后果**：300s 缓存对 legacy 路径形同虚设，每条消息重跑 rule+vector；`brief_summary`（dict）直接 f-string 进键，序列化稳定性无保证。**当前预警手段**：无命中率指标。**未验证项**：命中率未实测（机制推断，需加指标验证）。

**P5. LLM 兜底层的级联故障模式。**
路由异常 → `route_mode="plan"` 兜底（设计意图正确）。但含义是：**上游 qwen 端点抖动/限流的瞬间，所有消息涌入 planner→critique→supervisor 多节点支线**——路由层局部故障被放大为主图全链路负载风暴，且恰逢重试洪峰时刻。
**当前预警手段**：有 `router_fallback_reason` 状态字段与日志，无并发闸、无告警。

### C 类：结构性增长成本

**P6. 三条路由代码路径并存，无退役纪律。**
legacy 三层 + hierarchical + shadow 三套并存，各有边界情况（`route_legacy` 绕缓存防死循环即实战产物）。shadow 只记对比指标，无评审节奏、无晋级/退役标准——shadow 跑得越久，切换依据的时效性越差，最终演变为永久双倍维护。

**P7. 短路链顺序语义随域增长呈 O(n²)。**
现有 8 步、4 个域 prefilter，每新增一域需与所有既有域重新对齐优先级语义（守卫测试须同步改）。代码注释已自我承认两处债务：①"①与⑦同源（都走 _rule_channel 正则），属可收拢的冗余；收拢会改判定语义，需另立变更单"；②"redirect_main 该正则只认种子城市（福州/厦门/杭州）——『去大阪怎么玩』仍留守客服管线"，而旅游识别名录不止种子城市 → **同一问题在客服窗口与全局入口行为分叉**，此类工单将随城市名录增长而增多。

**P8. 开关矩阵超出测试覆盖能力。**
路由相关可热改开关 ≥9 个（CS_ENABLED / TRAVEL_ENABLED / SELECTION_FUNNEL_ENABLED / CS_ROLLOUT_PERCENT / CS_WINDOW_STANDALONE / CS_REDIRECT_MAIN_LLM_ENABLED / ROUTING_ARCHITECTURE / ROUTING_SHADOW_MODE / TRAVEL_REQUIRE_PERSISTENCE），且域开关经 sys_config 免重启热改。被测组合只是矩阵的一个切片，运维热改一个开关即离开被测区域。

### D 类：反馈闭环缺失（问题靠投诉发现）

**P9. 误路由没有纠错回流，路由资产变更无评估门。**
shadow 只记对比；prefilter 无 precision/recall 评估；词表/阈值/examples 变更**不经过任何离线评估**——对比之下，本项目 prompt 变更有完整 Release Gate 评测门禁、Tool 契约有 lock 校验门，唯独路由资产裸奔。评测集为固定快照，真实 query 分布随季节/功能漂移（旅游节假日峰、电商大促峰）。

**P10. 追问防循环守卫的跨副本一致性未核查。**
L1 追问的 `mark_clarified(session_id, query)` 防循环守卫若落在进程内存，多副本部署下同一用户被不同 worker 各自追问、封顶计数各算各的。单副本不显现，横向扩容时变成"追问循环"工单。**状态：待核查项，未定论。**

## 3. 企业实践对照

核心差异一句话：**成熟公司把路由当"被管理的模型产品"养（数据、评测、发布、监控、退役五件套），而不是当"代码资产"养（散落的正则 + 拍定的阈值）。**

| # | 你的现状 | 企业标准做法 |
|---|---|---|
| 词表 | 正则表单调增长，隐式顺序耦合 | 规则只保留两类：安全门（高精度、漏了出事故）与强特征 shortcut；其余靠标注数据训练的意图分类器，定期重训；每条规则有 owner、命中率遥测、失效日期，死规则自动下线 |
| 阈值 | 代码里的魔法数字 | 由错误预算倒推：目标误路由率 → 标注集上找满足精度的最低阈值 → 写配置并记录校准日期 → 季度重标；置信度做校准 |
| 静默退化 | 维度不符静默降级 LLM | 向量索引携带 embedding 模型指纹，失配 = fail loud（显式报错/自动触发重建），"换模型"是迁移事件不是配置开关；层分布有 SLO 告警；定期故障演练 |
| 缓存 | 键 = query + 全量 context 堆料 | 键 = 决策真正依赖输入的指纹（版本 + 模型 + 归一化 query）；依赖上下文的决策不进缓存 |
| 双架构 | shadow 永续并行 | shadow → canary（按流量灰度 + 守护指标）→ GA → 退役旧路径；每级有预定义晋级/回滚标准，shadow 有明确 deadline，到期不晋级即回滚 |
| 误路由闭环 | 无 | 三条回流：①显式信号（用户换说法重问 → 纠错集）②主动学习（低置信决策定期人工标注）③发布门（路由资产变更强制过离线评估，与 Tool lock --check 同地位） |
| 开关矩阵 | 9+ 开关热改 | 依赖声明、经过测试的标准组合（配置快照在 CI 各跑一遍关键回归）、灰度按用户分桶 |

## 4. 改造方案（三阶段）

**总原则：治理化改造，不重写。** 每项给出改什么 / 影响面 / 验证方式 / 回滚方式。工作量按"单人 + AI 会话协作"估计。

### 阶段一：止血（P0，合计 2~3 天）

**C1. 修复缓存键（半天）**
- 改什么：legacy 决策只依赖 query → 缓存键收窄为 `版本号 + 架构位 + 归一化 query`；会话态字段仅透传给真正消费它们的 hierarchical 粗分类器，不进键。
- ⚠️ 实施前必查一处：`router.py` 注释称 context "供粗分类器/HierarchicalRouter 消费"——若 hierarchical 决策确实依赖 context，则仅收窄 legacy 键、hierarchical 键保留 context 位（或仅把实际消费的维度纳键）。
- 影响面：`router.py::_route_cache_key` + `router_node.py` 传参，约 20 行。
- 验证：单测（同文 query 跨会话命中同一缓存项）+ 加缓存命中率指标对比前后。
- 回滚：revert 单函数。

**C2. 路由层分布指标 + 告警（半天）**
- 改什么：基于既有 `record_router_decision(mode, layer, confidence)` 增加两个派生指标——各层拍板占比（5min 窗口）、缓存命中率；配置告警规则：llm 层占比突增（如 >40% 持续 10min）或命中率骤降即告警，接入既有告警渠道。
- 影响面：`observability/metrics.py` + 告警规则配置，零链路侵入。
- 验证：演练——人为停掉 embedding 依赖，确认告警触发、恢复后消除。
- 回滚：删告警规则即可。

**C3. embedding 指纹 fail-loud（1 天）**
- 改什么：router_index 的文档 metadata 记录 embedding 模型指纹（model_id + 维度）；VectorRouter 查询前校验当前角色模型指纹一致，不一致不再静默降级，改为：抛显式错误 + 告警 + 触发索引重建任务提示。开关三态 `ROUTER_EMBEDDING_FINGERPRINT` = off / audit（只告警不拦）/ enforce（默认 audit，观察一周后切 enforce）。
- 影响面：`vector_router.py` + 索引写入处 metadata。
- 验证：管理端切 embedding 角色 → audit 态看到告警与指纹不一致记录 → enforce 态看到显式错误而非静默变慢。
- 回滚：开关切 off。
- 设计取舍（§6 争议点 2）：fail loud 牺牲"向量层坏掉仍能路由"的可用性，换取退化可见性。备选方案：降级照旧 + 强告警。请评审人给意见。

### 阶段二：收拢（P1，合计 1~2 周）

**C4. 双架构二选一，限期一个月（最大结构简化）**
- 决策规则（§6 争议点 1）：先查 shadow 累积的 `is_match` 真实数据——match 率高且无已知回归 → hierarchical 毕业为唯一架构；match 率不可信或无人看过 → **默认留 legacy 三层**（在岗、简单、可测），删除 hierarchical 与 shadow 代码路径。倾向前者还是后者不拍脑袋：数据说了算；没有数据本身就是"留 legacy"的证据。
- 影响面：`router.py`（hierarchical 分支 + shadow ~150 行）、`routing/hierarchical.py`、相关配置与测试。
- 验证：删除后全量路由回归 + 守卫测试。
- 回滚：git revert（删代码类变更天然可回滚）。
- 注意：hierarchical 的粗分类思路将在阶段三以独立分类器形态重生，此处删除不损失方向。

**C5. 短路链冗余收拢 + 行为分叉修复（2~3 天）**
- 改什么：①CS 两次同源检测收拢为一次完整检测 + 分支控制（本文档即当初注释要求的"另立变更单"）；②redirect_main 城市名录与旅游识别名录对齐（消费同一来源），消除"客服窗口留守 vs 全局入口转出"的分叉。
- 影响面：`router_node.py` + `lock_domain.py`，需回归 `test_router_prefilter_order.py` 全量语义。
- 风险：判定语义变更，必须逐用例对照旧行为；建议先②后①。

### 阶段三：变聪明（P2，按周推进，可与业务迭代并行）

**C6. 路由考卷 + 评估门（1 周，阶段三的地基，优先级最高）**
- 建考卷：从真实 trace 流量分层采样 200 条（域覆盖：客服/旅游/选品/SQL/workflow/RAG/寒暄/跨轮追问），人工标注期望路由 → `datasets/routing/routing_eval_v1.jsonl`。
- 离线评估脚本：跑 rule/vector 两层 + prefilter 链，输出各层 precision/recall 与混淆矩阵（复用既有评测基建 M7 台账）。
- 评估门：任何路由资产变更（词表/examples/阈值/prefilter 正则/路由代码）PR 强制过考卷，门槛=不劣于基线（机制对齐 `rag_smoke.yml` 的变更检测触发）。
- ⚠️ 这张考卷同时是 C2 阈值校准、C7 分类器训练与验收的前提。200 条规模是否够起步，请评审人给意见（§6 争议点 3）。

**C7. 阈值重标（考卷就绪后半天）**
- 用考卷实测 rule≥0.8 / vector≥0.85/0.6 的真实 precision-recall，按目标误路由率定线，写入配置并记录校准日期；"季度重标"写进运维巡检清单。

**C8. 词表 → 本地意图分类器渐进迁移（1~2 周，可延后）**
- 路线：本地 bge-small INT8 意图分类器（onnxruntime 已在依赖锁，零新增重依赖；此前专项评估结论：512 维勿动 RAG 面、阈值须重标、检索指标≠分类准确率）。
- 步骤：旁路 shadow 打分不动线上 → 考卷+真实流量评估达标 → 灰度替换 rule **弱信号层**（强信号正则与安全门保留）→ LLM 兜底层保留。每步可独立回滚。

**C9. 纠错回流管道（2~3 天）**
- 最小版：低置信决策自动采样落盘（vector 中置信采纳段 + LLM 兜底层拍板的 query + 决策结果），定期人工标注升级考卷。
- 进阶版（可延后）：同会话短窗口"换说法重问"模式识别为纠错信号。

**C10. 开关矩阵配置快照测试（1 天）**
- CI 中取 3~4 个典型开关组合（全关 / CS 灰度中 / hierarchical+shadow / 全开）各跑一遍路由关键回归。

## 5. 明确不做的事

1. **不重写为"大模型全权路由"**——慢（3-5s）、贵、不可复现、不可测试；分层确定性路由方向正确。
2. **不引入外部路由框架**——现有骨架已覆盖其价值，引入只增依赖。
3. **不一次性废除 prefilter 正则**——它们便宜（µs 级）且大部分判定正确，问题在"缺管教"而非"方向错"。
4. **不引入外部可观测平台**——项目已拍板自建 trace + PG 权威，数据不出境。

## 6. 请评审人拍板的争议点

1. **双架构退役方向**：本方案给的是决策规则（数据说话、无数据留 legacy），而非结论。评审人若有真实企业经验，请给"shadow 数据要看到什么程度才敢毕业"的可操作标准。
2. **embedding 失配的处置**：fail loud（拒服务，退化可见）vs 降级+强告警（可用性优先）。单机部署、无 SLA 压力下哪个更对？是否存在第三选项（如自动触发异步重建 + 期间临时走 rule→LLM 短路）？
3. **考卷规模**：200 条对起步是否足够？按域分层的配比有没有更优实践？
4. **阶段三 C8 分类器**：单人项目下"本地小模型 + 重训闭环"的维护成本是否物有所值？还是"正则安全门 + LLM 兜底"的简化双层已足够？
5. **遗漏风险**：评审人从企业视角看，本清单（P1-P10）还有哪些上线 1~3 年必然出现但未覆盖的问题？

## 7. 预期收益与风险声明

**收益**：阶段一消除最贵的静默退化路径与白付的缓存成本；阶段二砍掉 1/3 维护面；阶段三让路由具备"越用越准"的闭环，误路由从"用户投诉驱动"变为"指标驱动"。

**已知未验证项（诚实声明）**：P4 缓存命中率机制推断未实测（C2 加指标后可证）；shadow match 率数据未查询（C4 决策前置）；P10 clarify 守卫存储位置未核查（C 阶段实施前核查）；LLM 兜底层当前实际占比未测量。

**总体风险**：阶段一、三低风险（新增/旁路为主）；阶段二 C5 触碰判定语义，为中风险，已安排先易后难与全量语义回归。
