## 1. 修复前根因与复现证据

### 根因链（全部实锚）

1. `POST /selection-decision/tasks` 用 `asyncio.create_task(_run_task(...))` 在 **API 事件循环**上派发后台 workflow（`backend/app/api/routes/selection_decision.py:84` 原行号）。
2. workflow step 由 `asyncio.wait_for(fn(ctx), timeout_sec)` 驱动（`backend/orchestration/workflow/executor.py:271-274`），step 是协程，跑在该事件循环上。
3. `review_pain`（痛点推断）与 `differentiation`（差异化分析）两个协程体内**直接同步调用** `llm.invoke`（`backend/orchestration/workflows/selection_decision.py:135-136` 原行号，经 `_llm_json`）。
4. 后果一：同步 `llm.invoke`（阻塞 HTTP）卡死整个事件循环——**全进程所有并发请求停摆**（含 chat、健康检查）。
5. 后果二：`asyncio.wait_for` 的定时器回调也在同一被阻塞的 loop 上——**step timeout_sec（180s）形同虚设**，慢 LLM 无论多久都等它。
6. 后果三：`asyncio.create_task` 无并发上限——任务可无限提交，每任务占一个协程与一个 LLM 线程额度。

同仓库 `backend/selection_decision/panel.py:67-71`（AI 评审团）已正确使用 `asyncio.to_thread` 并行（代码注释自证"运行在 to_thread 中"），证明本处是漏网之鱼而非风格约束。

### 修复前复现实测

复现脚本：`D:/tmp/b1a_repro_event_loop_block.py`（LLM 桩 sleep 8s，同 loop 心跳协程每 0.2s 一跳，代表"其他 API 请求可响应"）。

## 3. 超时与取消语义的明确口径（如实边界）

- **修复后 step 超时真实生效**：LLM 超过 `timeout_sec`（review_pain/differentiation 均 180s）→ wait_for 以 CancelledError 打断协程（不被内部 catch-all 吞掉）→ executor 判超时 → 走 on_error（两者均默认 `abort`）→ workflow failed → 任务行标 failed。**这是行为变化**：修复前超时永不触发（缺陷本身），修复后按 `@step` 声明生效——即验收标准要求的"workflow timeout 能按预期触发"。慢 LLM（>180s）从"无限等"变为"按声明失败"，业务正常成功路径（LLM 在超时内返回）不受影响。
- **to_thread 不能强制终止已运行的同步 LLM 调用**（任务书明确要求如实声明）：wait_for 超时只是放弃等待，已在途的线程跑到 Provider 客户端自身超时为止，**迟到结果被丢弃、不入 outputs、不触发第二次回写**（验收场景 3 实证）。底层物理取消（真停 Provider 调用、停表计费）不在本批范围，归第二批资源生命周期治理（B1-C 之后的挂账），本批不重写 LLMProxy。

## 6. 需要 GPT 复核的架构决策

1. **超时触发后的 on_error 取默认 abort**（review_pain docstring 原称"无需 on_error=skip"）：修复后超时不再被内部吞掉，step 超时 → 整个 workflow failed。备选是给两个 LLM step 显式 `on_error="skip"`（下游已全部 `or {}` 防御，超时可降级续跑）。本批选择不动声明（最小改动、不伪造成功），如评审认为痛点推断应降级续跑，改一行声明即可，不影响本批其他内容。
2. **闸门排队 vs 显式拒绝**：当前超限排队（running 行等待），并发 3 为经验值。若运营侧希望过载快速反馈，可改为非阻塞 acquire + 429。
3. **market_research 同型 `_llm_json` 不在本批**（见 §7-1），是否随 B1-C 一并处理。

## 7. 未解决问题、回滚方法与剩余风险

**剩余风险（不扩范围，如实记录）**
1. `market_research.py:71-72` 存在同型 `_llm_json` 同步调用。它经主图 `workflow_executor_node` → `direct_executor` 的独立 `asyncio.run` loop 执行，阻塞的是**本请求的 SSE worker 线程**而非 API 主循环，后果轻一级；且其重试逻辑含 `asyncio.sleep` 依赖 loop 存活，改动需连同超时语义一起评估——归入 B1-C（workflow deadline 接入）一并施工。
2. to_thread 线程不可强杀：超时后在途 LLM 调用继续消耗 Provider 配额直至其自身超时，迟到费用仍会入账（llm_usage 由 proxy 同步记录）——属审计 P0-2/B1-B 范围，本批未动。
3. 闸门只限本 workflow；asyncio 默认线程池是全仓共享的，其他模块的 to_thread 用量不受本闸门约束（审计 P1-5 共享池挤占问题的子项）。

**回滚方法**：`git revert 8ee1ed8`（单提交自包含，含测试；无迁移、无配置变更、无数据影响）。回滚后恢复原行为（超时失效 + 事件循环阻塞风险），无中间态。
