# 线上问题收集 → 候选评测集 改造方案（data-explorer 承载）

> 2026-10-08｜需求来源：演示问题 #13「data-explorer 可以当成记录用户的问题，线上收集候选测评集展示，travel/sql/planner/cs/rag 这些方面需要记录，给具体方案，要不要用队列」
> 结论先行：**不要新建队列**；新建 `ai.question_ledger` 旁路台账表 + 三挂点进程内软失败写入 + 复用既有「trace→候选→审核→不可变版本」管道；data-explorer 加「问题收集」tab。

## 一、先回答：要不要用队列？——不要

| 维度 | 进程内旁路写（推荐） | Celery 任务 |
|---|---|---|
| 写入量 | 每请求 1 行，4C8G 毫无压力 | 同样低，但每条多一次 broker 投递 |
| 失败耦合 | except 全吞只 warning（软失败），主链路零感知 | Redis broker 不可用时需自行降级 |
| 基建成本 | 零 | **必须在 queue_router 三张表登记**（interactive_agent/rag_index/…+task_routes+beat_routes），漏登记入队即抛 QueueRoutingError（fail-closed） |
| 先例 | security/events.py、unanswered.py、trace_writer.py（Redis Streams 批写管道） | 无此场景先例 |
| 削峰收益 | 不需要（无峰值场景） | 唯一理论收益，本场景不成立 |

**既有先例直接照抄**：`backend/security/events.py:54-96`（同步函数、直插 PG、except 全吞只 warning）就是平台标准的「旁路软失败」范式。要批量合并写，可挂进 `backend/observability/trace_writer.py` 的现成异步管道（Redis Streams + consumer group + 批 50/2s flush 的 daemon 线程）。

## 二、平台已有什么（不重复造轮子）

**「trace→候选→审核→不可变评测集」全链路已存在**：

- `POST /evaluation/dataset-candidates/from-trace`（`backend/app/api/routes/evaluation_datasets.py:398-422`）：按 trace_id 取数→脱敏→`register_dataset_candidate(source_type="trace")`；
- 候选持久化 `data/eval_dataset_candidates/*.json`，`approve`（:425-446，强制 redacted=true）后 `_stage_candidate`（:292-341）生成**不可变版本目录** `data/eval_dataset_versions/{module}/...（cases.jsonl+manifest，immutable=true）`；
- 审核 UI 已有：`DatasetGovernancePanel.tsx` + `DatasetReviewQueue.tsx`（pending_review 列表+approve/reject）；
- 数据集不可变指纹机制（manifest/cases hash，原地修改 fail-fast）与 `ai.eval_run_records` 台账全部现成。

**问题文本的逐域现状**：

| 域 | 问题文本在哪 | 缺口 |
|---|---|---|
| AI 助手(main) | `trace.question`（明文**未脱敏**） | 导出前必须过 export_masking |
| 客服(cs) | `ai.cs_faq_query_log.question`（截 300 字）+ trace（tags.domain=customer_service） | 无 |
| 旅游(travel) | `trace.question`（已 PII 掩码，travel.py:69-79） | 无 |
| SQL | `sql_query_audits.sql_text` **只有生成的 SQL，没有自然语言问题** | 挂点需补记 question |
| RAG | `trace.question`（workflow_name=rag_agent） | 无 |

既有旁路写库先例：`ai.unanswered_questions`（拒答收集，含 question_hash 去重）、`ai.clarify_funnel_events`——本方案表结构直接仿前者。

## 三、目标形态

```
各域请求完成 ──旁路软失败──▶ ai.question_ledger（问题台账）
                              domain│question│answer_summary│trace_id│user│ts│status
                                                                        │
管理端 data-explorer 第三个 tab「问题收集」                                ▼
  ┌────────────────────────────────────────────────┐   批量勾选 → POST 候选接口
  │ 筛选: [全部|travel|sql|planner|cs|rag|ai助手]    │  ───────────────────────────▶
  │ 列表: 问题/域/用户/时间/答案摘要/trace 链接       │   register_dataset_candidate
  │ 操作: [加入候选集] [忽略]                        │   (source_type="online_ledger")

```

## 四、实施内容（方案 B：新表 + 三挂点）

### 后端

1. **新表迁移**（`backend/sql/migrations/080_question_ledger.sql`，编号以提交时 init_db 登记序为准）：
   `ai.question_ledger(id, tenant_id, user_id, session_id, domain, question, question_hash, answer_summary, trace_id, source, status, created_at)`；
   `question_hash` 去重 + `status`（pending/accepted/dismissed）+ 域取值枚举 CHECK（travel/sql/planner/cs/rag/ai_assistant）。
2. **写入器** `backend/observability/question_ledger.py`：仿 security/events.py，`record_question()` 旁路软失败；PII 脱敏统一调 `shared/pii_mask`（主图 question 明文必须过）+ question 截断口径统一（500 字）。
3. **三个写入挂点**（各自 try/except 软失败）：
   - main+cs+planner：`orchestration/graph/runner.py` trace 收口处（runner.py:499 之后主流程终点，一次覆盖主图全部出口）；domain 判定 = `tags.runtime_domain` → 枚举映射（customer_service→cs；travel→travel；其余 agent 流量→ai_assistant 或 planner 按 route_mode 细分）；
   - travel：`app/api/routes/travel.py:308 _finish_travel_trace`（非流式/流式共用收口）；
   - sql：`app/api/routes/sql.py` NL2SQL worker 收口（`record_sql_audit` 旁，audit.py:84 附近）——**补记自然语言 question**（存量 sql_query_audits 没有的字段）。
   - rag 独立链可从 trace_writer `_flush_batch`（trace_writer.py:250-290）按 workflow_kind=rag 过滤补第四路，P2 再做。
4. **读+导出路由** `backend/app/api/routes/question_ledger.py`：`GET /question-ledger?domain&status&page`（分页）、`POST /question-ledger/accept|dismiss`、`POST /question-ledger/to-candidates`（批量调 `register_dataset_candidate(source_type="online_ledger")`，导出复用 `evaluation/export_masking.py`）。admin 权限，挂 X-Tenant-Id 租户钩子（与评测读端点同口径）。
5. `backend/app/server.py` 注册新路由；`scripts/gen_tool_contract_lock` 无涉（非 Tool）。

### 前端（frontend-admin，未占领）

6. `data-explorer/page.tsx` Tab 扩展为三态：问数据 / 浏览表 / **问题收集**（沿用现有 Tab 联动与样式）；
7. 新 `src/api/questionLedger.ts`；列表组件复用表格范式（分页+域筛选+状态筛选+trace 链接跳 observability）；
8. 「加入候选集」成功后提示去 DatasetGovernancePanel 审核闭环。

### 测试

9. 写入器单测（软失败不抛、脱敏生效、hash 稳定）；三挂点集成测试各 1 条（收口后台账有行、主链路异常时台账无行且不抛）；路由 RBAC/分页测试；golden：既有评测数据集测试不回归。

## 五、方案对比（为什么不是 A/C/D）

- **A. 不建表，直接查 trace_summary 派生**：零写路径，但 ①trace_summary 滚动删除只留 2 万行，收集会丢；②SQL 域完全覆盖不到；③主图 question 明文问题依旧要解决；④无法承载「accepted/dismissed」运营状态。仅适合做过渡只读视图，不满足「候选集」语义。
- **C. 只挂 trace_writer 单点**：覆盖最广（含 rag），但 embedding/索引类 trace 要过滤、SQL 域仍缺、answer 语义混杂。可作为 rag 域补点的补充，不作为主方案。
- **D. Celery**：见第一节，否。

## 六、分阶段

- **P0（1 天）**：表+写入器+三挂点+只读列表 tab——线上问题开始积累；
- **P1（1 天）**：accept/dismiss + 批量转候选 + 审核闭环打通；
- **P2（按需）**：rag 域补点、planner 域细分（按 route_mode）、去重聚类（同 question_hash 聚合展示频次）、从台账直接生成 suites。

## 七、风险与红线

- **PII**：主图 question 明文入库前必须脱敏（复用 export_masking 口径），否则台账变成敏感数据二次落库点；
- **写入失败静默**：软失败必须打 warning 日志（带 domain/trace_id）便于发现台账断流；
- **G2**：domain 枚举映射只写一份（question_ledger.py 内 util），禁止 runner/travel/sql 三处各抄一套；
- **量纲**：按 user+domain+天加简易限流（如同 user 同 hash 一天只记一次），防止压测把台账灌爆。
