## 0. 一句话总结

旅游助手当前形态是：**「正则填槽 + 规则排程引擎」的单会话重规划器 + 一条独立 SSE 协议 + 一个以草案确认为中心的三栏页面**。它不是设计文档里的「七 Agent 智能规划系统」——全部节点零 LLM；也还不是真正的多轮 Travel Agent——**任何一句带新信息的话都会触发全量重排，自然语言逐条改单被后端明确告知「还在建设中」**。规划能力本身（排程/校验/版本链/持久化）骨架完整且持久化真实，但**需求抽取的鲁棒性缺陷会把整个规划带去错误的城市**，且每轮全量重排使「局部修改」在事实上不存在。

首轮（Case1 实测 15s，7 Tool，19 stage）：

逐条改单（Case8 实测）：后端直接返回建设中文案：「逐条改单（换某天的安排、调整顺序）还在建设中。目前可以直接支持的改法：不去/避开 XX、重新规划、补充 X 天/预算/必去」。

## 5. 问题清单

### P0-1：目的地抽取缺陷把规划带去错误的城市（实测复现）
- **现象**：Case2 输入「我从上海出发，下周去杭州玩三天，预算3000」→ 输出**《上海 3 天行程》**，此后 7 轮全部规划上海，杭州彻底丢失。
- **复现**：任意含「从 X 出发，(隔断词)去 Y」且 X/Y 均在识别名录内的首消息。
- **根因**：`_extract_route_city_pair`（requirement_agent.py:378-400）的两个正则要求「上海出发去杭州」**连续出现**，被「下周」隔断后配对失败；回落到 `extract_destination` 消歧规则 2（:357-360）——「多候选含上一轮目的地时按换目的地语义剔除上一轮」，把真目的地杭州当旧目的地剔除，取了最左的上海。
- **代码位置**：backend/travel/agents/requirement_agent.py:326-400。
- **影响**：chat 单入口所有跨城句式；一旦污染，brief.destination 被写入并持久化到用户偏好（见 P0-3），**后续每轮继续错**。
- **方向**：route 配对失败时不得落入「换目的地」消歧；「出发/由」紧邻的城市应先标记为 origin 候选再参与 destination 消歧。

### P0-2：must_go/avoid 语义不闭环，「不要去西溪换成灵隐寺」实测两头都失败
- **现象**（浏览器实测，杭州会话）：「第二天不要去西溪湿地了，换成灵隐寺」→ 应用 v3 后 **西溪仍在行程（D1）**、灵隐寺被排到 **D1 而非 D2**、其余地点全量重排（径山寺 D1→D3 等）。
- **根因**：avoid/must_go 是全局字段非按天字段；planning_reset 后骨架重建完全不受「第 N 天」约束；avoid 词表抽取成功（西溪进了 avoid）但排程/校验没有按天 avoid 执行面；灵隐寺由 must_go 补全后按地理就近排入第一天。API 侧 Case3 更严重：目的地已错成上海后，灵隐寺根本不在候选池，must_go **静默失效**，validator coverage 仅 warning 不阻塞。
- **代码位置**：graph_state.py:278-318(planning_reset)、poi_service.py:354+(骨架)、validator.py coverage 轴。
- **方向**：①validator coverage 对 must_go 未落地应升 error；②avoid/must_go 支持携带 day 修饰（结构上 brief 需 `per_day` 槽位）；③改动不满足时 reporter 应明说「未做到」，不能「行程已按你的需求排好」。

### P0-3：用户偏好跨会话污染（实测坐实 + 本轮自伤）
- **现象**：`public.travel_preferences` 中 uitest_user（user_id=440）一行在 8 轮 API 回放后被写成 `origin=上海, preferences=[美食,人文,自然], pace=relaxed`；随后**另一个全新浏览器会话**首轮规划即带 pace=轻松、偏好人文/自然。案例 1 里 origin=福州 同理来自此前存量。
- **根因**：slot_filler.py:208-242 把会话内抽取值当「稳定偏好」直接落库并跨会话注入，没有区分「用户明确说的长期偏好」与「本轮临时推导」；preferences 数组只增不减。
- **影响**：一次口误/抽取错误永久改变之后所有会话；审计过程本身也污染了测试账号（已如实记录）。
- **方向**：偏好落库需显式「记住这个偏好」类确认信号，或至少提供会话级隔离 + 管理端清除。

### P0-4：多轮会话「动辄全量重排」的精确边界（2026-10-06 晚间补充实测，6 条边界消息）

| 消息 | 意图 | 是否重排 | 耗时 | 备注 |
|---|---|---|---|---|
| 「谢谢，辛苦了」 | out_of_scope | ❌ 否 | 2.7s | 但回复是「超出范围请去主页」话术，寒暄体验差 |
| 「杭州有什么好吃的？」 | query_static | ❌ 否 | 1.5s | 知乎摘录轻回答 |
| 「西湖值得去吗？」 | query_static | ❌ 否 | 0.2s | 轻回答 |
| 「帮我看看天气怎么样」 | query_dynamic | ❌ 否 | 0.1s | 诚实拒绝（无实时源） |
| 「我想吃点当地特色美食」 | query_dynamic | ❌ 否 | 2.4s | **但 requirement 层 assumptions 已发出「需求已变化，已按新需求重新规划（上一版行程作废）」——遥测与行为自相矛盾** |
| 「第一天别太赶」 | （词表未命中） | ✅ **全量重排** | 5.9s | 7 Tool 全链跑，版本号回跳 v2（前次已到 v9，版本链出现倒退异常） |

结论：**「不管说什么都规划」在字面上不成立**（纯提问/寒暄有轻回答通道），但**体验上接近成立**：
1. 凡是被正则抽出任何 brief 槽位变化的消息——天数/预算/必去/避开/偏好/节奏，包括「第一天别太赶」这种纯节奏微调——一律 planning_reset 全量重排 7 Tool（P1-1 的触发面比想象更宽）；
2. 旅游页所有快捷话术（「第 1 天太挤了」「预算调到 ¥2000」等）与画布动作全部**代发进规划管线**，用户没有「只聊聊」的通道；
3. `assumptions` 字段在未重排的轻回答轮也携带「已重新规划」文案（slot_filler 在意图分流前发出），前端若展示会误导用户以为行程又被重排了；
4. 版本链在轻回答轮之后出现 v9→v2 倒退，需查 `_seed_cross_turn_base`/stamp 链是否被 answered 轮打断。

### P0-5：会话出过行程后，**任何消息（包括「谢谢」「你是模型吗」）都全量重排**（用户主诉实锤，2026-10-06 晚间二轮实测）

用户报告「多轮会话不管说什么都会规划行程」——**实测证实，且比预想更严重**：

| 消息 | 上下文 | 实测行为 |
|---|---|---|
| 「谢谢」 | 已有行程的会话 | **7 Tool 全链重跑，新版本 v4** |
| 「好的」 | 同上 | **7 Tool 全链重跑，新版本 v6** |
| 「你现在在是模型吗」 | 全新会话（brief 不完整） | ✅ 正常：0 Tool，out_of_scope 拒答（needs_clarification 早退） |
| 「你现在在是模型吗」 | **已有行程的会话** | ❌ **7 Tool 全量重排出新行程 + 回复「超出范围」**（done 帧同时带 refusal 文案和新 plan，plan_status=waiting_confirmation）——与用户截图完全一致 |

**双根因**：

1. **out_of_scope 早退只发生在 reporter 文案层**（`reporter.py::_assemble` :339-341，`_answer_out_of_scope()` 定义 :113）。slot_filler 写入 intent 后**没有任何早退边**：只要会话 brief 完整（出过行程），supervisor 照常调度全部专家跑完管线；「超出范围」只是换了段最终文案，done 帧照样携带全新 itinerary + waiting_confirmation → 前端同时渲染「拒答卡」和「新行程草案卡」。brief 不完整时走 clarification 早退才表现为正常拒答——这就是同一句话两种行为的分界。
2. **brief_fingerprint 通道失稳，每轮假报「需求已变化」**：日志实证该会话自某轮起，每轮 `last_fingerprint` 恒为历史旧值 `22a8cb2cc6d3`（经计算=Case8 轮的 brief 指纹），而新算指纹恒为 `6e5dc99d1243`（当前 brief 的真实指纹）——**指纹通道读回值卡死在 8 轮以前的旧状态，brief 通道却正常前进**，于是 `changed=True` 每轮成立、`planning_reset` 每轮触发、版本号 v2→v4→v6 空转虚增。已排除「brief 本身每轮变化」（对 checkpoint 里的 brief 直接调 `detect_brief_change` 返回 changed=False，指纹函数幂等）。精确机制（疑 planning_reset 清理/schema 外键剥离/checkpoint 写入时序，AGENTS.md 已有 prompt_versions 同型前科）待修复时定位，但「读回旧 fp→每轮假变化」的现象链已闭环。

另附带实测：**提问里出现城市名会翻转 destination**（「杭州有什么好吃的？」把 上海→杭州，之后整套行程跟着换城市），因为 extract_destination 不区分「提问提及」与「需求变更」。

**方向**：①slot_filler 在 intent=out_of_scope/query_* 且 brief 无实质变化时直接 Command(goto=reporter) 早退，不进专家链；②修指纹通道读回（对齐 prompt_versions 的 schema 教训，加守护测试）；③extract_destination 仅在 plan/modify 意图下参与 merge。

### P1-1：每轮全量重排 + 版本号一轮双跳


**当前旅游助手最核心的 3 个问题**：
1. **需求抽取不可靠**——一句「从上海出发去杭州」能把 7 轮对话全部规划到上海，且错误被偏好层永久固化（P0-1 + P0-3）。
2. **「局部修改」不存在**——任何修改都是全量重排，按天/条件语义无承接字段，用户说「换掉第二天」系统回答的是一份全新行程（P0-2）。
3. **方案切换是有壳无芯**——版本链在后端真实存在，但 active 指针、切换、回滚在前端一个都没接，「换一个方案/恢复方案」对用户而言是不可用的（P1-4 + §7）。

**下一步先改的 3 件事**：
1. 修 `extract_destination`/route 配对（Phase A）——改动小、收益直接决定所有对话成败；
2. 偏好落库加显式确认（Phase B）——防止抽取错误变成永久状态，同时清掉本轮实测污染的测试账号数据；
3. 打通版本链前端接线 + active_plan 指针（Phase D 的前端半边）——后端 restore/versions API 已在，纯前端工程即可把「方案切换」从 FAIL 变可用。
