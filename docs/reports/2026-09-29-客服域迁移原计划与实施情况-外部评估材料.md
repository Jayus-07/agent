## 0. 背景与约束（评估基准）

**系统**：电商 RAG + Multi-Agent 平台（FastAPI + LangGraph + PostgreSQL + Redis + APISIX 网关）。客服域为独立 LangGraph 域图（5 专家 + Supervisor）+ 坐席派单子系统（独立 dispatcher 容器）+ 用户端抽屉与坐席工作台两前端。规模：`backend/customer_service/` 约 1.66 万行、CS 域测试 1000+ 条、锁版评估集 320 条。全部结论来自对工作区代码实读，标注提交号可回溯。

**目标**：将现有客服域收敛到《客服域 CustomerServiceDomain 设计方案 v1.1》所述目标架构。**不是从零重写**。

**委托方给定的硬约束**（本文一切实施以此为验收基准）：

1. 已存在客服域实现，不允许从零重写；实施目标是把现有实现收敛到目标架构；
2. 执行顺序：审计 → 输出现状与目标差异 → 保留已有生产资产 → 小步迁移 → 每次修改必须测试并提交报告；
3. 禁止：删除已有能力后重新实现 ｜ 新增重复 Runtime ｜ 绕过已有 Authorization / Trace / Tool Runtime ｜ 破坏已有测试和生产门禁。

**环境特殊性**：多会话并行操作同一仓库（评估期间确有其他会话穿插提交 STOP G / 旅游域改动），全部迁移提交采用 pathspec 双限定（`git add -- <paths>` + `git commit -- <paths>`），未触碰他人文件。

### B1：消除投诉路径无界挂起（D1）— 提交 8b0546e ✅

**计划**：修 complaint LLM 兜底无界挂起（审计定位为可立即修的最高优先缺陷）。

**实施**（两处，纯加固、正常路径零行为变化）：
1. `complaint_service._llm_assess`：`config={"timeout":...}` 换 `sync_call_with_timeout(llm.invoke, CS_COMPLAINT_LLM_TIMEOUT_MS/1000, ...)` —— 与 Supervisor L3 既有同款范式；超时异常被既有 except 捕获 → 返回 None → 确定性回退规则结果（回退语义不变，只是从「可能永不返回」变为「3s 内必返回」）。
2. `experts/{complaint,query,handoff}.py` 三节点补 `timeout_s=CS_EXPERT_TIMEOUT_S`（默认 60s，与 knowledge/action 同口径）；超时走 `status=timeout`，三节点后处理均为 `.get()` 安全访问（已核不会炸节点）。

**验证**：新增回归测试 2 组——①LLM 挂死（sleep 2s）+超时压到 300ms → 断言 1.5s 内返回 None；②三节点参数化：`execute_*` 挂死 → 断言 1.5s 内 `status=timeout` 且进入 expert_history（Supervisor 循环检测依赖）。定向 5 文件 54 条全绿；**CS 域全量 1016 passed / 0 failed（610s）**。

**回滚**：revert 8b0546e。

### B4：Context Manager 落地（D4）— 提交 edf3210 ✅（含一处已申报的范围收窄）

**计划**：设计方案 §4.1 全量五项上下文（身份三元组/当前订单/投诉情绪/待确认动作/人工状态）收敛为纯函数组件。

**实施前审计发现**（收窄依据，已写入批次报告）：
- 「三处重复解析」在现状代码的真实剩余形态只有：①实体抽取包装循环 ×2（query/action 各抄一份 6 行「规范化→understanding 抽取→ORDER_ID 过滤」，P1 收敛后均已委托同一单源）；②「预过滤注入 > 当前轮显式实体」优先级拼接 ×2；
- **身份解析的三种语义是有意差异而非重复**：query/action 强校验（PermissionChecker，缺身份抛 AuthenticationError）、complaint 匿名兜底（投诉允许匿名建单）、action `_resolve_tenant` 可信租户链（**STOP D §67 冻结语义**）——强行统一会改变行为并触碰冻结区；
- query 物流分支的 `注入 > latest` 兜底有注释显式锁定「保留原行为不在本轮扩大」；
- 五项上下文中的 pending/handoff 状态已由 state_loader 装载进图 state，独立图节点只做搬运。

**实际实施**：新建 `context_manager.py`（`extract_order_entity` + `resolve_order_slot`，纯函数零 LLM 零 IO），query/action 四个函数改单行委托（保留原签名与 None/空串契约，测试导入面不变）；图拓扑零变更。**未做**：身份解析统一（依据如上）、request pin 注册当前轮实体（避免本批引入非等价变更）。

**验证**：新增 `test_context_manager.py` 9 条（优先级/空白注入/None route/缺槽空串契约）；既有 `test_order_ref_resolution` 等经委托路径继续覆盖抽取行为；**CS 全量 1025 passed / 0 failed（580s）**（用例数比 B1 时多 9 条为并行会话增量，两轮均全绿）。

**回滚**：revert edf3210（无开关——等价重构以全量回归门证明等价）。

### B5：understanding 信号接入 Supervisor 决策（D5）— 提交 aeb95ea ✅

**计划**：情绪/风险信号接入 Supervisor L1/L2（P0 投诉直通转人工、风险拦截）。

**实施**（全部确定性规则，零 LLM，配置开关 `CS_SIGNAL_GATE_ENABLED` 默认开）：
1. `signals.py`：新增 `P0_ESCALATION_MARKERS = ("12315","曝光","报警")` —— **只从既有 `_ANGRY_MARKERS` 里选高危子集，不新增词条**（词表扩充归 B8 词表治理）；`is_p0_escalation()` 判定 helper。
2. `router_node._enrich_with_understanding`：`sentiment` / `sentiment_hits` / `urgency` / `risk_hits` 四字段随 `cs_route.metadata` 进 CS 图状态（此前信号产出后被丢弃，仅实体/槽位被搬运）；trace 补 `cs_sentiment` / `cs_risk_hits` tags。已核实 CS 域锁与全局两条入口都经过此处。
3. `supervisor.make_supervisor_decision` 新增「信号兜底」段，插入位置刻意在 **2a pending 之后**（确认等待中的会话不被改道）：
   - **风险兜底拦截**：risk_hits 非空 → FINISH（拒答+转人工建议）。定位是 Input Guard 图前主拦截的兜底位；**确定性拒绝优先于一切执行类分支（含 P0 直通）**；
   - **P0 投诉直通**：命中监管/舆情子集 → 强制派 complaint expert（其防重入+升级转人工为既有链路），**不依赖路由置信度**——修复「低置信时 P0 投诉被降级/知识兜底吞掉」。
4. 开关关闭 = 回到接线前行为，只影响这两个兜底分支（Input Guard 不受影响）。

**有意不做（推迟到 B12，已申报）**：非 P0 情绪（ANGRY/DISSATISFIED）的 P1/P2 分级消费需要 cs_case 案件体系与 SLA 分级支撑——否则「垃圾快递太慢了，帮我查物流」这类愤怒但诉求明确的消息会被错误改道投诉，损害核心功能。

**验证**：新增 `test_supervisor_signal_gate.py` 12 条（P0 判定 4 + 风险兜底 5 + P0 直通 3；覆盖：风险拒绝压过 P0 直通、pending 压过风险门、开关关闭还原、无 metadata 向后兼容、低置信仍直通）；`test_router_understanding.py` 补信号 enrichment 3 条。定向 79 条全绿；回归门 **CS 全量 + orchestration/graph 共 1253 passed / 0 failed（572s）**。

**实施中的一个实测发现**（已写进测试注释）：「帮我查别人的订单」在图前即被 CS InputGuard 以 `scope violation: query_other_user` 拦截，根本到不了 enrichment——证明「Input Guard 主防线 → Supervisor 信号门兜底」的分层符合设计意图；enrichment 的风险信号用例因此直测 `_enrich_with_understanding` 函数而非走 prefilter 全链。

**回滚**：`CS_SIGNAL_GATE_ENABLED=false` 一键关闭；或 revert aeb95ea。
