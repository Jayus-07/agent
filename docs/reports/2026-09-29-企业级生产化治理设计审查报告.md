## 1. 当前架构评价

### 1.1 总体结论

**底座成熟度高于典型的「能跑起来」项目，治理层是短板而非 Runtime。** 运行时（图编排/域图/Tool Runtime/Node Runtime）、可观测性（自研 Trace + llm_usage 明细 + 90 个 Prometheus 指标 + 可选 Prometheus/Grafana 栈）、发布门禁（release.sh 12 门）、Prompt/模型两资产的版本治理（版本+发布+回滚+审计四要素齐）都已达到或接近生产标准。真实缺口集中在**治理闭环的最后一段**：契约无快照无 CI、错误无统一归因口径、成本不分币种不归因到 Skill/Tool、安全事件大半不入库、评测不落库不成门禁、发布无记录。以下所有设计都是**补最后一公里**，不动 Runtime。

### 1.4 运营监控的具体断层（决定 Dashboard 怎么建）

**可直接聚合（已有结构化落点）**：请求成功率（`chat_request_total{status}` / trace_summary.status）、延迟分位（chat_request_duration_seconds / chat_ttft_seconds / chat_tpot_seconds histogram 直接 `histogram_quantile`）、Tool 失败 Top（`agent_tool_calls_total/failure_total{tool,domain,status}`）、任务错误分布（tasks.error_type 10 类枚举列直接 GROUP BY）、Token/成本全维度（llm_usage：tenant/user/model/component/cached/分项成本）。

**根本没记录 / 聚合不了**：
1. `skill_failure_total{skill,error_type}` 是死指标——有定义零埋点（`observability/metrics.py:122-126`，仅测试引用）；
2. 主链路请求级 error_type 不进 trace 标签（trace 顶层只有 success/error/rejected/degraded/failed 五值），Tool 指标只有 ToolStatus 无 error_type 标签——**用户要求的七类失败原因（timeout/network_error/permission_denied/validation_error/business_error/contract_error/provider_error）目前没有统一落点**；
3. TTFT/TPOT 只在 Prometheus，不进 DB——不能按 user/tenant/session 分析延迟；
4. trace_summary 无 tenant_id/user_id/domain 独立列（埋在 data JSON 里，PG 不能直接 SQL 聚合）；
5. CS expert 层、travel booking/commerce 内部无 span（root span 的 `uncovered_ms` 即为此设计的量化指标），slot_filler 追问连计数器都没有；
6. 错误分类学实际有三套正交词表（模型层 5 类 `infra/llm/error_taxonomy.py:19-25`、任务层 10 类 `tasks/error_taxonomy.py:41-52`、Tool 层 ToolStatus 8 值 `core/tool_runtime/models.py:13-21`）——**不缺分类，缺统一映射**。

### 1.5 资产一致性现状

一致性守护测试体系完整（test_registry_consistency / test_layer_consistency / test_adr0001 + base_output / output_type_declarations / tool_contract_boundary / tool_envelope 共 7 组），管理端 `/api/agents`、`/api/capabilities`、`/api/agents/tools`（loaded/duplicates/not_loaded/phantom 对账）都是实时从 registry/yaml 派生。**断层在于：① CI 全部 disabled（.github/workflows 三个 .disabled），守卫只靠本地约定跑；② `/agents/tools` 端点无前端入口；③ 无一个页面把六类资产对账拼成一张一致性总览。**

### 1.6 必须遵守的既有铁律（设计约束）

- **G1-G4**：声明式注册、单一事实源、谁定义谁注册、例外登记台账——一切治理数据必须**派生**自代码/yaml，禁止手抄第二份。
- **契约不加版本号**（AGENTS.md:111，Frozen-Contracts §4/§6）：契约与消费方同仓同发布。用户要求的「Tool 版本化」必须调和为**契约快照 hash + 构建版本（git_sha）派生**，不给 Tool 加独立版本字段（见 §4.2）。
- **任务状态机 SUCCESS/CANCELLED 封闭**（models/task.py:102-103，Frozen-Contracts §5 域）——「重新执行」不得解锁状态机，只能克隆新任务。
- 最小改动、不引入新框架、本机可运行。

## 3. 企业级目标架构

### 3.1 五层 + 治理平面（不推翻，只加一层平面）

```
┌──────────────────────────────────────────────────────────────────┐
│  用户端 frontend │ 管理端 frontend-admin（治理平面 UI） │ 客服端 frontend-cs │
└──────────────────────────────┬───────────────────────────────────┘
                               ↓ APISIX :9080（认证/限流/访问日志）
┌──────────────────────────────────────────────────────────────────┐
│ Agent Runtime：GraphRunner + Input Guard + 9 主图节点 + Router    │
├──────────────────────────────────────────────────────────────────┤
│ Domain Runtime：cs │ travel(+commerce/booking) │ selection_funnel │
├──────────────────────────────────────────────────────────────────┤
│ Skill Runtime：12 Skill ← capabilities.yaml（G2 单一事实源）      │
├──────────────────────────────────────────────────────────────────┤
│ Tool Runtime：34 @tool + registry + 熔断/审批门 + 契约快照派生     │
├──────────────────────────────────────────────────────────────────┤
│ External：PostgreSQL×2 │ Redis │ LLM 代理 │ MCP │ Java 业务系统   │
└──────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────┐
│  Governance 治理平面（新增，全部只读派生或追加式记录，不改执行路径）│
│  ①可观测聚合：错误七分类统一视图 / Tool 统计 / Trace 下钻 / 健康总览│
│  ②资产治理：契约 lock+CI / 一致性 Check / 发布记录 / 配置视图      │
│  ③成本治理：归因列 / 币种口径 / 预算维度 / 告警外推                │
│  ④安全治理：security_events 统一表 / 拒答归因                     │
│  ⑤评测治理：run 落库 / 版本关联 / 发布门禁                        │
│  载体：PG（新表+视图）+ Redis（已有）+ Prometheus（已有）+ 自研 Trace│
└──────────────────────────────────────────────────────────────────┘
```

**关键原则**：治理平面是「平面」不是「层」——它不进入请求执行路径（唯一例外是 M5 归因列的 contextvar 注入与 M9 埋点，均为旁路记录），不新增 Agent、不拆分现有域、不引入新中间件（OTel/Tempo/Jaeger 都不要，自研 Trace + PG + Prometheus 够用）。

### 3.2 与用户目标分层的差异说明

用户分层中的「客服端」即 frontend-cs（已在 devctl 纳管）；「审计」在网关已有 `ai.gateway_access_logs`，本方案补的是**安全事件语义层**（M9），不是重复记访问日志。配置治理目标态：**DB 覆盖层（sys_config）扩容为治理开关唯一动点，.env 退化为「进程引导参数 + 首次默认值」**，域开关迁入 sys_config 登记表（保留 env 作默认值来源），即可获得免重启、审计、回滚三件事——机制现成（`sys_config.py` 的 15s 轮询 + 历史表），只是登记范围从 3 键扩到 ~10 键。

### 4.2 Tool 治理中心（新页 `/tools`）

**为什么**：34 个 Tool 是平台风险最集中的层（外部 IO + 副作用），但管理端只有 `/agents`、`/skills` 两个只读清单一笔带过，`/api/agents/tools` 的 loaded/not_loaded/phantom 对账甚至没有前端入口。

每 Tool 卡片/详情五段：

1. **基础信息**：tool_id（函数名）、name、description、所属 Skill/Capability（派生自 tool_registry + capabilities.yaml，G2 禁手抄）、模块路径、owner（新增：registry 登记时可选 owner 元数据，缺省=模块 git 最近提交者，派生不手填）。
2. **版本**：`contract_hash`（见 4.7 lock）+ 首次出现该 hash 的构建版本（git_sha 派生）+ 变更历史（lock diff 记录表）。**不引入独立版本号字段**（铁律调和，见 §1.6）。
3. **契约**：args_schema（LangChain 派生）、output_type/structured 声明、封套类型（ok/fail/not_configured）、schema hash。
4. **运行统计**：调用量/成功率/P95 延迟/超时/重试/熔断次数（`agent_tool_*` 指标 PromQL 代理）、Top 错误码。
5. **变更检测**：BREAKING / DEGRADED / COMPATIBLE 三级徽标（分类规则见 4.7），BREAKING 未消解时页面顶部横幅。

### 4.7 Tool 契约 lock 与变更分类（Tool 治理的地基）

**为什么**：契约一致性目前完全依赖 7 组本地测试且 CI disabled——漂移只能靠人记得跑；用户要求的「schema 快照 + CI 检测漂移 + BREAKING/DEGRADED/COMPATIBLE 分类」目前为零。

**设计**（与「契约不加版本号」铁律的调和：版本=构建身份派生，不新增 Tool 版本字段）：

- `backend/scripts/gen_tool_contract_lock.py`：启动期从 tool_registry 派生（复用 registry/layer 测试同款遍历），生成 `backend/tool_contracts.lock.json`——每 Tool 记录：`name / module / args_schema(canonical JSON) / output_type / envelope / capability / skill / content_hash(sha256[:16])`；顶层记 `generated_from_git_sha`。**lock 是派生物**（G2：源头是代码，lock 是快照，禁止手编）。
- **CI 漂移检测**：`gen` 后与仓库内 lock 比对，不一致 exit 1 并输出分类 diff。执行点：① release.sh 在迁移 preflight 前加一步（改 `scripts/release.sh` 一行）；② 重启 `tool_quality.yml.disabled` → `tool_quality.yml`（仓库已有现成内容，取消 disabled 即可）。
- **变更分类规则**（lock diff 自动判定）：删除字段 / 改字段类型 / 删除 Tool / 新增必填参数 = **BREAKING**；output_type 变化 / 封套语义变化（structured↔text）/ 输出字段收窄 = **DEGRADED**；新增字段 / 新增可选参数 / 描述更新 = **COMPATIBLE**。
- **版本归属**：lock diff 记录写入 `ai.tool_contract_changes` 表（from_hash/to_hash/classification/changed_tools JSONB/git_sha/created_at），页面上「当前生产版本」= 最近一次 release_records.git_sha 对应的 lock 快照（M8 提供时间轴）。
- **回滚**：Tool 随代码镜像回滚（现状不变）；lock/变更表提供「回滚到哪个 commit 契约是兼容的」的判据。

### Phase 3（季度级）：门禁自动化与自愈

- **评测门禁强制化**：prompt 发布 evaluation 态强制关联 pass 的 run；release.sh 增可选 Gate13（旅游金标 34 条 + CS 320 抽样，标记 P1 可 waiver——先观察误报率再转硬门）；
- **自动异常发现**：扩展 `docker/prometheus-alert-rules.yml`（错误率/延迟/队列积压/预算/安全事件频率五类规则，Alertmanager 栈已含）；trace_lint.py 从手工巡检变 beat 周任务；
- **自动降级**：错误率阈值→自动关域开关（走 sys_config 通道，人工确认模式先行 = 检测+建议、不自动执行，避免与「人机边界白名单」原则冲突）；熔断已有（circuit breaker + TOOL_RUNTIME_ENABLED 回退），补「熔断事件→alerts 流」；
- **网关拒因字段**：gateway-access-log.lua 增 auth 失败分类（唯一的 lua 改动，独立评审）；
- **多币种预算原生化**：budget 表族按 currency 分行（当前保持 USD 折算口径）。

不引入 OTel/Langfuse/Tempo 等新观测栈；不新建任何 Agent；不把治理逻辑塞进请求执行路径；不给 Tool/Skill 加独立版本号字段（lock+git_sha 派生已满足追溯）；不解锁任务终态；不把 .env 全量迁 DB（只迁治理开关）。
