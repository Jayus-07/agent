## 1. D1 方案：会话结构化上下文 + follow-up 解析

### 1.1 架构与数据流

```
raw user query
  ↓
FollowUpResolver（新，backend/travel/context/）
  ├─ ① 域延续判定：本轮 query 无任何域信号 + SessionContext 有活跃 travel 槽位
  │     → 判定 travel 延续，交给 travel 域（router 消费此信号）
  ├─ ② 规则解析：中文指代表（当地/那里/这个地方/它/第二天/然后呢/便宜一点呢…）
  │     结合 SessionContext 槽位，"当地" → 当前最具体槽位（cities 优先于 destination）
  ├─ ③ LLM rewrite fallback（仅规则置信不足时）：llm.invoke + 新 role "query_rewrite"
  │     输出 JSON {standalone_query, resolved, used_context, need_clarification, clarification_question}
  └─ ④ 无槽位可解析 → need_clarification=true，走 clarification，不进检索
  ↓
standalone_query（而非 raw query）
  ↓
Router（消费延续信号）→ Travel Graph / RAG 检索
```

### 1.2 SessionContext 存储（新建）

- 新表 `agent_memory.session_context`（migration 033）：
  `conversation_id PK, slots JSONB, updated_at, expires_at`。slots 结构：
  ```json
  {"destination": "云南", "cities": ["大理"], "date_range": null, "days": 5,
   "party_size": 2, "preferences": ["美食"], "current_topic": "travel"}
  ```
- **更新语义**：`set / overwrite / clear` 三操作，不做 append；用户显式换目的地（"算了，改成成都"）→ overwrite destination 并 clear cities。
- **写入口**：travel slot_filler 更新 brief 时**同步**写 SessionContext（同一事实，单向同步：brief → SessionContext 不行，因为 router 层在图外也要读；定 SessionContext 为 router 层可读副本，brief 仍是图内权威，双向同步点只在 slot_filler 一处 + resolver 识别到显式切换时）。
- 主图 direct/RAG 若也要继承（待确认 Q2），同一张表按 conversation_id 即可复用，与域无关。

### 1.3 Router 域延续（关键新增）

`router_node.py` travel prefilter 前插一步：query 命中追问指代模式（或 resolver 判定 follow_up_detected）且 SessionContext.current_topic=travel 且无 CS/选品强信号 → 直进 travel 域图。**不碰 CS 优先级**（CS 规则预判仍在最前，遵守 AGENTS.md 既有顺序与守护用例 `test_router_prefilter_order.py`，需同步扩展该守护测试）。

### 1.4 澄清（clarification）

resolver 返回 `need_clarification=true` 时：主链直接以澄清问题作答（不进检索、不计 EvidenceGate），并打 `need_clarification` trace。文案走 prompt YAML 可配置。

### 1.5 Evidence 复用

- follow-up 检索 top_score 低于阈值时，取上一轮 trace 里已过 Gate 的 source ids 对应 chunks，**注入 rerank 候选池重打分**，仍须过 EvidenceGate——不是把上轮答案当证据。
- 禁止：上轮 assistant 生成文本进证据集。

### 1.6 可观测（挂现有 trace tags，非 structlog）

`raw_query / standalone_query / follow_up_detected / context_slots_used / rewrite_method(rule|llm|none) / need_clarification`，新 span `follow_up_resolve`（照抄 multi_query 的 span 写法 `multi_query.py:134`）。

### 1.7 实施顺序与测试

- **D1-A（先做，纯规则可测）**：SessionContext 表 + 规则 resolver + 域延续路由 + clarification → 覆盖验收 Case 1-5 的规则路径。
- **D1-B（后做）**：LLM rewrite fallback（新 model_role + prompt YAML + JSON 解析容错）+ evidence 复用。
- 测试：resolver 纯单测（Case 1-5 全覆盖，含 5 轮连续）+ router 顺序守护测试扩展 + graph 集成测试（真实 travel 图两轮对话）。

## 2. D2 方案：memory embedding 修复

存量 embedding 全空 → **不需要数据迁移/重嵌入**，直接改列即可（若实施时发现非空 bytea 数据，降级为"重建向量列+重嵌入"方案，实施前再实查一次）。

1. **新 migration `032_memory_embedding_vector.sql`**（进事实源链，受 `scripts/init_db.py` 登记）：
   - `ALTER TABLE memory_records ALTER COLUMN embedding TYPE vector(1024);`（列全空，无 USING 需求）
   - 补 ivfflat 索引 `USING ivfflat (embedding vector_cosine_ops) WITH (lists=100)`（表小，先用 ivfflat 对齐 RAG 侧现状）。
2. **ORM**：`models/memory.py:19` `Vector(512)` → `Vector(1024)`；维度来源与 RAG 对齐同一配置常量（`VECTOR_PG_DIM`），不再两处写死。
3. **查询 cast 防御**：`memory_repo.py:33/52` 的 cosine_distance 参数显式绑定 vector 类型（pgvector SQLAlchemy 会正确 typed bind，实施时验证编译 SQL 带 cast；asyncpg 路径必须实测）。
4. **metrics**（`observability/metrics.py`，按现有 snake_case 风格）：
   `memory_retrieval_total / memory_retrieval_failure_total{op} / memory_retrieval_latency_seconds`；manager 降级路径打 `memory_retrieval_status=degraded` 到 trace tags + 保留现有 `degradation_alerts_total`。
5. **清理误导源**：`backend/memory/migrations/001_init.sql`（不在事实源链、维度错）标注废弃或删除，003 seed 的 vector 注释核对——防止下个人再被 512/bytea 误导。
6. **验收**（真实库执行）：①start_session 无 bytea 报错 ②写入 1024 维向量成功 ③相似度查询返回 ④重启进程后再查仍召回 ⑤不同 user_id 检索互不可见（现表只有 user_id 隔离，无 tenant 列）。

## 3. D3 方案：CS 事务边界统一（方向性，需求原文被截断，见 Q1）

原则：**行为兼容收敛**——对外 API 响应不变（含 409 语义），只把事务边界与锁收口到一致模式。

分四批，每批独立可验收、可单独提交：

- **D3-A 统一 session 依赖语义**（对应 R6/R7/R9）：CS 路由的 `get_session` 改为语义明确的唯一实现（commit 职责收口在 service 层返回前，路由不再手写 commit）；accept/decline/reassign 的 route 层补丁式 commit 移入 service；删除 `run_sync` 死参数。**此批是 F2/F3 补丁的正规化，必须补自动化回归：「accept → 立即 agent-message 不 409」**（现有测试缺口）。
- **D3-B 锁补齐**（R1/R5）：close 按 dispatch 既有锁序（conversation→handoff→assignment）加 FOR UPDATE；agent-message 归属判定改锁内读。跑 `test_p3_concurrency_pg.py` 同款并发回归。
- **D3-C outbox 统一**（R2）：claim 广播迁 `outbox.append_event` 同事务持久化，relay 统一推送；对齐 accept 路径。
- **D3-D 边缘收口**（R3/R4/R8）：offers 三路径补 handoff_store 缓存失效；Redis 置忙移到 DB commit 之后（或明确登记为 fail-open 例外）；`conversation_store` fire-and-forget 加失败计数 metric（不改变异步性质）。

每批不改 F1（用户侧 role gate）、不破坏现有 409 语义；`test_dispatch_offers.py`、`test_p3_concurrency_pg.py`、`test_p4_handoff_ingress.py` 全量回归。
