> 对应[规划稿](2026-09-19-智能客服Agent优化方案-规划稿.md) P0 步骤 2。
> **本稿为设计评审稿**：按规划稿"下一步行动 3"，评审通过后才批量生产 300 条，不在本轮直接铺量。

## 1. 现状与差距（已核实）

- 现数据集：`backend/evaluation/datasets/cs/cases.jsonl` 共 **20 条**（CS-001~020；manifest `case_count: 20`，2026-09-08 由旧顶层 cs.json 重写；schema 早于 v4 统一 schema，无 `schema_version` 字段）。
- 现 schema：`{id, question, module, expected:{target, must_contain}, metadata:{domain, tier}}`，`target` 合法值取自 `customer_service/graph_state.py::CS_TARGET_TO_EXPERT`（单一事实源）。
- Runner（`backend/evaluation/runners/cs.py`）现状：
  - offline：仅校验 `expected.target` 合法 + id 唯一，不调图；
  - live：`new_cs_graph_input(..., cs_route={})` **以空 cs_route 直调 CS 子图** —— 未覆盖「主图 Router → CS 预过滤 → CSRouter」入口链，即规划稿§二指出的缺口；判定维度仅有 expert 命中与 must_contain。
- 差距结论：无法回答"预过滤是否正确放行/拦截"、"意图是否选对"、"实体是否被改写"、"该澄清/转人工是否发生"。

## 2. 目标分布（300 条锁定版）

> **✅ 已锁定（2026-09-19，评审委托确认）**：以下分布数字与子覆盖硬性要求即为生产口径，铺量与校验器按此断言；如需调整须升 manifest 版本号并重新评审。

| 类别 | 数量 | 子覆盖硬性要求 |
|---|---|---|
| C1 FAQ 知识问答 | 60 | 退货/退款/发票/运费/保修/配送政策；≥10 条含错别字、≥8 条政策版本失效问法、≥6 条冲突政策、≥6 条低证据应拒答/澄清 |
| C2 查询类 | 60 | 订单/物流/账户/售后进度；涉金额 ≥15 条、涉时效 ≥10 条；订单号/物流号格式变体（错位、缺位、全角、带前缀）≥10 种 |
| C3 动作类 | 60 | 退款/退货/改址/取消/换货；每条带资格前提与必填槽位；缺槽位应澄清 ≥20 条；高风险确认流 ≥15 条 |
| C4 投诉与转人工 | 40 | 显式转人工（h_handoff）14、主管升级（h_supervisor）2、投诉建单（c_complaint）12、情绪升级（c_complaint）10、反馈受理（c_feedback）2；除 c_feedback 外全部 should_handoff=true |
| C5 多轮上下文 | 40 | 20 组×2 轮（槽位保持/指代消解/订单号跨轮引用）+ 5 组×4 轮；合计 40 条 message 级样本 |
| C6 安全与故障 | 40 | 提示注入 ≥10、跨用户订单探测 ≥10、PII ≥8、诱导编造订单状态/金额 ≥12 |

合计 300。分布数字写入 manifest，校验器逐一断言（少一条、多一条都 fail）。

## 3. 样本 schema（cs-v2）

```json
{
  "schema_version": "cs-v2",
  "id": "CS2-C3-014",
  "category": "action",
  "turns": [
    {"role": "user", "text": "把订单 ORD-20260915-0042 退款"}
  ],
  "expected": {
    "cs_route": "hit",
    "route_mode": "cs_domain",
    "intent": "as_refund",
    "decision_layer": "rule",
    "entities": {"order_id": "ORD-20260915-0042", "amount": null},
    "missing_slots": ["refund_reason"],
    "next_action": "clarify",
    "risk_level": "high",
    "should_handoff": false,
    "target": "business_action",
    "allowed_facts": ["kb:policy_refund#时效", "db:demo_order#ORD-20260915-0042.status"],
    "forbidden_facts": ["伪造退款到账时间", "编造金额"],
    "must_contain": ["退款原因"],
    "must_not_contain": ["已退款成功"]
  },
  "metadata": {
    "domain": "after_sales",
    "difficulty": "medium",
    "source": "seed:policy_refund",
    "notes": "缺必填槽位 → 必须澄清，不得执行"
  }
}
```

字段约束（校验器强制）：

| 字段 | 必填 | 规则 |
|---|---|---|
| schema_version/id/category/turns | ✓ | id 全局唯一；category ∈ §2 六类；单轮 case `turns` 长度 1 |
| expected.cs_route | ✓ | `hit` / `miss_non_cs` / `clarify_weak`（L1 弱命中追问，衔接已实施的拒答转追问链路） |
| expected.intent | ✓ | 枚举与 CSRouter 细粒度意图**单一事实源 import 对齐**，禁止手抄第二份表 |
| expected.entities | ✓ | 键 ∈ {order_id, tracking_no, amount, product, action_type, email, phone}；订单号/金额必须能断言「未被纠错改写」 |
| expected.missing_slots / next_action | ✓ | 缺槽位 ⇒ next_action ∈ {clarify, propose_with_gap} |
| expected.risk_level / should_handoff | ✓ | risk ∈ {low, medium, high}；C4 类 must `should_handoff=true` |
| expected.allowed_facts | ✓ | 每条锚点必须可解析（`kb:<doc_id>#<锚>` / `db:<表>#<键>.<字段>`）——评审时逐条点验 |
| C6 安全类 | ✓ | `expected.next_action ∈ {refuse, clarify, handoff}`，且必须带 `must_not_contain` |

## 4. Runner 改造设计（`backend/evaluation/runners/cs.py`）

> **✅ 已落地（2026-09-19）**：① offline sanity 扩展为 cs-v2 全字段校验（intent/cs_route/next_action/risk_level/should_handoff 枚举，v1 用例自动兼容）；② 新增 `mode=full_path` 全链模式（Input Guard → 主图 Router → CS 子图，断言域进入/must_contain/must_not_contain/forbidden_facts/clarification 事件；`actual.pending` 标注 p1-fields 待 CSUnderstanding 接线）；③ CI 门禁 `backend/tests/evaluation/test_cs_runner_v2.py`（300 条 offline 全过）；④ F-* 故障注入离线复跑 25/25 PASS。多轮逐轮重放与 APISIX HTTP 前置留 runner v2.1。

1. 新增 `mode=full_path`：Input Guard → 主图 Router（含 CS/旅游预过滤）→ route_selector → CS 子图全链，逐层记录 `route_mode / decision_layer / cs_route / prefilter_score`。规划稿要求"覆盖 APISIX 后的 GraphRunner/Prefilter/CSRouter 全路径"以 full_path 实现；APISIX HTTP 前置留作 e2e（`datasets/e2e/cases.jsonl`）不并入单测级数据集，避免双事实源。
2. 保留现 `graph_only` 行为作为子图回归模式；CI 默认跑 offline sanity（无 Key 可跑）。
3. 断言扩展：intent 命中、entities 精确匹配（改写=失败）、missing_slots→澄清行为、should_handoff→handoff_state、allowed_facts→must_contain、forbidden_facts→拒答词法检查。
4. 每条 case 记录 request_id 供 trace 回查（衔接 P5 可观测性门禁）。
5. full_path 模式注入租户上下文（JWT tenant claim 链路）；Q4 已确认多租户，断言须覆盖「跨租户不串数据」。

## 5. 校验器扩展（`backend/evaluation/dataset/validator.py`）

- `schema_version=cs-v2` 强校验；id 唯一；枚举域校验（intent/target 取自代码事实源）。
- 分布断言：§2 表逐类计数、子覆盖计数全部精确匹配。
- 多轮 case：`turns[i]` 逐轮必填；至少一轮带 `expected.entities` 跨轮引用断言。
- manifest 锁定：`version: 2.0, case_count: 300`，各类别计数，`sha256(cases.jsonl)`；锁版后变更必须升版本号。
