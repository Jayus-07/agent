# 数据库一键初始化脚本（scripts/init_db.py）

> 目标：一条命令把两个库（agent_memory / agent_business）从零建起来，
> 或者在已有库上补齐缺失的表/字段/索引，并且**想跑几次就跑几次，不会产生重复数据**。

---

## 一、数据库现状（2026-09-21 实测）

### 1. 用的什么库、怎么连

| 项 | 值 |
|---|---|
| 数据库 | PostgreSQL 16（镜像 `pgvector/pgvector:pg16`，因为 RAG 要用向量） |
| 库数量 | 2 个：`agent_memory`（Agent 自己的元数据/记忆/日志）、`agent_business`（业务数据仓库） |
| 连接方式 | `psycopg2` 直连，参数全部来自环境变量 |
| 有没有 ORM | 只有极少数接口用了 SQLAlchemy；**建表不靠 ORM，全靠手写 SQL 迁移文件** |
| 迁移工具 | Alembic 只留了个空壳（`backend/sql/alembic/`，business 只有 1 个版本文件，memory 为 0），**真正的事实源是 `backend/sql/migrations/*.sql`（32 个）** |

连接参数沿用 `backend/config/database.py` 的命名：

```
PGHOST / PGPORT / PGUSER / PGPASSWORD   # 共用
MEMORY_PGDATABASE   → agent_memory
BUSINESS_PGDATABASE → agent_business
PG_READONLY_USER / PG_READONLY_PASSWORD # 应用查业务库用的只读账号
```

⚠️ **端口坑**：`.env` 里写的是 `PGPORT=5432`，那是**容器内**的地址（容器里 `PGHOST=postgres`）。
在**宿主机**上执行脚本必须显式 `--port 5433`（compose 把容器 5432 映射到宿主 5433）。
宿主机 5432 上跑的是另一个原生 PG（18.4），里面也有同名的库，连错了会在错误的库上建表。

### 2. 已有建表/迁移文件

`backend/sql/migrations/` 共 **32 个** SQL 文件，按编号排列：

- `001` 业务仓 7 个 schema（product/order/inventory/customer/crawler/finance/ai）+ 示例数据
- `002` / `003_agent_memory_seed` memory 库结构 + 示例数据
- `003_agent_business_schema` 业务库结构 dump（序列/索引）
- `004` 只读角色 `agent_readonly`
- `005`~`030` 各类加固与新增模块（客服域、认证、可观测、RAG 存储、派单治理等）

真实库现状（5433）：`agent_memory` 62 张表、`agent_business` 35 张表，
业务表里有种子数据（商品 10、订单 19、库存 12……）。

### 3. 已有的初始化/种子脚本（都有问题）

| 脚本 | 问题 |
|---|---|
| `docker/init-dbs.sh` | 只在**数据卷为空的首次启动**跑一次；迁移清单手抄，缺 `003_agent_business` / `021`~`024` / `028`~`030` |
| `scripts/ensure_dbs.py` | 给存量卷补齐用；缺 16 个迁移（008~026、028~030），同样是手抄清单 |
| `backend/sql/seeds/demo_sandbox.sql` | 客服演示数据（DELETE + INSERT，会重置演示数据），没被任何一键入口串起来 |
| `backend/seed/` | Python 生成器（另一套数据模型，产出 json/DB），与当前 7 schema 不是一回事 |

**根因**：两套脚本都是"手抄清单"，人加了新迁移但没同步清单 → 新表没人建，
只能靠应用启动时"缺表就建"兜底，库结构跟着应用版本漂移。

## 二、脚本设计

`scripts/init_db.py`，**不引入任何新框架**：psycopg2 + python-dotenv（项目本来就在用）+ 标准库。

### 核心机制

1. **自动扫描 + 未登记就报错**
   扫 `backend/sql/migrations/*.sql`，按文件里的 `MIGRATION_TARGETS` 决定归属哪个库。
   **扫到没登记的文件直接退出并点名**（而不是悄悄跳过）—— 以后谁加了新迁移忘了登记，
   跑一次就会被告知，不会再出现"清单落后"。

2. **执行记录表**：每个库建 `public.schema_migrations(filename, checksum, status, applied_at)`。
   已应用且文件内容没变 → 跳过；内容变了 → 重新应用。

3. **撞到"已存在"自动降级逐语句执行**
   整文件一次性执行最快；一旦撞到"表已存在/字段已存在"这类错误，
   就自动拆成单条语句逐条跑，把文件里**还没建的部分补上**。
   （旧脚本这里是"整个文件跳过"，所以新增对象会被漏掉。）

4. **表已存在 = 跳过，绝不删数据**（详见第四节）。

5. **只读角色密码对齐** + 只读账号实测连通性验证。

## 三、怎么用

### 存放位置

```
scripts/init_db.py          # 脚本本体
backend/sql/migrations/     # 迁移 SQL（脚本自动扫描）
backend/sql/seeds/          # 可选种子（--demo-sandbox 时加载）
```

### 执行命令

```bash
# ① 宿主机：一键初始化（重点：--port 5433）
./.venv/Scripts/python.exe scripts/init_db.py --port 5433

# ② 容器里（compose 已注入 PGHOST=postgres，不用指定端口）
docker compose exec app python scripts/init_db.py

# ③ 只体检，不动库
./.venv/Scripts/python.exe scripts/init_db.py --port 5433 --check

# ④ 强制重跑全部迁移（仍不删数据）
./.venv/Scripts/python.exe scripts/init_db.py --port 5433 --force

# ⑤ 额外灌客服演示数据
./.venv/Scripts/python.exe scripts/init_db.py --port 5433 --demo-sandbox

# ⑥ 危险：删库重建（必须加 --yes）
./.venv/Scripts/python.exe scripts/init_db.py --port 5433 --reset --yes
```

Windows 也可以用 `python scripts/init_db.py`（只要该 python 装了 psycopg2）。

### 使用前的前提条件

1. **PostgreSQL 已经在跑**且能连通。项目里就是 `docker compose up -d` 起来的 `agent-postgres-1`。
2. **账号有建库权限**：默认用 `PGUSER=postgres`（`.env` 里有）。只读账号跑不了建表。
3. **端口/地址填对**：宿主机 `--port 5433`；容器内不用填。
   分不清就先跑 `--check`，看它打印的 `服务端: PostgreSQL 16.14 (Debian...)` 是不是你想要的那个实例。
4. **依赖已装**：`psycopg2`（`.venv` 里有 2.9.12）。脚本不依赖应用代码，不启动服务。
5. **`.env` 存在**（脚本会读，但不覆盖已有的环境变量）。
6. **线上执行前先 `--check`**：确认目标实例、库名、待应用迁移列表，再正式跑。

### 表已存在时怎么处理（重要）

| 场景 | 行为 |
|---|---|
| 默认 | **跳过**，保留现有表和数据。不 DROP、不 TRUNCATE、不重建 |
| 文件里一部分已存在 | 逐语句降级，只补缺失的对象 |
| 种子数据所在表已有数据 | **整表为空才播种**，有数据就不插（见第四节 bug 修复） |
| `--force` | 忽略"已应用"记录全部重跑，但仍靠 SQL 自身幂等，**不删数据** |
| `--reset --yes` | **唯一会丢数据的选项**：删掉两个库重新建。生产慎用 |

## 四、本次顺带修掉的 3 个历史 Bug

不修的话，"可重复执行"就是空话——实测每跑一次数据就翻倍：

| 文件 | 问题 | 修法 |
|---|---|---|
| `001_business_warehouse.sql` | 8 张表（商品标签/库存/客户行为/订单明细/退款/竞品价格/竞品评论/费用）**没有唯一约束**，`ON CONFLICT DO NOTHING` 等于没写，每次重跑都翻倍 | 改成"整表为空才播种"：`INSERT ... SELECT ... FROM (VALUES ...) WHERE NOT EXISTS (SELECT 1 FROM 表)` |
| `003_agent_memory_seed.sql` | `chat_messages` 的 INSERT **完全没写 ON CONFLICT**，每次重跑 +6 行 | 同上 |
| `003_agent_business_schema.sql` | `order` 是保留字却没加引号，`CREATE SEQUENCE order.xxx` 语法错误 → **这个文件从来没成功执行过** | 加双引号 `"order"` |
| `006_customer_service.sql` | 建索引引用 `status` / `assigned_agent` 列，但 `020` 会把这两列改名 → 重放时报 `UndefinedColumn` | 加"列存在才建"守卫 |

### 验证结果（在隔离的测试库上跑的，没碰真实库）

```
全新初始化：32 个迁移全部成功，rc=0
  agent_memory_test  = 42 行数据
  agent_business_test = 62 行数据

连续 3 次 --force 强制重跑：
  数据差异：无（行数一模一样）
  rc=0
```

另外 `backend/tests/sql/test_pg_integration.py` 16 个用例全绿。

## 五、和旧脚本的关系

- `scripts/init_db.py` = **唯一推荐入口**（本地开发 + 存量库补齐都用它）。
- `docker/init-dbs.sh`：容器首次启动仍在用，**未改动**。后续建议让它直接调 `init_db.py`，
  这样"首次启动"和"手动初始化"走同一套逻辑，不会再分叉。
- `scripts/ensure_dbs.py`：功能已被覆盖，**建议废弃**（暂未删除，避免影响其他会话）。

新增迁移的正确姿势：把 SQL 放进 `backend/sql/migrations/`，然后**在
`scripts/init_db.py` 的 `MIGRATION_TARGETS` 里登记归属库**——漏了会立刻报错提醒你。
