### 执行中发现并修复的缺陷（3 个）

1. **坐席辅助 relay 触发缺失（P0）**：outbox relay 经 `publish_envelope` 直投 Redis，
   绕过 `_persist_and_broadcast` —— 认领/坐席消息类事件永远不会触发辅助。
   修复：钩子补到 Redis 订阅转发点（`maybe_schedule_assist_from_envelope`）。
2. **重复投诉幂等漏判（P0）**：`get_active(user_id)` LIMIT 1 无排序，同用户多条
   历史未关闭 handoff 时返回任意一条 → 漏判同会话重复投诉、重复建单。
   修复：优先按会话维度 `get_open_by_conversation` 查。
3. **辅助总超时过紧（P2）**：8s 对真实 RAG+LLM 生成不够（实测 10-50s），
   默认调至 15s。

### 本轮发现并修复/待修复的缺陷（4-9 号，接上轮 1-3）

**P0（主线待修，影子副本已验证修复方案）**

4. **用户端 BFF 代理白名单缺 `idempotency-key`（转人工入口全断）**：前端 `requestHandoff`
   带了幂等键头，但 `frontend/src/app/api/[...path]/route.ts` 的 FORWARD_REQ_HEADERS
   白名单没有它 → 代理剥掉 → `POST /cs/conversations/{id}/handoff` 必 400「请求参数有误」。
   811c39b（09-20）引入强制幂等键时遗漏（frontend-cs 白名单有、frontend 没有），P0 脚本
   绕过 BFF 直调 API 故未暴露。修复：白名单加 `"idempotency-key"`（一行，已验证）。
5. **双端 client.ts Content-Type 双写（所有带 body 的 POST 全 422）**：client 默认头
   `"Content-Type": "application/json"` 与调用方自带的头构成大小写两个变体键，fetch 的
   Headers 构造按 append 语义将重复头逗号拼接为 `application/json, application/json`，
   后端视为非法媒体类型、body 丢弃 → 坐席认领/发消息/确认、用户确认卡等全部 422
  （无 body 的 ws-ticket/转人工与走独立 fetch 的登录不受影响，故 P0 脚本未暴露）。
   修复：请求头归一为单键（frontend、frontend-cs 两处 client.ts，已验证）。
6. **退款/退货动作链路（#8 相关，组合缺陷）**：① 缺订单号时回退 "latest" 取最近一单、
   无结构化追问，且 latest 解析到 sandbox 库的 DEMO-1006（pending）→ 状态门直接拒绝；
   ② 第二轮补订单号不承接 → 重新走 KB 检索 → 拒答；③ http 网关模式下动作专家绕过
   BUSINESS_SERVICE_URL 直查 agent_business 库校验订单，MO- 单只存在于 business-mock
   侧 → "order not found"（查询走网关、动作查本地库，数据源割裂）；④ 库内 DEM- 单
   （completed）可走到建提案，但 confirmations.conversation_id FK 指向的会话行在聊天流
   结束后才懒创建 → strict 模式 FK 违例 → 通用报错。即真实 UI 上退款确认链路不可用。
7. **坐席消息读接口 IDOR 收口漏掉认领坐席**：`GET /cs/conversations/{id}/messages`
  （events 补发端点同口径）只放行属主/admin/API-Key，认领坐席 403 → 选中会话永远
   「暂无消息」、重连对账不补齐、降级轮询收不到消息。P0 脚本走 WS 实收，未覆盖 REST 读。
   修复建议：`_ensure_conversation_access` 增加「当前认领/被派单坐席」分支（与 claim/close
   的 _assert_current_agent 同信任口径）。本轮测试环境临时将 cs_wire_agent 提为 admin 完成
   验证（容器可写层热修两次被并行会话的容器重建冲掉，故改用 DB 角色方案）。
