# 客服四能力补齐 MVP 方案（坐席辅助 / 业务API编排 / 工单系统 / 质检分析）

日期：2026-09-22
基线：main @ 0311cab（客服域文件当前干净；工作区另有并发会话的 model-config 脏改动，**本方案不触碰**）
设计原则：复用既有机制（business_client / beat 薄壳 / WS hub / event outbox / demo 沙盒开关），不引入新框架、不建独立子系统。

---

## 一、结论先行

| 能力 | 已有底座 | 真实缺口 | MVP 改动量 |
|---|---|---|---|
| 坐席辅助 | WS 下行通道 + 意图识别 + RAG 全部现成 | 只差"接单/来新消息时自动推荐回复"这一段胶水 | **最小**，无新表 |
| 业务 API 编排 | `infra/http/business_client.py` 统一 HTTP 客户端**已存在且客服域已在用** | OrderService/LogisticsService 等仍直查演示库，没走网关 | 小，无新表 |
| 工单系统 | handoffs 表 + 投诉工单（**仅内存模拟，不落库**） | 缺统一落库的 tickets 表与用户侧查询/跟进 | 中，需 migration |
| 质检分析 | cs_stats 已有满意度/意图分布；beat 基建就绪（cs_maintenance_tasks 模式） | 缺每日自动聚合沉淀 + 坐席维度质量 | 中，需 1 张报表表 |

实施顺序（按依赖与风险）：**A 坐席辅助 → B 业务API编排 → C 工单系统 → D 质检分析**。
每批次独立验收、独立提交（双重限定 pathspec），批次间互不阻塞（D 依赖 C 的数据更完整，故排最后）。

## 二、现状盘点（依据代码）

### 已确认的关键事实

1. **坐席 WS**（`backend/app/api/routes/cs_agent_ws.py`）：下行推送 `conversation.waiting / claimed / closed`、`message.created`、`heartbeat`；上行只承载 ping 保活，业务操作走 HTTP。鉴权用一次性 ticket，hub 在 `customer_service/realtime.py`（Redis presence + outbox 补偿）。
2. **业务服务层**（`customer_service/service/`）：order/logistics/refund/after_sales/account 全部直查内部演示库；`demo_mode.py` 提供 `CS_DEMO_MODE` 身份映射收口（演示数据由 `demo_sandbox.sql` 播种）。
3. **HTTP 客户端基建**（`infra/http/business_client.py`）：httpx 单例 + 超时(3s/10s) + GET 重试 + `X-Internal-Token` + trace 透传 + `BusinessServiceError` 统一异常——**这正是业务编排需要的全部基建**，已被 conversation_store / state_transition / cs_admin 使用。
4. **投诉工单不落库**：`complaint_service.create_ticket()` 注释明确"(模拟)"，`simulate_execute()` 只返回 dict；ticket_id（`COMPLAINT-xxx`）只活在会话上下文里。
5. **handoffs 表已有 `ticket_id` 列**（`HANDOFF-xxx` 字符串），转人工即工单的雏形已存在。
6. **统计现状**：`GET /cs/admin/stats` 已含会话量/满意度均分与分布/意图分布/转人工数；派单运营有 `GET /cs/ops/dispatch/stats` + Prometheus 指标。缺：**按天沉淀的报表**与**坐席维度质量**。
7. **beat 模式**：`tasks/cs_maintenance_tasks.py` 薄壳 + `customer_service/maintenance.py` 核心逻辑（转人工超时扫描、确认过期扫描）；beat 已正式进主干 compose，**单实例**。
8. **migration 编号**：下一个可用 **035**（032 已撞号，勿再用 032）。
9. **客服端前端**：`frontend-cs`，工作台页面在 `src/app/cs/`（conversations / handoff / stats）。
10. **满意度字段已就位**：`CSConversation.rating / rating_comment / rated_at / first_reply_at`；消息表带 `role / intent_name / created_at`，坐席响应时长可从消息序列直接算。

## 三、批次 A：坐席辅助（agent assist）

### 范围（最小 MVP）
坐席接单（human_active）时、以及人工会话中用户每发一条新消息时，后台异步生成 **top3 推荐回复**，经 WS 推给坐席端；坐席点击即填充输入框，**绝不自动发送**。

### 设计
- 新增 `backend/customer_service/agent_assist.py`：
  - 入参：conversation_id + 最近 N 条消息（N=10）+ 用户最新问题；
  - 复用：`understanding`（意图/实体）→ `rag_search` 检索 → `knowledge/answer_decision` 判定 → 组装候选；
  - 每条推荐带来源标注（知识库 / 订单数据 / 历史工单）与置信度；无证据时标注"仅供参考"（对齐 EvidenceGate 精神）；
  - 整体超时兜底（如 5s），失败静默——辅助功能不允许拖垮消息主链路。
- 触发点：`realtime.py` 的 message.created 持久化/广播路径之后，`asyncio.create_task` 异步执行（RAG 同步调用丢 `run_in_executor`）。
- WS 新事件类型：`assist.suggestion`（payload: conversation_id, suggestions[{text, source, score}]）。
- 前端（frontend-cs 会话详情页）：右侧新增"推荐回复"卡片组件 `AgentAssistPanel.tsx`；点击填入 Composer；每次来新消息刷新。

### 改动文件
| 动作 | 文件 |
|---|---|
| 新增 | `customer_service/agent_assist.py`、`tests/customer_service/test_agent_assist.py` |
| 修改 | `customer_service/realtime.py`（触发点 + 推送）、`frontend-cs` 会话详情页 + 新面板组件、WS 事件类型文档注释 |

### 验收
1. 坐席接单后 3 秒内收到推荐（知识库命中场景）；用户追问后推荐刷新。
2. RAG 服务宕机时消息收发完全不受影响（无推荐、无报错冒泡）。
3. 前端点击推荐能填充输入框且不会误发送。
4. pytest 新增用例全绿；前后端联动手测。

### 明确不做
话术库管理、推荐效果回流标注、自动学习——后续再说。

## 四、批次 B：业务 API 编排（接真实系统）

### 范围（最小 MVP）
把 **查订单** 一个只读接口从"直查演示库"切到"经 business_client 调 Java business-service"，其余服务照旧；打通后写接口照抄此模式。

### 设计
- `OrderService` 内部改为双实现收口：
  - `CS_BUSINESS_GATEWAY_MODE=sandbox`（默认，现状不变）：直查演示库 + demo 身份映射（demo_mode 逻辑原样保留）；
  - `CS_BUSINESS_GATEWAY_MODE=http`：经 `business_client` 调 `GET /business/orders?user_id=`（Java 侧）；
  - 收口点只在 service 层（与 demo_mode 同位），Router/权限层零改动。
- 网关失败（`BusinessServiceError`）：返回"暂时查不到订单信息，请稍后再试"，**不降级回 sandbox**（避免真环境假数据误导）。
- Java 侧接口清单需要先确认（business-service 是否已有只读订单查询；若无，Java 侧补一个只读端点，或本期先用 HTTP mock 容器联调）。
- 配置进 `backend/config/customer_service.py`：`CS_BUSINESS_GATEWAY_MODE / CS_BUSINESS_API_TIMEOUT`（URL 复用 business_client 既有 env）。

### 改动文件
| 动作 | 文件 |
|---|---|
| 修改 | `customer_service/service/order_service.py`（双实现）、`config/customer_service.py`（配置）、`tests/customer_service/`（两种模式用例） |
| 新增 | `docs/customer-service/业务网关切烫说明.md`（接口清单 + Java 侧契约，随联调补充） |

### 验收
1. sandbox 模式回归：现有全部演示流程不受影响（回归用例不破）。
2. http 模式：前端查订单返回真实（或 mock）数据，断网/超时时用户收到友好话术。
3. 权限不变：仍按登录 user_id 查询，无越权。

### 明确不做
写操作（创建退货单/退款执行）——等只读链路稳定、Java 侧幂等方案明确后再排。

## 五、批次 C：工单系统（落库 + 用户侧闭环）

### 范围（最小 MVP）
一张统一 `tickets` 表收编投诉工单与转人工单；用户侧能查"我的工单/工单进度"；管理端能看列表与状态流转。

### 设计
- migration `035_cs_tickets.sql`，表 `customer_service.tickets`：
  ```
  id BIGSERIAL PK
  ticket_id VARCHAR(64) UNIQUE            -- COMPLAINT-xxx / HANDOFF-xxx / TCK-xxx
  tenant_id VARCHAR(64) DEFAULT 'default'
  type VARCHAR(30)                        -- complaint | handoff | inquiry | repair
  status VARCHAR(30)                      -- open | processing | pending_user | resolved | closed
  source VARCHAR(30)                      -- ai | agent | user
  conversation_id VARCHAR(64)             -- 关联会话
  handoff_id VARCHAR(64) NULL             -- type=handoff 时关联
  user_id VARCHAR(64)
  assigned_agent_id VARCHAR(64) NULL
  priority VARCHAR(10) DEFAULT 'medium'
  title VARCHAR(200) / description TEXT
  resolution TEXT NULL
  created_at / updated_at / resolved_at / closed_at
  索引：(tenant_id, user_id, status)、(tenant_id, status, priority)、(conversation_id)
  ```
- 收编两处现有写点：
  - `complaint_expert`：`create_ticket` 后**真正落库**（替换 simulate_execute 模拟）；
  - `handoff_expert`：创建 handoff 时同步建 `type=handoff` 的 ticket（复用同一 ticket_id，双表关联）。
- 状态机：简单线性校验（复用 `errors.BusinessRuleError` 模式），不引新库。
- API（挂现有路由风格）：
  - 用户侧：`GET /cs/tickets`（我的工单）、`GET /cs/tickets/{ticket_id}`（详情+进度）；
  - 坐席/管理侧：`GET /cs/admin/tickets`（列表，支持 type/status 过滤）、`PATCH /cs/admin/tickets/{id}`（改状态，写 audit_log——复用既有审计）。
- Graph 接线：query_expert 增加"查工单/工单进度"意图 → 查 tickets 表回复（用户问"我的投诉处理得怎么样了"能直接答）。
- 前端：frontend-cs 新增"工单"列表页（可挂 stats 页旁）；用户端（frontend）会话内回复已带 ticket_id，本期不做独立用户工单页。

### 改动文件
| 动作 | 文件 |
|---|---|
| 新增 | `sql/migrations/035_cs_tickets.sql`、`customer_service/ticket_store.py`、`app/api/routes/cs_tickets.py`、`tests/customer_service/test_tickets.py` |
| 修改 | `experts/complaint.py`、`experts/handoff.py`、`experts/query.py`（查工单意图）、`app/api/router.py`（**注册行独立提交，防 import 失败**）、`customer_service/models/__init__.py`、frontend-cs 工单页 |

### 验收
1. 投诉后 DB 有落库记录，用户"查我的工单"能报出单号与状态。
2. 转人工自动生成关联工单，接单/关单时工单状态联动。
3. 状态非法流转被拒（409/422 语义与现有路由一致）。
4. ⚠️ 提交时按并发协作规范：`tickets` 模块文件与 router 注册行分两笔提交，先确认无并发会话占用 router.py。

### 明确不做
SLA 自动升级、工单模板、多级流转——数据攒够再议。

## 六、批次 D：质检分析（每日报表沉淀）

### 范围（最小 MVP）
beat 每天凌晨聚合前一天运营数据写入 `qa_daily_reports`；管理端可查任意日期报表；坐席维度出基础质量指标。

### 设计
- migration `036_cs_qa_reports.sql`：`qa_daily_reports`（report_date UNIQUE、metrics JSONB、generated_at）。指标走 JSONB 而非宽表——字段还会演进。
- 新增 `customer_service/qa_report.py`（核心逻辑）+ `tasks/cs_qa_tasks.py`（薄壳，照抄 cs_maintenance_tasks 模式），beat 每日 06:10 跑：
  - 会话量 / 满意度均分与分布 / 意图 Top10 / 转人工率 / AI 独立解决率（closed 且 handling_mode=ai）/ 首次响应超时数；
  - 坐席维度：接单量、平均响应时长（messages 相邻时差）、其服务会话满意度均分；
  - 工单维度：新增量、按 type 分布、超 48h 未解决数（依赖批次 C）。
- 复用：统计 SQL 直接在 customer_service schema 上做（cs_admin._async_cs_stats 已有可参考的查询模式）；写完报表发一条 Prometheus gauge（对齐 cs_dispatch_* 风格）。
- API：`GET /cs/ops/qa/reports?start=&end=`（supervisor 权限闸，复用 cs_ops 的 require_cs_supervisor）。
- 前端：frontend-cs stats 页加"昨日质检日报"卡片（核心指标 + 坐席排行表格）。

### 改动文件
| 动作 | 文件 |
|---|---|
| 新增 | `sql/migrations/036_cs_qa_reports.sql`、`customer_service/qa_report.py`、`tasks/cs_qa_tasks.py`、`tests/customer_service/test_qa_report.py` |
| 修改 | `tasks/celery_app.py`（include + beat_schedule 各一行）、`app/api/routes/cs_ops.py`（报表查询）、frontend-cs stats 页 |

### 验收
1. 手动触发一次任务，报表落库且数值与手写 SQL 抽查一致。
2. 次日 beat 自动生成；重复执行幂等（同 report_date 覆盖不重复插入）。
3. 管理端能看到报表；非 supervisor 403。

### 明确不做
会话逐条抽检打分、情感分析、骂人话术识别——二期。

## 七、并发协作红线（每批次通用）

1. **不碰** 工作区里 model-config 相关脏文件（proxy.py / pricing.py / sys_providers.py 等 13 个）；提交一律 `git add -A -- <paths>` + `git commit -m "..." -- <paths>` 双重限定。
2. 提交前核查新增 import 的模块是否已随同提交（防止"差一行让主干挂掉"）；router.py 的注册行单独确认无并发占用后再提。
3. 改 `realtime.py` / `celery_app.py` 前先 `git status` 确认无他人在改；跑全量 pytest 期间（约 20 分钟）冻结 backend 改动。
4. **beat 单实例红线**：新增 beat 任务只改 celery_app.py 的 schedule 表，禁止扩 beat 副本。
5. 每批次完成 = 后端用例绿 + 前端联动手测通过 + 路径限定提交完成。
