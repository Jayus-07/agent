# 客服演示业务沙盒方案（Demo Business Sandbox）

> 日期：2026-09-17
> 背景：外部评审建议为注册用户设计一套「演示业务沙盒」，使无真实业务数据的账号也能完整演示 RAG 检索、Agent 编排、队列暂停/恢复/人工接管等能力。
> 本文档职责：把该建议**逐条对照现有代码**，标出「已具备 / 部分具备 / 真缺口」，再给出最小改动量的实施计划。
> 编号约定：本文使用 `SB-`（Sandbox）前缀，**不占用**《总交接与实施计划》§5.3 的 B0~B15 批次号。

## 一、结论摘要

外部建议对「演示者要看什么」的判断准确，但它假设的很多能力**本项目已经落地**，不需要重做：

| 外部建议的场景 | 现状 | 结论 |
|---|---|---|
| A. 退款资格判断 + 人工确认 | `RefundService.check_refund_eligibility` + `ActionProposal` + `confirmation_store`/`pending_handler` + 前端 `CSConfirmCard` | **已具备**，仅缺演示数据 |
| B. 物流延误多步骤处理 | `logistics_service.py`（基于订单状态的物流摘要）+ `complaint_service.py`（工单） | **部分具备**：无真实物流轨迹 API/Mock，是状态推导 |
| C. 跨境政策 RAG 问答 | CS KB Service + 主 RAG 系统（R3 评测基线 94.4%） | **链路已具备**，缺「跨境售后政策」知识库内容 |
| D. 复杂编排（Planner→Supervisor→多 Skill→Trace） | CS 走 Router→Experts 路径；全链路 Trace 在 observability | **部分具备**，CS 内是多 Expert 编排而非 DAG，演示口径要如实 |
| 注册账号无业务数据 | 订单查询直查真实 PG `"order".orders`，按 `customer_id = user_id` 隔离 | **真缺口**：需要演示数据租户 |

**真缺口只有 4 个**：①演示数据与身份映射；②政策知识库内容；③物流轨迹 Mock（可选）；④异常注入演示开关。其余是把现有能力「喂上数据」。

## 三、真缺口与实施方案

### SB-1 演示数据租户（P0，核心缺口）

现状：`OrderService._get_single_order` 直查 `"order".orders` 且强制 `customer_id::text = user_id`（order_service.py L59-68）。新注册用户查不到任何订单。

方案（推荐 A，改动最小）：

- **A. 演示身份映射**：新增配置 `CS_DEMO_CUSTOMER_ID`。客服模块启动时若开启 `CS_DEMO_MODE=true`，在 `OrderService`/`LogisticsService`/`RefundService` 的 `_get_order` 入口把 `user_id` 替换为 demo customer_id（单一收口点，不动权限模型）。
  - 优点：不加新表、不动 Router；关闭开关即回到真实模式。
  - 安全：`CS_DEMO_MODE` 默认 false；开启时所有回复由现有 `output_guard` 过滤，前端欢迎页与消息气泡加「模拟数据」角标。
- **B. demo_tenant_id 独立租户**（外部建议的方案）：需在 orders 表加 tenant 字段并改全部 SQL。改动大，**暂不采用**，留作多租户化时的演进方向。

配套 seed 数据（~15 条，直接建 SQL 脚本 `backend/sql/seeds/demo_sandbox.sql`）：
- 订单 15 条：覆盖 已签收/已发货/处理中/已取消，含 1 条「5 天物流停滞」（供场景 B）、1 条「已签收 3 天内可退」（场景 A 主角）、1 条「超 7 天不可退」（演示拒答/不合格分支）。
- 售后工单 2 条：1 条处理中、1 条已完成。
- 全部 `customer_id = CS_DEMO_CUSTOMER_ID`，`order_no` 用 `DEMO-` 前缀便于辨识。

### SB-2 跨境售后政策知识库（P0，内容缺口）

RAG 链路（混合检索+Rerank+证据门禁+引用）已就绪，只缺语料。准备 8~12 份政策文档：
- 退货政策（按国家：美国/英国/德国/日本/加拿大 × 通用）、运费承担规则、退款时限、质量问题举证要求、物流异常处理政策、催件条件。
- 格式：Markdown，走现有 CS KB 上传链路（`CSKnowledgeService`）。
- 验收：场景 C 三连问（美国退货条件 / 运费谁承担 / 超期还能退吗——第三问应触发拒答或证据不足提示）。

### SB-3 快捷提问绑定演示数据（P1）

`CS_QUICK_PROMPTS` 现为泛化问题（「帮我查一下最近的订单状态」），演示模式下改为携带预置订单号的问题，保证一键命中：
- 查询订单 → 「帮我查一下订单 DEMO-1001 的状态」
- 物流追踪 → 「我的订单 DEMO-1003 包裹 5 天没更新了，帮我看看」
- 申请退款 → 「订单 DEMO-1002 的商品坏了，我想退款，应该怎么操作？」
- 投诉建议 / 转接人工：维持原文即可（不依赖订单号）。
- 实现点：仅改 `constants.ts`；如想保留双模式，可按 demo 开关取不同数组（配置经 `/api` 下发或编译期常量，建议先用常量，简单）。

### SB-4 物流轨迹 Mock（P1，可选）

若希望场景 B 更真实：新增 `LogisticsTraceProvider` 协议 + `MockTraceProvider`（按 DEMO- 订单号返回 3~5 段轨迹，DEMO-1003 固定「最后更新 5 天前」）。`LogisticsService` 优先走 Provider，未配置时回退现有状态推导。**注意 Mock 必须可注入失败**（见 SB-5）。

### SB-5 异常注入演示开关（P2）

外部建议第三阶段的「降级与恢复」演示。最小实现：一个 `CS_DEMO_FAULTS` 配置（JSON），各服务入口检查并注入故障：
- `logistics.timeout`：Mock 物流 Provider 超时 → 演示工具重试；
- `rag.insufficient`：知识检索临时过滤命中 → 演示证据门禁拒答；
- `sql.error` / `redis.down`：演示 DatabaseError 分类与降级话术。
- 只在 demo 模式生效，真实模式恒为空。

### SB-6 前端任务执行面板增强（P2，按需）

CSTimeline 已展示节点状态（含 cs_pending）。可选增强：
- 节点详情展开：显示工具调用参数/结果摘要（数据源：现有 trace/audit 记录）；
- 暂停节点上直接内嵌 CSConfirmCard 的确认按钮（目前确认卡片已存在，确认交互是否已挂到 pending 节点上**待核实**）。
- 建议演示前先跑一遍场景 A，确认暂停→确认→恢复全链路在当前前端可用，再决定是否投入。

### 启用演示模式的步骤（运维侧）

1. 播种：`docker compose exec -T postgres psql -U postgres -d agent_business < backend/sql/seeds/demo_sandbox.sql`（幂等可重跑）。
2. 上传 `docs/customer-service/demo-kb/` 语料到对应 CS KB（映射见 demo-kb/README.md）。
3. 后端环境变量加 `CS_DEMO_MODE=true`（可留 `CS_DEMO_CUSTOMER_ID=99001` 默认值），重启后端。
4. 前端以 `NEXT_PUBLIC_CS_DEMO_MODE=true` 构建/启动，欢迎页出现演示提示、快捷提问携带 DEMO 订单号。
5. 故障注入演示：设 `CS_DEMO_FAULTS='{"logistics.timeout": true}'` 后重启（故障在 Provider 单例创建时固化，改配置需重启）。

### 演示话术红线（实测发现，勿说过头）

- **7 天退货窗口未生效**：`RefundService.RETURN_WINDOW_DAYS=7` 与 `AfterSalesService` 中该常量**均只定义未使用**，资格判断仅看状态（paid/shipped/completed）+ 是否已有退款记录。演示「超期不可退」分支时**不要承诺按天窗口拒绝**——或先补齐窗口判断再演。
- 退款执行仍是 `simulate_execute`，不写 DB；「退款凭证号 DEMO-REF-xxxxx」仅为知识库话术，系统不生成该编号。
- 订单地区/渠道（美国/英国等）不在 `orders` 表列中，仅存在于演示轨迹与政策话术层；SQL 查不到地区字段。

## 七、人工介入通道（坐席侧）实施回执（2026-09-17）

### 机制结论

人工介入 = 状态机 + 队列 + 双通道：**用户侧靠现有 SSE 流收状态**（无需轮询），**坐席侧 v1 用 2s 轮询**发现新会话（企业标准是 WebSocket/SSE 推送，v1 选轮询保证 APISIX 兼容与实现简单，二期可平滑替换——下行端点已按增量拉取设计，换成 SSE/WS 只改传输层）。

### 已落地

| 项 | 交付物 |
|---|---|
| 队列查询 | `GET /cs/conversations/handoff/queue?states=` — 未关闭 handoff + 最新消息预览（`HandoffRepository.list_open`） |
| 坐席认领 | `POST /cs/conversations/{id}/claim` — 状态机校验（仅 `waiting_human → human_active`，`handoff_requested` 返回 409）+ `handling_mode` 置 human |
| 坐席发言 | `POST /cs/conversations/{id}/agent-messages` — 落库 `sender_type=human_agent`（需已认领，否则 409） |
| 消息增量 | `GET /cs/conversations/{id}/messages?since_id=` — private 过滤，返回 `last_id` 游标（用户侧/坐席侧通用轮询源） |
| 坐席工作台 | `frontend-admin/src/app/cs/handoff/page.tsx`（坐席工作台仅在管理端；2026-09-17 曾临时移植用户端 /cs/handoff，同日应要求撤下——用户端客服入口改为 /agent 右下角 CSDrawer 浮动按钮）— 队列轮询(2s)/认领/消息增量(2s)/回复框/坐席 ID 持久化 |
| 测试 | `test_handoff_repo.py` +6（mock DB）、认领状态机约束 2 项；tsc --noEmit 通过；现有 CS API 22 项回归通过 |

### 边界与二期

- **用户窗口实时收坐席消息**（二期）：`conversation_id` 目前不随 chat SSE 流下发到前端 store，用户侧暂以消息增量接口轮询兜底；需在 graph 流事件里带 conversation_id 后，用户窗口才能订阅同一增量源（或换 WS 推送）。
- 坐席认领会同步写入 `customer_service.conversations.assigned_agent_id` 与 `customer_service.assignments`；若坐席档案不存在，认领时会先补齐最小 `cs_agents` 记录以满足外键约束。
- 认领后 AI 不再回复该会话：`should_intercept` 已把 `HUMAN_ACTIVE` 列入拦截态（现有逻辑，未改动）。
