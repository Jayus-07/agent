## 3. 认证中心设计

### 3.1 独立部署与接入【已定，拓扑数值 ARCH-11】

- 独立 docker-compose 项目（`oa-auth`）：mysql8 + redis + nacos + auth-service + system-service；与当前项目同宿主机、独立网段，经 `AUTH_SERVICE_URL` 供网关路由（默认 http://localhost:8006）。
- 不与当前项目合仓合库；旧仓库先建 git 基线，改造在旧仓库；当前项目仅新增网关路由 + 环境变量。
- 网关路由 `id: auth-service, Path=/api/auth/**, StripPrefix=1` 置于列表最前；后端 context-path `/auth` 不变（/api/auth/login → /auth/login，旧接口契约零改动）。
- **Redis 安全约束**：现有 Redis `allkeys-lru 128mb` 会把令牌缓存/黑名单逐出（黑名单失效=安全洞）。认证 Redis 必须独立实例或 noeviction 专用 DB【ARCH-03】。
- 启动顺序：mysql → redis → nacos → auth → system → 网关（无健康检查强依赖）。

### 3.2 数据模型【已定复用 + 两个微迁移】

复用 25 表。微迁移（旧库内，带回滚脚本）：
- **M1【ARCH-04】**：`sys_role ADD COLUMN data_scope VARCHAR(16) NOT NULL DEFAULT 'SELF'`（DataScope 枚举落库，CUSTOM 留代码扩展点）。
- **M2【ARCH-05】**：`sys_dept ADD COLUMN dept_code VARCHAR(32)` + 唯一索引——与当前项目 department/KB owner_depts 的**唯一对接键**。
- 种子数据：SUPER_ADMIN 角色 + 初始 admin（强制首登改密）+ 9 部门树（dept_code 对齐当前项目：general/customer/order_dept/product_dept/warehouse/supply_chain/finance/hr/admin）+ 菜单/权限初始化（按实际 @PreAuthorize 注解核对生成，不臆造）。
- 不做：租户、存量数据迁移。

### 3.3 权限模型

```
sys_user ─ sys_user_role ─ sys_role ─ sys_role_permission ─ sys_permission(接口/按钮)
                │                └ data_scope(M1)：SELF / DEPT / DEPT_AND_SUB / CUSTOM
                └ dept_id ─ sys_dept(树, M2: dept_code)
```

- 功能权限：阶段一仅在认证中心内管理；消费方阶段一只消费身份与部门。
- 数据范围：M1 落库后，Java @PreAuthorize(dataScope) 与 Python 行级安全共用同一来源（执行时机 ARCH-06/09）。
- subject_type 三分法【已定 D3】：employee=sys_user 登录态；customer=渠道外部身份（不入 sys_user）；anonymous=游客。**在应用层派生，认证中心与 JWT 均不携带**。

### 3.4 认证协议

| 环节 | 设计 | 修正/新增 |
|---|---|---|
| 登录 | POST /api/auth/login，username/password/deviceId，BCrypt | 移除 AuthServiceImpl 调试密码注释（P0） |
| 刷新 | POST /api/auth/refresh，HttpOnly Cookie，JWT+Redis 双校验，令牌轮换 | 不变 |
| 登出 | 按设备吊销 + access/refresh 入黑名单 | **黑名单前缀统一 `auth:blacklist:`**（旧网关读 `token:blacklist:` 导致登出不生效——移植时修正） |
| 全量吊销 | revokeAllTokensByUserId | 保留 |
| 会话 | auth.multi-device-enabled 开关 | 默认值 ARCH-15 |
| claims | userId/username/type/deviceId + issuer | 新增 `dept`(dept_code) claim【ARCH-13】；jti=userId 旧实现不改（黑名单按整 token 存） |
| TTL | access/refresh 可配 | 推荐 access 2h / refresh 7d / 提前刷新阈值 30min（现 nacos 24h 过长）【ARCH-14】 |
| 验证码/找回密码 | 旧系统缺端点 | 本期不建 |

**JWT 算法演进**【ARCH-01，推荐 HS256 起步 + JWKS 演进】：

```
阶段一（本期）：HS256 共享密钥——持有方仅 auth-service（签发）+ api-gateway（验签）。
  Python 不持有密钥，信任网关注入头（网络隔离+网关剥头）。密钥轮换：jwt.secret-previous 双密钥验签窗口。
阶段二（触发：Python 需独立验签 / 第三方接入 / 密钥不可共享）：RS256 + JWKS。
  预留：网关 JwtVerifier 接口化（HmacJwtVerifier / JwksJwtVerifier，配置切换）；
  auth-service 增加 GET /auth/.well-known/jwks.json。claims 与下游头协议两阶段不变 → 只换验签实现。
```

## 4. 网关接入设计

### 4.1 AuthenticationGlobalFilter（新类，order=-200）

```
filter(exchange):
  1. !gateway.auth.enabled → chain（等价现状）
  2. 【防伪造，无条件】remove 入站头：X-User-Id / X-User-Name / X-User-Dept / X-Auth-Type
     （旧 AuthFilter 无此步且 .header() 是追加——移植必改；本步在白名单放行前执行）
  3. path ∈ exclude-paths（配置化）→ chain
  4. 带 X-API-Key → 注入 X-Auth-Type: api-key，key 原样透传 → chain（校验仍在下游）
  5. 提取 Bearer token；无 → 按 route-policy
  6. 黑名单 auth:blacklist:<token> 命中 → 401
     【安全修正】Redis 异常 → fail-closed 401 + ERROR（旧实现 fail-open，必改）
  7. JwtVerifier.parse：签名 + issuer + exp（±60s skew）→ 失败 401
  8. 注入：X-Auth-Type: jwt / X-User-Id / X-User-Name / X-User-Dept(ARCH-13) / X-Trace-Id → chain
  9. 401 统一 {"code":401,"message":...,"data":null,"timestamp":...}
```

### 4.2 白名单与路由级策略（配置结构）

```yaml
gateway:
  auth:
    enabled: ${GATEWAY_AUTH_ENABLED:false}
    exclude-paths:
      - /api/auth/login
      - /api/auth/refresh          # refresh 凭 HttpOnly Cookie
      - /api/channels/whatsapp/webhook
    route-policies:                # 未列出的路由用 default-policy
      default-policy: ${GATEWAY_AUTH_MODE:shadow}
      # enforce=401 / shadow=只记日志放行(灰度影子) / guest=注入游客身份放行 / open=现状
    jwt:
      secret: ${JWT_SECRET:}       # HS256，≥32 字节，启动校验
      issuer: ${JWT_ISSUER:hongmeng-oa}
      blacklist-prefix: auth:blacklist:
      clock-skew-seconds: 60
```

启动 fail-fast：enabled=true 且 secret 空/短 → 拒绝启动；enabled=true 且 user-header-enabled=true → 拒绝启动（互斥）。

### 4.3 UserHeaderGlobalFilter 处置【已定】

代码保留、auth.enabled=true 时短路（否则默认用户覆盖真实身份）；`GATEWAY_USER_HEADER_ENABLED=false + demo-user` 保留为本地无认证演示模式，语义并入 guest。

### 4.4 三种凭据兼容【已定】

| 调用方 | 凭据 | 网关行为 | 下游身份 |
|---|---|---|---|
| 浏览器用户 | JWT | 验签+注入 jwt 头组 | employee |
| 机器客户端 | X-API-Key | 打标 api-key 透传 | app 现行 api_key_middleware 不变 |
| 服务间 | X-Internal-Token | 不经网关（8090/8091 不入网关），直连自校验 | system+委托 user_id |

`ALLOW_UNAUTHENTICATED=true` 行为完全不动直到 P7；API Key 与 JWT 双轨长期共存。

### 4.5 SSE 注意点【已定】

/api/chat/stream 路由级：关响应缓冲（前端 compress:false 同因）、调大 response-timeout（SSE 长连接）、401 在首帧前返回（过滤器先于流建立，天然满足）。

## 6. Token 与用户上下文协议【已定】

| 头 | 值语义 | 注入方 | 消费方 |
|---|---|---|---|
| X-Auth-Type | jwt \| api-key \| anonymous | 网关（剥后重设） | app 模式机、business-service |
| X-User-Id | 员工=数字串；游客="anonymous"；api-key 不带 | 网关 | RequestContext.user_id、CS、审计 |
| X-User-Name | username | 网关 | 审批 reviewer、审计 |
| X-User-Dept | dept_code（M2） | 网关 | RAG 主体授权、行级安全（未来） |
| X-Internal-Token | 服务间共享令牌 | 调用方 | internal_ai.py / InternalTokenFilter（prod 空拒启动） |
| X-Trace-Id | 透传 | 网关/服务 | 观测 |

401=未认证（统一 JSON）；403=已认证但业务权限不足（服务返回）。直连请求因剥头退化为游客或按 TRUST_USER_HEADER 现状——**信任边界即网络边界**，8000 收口是硬前提（P3）。

## 7. 三个鉴权流程

① HTTP：登录 → 业务请求（剥伪造头→黑名单→验签→注入→app→RAG/SQL/审批）；SSE 首帧前完成认证。
② Java→Python：AiClient（X-Internal-Token+X-Trace-Id）→ /internal/ai/call → payload.user_id 委托 → set_tool_user_id → 工具（审批门/行级安全生效）。
③ Kafka：whatsapp.inbound(customer) → Python → ai.reply.events(customer)；员工会话事件 subject_type=employee。

```
                        business-service 身份消费 + InternalToken fail-fast + WhatsApp 签名；
                        rag-server 内部令牌 + 8000 loopback
P4 Java/MQ（依赖P3）── Kafka 信封 subject_type/actor_source 双端 +（可选 SASL）
P5 临时用户兼容（依赖P3，可与P4并行）── guest 路由策略 + department.ts 登录态化 + dept_code 对齐
P6 测试与灰度（贯穿）── 既有回归网 + 新增契约测试 + shadow→enforce 分路由放量
P7 迁移与正式切换（依赖P6）── ALLOW_UNAUTHENTICATED=false、IDENTITY_SOURCE=strict、生产 fail-fast
```

关键路径 P0→P1→P2→P3；P4/P5 可并行；P0-F 越早越好（影子观测需前端流量先过网关）。

## 10. 灰度、兼容、回滚、安全

**灰度阶梯（每条路由独立）**：open（现状）→ shadow（只记不打，指标 gateway_auth_would_deny_total{route,reason}）→ guest（游客可过路由先切）→ enforce。

**开关矩阵（全部默认=现状）**：GATEWAY_AUTH_ENABLED/route-policy（网关）、IDENTITY_SOURCE（app）、TRUST_USER_HEADER、SQL_ROW_SECURITY_ENABLED、ALLOW_UNAUTHENTICATED（P7 才关）、AI_TOOLS_ENABLED/INTERNAL_API_TOKEN。

**回滚**：任一异常→对应开关回退（enforce→shadow/open；header→legacy）；认证中心故障不影响存量服务（auth.enabled=false 即完全旁路）；Kafka 新字段向后兼容无需回滚。

**安全清单**：① 网关剥伪造头；② 黑名单 fail-closed + 专用 noeviction Redis；③ JWT secret 双密钥轮换 + 旧内置 secret 作废；④ 8000 loopback 收口；⑤ WhatsApp 签名验签；⑥ 初始 admin 强制改密+口令一次性交付；⑦ CORS 收紧【ARCH-16】；⑧ 审批门"申请人≠审批人"约束。
