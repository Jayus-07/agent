## 结论速览

1. **旧系统能复用，但只能"复用内核、不能整体搬用"**：其认证中心（auth-service）+ RBAC 五表 + Redis Token 生命周期管理完整可用【事实】；旧 gateway 不复用——按约束必须复用当前项目 `api-gateway`，把旧网关验签逻辑**移植**过去【建议】。
2. **当前项目已为统一鉴权预留全部接缝**：`X-User-Id` 信任头（Python/Java 双侧同构）、行级安全、RAG 主体授权、工具审批门均已就绪，只差可信身份源【事实】。
3. **临时用户兼容有明确路径**：`"default"`/`"anonymous"`/渠道外部用户三类兜底可归入四层身份模型，靠 feature flag 灰度，不动 schema【建议】。
4. **主要债务**：旧系统完成度约 55%、git 仓库零提交、无种子数据；当前项目存在"身份客户端可自报""内部令牌空即放行"等 15 处已确认风险点（§1.7）。

## 1. 当前项目现状

### 1.2 现有网关的鉴权机制【事实】

- `UserHeaderGlobalFilter.java`（order=-10）：`GATEWAY_USER_HEADER_ENABLED`（默认 false）开启后，请求未带 `X-User-Id` 注入 `GATEWAY_DEFAULT_USER_ID`（默认 `demo-user`）；**已带则原样透传**（客户端可伪造）。
- `application.yml:39-42` 注释明确预留：「对接 Python 侧 `TRUST_USER_HEADER=true` + `USER_ID_HEADER=X-User-Id`」。
- CORS 全局放通（`allowedOriginPatterns="*"` + `allowCredentials=true`），与 backend 内 CORS 两套并存。

### 1.3 身份链路现状【事实】

- 权威定义 `backend/core/request_context.py:64-85` `RequestContext`：`user_id="default"`、`department=""`、`subject_type=""`（空=授权未启用）等；`bind()`（87-112 行）是唯一写入转换点（工具层 ContextVar、LLM 限流、日志、RAG 运行态）。
- 身份解析不在中间件、在各路由手工做：`routes/chat.py:140-146` **请求体 user_id 优先**（客户端可控），兜底 "default"；仅 body 未提供且 `TRUST_USER_HEADER=true`（默认 false）才读 `X-User-Id` 头；`department` 完全取请求体（176 行）。`routes/sql.py:15-40` 仅信任头 + `int()` 转换。
- 四套身份载体并存（core RequestContext / rag.context.identity / tools.session ContextVar / llm proxy 限流变量），靠 `bind()` 单点转换（fe5aade 刚完成统一）。
- 兜底值全景：`"default"`（chat/report/memory/审批单）、`"anonymous"`（客服链路、审计表）、`"whatsapp"`（MQ 消费者）、`demo-user`（网关）。

### 1.7 关键风险点（已核实清单）

1. 身份可伪造：请求体 user_id/department 优先于信任头；前端部门 localStorage 自选。
2. 网关透传客户端自带 `X-User-Id`（UserHeaderGlobalFilter:35-36）。
3. `.env` 当前 `ALLOW_UNAUTHENTICATED=true`：全部业务端点无鉴权开放。
4. 行级安全默认关；工具路径字符串身份与 /sql 路由 int 口径不一致。
5. **客服链路身份断链**：`make_initial_state`（events.py:231-252）不写 user_id，`cs_prefilter.py:73` 兜底 "anonymous" → `PermissionChecker` 恒拒未认证（存量功能缺陷）。
6. rag-service(8090) 零鉴权且不经网关——旁路。
7. 直连 `/rag/ask` 绕过主体授权。
8. 审批接口可自批（reviewer 自报 + 默认 "admin"）。
9. 服务间令牌"空即放行"（Python `internal_ai.py:33-34` 与 Java `InternalTokenFilter.java:33-35` 同款）。
10. 代码内默认弱口令：`PG_READONLY_PASSWORD` 默认 `agent_readonly_dev`、business-service `postgres/postgres`、Grafana admin/admin。
11. MCP/直调路径无用户上下文（`/mcp/call`、`/internal/ai/call` 不设 tool 身份）。
12. 双 CORS 并存。
13. compose 中 `AI_SERVICE_URL=http://host.docker.internal:8000`——流量路径需确认。

## 2. 旧权限系统现状（Enterprise_OA / anonymous-rating-system）

### 2.1 技术栈与模块【事实】

Java 1.8 + Spring Boot 2.7.18 + Spring Cloud 2021.0.9 + Nacos + MySQL 8 + MyBatis-Plus + Redis + JJWT 0.12.3。

| 模块 | 端口（Nacos 配置） | 完成度（项目检查总结.md 自评） |
|---|---|---|
| gateway-service（WebFlux） | 8800 | 85% |
| auth-service | 8006 `/auth` | 90% |
| system-service（15 个管理 Controller） | 8001 `/system` | 85% |
| task-service | 8002 | 60%（无权限注解） |
| rating / statistic / notification | 8003-8005 | 各 5%，仅启动类空壳 |
| common-core / common-auth / common-api / user-api / common-feign | — | 80-95%（feign 服务名不匹配除外） |

### 2.2 数据模型【事实】

`anonymous_rating.sql` 共 25 表：sys_user（dept_id、BCrypt 密码、status、逻辑删除）、sys_dept（parent_id 树）、sys_role、sys_permission（菜单+接口双职责）、sys_menu（与 permission 重叠）、sys_user_role/sys_role_permission/sys_role_menu、sys_post、sys_login_log、sys_operation_log、字典/配置/业务表。**无租户表；sys_role 无 data_scope 列；dump 零 INSERT（无 admin/菜单/权限种子数据）**。

### 2.3 认证实现【事实】

- AuthController：`POST /login`、`POST /refresh`、`POST /logout`、`GET /info`；refresh 经 HttpOnly Cookie（7 天）。
- 双令牌 JWT（HMAC，JJWT 0.12.x）：claims=`userId(Long)/username/type(access|refresh)/deviceId`，jti=userId 字符串，sub=username，issuer 可配（默认 MyApp）；最小密钥 32 字节；parseToken 验签名+issuer+过期。
- Redis（PermissionCache）：token 缓存（auth:access:/auth:refresh:）、黑名单（auth:blacklist:）、按设备 Set、全量吊销、多设备开关、权限/角色/部门缓存（24h）。
- 密码 BCrypt。验证码字段/白名单存在但**端点不存在**；自助找回密码缺失。

### 2.4 网关与权限校验【事实】

- 旧网关 AuthFilter（order=-100）：白名单**硬编码** → `Authorization: Bearer` → Redis 黑名单（默认前缀 `token:blacklist:`，与 PermissionCache 的 `auth:blacklist:` **不一致，登出实际不生效**；且 Redis 异常 fail-open）→ 本地验签 → 注入 `X-User-Id`/`X-User-Name`（**不剥离入站同名头**）。另有 Redis 令牌桶限流（读未设置的 attribute，实际只按 IP 生效）。
- 权限体系：`@PreAuthorize(权限码, dataScope)` + AOP；DataScope 枚举 SELF/DEPT/DEPT_AND_SUB/CUSTOM（仅代码枚举，无列）；超管=硬编码角色码 "SUPER_ADMIN"；注解覆盖率约 70%；审计接口 AuditService 无实现。
- common-auth SDK 是 Servlet 栈（Spring MVC + Spring Security 5），**不兼容 WebFlux**。

### 2.5 工程健康度【事实】

- **git 仓库零提交**（全部 untracked）；**零单元测试**。
- 已知缺陷：大量 return null、AuthServiceImpl 调试密码注释、JWT TTL 配置（nacos 86400000=24h）与代码默认（9000000ms）不一致且注释错误、网关/SDK 黑名单前缀不一致、Nacos 地址历史不一致、common-feign UserFeignClient 服务名不匹配、sys_operation_log 无写入切面、Nacos yaml 内**明文弱口令与内置 JWT secret**（值不在此展开）。

## 3. 匹配度分析

| 维度 | 旧系统 | 当前项目 | 匹配判定 |
|---|---|---|---|
| 身份传递协议 | 网关验签后注入 X-User-Id/X-User-Name | 网关有同头注入器；Python 已实现 TRUST_USER_HEADER + USER_ID_HEADER=X-User-Id | **完全同构，核心匹配点** |
| 认证能力 | 登录/刷新/登出/吊销/多设备全链路 | 无（仅全局 API Key） | **互补：旧补新缺** |
| RBAC 模型 | 五表 + 3 关联 + 部门树 + 数据范围 AOP | 无（ROADMAP 规划中） | 旧可直接供新 |
| user_id 语义 | 数值型 DB 主键 | 字符串（"default"/"anonymous"/外部渠道 ID） | **需 ID 语义约定** |
| 部门 | sys_dept 树（MySQL，无编码列） | department 字符串 ↔ KB owner_depts | 需映射规则（dept_code） |
| 主体类型 | 无此概念 | subject_type customer/employee | 需定义映射 |
| 技术栈 | Java 8 + SB 2.7 + MySQL + Nacos | Java 17 + SB 3.3 + PostgreSQL + env/yml | **有代差，独立部署而非合仓** |
| MQ | RocketMQ 仅声明未用 | Kafka 双端闭环 | 保持 Kafka |

## 4. 复用结论及依据

**结论【建议】**：**有条件复用——"认证中心内核整体复用 + 网关逻辑移植 + 空壳弃用"**。

依据：① auth-service(90%)+PermissionCache+system-service(85%) 是完成度最高的闭环内核；② 旧网关"验签→注入 X-User-Id"协议与当前网关、Python 信任头三方同构，移植成本在 SB2.7→3.3/WebFlux API 适配；③ 当前项目 ROADMAP/auth-decision.md 已定 JWT+current_user 目标路径，row_security/主体授权/审批门"插上可信身份即生效"；④ 不可整体搬用：旧 gateway 复用违反约束、Vue 前端不可迁移、Servlet SDK 进不了 WebFlux、空壳带病；⑤ 缺口（种子数据/黑名单前缀/无 git 历史）属可修债务，必须作为前置清偿。

分级：**直接复用**=auth-service、system-service、25 表 DDL（补种子后）、common-auth/common-core/user-api、@PreAuthorize/@DataScope；**参考移植**=网关 AuthFilter 逻辑、前端登录+动态路由交互思路；**弃用**=旧 gateway 本体、task/rating/statistic/notification、Vue 前端本体。

## 5. 接入边界（概要，详见 02 设计文档）

认证中心独立部署，经现有 api-gateway 新增 `/api/auth/**` 路由暴露；网关是唯一信任边界（验签、剥伪造头、注入身份头）；下游信任网关注入头；服务间走内部令牌；rag/mcp 保持 loopback；Kafka 事件信封加身份标注。

## 6. 权限影响面

- **HTTP**：~22 路由 ~90 端点从"全局 API Key（当前全开放）"切为"JWT（人）+ API Key（机器）"双轨；前端需新增登录态；/approvals reviewer 必须取真实身份；/health、/metrics、/docs 白名单保留。
- **Java**：/cs/conversations 等经网关获得鉴权；/internal/* 令牌必须实配（修空即放行）；WhatsApp webhook 补 Meta 签名验签。
- **MQ**：事件 user_id 需区分企业/渠道身份（加 subject_type）；消费侧身份语义显式化；Kafka 认证起步用网络隔离。

## 7. 临时用户兼容初步方向

四层身份模型：① 登录员工（JWT.sub→sys_user）② 渠道外部用户（channel:external_id，不入 sys_user）③ 未登录临时用户（"default"/"anonymous"→显式 guest 语义）④ 服务间（内部令牌→系统身份）。兼容策略：TRUST_USER_HEADER/IDENTITY_SOURCE 开关化新旧行为并存；guest 映射游客角色（只读工具+customer KB 集）；WhatsApp user_id 原样保留；user_id 列保持字符串/可空，不 backfill。

## 8-10. 方案/清单/阶段

推荐方案 A：复用旧 auth-service 为统一认证中心 + 现有 api-gateway 移植鉴权过滤器 + Python 开信任头 + 四层身份模型。备选 B：当前栈自建轻量认证中心（技术栈统一但重复造轮子）；C（否决）：旧整套系统以旧 gateway 为入口（违反约束）。改造清单 P0-P7 与风险/验证/回滚详见 `02-详细架构设计.md` §8-§10。
