**P2 新增的安全修正（相对旧 AuthFilter 的 4 处缺陷）**
1. 无条件剥离入站 `X-User-Id/X-User-Name/X-User-Dept/X-Auth-Type`（用 `remove` 而非追加）——旧实现用 `.header()` 追加且不剥，下游取到伪造值。
2. 黑名单 Redis 异常 **fail-closed**（401 + ERROR）——旧实现 fail-open。
3. 白名单配置化（`gateway.auth.exclude-paths`）——旧实现硬编码。
4. 黑名单前缀统一 `auth:blacklist:`（读侧在新过滤器实现，与写侧一致）。
额外加固：**拒绝 `type=refresh` 的令牌当访问令牌用**（否则 7 天有效的 refresh 等于长效 access；02 文档未提，实现时补上）。

**P2 期间踩到并已解决的工程坑（后续复用）**
- Spring Cloud Gateway 的 `GatewayRedisAutoConfiguration` 要求容器内**有且仅有一个** `ReactiveStringRedisTemplate`：既不能排除 Redis 自动配置（会缺 `redisTemplate`），也不能自建第二个（`redisRateLimiter` 选不出依赖）。**正解：统一走 `spring.data.redis.*` 指向 oa-auth-redis，不自建连接工厂**。
- `blacklist-prefix: auth:blacklist:` 裸写含冒号会被 SnakeYAML 判为非法映射，**值必须加引号**（02 文档 §4.2 示例是错的）。
- Git Bash 下 `docker compose -f/--env-file` 传 MSYS 路径会产出 `D:\d\Program Files\...` 畸形路径，**必须 cygpath -w**（旧系统 deploy.sh 已同步修）。
- 本机存在占用 `127.0.0.1:8080` 的原生进程（"腾讯位置服务演示台"），Windows 优先匹配该更具体绑定，**导致 `curl 127.0.0.1:8080` 打不到 Docker 发布的网关**（Docker 只监听 0.0.0.0:8080）。冒烟脚本已自动探测并回退到容器网络内 `api-gateway:8080`。

**P2 未做（有意延后，非遗漏）**
- **ARCH-13（JWT 加 dept claim）延后到 P3**：`X-User-Dept` 的唯一消费方是 P3 的 `IDENTITY_SOURCE=header` → `authorized_kbs()`；现在加需要打通 auth-service → sys_dept.dept_code 的查询链路（跨模块），而网关已能容忍 claim 缺失（不注入该头）。P3 与消费方一并做，避免无消费者的空改动。
- ARCH-16（CORS 域名清单）仍待用户提供。

**发现 2 个缺陷（P2 动手前必须先处置）**

- **D-1【P0 遗留·配置键名不匹配】ARCH-14 的 access TTL 2h 实际未生效。**
  - 事实：nacos `auth-service.yaml` 写 `jwt.expiration-time: 7200000`，而 `JwtUtil.java:40` 读的是 `${jwt.expiration:9000000}` —— **键名不一致，yaml 值从未被读取**。

  - 影响：P0 "access TTL 2h" 是空操作；P2 网关 skew/前端刷新阈值判断都按 2h 写会与事实不符。
  - 处置：二选一（推荐改 yaml 键名 → `jwt.expiration`，代码兜底值同时改成 7200000 消除歧义）；`refresh-expiration`/`refresh-threshold` 两项 yaml 完全未配，走代码默认 7d/30min，与 ARCH-14 一致，无需动。
- **D-2【02 设计文档错误】`JWT_ISSUER` 默认值写错，照抄会全量 401。**

**D-4【P1 遗留·潜伏缺陷】MySQL 8 认证插件 + JDBC URL 缺 `allowPublicKeyRetrieval` → MySQL 容器一重启，认证中心登录永久挂死。**
- 症状：`POST /auth/login` **无任何响应**（curl 超时，20012ms 无字节返回），但 `GET /auth/` 仍返回 401、容器 healthcheck 仍 healthy —— 极易误判成"服务正常"。网关侧表现为 `/api/auth/login` 卡住。
- 根因：MySQL 8 用户默认 `caching_sha2_password`；JDBC URL 为 `useSSL=false`，驱动必须向服务端索取 RSA 公钥，缺 `allowPublicKeyRetrieval=true` 直接抛 `Public Key Retrieval is not allowed`。**真正的隐蔽点**：服务端会缓存已认证过的凭据走 fast-path，所以"首次部署能用、MySQL 重启后就挂"——即 P1 的部署只在新鲜 MySQL 上验证过。
- 定位证据：`docker logs oa-auth-service` 里 Druid `CreateConnectionThread` 刷 `SQLNonTransientConnectionException: Public Key Retrieval is not allowed`；用 CLI 连一次 MySQL（`mysql -uoaauth -p...`，走本地 socket 完成完整握手）预热缓存后，登录立刻 200。
- 已修：`config/nacos/auth-service.yaml` + `system-service.yaml` 的 JDBC URL 加 `&allowPublicKeyRetrieval=true`（loopback 单机开发可接受；生产应改走 TLS）。**验证方式**：`docker restart oa-auth-mysql` + `FLUSH PRIVILEGES` 清空缓存后，直连 8006 与经网关 8080 登录均 200。

**D-5【本仓库·端口冲突】`backend/scripts/serve_map_demo.py` 默认端口 8080 与 api-gateway 撞车。**
- 症状：`curl 127.0.0.1:8080` 打到地图演示台（404 `{"detail":"Not Found"}`），经网关的登录/业务请求全被劫持；而 `0.0.0.0:8080` 上网关其实好好的。根因是 Windows 优先匹配更具体的绑定（`127.0.0.1:8080` > `0.0.0.0:8080`）。
- 已修：演示台默认端口改 **8085**（`MAP_DEMO_PORT` 可覆盖），文档串同步改；已在 8085 重启验证 `/map/health` 200。排查手法见 §十一。

**D-6【旧系统·部署健壮性】oa-auth compose 未配 restart 策略。**
- 事实：主项目 compose 各服务均有 `restart: unless-stopped`，oa-auth compose 没有 → Docker Desktop 重启后认证中心 5 个容器**不会自动回来**（P2 收尾实测），而主项目容器会自动回来，形成"半死不活"状态。
- 已修：5 个服务（mysql/redis/nacos/auth/system）均加 `restart: unless-stopped`。
