# 上下文预算管理（L1–L5）—— 项目现状说明

> 用途：给方案设计者（人或 AI）的背景简报。本文只描述**现状与约束**，不含方案。
> 日期：2026-09-22 ｜ 基线：`D:\Program Files\workplace\agent`（多会话并行开发仓库）

---

## 1. 项目是什么

电商 RAG + Multi-Agent 平台：

- **后端**：FastAPI + LangGraph，四层架构 Agent → Skill → Tool → External；对话入口 `POST /chat/stream`，SSE 流式返回（帧序 `meta → status/log/delta → done/error`）。
- **前端**（聊天窗口）：Next.js 14 App Router + React 18 + Tailwind 3 + Zustand；另有 frontend-admin / frontend-cs / frontend-mp 三套端。
- **数据库**：PostgreSQL 双库 `agent_business`（业务）+ `agent_memory`（会话/记忆/检查点）。
- **LLM**：DeepSeek（langchain-openai 兼容接口），另有 qwen / ollama / vllm 等 provider 适配层。
- **部署**：docker compose 多容器——`app`(:8000)、`worker`、`beat`、`rag-service`(:8090)、APISIX(:9080) 等。**app 与 worker 是不同容器，本地磁盘不共享**。

## 2. 目标

引入分级上下文预算管理（概念示意，最终以方案为准）：

| 层级 | 概念 | 说明 |
|---|---|---|
| L1 | 工具结果预算 | 单条工具输出超限 → 落盘 + 预览 |
| L2 | 历史裁剪 | 回收陈旧对话脚手架/冗余记账 |
| L3 | 微压缩 | 回收旧工具输出（时间型/缓存型） |
| L4 | 上下文折叠 | 投影式折叠、可回滚、非破坏性 |
| L5 | 自动压缩 | 阈值触发、LLM 摘要、不可逆 |

## 3. 现状：与上下文长度/预算直接相关的既有机制

### 3.1 token 计数（地基，已存在）

`backend/memory/token_budget.py`
- `count_tokens` / `count_message_tokens`：tiktoken `o200k_base` 精确计数；加载失败降级为「中文约 2 字符/token」粗估，只尝试一次。
- `trim_messages_to_budget(messages, budget)`：SystemMessage 全保留，其余从最新往回保留，超预算丢最旧。返回 `(kept, dropped)`。
- `trim_texts_to_budget(texts, budget)`：按顺序从头保留（用于 RAG 证据，尾部整体丢弃、不截断单条）。

### 3.2 会话记忆装配（每轮对话入口）

`backend/memory/service.py::MemoryService.start_session()`（runner 每轮先调它）：

装配顺序：
1. **L2→L1**：从 PG 拉最近 `SHORT_TERM_MAX_MESSAGES*2`（默认 40）条历史，按 `(role, content)` 连续去重后放入 ShortTermBuffer。
2. **会话摘要注入**：`chat_sessions.summary` 字段非空（≥30 字符）时，作为 SystemMessage 插到最前。
3. **L3 长期记忆**：用当前 query 做 pgvector 语义检索 top_k=5，format 后作为 SystemMessage 插入；失败软降级不阻断。
4. **token 预算裁剪**：`trim_messages_to_budget(l1._messages, HISTORY_TOKEN_BUDGET)` 整体裁剪。

相关配置（`backend/config/memory.py`，均可 env 覆盖）：
- `SHORT_TERM_MAX_MESSAGES = 20`（历史条数窗口）
- `HISTORY_TOKEN_BUDGET = 2048`
- `LLM_CONTEXT_LENGTH = 4096`（`backend/config/llm.py:161`，provider 侧用作 max_tokens/num_ctx）

### 3.3 会话摘要（现有「压缩」雏形）

`MemoryService.end_turn()`（每轮回答结束后）：
- `srepo.needs_summarization(session_id)`：**按消息条数**（>50 条）判断是否需要摘要，不是按 token。
- 触发后 `SessionMemory.summarize()` 生成摘要 → `update_summary` 落库 → 下轮 `start_session` 注入。
- 摘要失败保留旧摘要并发 metric（`degradation_alerts_total{code="memory_summary_failed"}`）。

### 3.4 RAG 证据预算

`backend/rag/chain.py`：rerank 后证据用 `trim_texts_to_budget` 裁剪，已接入。

## 4. 现状：工具输出在架构里的真实流向（方案设计的关键事实）

本平台**不是** ReAct function-calling 架构，工具输出**不进聊天消息历史**：

```
Planner（拆解 → Capability DAG，禁调工具）
  → Critique
  → Supervisor（纯规则 DAG 调度）
      → Send 并行派发 Skill 节点
      → 注入 previous_outputs = {依赖步骤id: step_results[id].output}
        （orchestration/supervisor/scheduler.py:236）
  → Skill 节点内部调 Tool
  → Reporter（step_results → Markdown）
```

- 工具返回 JSON 字符串；新 Tool 统一走 `backend/tools/map/_base.py` 的 `ok()/fail()/not_configured()`；**存量 18 个 Tool 直接返回 Markdown**（规范例外台账 E8，不经过 `_base.py`）——所以做「工具出口统一拦截」不能只挂 `_base.py`。
- 跨步数据传递 = `step_results` + `previous_outputs` 注入，这是「旧工具输出」实际驻留的位置。
- Skill 节点拿到 `messages`（含历史）+ `previous_outputs` 拼 prompt 调 LLM。

## 5. 现状：前端聊天窗口与 SSE

- 前端已解析的 SSE 事件类型：`meta / status / log / delta / thinking / done / error`；单一网络出口 `frontend/src/api/client.ts`。
- 后端流式机制：节点 status/log + LLM stream_sink delta 汇入 merged_q → SSE。若后端新增「压缩发生」类事件，前端加一个事件分支渲染系统提示条即可，改动很小。
- 会话列表/历史读取走 `MemoryService.list_sessions / get_session_messages`（PG `chat_sessions` / `chat_messages`）。

## 6. 硬约束与坑（方案必须兼容）

1. **窗口很小**：`LLM_CONTEXT_LENGTH=4096`。「单条工具输出 50K 字符才落盘」这类阈值在本项目约等于 25K token，单条即爆窗。阈值应以 token 计。
2. **多容器不共享磁盘**：app 与 worker 各自容器内落盘对方读不到。跨容器可见的「落盘」需走共享卷或 PG 大字段。
3. **状态权威在 PG + LangGraph checkpointer**（postgres 优先，失败降级 MemorySaver）。跨轮状态持久化已有权威路径，任何「折叠/快照/回滚」机制都不应另起炉灶。
4. **Travel/客服域图有自己的跨轮契约**：`new_*_graph_input()` 只放本轮输入、读状态一律 `.get()`（checkpointer 把 input 当更新合并）。上下文折叠若触碰域图状态，必须遵守该契约。
5. **多会话并行开发仓库**：同一文件可能混有其他会话的未提交改动；改动前后需 `git status` 核对。
6. **规范红线**：业务代码禁止直接 `os.getenv`（配置收口到 `backend/config/`）；新增配置走 env + config 模块；禁止 `except Exception: pass`。
7. **域开关**：CS/旅游/选品三个 prefilter 由 `.env` 控制，上下文管理若在 router 前插逻辑不得影响 prefilter 顺序（有守护测试 `tests/orchestration/graph/test_router_prefilter_order.py`）。
8. **测试门禁**：局部跑 pytest 必须带 `--no-cov`（覆盖率门禁 EXIT=1 问题）；新增 marker 须登记。

## 7. 缺口清单（现状 vs 目标）

| 能力 | 现状 |
|---|---|
| token 计数 | ✅ 已有（tiktoken + 降级粗估） |
| 历史窗口裁剪 | ⚠️ 有，但纯「丢最旧」，无「陈旧脚手架/冗余记账」语义识别 |
| 工具输出预算（落盘+预览） | ❌ 无任何拦截，工具输出原样进 step_results |
| 旧工具输出回收（时间型/缓存型） | ❌ 无；作用对象应是 step_results/previous_outputs 而非聊天历史 |
| 上下文折叠（可回滚） | ❌ 无 |
| 自动压缩 | ⚠️ 半成品：摘要管线+注入管线齐全，但触发条件是「条数>50」而非 token 阈值，且只在回合结束后触发 |
| 前端压缩提示 | ❌ SSE 无对应事件类型 |

## 9. 留给方案设计者的问题

1. L1「落盘」的存储介质选型：共享卷 vs PG 大字段 vs 直接丢弃只留摘要？（多容器约束见 §6.2）
2. L2「陈旧脚手架」的判定标准：本项目历史消息里什么是「脚手架」？（聊天历史主要是 user/assistant 文本，过程性内容在 step_results 里，两处性质不同）
3. L4 投影折叠的「可回滚」快照放哪：checkpointer 已有持久化，是否复用？
4. L5 双阈值（95% 窗口 / 剩余 13K）在 4096 总窗口下如何换算？13K 剩余显然是按大窗口模型（如 128K）设计的口径，本项目需重新标定。
5. 分层触发的观测指标：现有 metrics 体系（`observability/metrics.py`）加哪些计数器来验证每层实际省了多少。
