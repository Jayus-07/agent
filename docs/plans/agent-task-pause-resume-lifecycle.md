# Agent 暂停、取消与恢复规范实施计划（设计稿）

> 状态：PROPOSED / documentation-only。适用基线：2026-10-11 main。此文是后续实施设计，不宣称产品运行时已经支持主动暂停或断点恢复。
> 关联规范：[AGENTS.md](../../AGENTS.md)、[AI Runtime](../architecture/ai-runtime.md)、[Frozen Contracts](../architecture/Frozen-Contracts.md)、[跨层契约](../development/cross-cutting-contracts.md)、[测试规范](../development/testing-guide.md)、[幂等手册](../operations/idempotency-runbook.md)。

## 1. 目的与边界

区分两个不同问题：

- **开发 Agent 任务暂停/交接**：Zcode/Codex 的代码施工暂停、换会话、取消、交接，使用 Git Worktree 和任务文档保存进度；不创建应用数据库表或后端运行状态机。
- **产品 Agent 运行时任务控制**：用户通过 Chat/旅游/客服等入口提出暂停、恢复或取消；涉及 LangGraph、SSE、Checkpoint、Tool 副作用，必须按域和入口实测能力推进。

本轮只制定规范和审计要求；不改动业务运行逻辑、数据库、事件 Schema 或前端。沿用当前 D1～D7 与施工顺序：MCP P0 → PR #24 规范重落地 → 最小 CI → 公共治理 → 业务域 → 清理。开发 Agent 补充规则列入 PR #24；运行时能力列入公共 Runtime 治理规划，未满足依赖不施工。

## 2. 现状与禁止误判

- AGENTS.md 已要求跨会话用 `docs/tasks/<task-id>/TASK.md`、`PROGRESS.md`，续工核对 Git/测试，用户暂停或取消时遵从最新要求，分支和工作树保护按现有规范。
- ai-runtime.md 记录主图使用不透明单次 thread_id，目前**没有据此恢复中断主图执行的公开路径**。
- SSE 断线事件重放是**展示通道恢复**，不等于 LangGraph/Tool 业务任务暂停、断点续跑。
- 浏览器断线、用户主动取消、等待审批、后台任务继续运行彼此不同。不能因为 Checkpointer 组件存在，就宣称各域具备安全可恢复功能。
- 上述结论来自当时仓库文档；施工前必须以实际源码、配置、数据库迁移及测试再次核实。

## 3. 开发 Agent 的最小暂停与交接契约（候选追加至 AGENTS.md）

仅长任务或跨会话任务维护 TASK/PROGRESS，简单任务无需建档。开发 Agent 接到暂停指令时：
1. 不启动新改动或新测试；对进行中的命令/写操作尽可能安全中止，无法即时停止则明确报告正在执行的操作与后果。
2. 在不覆盖其他并行修改的前提下记录任务 ID、目标/范围、worktree 路径、branch、HEAD、已改文件、未提交状态、已执行测试证据、阻塞与下一步；必要时更新 PROGRESS，不擅自 stash、reset、清理、合并或强制提交。
3. 区分 `PAUSED`（预计可能续工）、`BLOCKED`（外部阻塞）、`CANCELLED`（用户取消）。取消不等于撤销已提交/已执行副作用。
4. 恢复前先重新阅读最新用户指令、TASK/PROGRESS，确认 worktree、HEAD、未提交修改和上游变更，核实旧测试证据是否仍适用；有冲突先报告，绝不覆盖其他会话成果。
5. 交付使用短格式：状态、分支/HEAD、最后安全点、已完成、尚未完成、验证证据、下一步；不得声称未执行项 PASS。

## 4. 产品 Agent 运行时生命周期契约（目标，不代表已实现）

### 4.1 状态与语义

建议目标状态：`CREATED` → `RUNNING` → `PAUSING` → `PAUSED` → `RESUMING` → `RUNNING`；旁路可进入 `WAITING_APPROVAL`、`BLOCKED`；终态 `SUCCEEDED`、`FAILED`、`CANCELLED`。是否有 `PARTIAL`、`UNKNOWN` 按领域副作用契约确定，不能用 `FAILED` 掩盖不确定写入。

- **暂停**：协作式停止后续节点；必须在可确认的安全点持久化状态之后才响应已暂停。无法安全暂停时返回拒绝/处理中，不伪报成功。
- **恢复**：需经认证、资源归属和租户授权；校验任务状态、版本/CAS、Checkpoint 与外部副作用账本，拒绝重复恢复和重复写入；缺可靠恢复条件时不暴露恢复功能。
- **取消**：尽量停止尚未开始的操作；不保证撤销已完成外部副作用，执行结果未知需进入核查/人工处理，不得盲目重试。
- **等待审批**：属于业务门禁，不应伪装成暂停；重新进入执行前重新校验身份、授权、确认内容、参数指纹和时效。
- **浏览器断线**：只影响传输/订阅；是否保持生产者存活以现行流契约为准，不从断线自动推导取消。
- **服务重启**：只有持久化检查点、可恢复执行器、幂等策略及实际测试均具备时才承诺恢复。

### 4.2 控制面与数据约束

后续实施须明确权威 task/run ID、tenant/user/resource 作用域、状态版本、执行租约/并发竞争、更新时间、请求幂等键、Trace 关联与终态。任何 REST/SSE/WS 消费端需以服务端状态为真值；重复 pause/resume/cancel 应有确定响应。优先复用已有 Runtime、Checkpoint、幂等和业务状态；不得仅为统一外观新增并行任务表、重复执行引擎或无必要消息队列。

Tool 分类：纯读可在安全点重跑（仍看 Provider 限制）；写入/下单/退款/行程正式版本修改必须通过授权、确认、幂等、CAS/账本，未知结果先查询不可自动二次执行。Local Tool 和 MCP Tool 共享一致安全语义；MCP 不等于唯一 Tool Runtime。

### 4.3 先审计再实现

按入口分别查明：主 Chat、旅游 V2、客服、SQL/RAG 查询、Celery 长任务，以及其对应 PC/移动前端。对每个入口记录：执行路径、当前控制 API、SSE 断线、Checkpoint 配置与 thread key、持久化位置、Tool 副作用和租户校验、支持/不支持暂停/取消/恢复的源码及测试证据。审计结果将功能分类为：
- `SUPPORTED`：有接口与真实恢复证据；
- `PARTIAL`：仅取消或 SSE 重连等；
- `UNSUPPORTED`：明确不具备；
- `UNVERIFIED`：无法确认。

## 6. 必须覆盖的验收场景

1. 非本人/跨租户 pause、resume、cancel 拒绝；猜测 run ID 不越权。
2. pause 与 complete、cancel 与 resume、两个 resume 并发竞争不出现双执行；重复请求幂等。
3. 暂停中的节点完成后不会继续执行后续 Tool；无法安全暂停时不显示 PAUSED。
4. Checkpoint 失效、丢失、过期、服务重启时诚实报不可恢复，或经实测安全续跑。
5. SSE 断网、刷新、重放不能被误认为运行时恢复；事件去重与终态一致。
6. 写 Tool 已成功、超时未知、确认过期时不得重投退款/下单/修改；对账与人工接管可追溯。
7. Local/MCP 双路径的权限、业务状态和审计一致；无多一条旁路即可越权。
8. Trace、SSE、数据库、UI 最终状态一致；取消不写成功轮次记忆。
9. 测试记录包含命令、环境、实际输出、退出码、时间、适用范围；未执行记 UNVERIFIED。

## 7. 当前不做

不启动运行时重构；不先增数据库表；不把所有 Tool 搬到 MCP；不一次性为所有业务域添加暂停按钮；不在 MCP P0 PR 中夹带生命周期设计的实现；不改用户已确认的旅行 V2 自动保存/版本恢复或客服确认与接管规则。

## 8. Zcode 后续交付格式

R0 审计应输出“入口/域 → 是否支持 pause/cancel/resume → 控制 API → 实际执行路径 → 状态存储 → 关键副作用 → 测试与源码证据 → 差距 → 建议批次”，并单独给出影响面、风险、无代码修改证明。不经用户批准不得实施 R1/R2。
