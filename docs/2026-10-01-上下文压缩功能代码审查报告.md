# 上下文压缩功能 · 代码审查报告

- 审查日期：2026-10-01
- 审查对象：`backend/context_budget/`（14 个文件，约 2700 行）+ `backend/memory/token_budget.py` + 各层接线点 + 评测套件
- 代码基线：工作区 HEAD `9475ef7`（本次审查涉及的文件均无本地未提交改动）
- 审查方式：逐文件精读 + 在项目 venv 中实际运行复现（非纯静态推断）

---

## 一、结论先行

**整体设计方向是对的**：L1→L5 逐级降级、只改"发给模型的那份内容"不动数据库原始消息、用户历史绝不塞进 SystemMessage（防提示注入提权）——这几条比一般项目做得扎实。

**但有一个必现缺陷，后果比"某层不生效"严重得多**：

> 异步链路（也就是生产聊天的实际链路）上，只要上下文用量达到 90%，L5 摘要层会抛一个 `NameError`；这个异常被上层的兜底 `try/except` 吞掉，导致**整条压缩链（L2 裁剪 + L4 折叠 + 硬裁剪）全部白做，消息原样超预算发给模型**，而且日志只有 debug 级别，生产环境看不见。

这不是"边缘 case"——它是**必然抛出**的实现错误（变量从未定义），只是被兜底逻辑掩盖成了"静默失效"。

另外，现有单测和评测**结构性地发现不了它**（原因见第四节），所以 `PHASE5_PASS / 生产就绪` 这个结论并不能证明线上 L5 真的在跑。

### 【严重】`_L5_TASKS` 未定义 → 异步链路必抛异常、整条预检静默失效

**位置**：`backend/context_budget/manager.py:397-398`

```python
_t = loop.create_task(_ac.run_auto_compact_async(...))
_L5_TASKS.add(_t)                          # ← 397：这个变量全文件、全仓都没有定义
_t.add_done_callback(_L5_TASKS.discard)    # ← 398
```

**核实过程**（不是猜的）：
- 全文件 AST 扫描：该名字在模块中从未被赋值，模块也没有星号导入或 `__getattr__`
- `git log -S "_L5_TASKS"` 只命中引入提交 `932fe59` 一次 → 说明从第一天起就只有使用、没有定义

**实测复现（项目 venv，两条对照）**：

```
# 1) 异步上下文里触发 L5
RAISED -> NameError : name '_L5_TASKS' is not defined

# 2) 异步上下文里走完整预检（超长消息）
输出与输入同一对象(说明完全没做压缩): True
输出内容长度: 120000            ← 一字未裁，且没有任何压缩日志

# 3) 同步上下文对照（同样的输入）
WARNING [ContextBudget] preflight 后仍超 hard budget: used=99004 budget=7168（已最大化裁剪，安全降级放行）
```

**后果链**：
1. 异步节点内调用 LLM（生产主链路）→ 用量比例 ≥ 0.90 → 进入 L5 判定 → 抛 `NameError`
2. 异常冒泡到 `backend/infra/llm/proxy.py:1633` 的 `except Exception`，被原样放行
3. 因为异常是在 `prepare_llm_context` **内部**抛出的，本轮**已经做完的 L2 裁剪、L4 折叠、硬裁剪结果全部作废**
4. 该兜底只记 `logger.debug`，生产 INFO 级看不到任何线索

**触发条件要特别注意**：不是"超预算"才出问题，而是"用量比例 ≥ 0.90"就出问题——**就算还在预算内，只要进入 L5 判定分支就会崩**。

**修法**（3 行，建议与测试一起提交）：

```python
# manager.py 模块级（模块级单例附近）
_L5_TASKS: set = set()
_L5_TASKS_LOCK = threading.Lock()
```
`add` / `discard` 加锁；同时补一个**异步上下文**的 L5 触发用例（见第四节）。

### 【中等】L4 折叠会吞掉历史中间的 SystemMessage

**位置**：`backend/context_budget/collapse.py:106-125`

注释写的是"最后一条 SystemMessage 之后的普通消息"才折叠，但实现取的是**第一条非 System 消息**的位置当作折叠起点：

```python
non_system_idx = [i for i, m in enumerate(messages) if not _is_system(m)]
fold_start = non_system_idx[0]      # ← 120：这是"第一条非 System"，不是"最后一条 System 之后"
```

于是折叠范围 `[fold_start, fold_end]` 会把夹在中间的 SystemMessage 一起卷进去。

**实测复现**：在历史中段插一条业务 SystemMessage（含订单号与金额），折叠后：

```
fold 发生: True | 折叠条数: 7
SYSTEM-MIDDLE 还在吗 -> False
```

**对照**：`auto_compact.fold_rebuild`（manager 的 L5 路径）会保留所有 SystemMessage，两处口径不一致。

**后果**：任何在对话中段动态插入的业务 system 指令/规则，一旦触发 L4 折叠就从本轮 prompt 里永久消失。

**修法**：`fold_start` 改为"最后一条 SystemMessage 的下标 + 1"（无 SystemMessage 时回退到 0）。

---

### 【中等】进程内单飞去重在异步分支失效

`manager.py:356-364` 用 `_l5_inflight` 集合做同会话单飞，但异步分支在 `392-403` 行 `create_task` 之后**立即 return**，`finally` 随即把 session 从集合里移除——而后台任务还在跑。同一会话的并发请求会重复触发摘要 LLM。

有 Redis 跨进程锁 + 水位线 CAS 兜底，**数据不会写坏，但会重复花 LLM 的钱**。

**修法**：异步分支把 `discard` 挪到任务的 `done_callback` 里，别在 finally 里立刻放行。

---

### 【中等】后台摘要任务绑定请求的事件循环

`manager.py:392-403`：`loop.create_task(...)` 挂在当前请求的事件循环上。SSE 请求结束后循环可能被回收，任务被取消 → 摘要没写完、水位线没推进，白跑一次。

**修法**：放进独立线程池/独立循环执行，不要绑请求 loop。

---

### 【中等】跨会话 SSE 事件串台

`metrics.py:179-200` 的补偿缓冲 `_pending_events` 是**进程级全局** deque；`runner.py:536` 是**任何请求**进来都会 `drain_pending_events()` 把缓冲全部推给自己的 SSE。

**后果**：A 会话触发的 L2 事件，可能被推到并发中的 B 会话前端。事件里只有 token 数不含内容，但仍是串台。

**修法**：缓冲按 session 分键。

---

### 【中等】分项 Token 指标用 Gauge，并发互相覆盖

`metrics.py:148-162` 把 system/history/previous_outputs/rag/tool_schema 五路占用写进 Prometheus Gauge。Gauge 是全局单值，并发请求互相覆盖，看板上是"最后写入者胜"，值失真。

**修法**：改 Histogram（带 bucket）或 Summary。

---

### 【中等】主力模型 Token 标定与注释自相矛盾

`token_counter.py:46-53`：

```python
_CALIBRATION = {
    "deepseek": (0.70, 0.30),      # ← ASCII 系数仍是 0.30
    "qwen": (0.70, 0.30),          # ← 同上
    "siliconflow": (0.70, 0.30),
    "ollama": (0.75, 0.33),
}
_CALIBRATION_DEFAULT = (0.75, 0.75)   # ← 默认已改成 0.75
```

而上面的注释明确写着："旧默认 0.33 对 ASCII/混合内容系统性低估 36-40%……新默认 0.75 不再出现低估"，并且强调"低估才会击穿真实窗口"。

也就是说：**被判为"系统性低估"的 0.33，反而是 deepseek/qwen 这几个主力 provider 现在的取值（0.30，更低）**。注释里的实测依据只有豆包一个样本（`doubao-seed-2.0-mini`）。

**风险**：如果 deepseek/qwen 的 tokenizer 与豆包特性接近，那么预检会低估用量 → 以为没超 → 真实请求爆窗。如果差异确实很大（各家 tokenizer 对英文/数字效率不同），那需要在注释里标明依据，避免下一个人误判。

**建议**：对主力模型补一次真实 `usage` 回测（项目已有成熟做法：STOP D 用豆包真实 usage 回测）。这是唯一能消除歧义的办法。

## 三、为什么测试与评测全都发现不了

这是本次审查最值得记的一点：

| 防线 | 为什么绕过 | 位置 |
|---|---|---|
| 单元测试 | L5 触发链路的用例全部是**同步 test 函数**。无事件循环 → `asyncio.get_running_loop()` 抛 RuntimeError → 走同步分支 → 永远进不了 `_L5_TASKS` 那一行 | `tests/context_budget/test_auto_compact.py:298-425` |
| 真实组件评测 | `run_l5_direct()` 本身是**同步函数**，`prepare_llm_context` 在无循环上下文调用，同样绕过 | `evaluation/run_context_budget_eval.py:338,398` |
| 直接单测的 async 入口 | 只测了 `auto_compact.run_auto_compact_async`（独立函数，不含该缺陷） | `tests/context_budget/test_pinned_context_wiring.py:192` |

**结论**：`PHASE5_PASS` 是真实的，但它验证的是"同步路径正确"，没有验证"线上异步路径有效"。

**补测建议**：加一条 `async def test_...`，在事件循环内构造 `ratio ≥ 0.90` 的输入调用 `prepare_llm_context`，断言不抛异常且确实发生了压缩。

## 四、做得好的地方

- **只动 active context**：L1~L5 全程不删改 `chat_messages` 任何原始行，前端历史永远完整可查
- **角色安全**：用户历史只进 AIMessage 的 `<historical_context>` 数据块 + 一条固定的 policy SystemMessage，从结构上堵住"摘要被当成系统指令"的提权路径
- **摘要后确定性校验**：ProtectedFacts 遗漏就追加补丁，零额外 LLM 调用
- **降级一致性**：每层都是软失败，任何一层出问题都不阻断聊天
- **指标低基数纪律**：Prometheus label 里不带 session_id/user_id，只进日志与 Trace

---

## 五、需要质疑的设计（不只是 bug）

1. **阈值贴得太紧**。窗口只有 8192，L2 历史封顶 2048，而 L4 在 0.80 触发、L5 在 0.90。层与层之间几乎没有缓冲——**一道防线失效就没有第二道**（本次 bug 正是这样被掩盖的）。

2. **"最后一道防线"用 fire-and-forget 是自相矛盾的**。L5 的定位是兜底，但它被异步化之后变成"本轮不生效、下一轮才生效"。**真正需要它的那一轮，它不在**。这个设计取舍需要重新讨论：要么接受"兜底只在下一轮"，要么把它做成同步且带硬超时。

3. **兜底异常范围过宽**。`_preflight_context` 的 `except Exception` 把"实现 bug"和"预期内降级"混在一起处理，于是 bug 变成了静默失效。建议至少把 `NameError/AttributeError` 这类"代码错误"单独抛出或记 error 级日志——它们不该被当成"降级"。

4. **两层 L2 名字相同、实现不同**（`memory/service.py` 与 `manager.py`），排查时极易误判。
