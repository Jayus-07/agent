### 任务卡 ①｜行程单花费口径不同源（小 bug，建议最先做）

- **现象**（评测 T-E02 实测）：行程单头部「预估总花费 ¥210」，notes 里「按常见消费水平估算的总额 ¥220」——同一次出单两个数。
- **机制**（已复核）：`backend/travel/reporter.py:145` 渲染头部花费用 `itinerary.cost.total`（**最终行程**的值）；`backend/travel/experts/budget.py:32` 的估算 note 也是用 `itinerary.cost.total` 拼文本，但它是 **budget expert 执行时刻的快照**——之后 repair 重排删了点，行程总额变了，note 文本不会跟随。
- **建议落点**：二选一——
  a) reporter 出单时**重写/剔除**这笔「无预算场景估算」note，改用最终 `cost.total` 渲染（推荐：事实产生处口径唯一）；

- **验收**：无预算低候选场景（参考评测 T-E02 输入「9月21日福州一日游，1个人」）两个数字一致；travel 全量回归绿；评测 22/22 不动。

### 任务卡 ③｜API 层 interrupt resume 端点（需要前端配合排期）

- **现状**：Phase 6 用户决策中断在域图与编排适配器层已闭环，但 API 层无通道——`backend/app/api/routes/` **没有 travel 专用路由**（旅游走主对话链路 chat → 编排 → `backend/orchestration/graph/travel_graph_node.py`）。
- **适配器已就绪的钩子**：`travel_graph_node` 已支持两段式——第一段中断时把 `pending_decision`（结构化 items + options）放进 `travel_context`；第二段上游在 `travel_context.resume_decision` 塞用户决策（dict，如 `{"action":"keep"}` / `{"drop":["福建博物院"]}`）即走 `Command(resume=...)` 恢复（同 conversation_id = thread_id）。
- **两个落点选项**：
  a) **专用端点**：新建 `routes/travel.py`（POST 决策：conversation_id + decision → 组装带 `resume_decision` 的主图状态 → 走 travel_graph_node）。优点：契约清晰；缺点：前端要对接新端点。
  b) **对话通道内解析**：用户回「保留」/「移除 XX」时，编排层检测 `travel_context.pending_decision` 存在 → 把自然语言决策归一化为 `resume_decision`（可复用 Phase 3 `_normalize_decision` 的形态）。优点：零前端改动；缺点：多一层意图识别。
- **验收**：开关 `TRAVEL_USER_DECISION_INTERRUPT=true` 下，从 API 发「9月21日福州一日游，1个人，必去福建博物院」→ 收到待决项 → 提交决策 → 收到最终行程单（keep→degraded / drop→ready）；`backend/tests/travel/test_user_decision.py` 的 TestAdapter 用例是行为基准。
- **预估量**：一天内（不含前端联调）。

### 任务卡 ⑤｜全量实时 POI（数据源工程，成本最高，最后做）

- **现状**：POI 主力是种子数据（`source=seed:local`）；用户点名但种子没有的地点走腾讯实时解析补全（`backend/tools/travel/live_map.py` 的 `resolve_place`，`source=tencent:lbs`）。补全 POI 的营业时间/票价是**默认占位值**（`live_map.py:297-298`：`suggested_minutes=120`、`ticket_cny=0.0`），行程单会如实标注来源与占位（用户可分辨，不伪装成核实事实——溯源纪律见 `live_map.py` 模块 docstring）。
- **为什么难**：腾讯 POI 检索不返回可靠营业时间/票价（实测确认过）；需要升级数据源（如商户平台 API）+ 采集缓存 + 时段规范化 + 票价口径对齐，属数据工程。
- **建议**：先做数据源调研（哪些源能给结构化营业时间），再决定接入方案；期间维持「seed 为主 + 点名补全 + 如实标注」现状即可，不阻塞任何功能。
- **验收（若做）**：补全 POI 的 open_time/close_time/ticket_cny 来自真实数据源且有 observed_at 时效标记（Phase 1 的 facts 机制已就位：`backend/providers/travel/facts.py`）。

## 3. 必读纪律（接手会话开工前过一遍）

1. **多会话仓库**：动手前 `git status` + `git log` 确认工作区与提交状态；已有实施只做增量不重写；**提交一律路径限定**（`git commit -- <paths>`；untracked 文件先 `git add` 再 pathspec commit）。
2. **pytest 约定**：`PYTHONPATH=. .venv/Scripts/python.exe -m pytest backend/tests/travel ... --no-cov --basetemp=tmp/pytest-tmp`（必须 `--no-cov`，否则全局覆盖率阈值必 FAIL）。
3. **评测基线保护**：`datasets/travel/` 当前 22/22 是回归门禁——扩量（任务卡 ②）可以加条目，但既有 22 条的 expected 不得悄悄改；改了必须说明原因。
4. **interrupt 语义**（改 validator/编排时必看）：LangGraph interrupt resume 后**节点从头重跑**，interrupt() 之前的计算必须确定性；无持久化（checkpointer disabled）时即使开关开也回退软处理；非法决策保守按 keep。
5. **LangGraph 状态语义**：未写入的键不出现在 final state（`get` 返回 None 而非默认值）；断言「键恒空」要接受缺席或空 list 两种形态。
6. **同文件编辑严格串行 + 回读**（多会话下并行 Edit 会静默丢改动，实测踩过多次）。
7. **并发跑全量 pytest 期间不改 backend/ 代码**（一次约 20 分钟，改了结果不可信）；其他会话可能改 sql/rag/customer_service 域，lastfailed 出现非 travel 域失败属正常，复跑即绿。
8. **报告纪律**：结论里写「实测」的每一处都要能指到 file:line；不确定的机制先查代码，宁可写「待核实」。
