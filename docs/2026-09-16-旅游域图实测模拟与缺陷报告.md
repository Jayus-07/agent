## 一、五场景实测结果

### A. 完整需求 → 一轮出单 ✅

> 用户：我想11月8号去杭州玩3天，2个人，预算5000元，喜欢自然和摄影，必去西湖和灵隐寺

- 抽取结果：destination=杭州 / days=3 / party=2 / budget=5000 / start=2026-11-08 / 偏好[自然,摄影] / 必去[灵隐寺,西湖] —— **全部命中，0 误差**
- 6 步走完（poi→transit→budget→risk→validate→report），0 error 0 warning，置信度 **0.80**
- 行程单：3 天详细时刻表（含午餐占时、逐段通勤时长/距离/费用）、费用拆分、需确认项、数据来源
- 总花费 ¥2275 / 预算 ¥5000；未排入候选如实列出（宋城、龙井村、钱江新城城市阳台）并给出「改紧凑节奏」的可操作建议
- **通勤数据确认为腾讯实时**：行程单「乘车 13 分钟（4.79km）」「18 分钟（7.17km）」「10 分钟（5.21km）」与直接调用 `live_leg` 的结果逐段一致（本地估算会给出约 1.86km，明显不同）

### B. 必填槽位缺失 → 追问而非乱猜 ✅

> 用户：帮我安排一下行程

1 步结束（slot_filler → supervisor → reporter），输出：

```

`expert_history` 为空 —— 没有触发任何专家，**没有编造行程**。

### C-1. 含「避开」约束 → 约束生效 ✅

> 用户：厦门玩2天，2个人，喜欢人文和摄影，必去鼓浪屿，不要去中山路步行街

- `avoid=['中山路步行街']` 正确抽取，行程 2 天 5 个点位中**中山路确实未出现**
- 必去鼓浪屿独占第 1 天（300 分钟）；总花费 ¥1329；置信度 0.75
- 未提供预算 → 明确写出「本次未做预算校验」，不假装已把关

### C-2. 同会话改需求 → ❌ **GraphRecursionError（P0 缺陷）**

> 用户：第二天想轻松点，节奏改成轻松（同一 thread_id，第二轮）

```
langgraph.errors.GraphRecursionError: Recursion limit of 25 reached

用户视角：适配器 `travel_graph_node` 捕获异常 → 返回兜底话术「抱歉，旅游规划服务暂时不可用」。**行程彻底丢失**，且原因不可见。

### D. 低预算 → 校验失败 + 自动修复 + 如实披露 ✅（最有说服力的一条）

> 用户：杭州玩2天，2个人，预算300元，喜欢自然

完整走完 `BUDGET_OVER → repair(第1轮) → validate → repair(第2轮) → validate → report`，共 10 步：

- 自动移除 2 项（西溪湿地 ¥80、灵隐寺 ¥75，均按「票价最高的非必去项」策略）
- 2 天被压缩为 1 天，总花费压到 ¥316，**仍超预算 ¥16**
- 未硬凑：行程单里「需要你确认」首条即「预估总花费 ¥316 超出预算 ¥300（超 ¥16）」，并附「行程自动调整说明」写明移除了哪两项、理由是什么
- 置信度由 0.80 降到 **0.50（中）**，修复轮数 2/2 达上限后如实披露

### E. 点名地点本地无数据 → 如实告知 ✅（行为正确，非缺陷）

> 用户：厦门玩3天，2个人，必去平潭岛，喜欢自然

输出「以下必去地点在当前候选数据中未匹配到，未能排入：平潭岛」+ `MUST_GO_MISSING` warning，行程照常给出，置信度 0.70。

**对照实验确认这是正确行为**：

| 调用 | 结果 |
|---|---|
| `place_search('平潭岛', region='厦门')` | hits=**0**（0.99s） |
| `place_search('平潭岛', region='福州')` | hits=3，首条「平潭岛」25.50,119.81 |

腾讯检索按 `boundary=region(厦门,0)` 限定 → 平潭岛属福州，搜不到。即便搜到，它距厦门中心约 190km，也会被 `_MAX_RESOLVE_DISTANCE_KM=120` 安全半径丢弃。两条防线口径一致。

> 体验改进建议（非缺陷）：此时可提示「平潭岛属福州，是否改为以福州为目的地」，比单纯说「未匹配到」更有用。

## 二、缺陷

### P0 · `supervisor ↔ repair` 死循环，用户拿不到行程

**触发条件**：校验失败，但违规项**全部不可自动修复** —— 最典型的就是「用户点名必去的地点本身超节奏上限」（必去项被 `_droppable()` 排除，`drop` 集为空 → `repair_itinerary` 返回 `None`）。

**最小复现**（100% 稳定）：

> 厦门玩2天，1个人，必去鼓浪屿，节奏轻松，喜欢人文和摄影

（鼓浪屿建议 300 分钟 > 轻松档 240 分钟上限，且它是必去项 → 删不掉）

日志轨迹：

```
step=5   validate  → 校验完成 errors=1 codes=['PACE_TOO_INTENSE']
step=6   repair    → 存在 1 项约束违反，执行第 1 轮局部修复
step=7   repair    → 存在 1 项约束违反，执行第 1 轮局部修复   ← 轮数原地踏步
step=8..12  同上
EXC: GraphRecursionError
```

**根因**：`backend/travel/repair.py:331-339` 的 `repaired is None` 分支

```python
    if repaired is None:
        return {
            "stage": "report",
            "repair_log": log,
            "notes": [...],
        }
```

该分支既不推进 `repair_rounds`、也不清除 `validation`。而 `supervisor.decide()`（`supervisor.py:136-147`）判定分支的依据正是

```python
    repair_rounds = state.get("repair_rounds", 0)
    if repair_rounds >= T.TRAVEL_MAX_REPAIR_ROUNDS:   # 永远为 0 >= 2 → False
        return TravelDecision(TravelStage.REPORT, ...)
    return TravelDecision(TravelStage.REPAIR, f"...执行第 {repair_rounds + 1} 轮局部修复")
```

→ 每轮都判 REPAIR，永远同一个 `stage="report"` 的返回值被覆盖，形成死循环。

对比：相邻的「轮数已达上限」分支（`repair.py:317-326`）是安全的，因为 state 里的 `repair_rounds` 已被上一轮 repair 写入。**只有「无法修复」这条路径漏了状态推进。**

**验证过的修法**（容器内 monkeypatch 实测，不改仓库）：

```python
if out.get("stage") == "report" and "repair_rounds" not in out:
    out["repair_rounds"] = 2
```

结果：**step=7 即收敛**，reason 变为「存在 1 项违反且修复轮数已达上限 2，如实披露」，正常输出行程单（保留鼓浪屿，第 1 天 300 分钟超限的事实如实呈现）。

建议 patch（2 行）：

```python
# repair.py —— 「无法修复」分支
    if repaired is None:
        return {
            "stage": "report",
            "repair_rounds": max_rounds,      # ← 新增：推进到上限，让 supervisor 下一轮判 REPORT
            "repair_log": log,
            "notes": [...],
        }
```

同一文件 `repair.py:317-326` 的「轮数用尽」分支建议也补上 `"repair_rounds": max_rounds`，让两条失败路径的状态语义一致（当前安全但依赖上游写入，属隐式契约）。

### P1 · `TRAVEL_MAX_STEPS=12` 在默认 `recursion_limit=25` 下轮不到生效

图步数与业务步数是 2:1 —— 每轮循环消耗 `supervisor + 节点` 两个图步。第 13 次进入 supervisor 时业务 `step_count` 才达到 12 从而触发「强制收尾」，此时已经烧掉 24 个图步，加上 reporter 需要 ≥26。默认 25 **刚好不够**，于是 recursion_limit 先炸，护栏形同虚设。

实测证明护栏逻辑本身是对的 —— 把 `recursion_limit` 提到 40（代码不改）后：

```
step=12  repair  → 存在 1 项约束违反，执行第 1 轮局部修复
step=13  report  → 达到步数上限 12，强制收尾     ← 护栏生效，正常出单
```

**建议**：`TRAVEL_GRAPH_RECURSION_LIMIT` 默认值改为 **30**（≥ 2×MAX_STEPS + 4 的安全余量），或在 `config/travel.py` 里加一条启动期断言把两者的关系钉死，避免以后单独调其中一个又踩坑。

### P2 · 观察项（非缺陷，供参考）

1. **腾讯路线偶发 read timeout**：预热阶段日志出现 `[TencentLBS] 网络错误: The read operation timed out ... (第 2/2 次)` → 该段回落本地估算。实测单段串行约 1s（6 段 6.2s），而 `prefetch_legs` 用 6 线程 + 4s 硬预算，抖动时必然有段来不及 → 这是**设计内的降级**，但会导致同一份行程单里混用真实数据与本地估算，而行程单只展示 `Poi.source`、不展示 `leg` 的来源，用户看不出通勤哪段是估算的。建议 `TransitLeg` 也带 `source` 并渲染。
2. **`place_search` 的 boundary 限定是双刃剑**：单城市限定避免了跨城错误点位，但用户说「厦门必去平潭岛」这类跨城需求时只能回「未匹配到」。P1 接入真实供给后建议做一次「改目的地？」的澄清。

## 三、结论

旅游域的**正常路径质量很高**：抽取 0 误差、约束真实生效、跨轮状态可改、失败时如实披露且置信度随之下调 —— D 场景（预算压到 300）是这套设计价值的最好证明。

但存在一条**必炸且很容易被用户触发**的路径（P0）：只要「必去地点本身超节奏上限」，用户就拿不到行程。修复只需 1 行状态推进，且已在容器内验证收敛。

落地上线前建议连同 P1 的 `recursion_limit` 一起修掉，并补一条针对「必去项不可删」的回归用例。

## 四、修复实施记录（2026-09-16 01:0x，已改码 / **未验证 / 未提交**）

上文「修法」是定位阶段的最小方案。实做时改了做法，理由如下，**其他会话请以本节为准**。

### 4.1 P0：改用显式状态标记，而不是挪用 `repair_rounds`

| | 定位阶段建议 | 实际实施 |
|---|---|---|
| 做法 | `repair.py` 无法修复分支补 `"repair_rounds": max_rounds` | 新增状态字段 `repair_stalled`，`decide()` 增加一个判定分支 |
| 改动量 | 1 行 | 4 个生产文件（`repair.py` / `graph_state.py` / `supervisor.py` / `config/travel.py`）+ 2 个测试文件，共 135 插入 / 7 删除 |
| 为什么换 | `repair_rounds` 是真实计数器，被 `travel_context`、trace metadata 与评估统计消费。把它当终止信号会让「1 轮都没修」记成「修满 2 轮」，污染「真实违反率」口径；且 supervisor 的 reason 会写成「修复轮数已达上限 2」，与事实（无自动修复手段）不符 —— 本项目的原则是披露口径必须为真 | |

具体改动：

- `backend/travel/repair.py`：`repaired is None` 分支写入 `repair_stalled: True`；成功分支写入 `repair_stalled: False`。
  **成功分支必须显式解除**：跨轮（checkpointer 开启）时该键会随状态延续，不解除会让后续轮次被误判为终态。
- `backend/travel/graph_state.py`：`TravelGraphState` 声明 `repair_stalled: bool`（LangGraph 只保留已声明的 channel，未声明会被丢弃）；`planning_reset()` 里置 `False`（需求变化重排时必须一并清掉）。
- `backend/travel/supervisor.py`：`decide()` 在「校验通过」之后、`repair_rounds` 判定**之前**判定 `repair_stalled` →
  REPORT（`存在 N 项违反且无自动修复手段，如实披露`）。顺序很关键：本场景轮数恒为 0，按轮数判会再次误判回 REPAIR。
  docstring 的终止护栏由 3 条扩为 4 条，并补了一条通则：
  **supervisor 只认状态里的事实，不认上游节点声明的 `stage`** —— 本次死循环的本质就是 repair 写了 `stage="report"` 却不落任何事实。
- `backend/config/travel.py`（P1）：`TRAVEL_GRAPH_RECURSION_LIMIT` 默认值改为由 `TRAVEL_MAX_STEPS` **派生**
  `max(25, TRAVEL_MAX_STEPS * 2 + 10)` = 34 —— 两个参数各自硬编码正是本次配错的原因。
  `.env` 未设置该键，故派生值在本机立即生效。
