## 1. 系统定位与总体架构

客服系统（CS Graph）是本电商 RAG + Multi-Agent 平台中的一个**独立 LangGraph 域图**，与主图通过「预过滤短路 + 适配器」方式接入：客服流量在主图 Router 三层路由之前被预过滤拦截，直接进入 9 节点的客服子图（Supervisor + 5 专家 + Reporter），不经过 Planner/Critique/Skill 体系。

```
用户（CSDrawer 抽屉 / 管理端工作台）
   │  POST /api/chat/stream (SSE)
   ▼
APISIX :9080（gateway-auth JWT 鉴权，唯一入口）
   ▼
FastAPI /chat/stream → GraphRunner（平台级 InputGuard → memory.start_session → graph.stream）
   ▼
主图 router_node → cs_prefilter（本文 §4）
   │  命中客服域（或显式转人工 / 人工接管期）→ route_mode="customer_service"
   ▼
cs_graph_node 适配器（State 转换，orchestration/graph/cs_graph_node.py:25）
   ▼
CS 子图（独立 StateGraph + 独立 checkpointer，thread_id=conversation_id）
  cs_state_loader → cs_pending_handler → cs_supervisor ⇄ 5 experts → cs_reporter → END
   ▼
回到主图 → SSE 帧流回前端；GraphRunner 收尾时 record_cs_turn 落库（runner.py:369,474）
```

主图接线方式：`customer_service/register.py:10` 自注册到 `domain_graph_registry`（由 `backend/domains/__init__.py` 触发 import），builder 自动布线，**不改 builder.py**。预过滤优先级：客服 > 旅游（`CLAUDE.md:28`）。

## 3. 端到端请求生命周期（一轮对话）

1. **前端发起**：CSDrawer → `streamChat` → `POST {API}/api/chat/stream`，body `{question, session_id, request_id}`（`frontend/src/api/chat.ts:44-55`）；中止走 `POST /api/chat/abort`。
2. **网关**：APISIX gateway-auth 验 JWT、注入身份头。
3. **Runner 门禁**：GraphRunner 平台级 InputGuard；对转人工类 CLARIFY 改写为 ALLOW 放行（BLOCK 不豁免），否则「转人工」话术进不了预过滤直通层（`runner.py:116-118`）。
4. **CS 预过滤**（`orchestration/graph/cs_prefilter.py:17`，判定顺序）：
   a. `CS_ENABLED` 关 → None（走主图）；
   b. **显式转人工直通**：正则命中 → 直接合成 `human_handoff` 路由结果（conf=1.0，零模型调用，`cs_prefilter.py:35-46,164-186`）；
   c. **人工接管期强制接管**：HandoffStore 存在 waiting_human/human_active → 一切消息强制转 handoff（`cs_prefilter.py:48-60,148-161`）；
   d. **DomainDetector**（embedding 语义检测，5min 缓存）判 `is_cs`，未命中 → None；
   e. **灰度放量**：白名单优先，否则 md5(session_id)%100 < `CS_ROLLOUT_PERCENT`（默认 100；md5 防进程重启分组漂移，`cs_prefilter.py:200-213`）；control 组打 trace 标签后走主图；
   f. 命中 → `CSRouter.route()`（§4）→ 组装 cs_context → **CS InputGuard**（BLOCK 直接以 final_answer 短路返回，`cs_prefilter.py:103-116`）→ 返回主图 state 更新。
5. **主图分派**：router_node 看 `route_mode="customer_service"` → `cs_graph_node` 适配器：`new_cs_graph_input()`（只放本轮输入）→ `get_cs_graph().invoke(config={recursion_limit: CS_GRAPH_RECURSION_LIMIT, thread_id: conversation_id})` → `build_cs_graph_result()` 映射回主图 state（`cs_graph_node.py:25-52,127-139`）。异常时安全网兜底文案，不炸主图（`cs_graph_node.py:112-124`）。
6. **CS 子图内部**（§5）。
7. **执行打标**：把 expert_final/visited、handoff_state、转人工 trigger 序列写进 trace tags/metadata，作为路由一致率与转人工率三桶分析的数据源（`cs_graph_node.py:55-92`）。
8. **持久化**：GraphRunner 收尾 `_persist_cs_turn_if_needed` → `conversation_store.record_cs_turn`（conversation_id 必须存在才落库；CS 轮次不落主图 memory，`runner.py:369-396,474-492`）。全链路 fire-and-forget，不阻塞响应。
9. **SSE 回包**：帧序 meta → status/log/delta → done/error；前端 done 时用 deltaText 终态写气泡，**不二次写库**（`useCSChat.ts:49-56`）。

## 4. 域内路由（CSRouter 门面，`router/cs_router.py`）

组合两级分类，`confidence = (conf_coarse + conf_fine) / 2`（`cs_router.py:67`）：

**粗分类 CSCoarseRouter**（输出 CSDomain，3 层 fallback，`coarse_router.py:52-73`）：
1. Rule：`CS_DOMAIN_KEYWORDS` 关键词计数，≥2 命中 → conf=min(count/3,1)，≥0.8 直接决定；
2. Vector：Chroma `cs_coarse_v1` 相似度（score=1/(1+distance) 域内取均值），≥0.85 决定、≥0.6 采纳；
3. 兜底：DomainDetector rule_hint（conf=0.5）或 UNKNOWN(0.0)。

**细分类 CSFineRouter**（输出 intent，`fine_router.py:70-89`）：
- KNOWLEDGE/COMPLAINT/HUMAN 域：规则关键词直接映射（≥1 命中，conf=min(count/2,1)，≥0.7 决定）；
- TRANSACTION/AFTER_SALES/ACCOUNT 域：向量 `cs_fine_v1`（≥0.6 采纳，只在同域 intent 内挑）；
- 兜底：域默认 intent（conf=0.3）。

**产物 CSRouteResult**：domain / intent / confidence / requires_auth / requires_action / risk_level / route_path / kb_ids / reason。route_path→cs_target→专家节点映射见 `graph_state.py:29-36`（单一事实源，预过滤/适配器/评测三方共用）：knowledge_query→cs_knowledge、business_query→cs_business_query、business_action→cs_business_action、complaint_flow→cs_complaint、human_handoff→cs_handoff、其余→cs_pending。

## 5. CS 子图（9 节点，Phase 5 拓扑）

```
START → cs_state_loader → cs_pending_handler
   ├─(有 pending 确认)→ 处理确认/取消/超时 → cs_reporter → END
   └─(无)→ cs_supervisor ──Command(goto)──→ 5 专家之一 → 回 cs_supervisor（循环）→ cs_reporter → END
```

### 5.1 cs_state_loader（`graph_builder.py:40-74`）
从 `state_transition.load_snapshot()` 加载会话状态快照（conversation_status / handling_mode / handoff_state / confirmation_state / pending_action），并**重置全部执行态字段**（expert_history 清空、loop 归零），防 checkpoint 残留。

### 5.2 cs_pending_handler（`pending_handler.py`）
处理"上一轮留了待确认动作"的场景：确认/取消/过期（TTL 900s，读时惰性判断 `confirmation.py:125-146`）→ 直接产回复进 reporter。

### 5.3 cs_supervisor — 三层决策引擎（`supervisor.py:104-204`）

| 层 | 规则 | 动作 |
|---|---|---|
| L1a | handoff 拦截：`should_intercept(handoff_state)`（requested/waiting/human_active 任一） | 强制转 handoff expert，is_finished |
| L1b | loop guard：`expert_loop_count ≥ CS_EXPERT_MAX_LOOPS(5)` | finish |
| L1c | confidence < 0.60 且无 expert 历史 | finish（低置信兜底） |
| L2a | confirmation pending | PENDING（等用户回复） |
| L2b | 同一 expert 连续执行 2 次 | finish（防死循环） |
| L3 | confidence < 0.60 且有历史 → LLM 决策（`CS_SUPERVISOR_LLM_ENABLED`，超时/无效输出返回 None 降级默认路由） | run_expert |
| 默认 | route_path→expert（`supervisor.py:54-69` 两张映射表，path 优先 domain 兜底） | run_expert |

另有**人工接入超时回退**：waiting_human/handoff_requested 超 `CS_HANDOFF_TIMEOUT_SECONDS(600s)` → 关闭转接、handoff_state 归 ai_active、写审计，本轮恢复正常路由（`supervisor.py:298-355`）。每次决策打 Prometheus 指标（layer/action，`supervisor.py:286-295`）。

### 5.4 五专家（`experts/`，均经 `run_expert_safely` 包装，异常→ExpertResult(failed)）

| 专家 | LLM? | 核心逻辑 |
|---|---|---|
| **knowledge** | 是（经 RAG） | `CSKnowledgeService.answer()` → RAGPipeline.ask（kb_ids 来自路由，主 kb 默认 `cs_faq`，`subject_type="customer"` 收权到客服知识库）→ 拿 `last_answer_meta.confidence` 做 **CSAnswerDecision 三档门控**：≥0.85 answer / ≥0.60 cautious（追加保留意见）/ 其余 refuse（引导转人工，`knowledge/answer_decision.py:26-58`）。证据取 top5 写入 evidence（`experts/knowledge.py:52-58`） |
| **query** | 复合问题时 | 先 `PermissionChecker.validate_user_identity`；规则预判复合诉求（命中 ≥2 服务域关键词）→ LLM 分解为 intent JSON 数组（超时/格式错回退单意图）；分发 order（直查 `"order".orders` 真实表）/ logistics（取最新订单号查摘要），Markdown 格式化输出（`experts/query.py:87-146,175-251`） |
| **action** | 否 | 双路径：有 pending → 处理确认/取消（关键词表 `CS_CONFIRM_KEYWORDS/CANCEL_KEYWORDS`，过期→EXPIRED 清 store）；无 pending → 构建 proposal（退款/退货/换货/地址/密码）存 confirmation store，按 **risk 分级**提示是否需人工审核，写审计（`experts/action.py:32-201`）。执行仍为 simulate，不实写业务 DB |
| **complaint** | 否 | 正则检测投诉→严重度→生成投诉工单（Phase 5 模拟写入），幂等标记 complaint_ticket_id 防重入（`service/complaint_service.py`、`reporter.py:184-186`） |
| **handoff** | 否 | 触发判定（显式正则/自动：连续 2 轮低置信 or 连续失败≥3）→ **幂等保护**：已在 waiting_human/human_active 时复用工单直接成功返回（防 supervisor 重复调度把非法转换炸成兜底文案，`experts/handoff.py:65-104`）→ 建工单 `HANDOFF-{8位hex}` → **立即推进 REQUESTED→WAITING_HUMAN**（2026-09-17 修复：此前无人执行这步，工单永久卡死、坐席认领 409）→ WS 广播 `conversation.waiting` → 写审计（`experts/handoff.py:106-176`） |

### 5.5 cs_reporter（`reporter.py`）
组装优先级：handoff 拦截固定话术 > pending 确认文案（proposal_text）> response_draft（+引用来源列表）> action_result 格式化 > **专家失败原因映射为可操作话术**（身份/权限/超时各有专门文案，不再用"正在处理中"占位，`reporter.py:64-92`）> 泛化总结。最终过 **OutputGuard** 安全审查（敏感信息脱敏等，`reporter.py:163-171`），并产出 cs_context 快照回传主图。

## 6. 关键横切机制

### 6.1 转人工状态机（`handoff.py`，纯函数）
5 状态：`AI_ACTIVE → HANDOFF_REQUESTED → WAITING_HUMAN → HUMAN_ACTIVE → CLOSED`（+REQUESTED→AI_ACTIVE 回退；WAITING/HUMAN 也可直接 CLOSED）。非法转换抛 `HandoffTransitionError`（`handoff.py:29-47,72-87`）。拦截集合 = REQUESTED/WAITING/HUMAN_ACTIVE（`handoff.py:51-55`）。转人工触发类型 6 种，按三桶归因分析：healthy_user（用户主动）/ healthy_escalation（业务升级/高危）/ capability_gap（AI 能力缺口，趋近 0 的目标桶，`handoff.py:130-146`）。

### 6.2 确认状态机（`confirmation.py` + `confirmation_store.py`）
pending → confirmed / cancelled / expired（TTL 900s、最多 3 次重试）。Store = 内存 dict L1 缓存 + DB 持久层，DB 失败降级 cache-only；坐席侧改库后 `invalidate()` 清 L1。

### 6.3 风险分级（`risk.py`）
LOW/MEDIUM/HIGH/CRITICAL 四级；`refund_execute/return_execute/order_cancel` 为 HIGH（需确认+审计）、`account_delete/bulk_refund` 为 CRITICAL（双重确认）、退款金额 ≥1000 元自动升 CRITICAL（`config/customer_service.py:34-52`）。

### 6.4 双重安全护栏
- **CS InputGuard**（`security/input_guard.py`）：注入（忽略指令/角色扮演/DAN）、SQL 注入、越权意图（查/改他人数据）、敏感信息输入（银行卡/身份证/密码）、系统探测；聚合规则 BLOCK > CLARIFY > ALLOW。
- **CS OutputGuard**（`security/output_guard.py`）：reporter 出口统一审查。
- **PermissionChecker**（`security/permission.py`）：query/action 专家强制身份校验，匿名用户触发可读的失败话术。

### 6.5 演示沙盒（`service/demo_mode.py`）
`CS_DEMO_MODE=true` 时把登录用户映射为 `CS_DEMO_CUSTOMER_ID`，数据来自 `sql/seeds/demo_sandbox.sql`（`DEMO-` 前缀订单）；仅在 Service 查询收口处生效，鉴权仍走真实身份。前端 `NEXT_PUBLIC_CS_DEMO_MODE` 控制快捷提问换成剧本问法 + 演示横幅。

### 6.6 Java 双轨（历史兼容）
`CS_ADMIN_SOURCE=local|java`、`CS_WRITE_SOURCE` 控制读/写数据源切换（`cs_admin.py:20-22`、`config/messaging.py:40-45`）；java 模式下消息写权代理到 Java 客服系统 `POST /internal/messages`（`conversation_store.py`）。

## 9. 前端实现

**用户侧**（frontend/src）：
- 入口：`/agent` 页 ChatHeader 按钮 + 全局导航「智能客服」→ `/agent?cs=1`；右侧滑出抽屉 440px（窄屏全宽），URL 直达自动滑出（`app/agent/page.tsx:10-31`、`components/cs/CSDrawer.tsx:80-94`）。
- 发消息：`useCSChat.startStream` 本地先加 user+空 assistant 气泡 → SSE 消费（status 事件更新节点时间线/意图，error 写文案，done 终态写气泡）；节点中文映射 `CS_NODE_LABELS`（`components/cs/constants.ts:1-9`）。
- 转人工同步：抽屉打开期间每 2s 轮询 `GET messages?since_id`，坐席消息→「人工客服」气泡、handoff_state→CSHandoffCard（requested/waiting/active/closed 文案），按 message_id 幂等去重（`hooks/useCSHandoffSync.ts`）。
- 状态栏 CSStatusBar：等待人工（橙）/人工已接入（绿）/「正在XX…」/「已识别意图：X」，空闲隐藏。
- 其他：CSTimeline 节点时间线、CSSatisfactionCard 满意度卡（最后一条为人工/AI 时显示）、CSWelcome（含演示模式横幅）、历史恢复 `GET /my?limit=10`（401 静默跳过）。
- 状态管理：zustand 纯内存（sessions/currentStatus/deltaText/confirmationState/handoffState/csTimeline 等，`store/csChat.ts:25-38`），刷新即失，历史靠 hydrateFromServer。

## 10. 用户操作流程（端到端剧本）

**AI 自助**：用户打开「智能客服」抽屉 →（可选点快捷提问）输入问题 → SSE 流式回复（带节点时间线：知识检索/业务查询/…）→ 知识问答附「参考来源」；查询订单/物流直出 Markdown 卡片。

**写操作确认**：用户提"退款" → action 专家生成 proposal（含风险提示）→ supervisor 置 PENDING → 回复确认文案 → 用户回「确认/取消」（或超时 900s 过期）→ 确认后 simulate 执行并出审计。

**转人工**：
1. 用户说「转人工」（或连续低置信/连续失败自动触发）→ 预过滤直通 → handoff 专家建工单 `HANDOFF-XXXX`，状态 waiting_human，WS 推给在线坐席；
2. 用户侧：状态栏转橙「等待人工接入」，后续**所有消息**被预过滤强制接管转达人工（不再漏进主图）；
3. 坐席在工作台 `claim` → human_active，状态栏转绿「人工已接入」，坐席发言 2s 内经轮询到达用户气泡；
4. 任何一方关闭 → closed；若 600s 无人接入 → supervisor 超时回退 ai_active，恢复 AI 服务并写审计。

**管理端**：坐席登录 frontend-admin → 工作台看实时队列（WS 推送）→ 认领/回复/关闭 → stats 页看满意度、意图分布、转人工率三桶归因。

## 11. 当前实现状态与已知问题（给优化 agent 的抓手）

**配置默认值**（`config/customer_service.py`）：CS_ENABLED=false、ROLLOUT_PERCENT=100、CHECKPOINTER_ENABLED=false、CONFIRMATION_TTL=900s、MAX_RETRIES=3、HANDOFF_TIMEOUT=600s、LOW_CONF=0.4、CONSEC_FAIL=3、ANSWER/CAUTIOUS=0.85/0.60、MAX_LOOPS=5、CRITICAL_REFUND=1000。

**已知缺口 / 待优化**：
1. **CSConfirmCard 未接线**：前端确认卡组件已写好（`CSConfirmCard.tsx`）但全库无挂载点 —— 写操作确认目前只能靠文本回复「确认/取消」，后端状态机已就绪、前端 UI 断链。
2. **写操作全是 simulate**：refund/after_sales 只做资格检查+proposal+模拟执行，不实写业务 DB；complaint 工单同样模拟写入。
3. ** Supervisor LLM 兜底 V1 未实装**：粗分类 LLM 层注释"V1 降级为 UNKNOWN"（`coarse_router.py:6`）；supervisor L3 依赖 `CS_SUPERVISOR_LLM_ENABLED` 开启。
4. **物流查询用最新订单兜底**：无指定 order_id 时取用户最新订单（`experts/query.py:202-211`），多订单场景可能答非所问；未接真实物流 API（基于 orders.status 摘要）。
5. **handoff/confirmation store 的 TTL 靠读时惰性判断 + 超时回退**，无后台清理任务；conversation 侧无自动过期。
6. **会话消息轮询 2s**（用户侧）——管理端已升级 WS，用户侧仍是轮询。
7. **路由索引种子硬编码**：coarse/fine Chroma 种子在 `router/seeds.py`，域/意图扩展需改代码重建索引；意图 profile 与 kb 映射在 `router/intents.py`。
8. **满意度评分入口**：`POST /{id}/rating` 管理端可调，用户侧 CSSatisfactionCard 与它的完整闭环待核实。
9. **Embedding 域检测延迟**：云端 embedding 1.0~3.4s/次（已有 5min query 缓存），冷启动首问延迟明显 —— 可考虑本地小模型或缓存预热。
10. **CS 域图与主图 trace 双轨**：CS 轮次不落主图 memory（`runner.py:392-396`），跨域会话（客服↔主图）上下文不互通。

**验证入口**：客服相关测试集中在 `backend/tests/`（test_registry_consistency / layer_consistency 为全局守护）；跑局部测试必须加 `--no-cov`（pytest.ini 挂死 cov-fail-under=55）。改动后建议跑路由一致率评测（tags.cs_target ↔ tags.cs_expert_final，映射源 `graph_state.py:29-36`）。
