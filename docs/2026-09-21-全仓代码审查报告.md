## 🔴 严重（7 项）

### 1. 行级安全：自连接绕过 — `backend/sql/row_security.py` `inject_row_filter`（L66-93）
`real_to_alias[matched_key] = alias` 按「表」覆盖写、`referenced_tables` 是 set：`FROM order.orders o1 JOIN order.orders o2` 时同一受保护表只注入**最后一个别名**的过滤条件，另一别名完全裸奔 → 跨租户/跨客户拉全量。触发条件：`SQL_ROW_SECURITY_ENABLED=true` + LLM 生成自连接。
**修复**：遍历 `find_all(exp.Table)` 按 (表, 别名) 逐引用注入条件，不得按表去重。

### 2. 行级安全：条件注入进错误作用域 — `backend/sql/row_security.py` L153
`stmt.find(exp.Where)` 全树 BFS：外层 SELECT 无 WHERE、子查询有 WHERE 时，条件注入到**内层**。相关子查询可引用外层别名 → SQL 合法但外层零过滤，如 `SELECT (SELECT 1 FROM x WHERE x.id=o.id) FROM order.orders o` 返回所有客户订单。
**修复**：改用 `stmt.args.get("where")` 定位顶层 Where（为 None 时走 `stmt.where(...)`）。

### 3. 审批单跨用户/跨租户复用 — `backend/security/tool_approval.py` `_fingerprint`（L317-322）+ `consume_approved`
指纹 = sha256(tool|action|detail)，不含 user_id/tenant；PG 版 consume 的 WHERE 也不核对身份。用户 A 被批准的 `send_email(to=x)`，用户 B 用相同参数即可消耗该审批单并执行副作用。
**修复**：指纹掺入 tenant_id+user_id，或 consume 加 `AND user_id = %s`（两条都做最稳）。

### 4. 客服 dispatch：超时不计入自动置忙（43fe77e 漏接）— `backend/customer_service/dispatch/reaper.py` `_release_offer`（L142-193）
commit 声称「拒单/超时达阈值 → 置忙」，但 `record_agent_reject` 仅在 `offers.py:305`（主动拒单）被调用；reaper 超时回收路径零调用（L28 的 `agent_busy` 是死导入）。坐席最常见的不响应形态就是超时 → auto-busy 对此永不生效。
**修复**：`_release_offer` 中对 `released_agents` 逐个 `await agent_busy.record_agent_reject(...)`（fail-open，可放事务内）。

### 5. Celery 重投导致任务重复执行 — `backend/orchestration/checkpoint/task_executor.py`（L121-141）+ `backend/tasks/agent_tasks.py`
acks_late + Redis visibility_timeout（默认 1h）内未 ack 会重投第二个 worker；此时若 `record.status != RUNNING` 判定「不恢复」→ 走全新执行分支，与第一个 worker 并发跑同一 thread_id：LLM 重复烧钱、step_results 互踩。
**修复**：执行前原子抢租约 `UPDATE tasks SET status='RUNNING' WHERE id=%s AND status<>'RUNNING'`，rowcount=0 则退出；并确保 visibility_timeout > 最长任务时长。

### 6. 熔断器 HALF_OPEN 探测风暴 — `backend/infra/circuit_breaker.py` `_check_state`（L139-140）
HALF_OPEN 直接 `return` 放行，注释「试探 1 次」与实现不符：OPEN 30s 到期瞬间所有并发请求同时穿透打到刚故障的上游（历史 LLM 402 争抢场景的放大器）。
**修复**：进入 HALF_OPEN 时置原子探测标志，仅首个调用放行，其余抛 `CircuitBreakerOpenError`。

### 7. 前端流式状态无请求归属（两栈同病）— `frontend/src/store/chat.ts:256`、`store/csChat.ts:238-266`、`hooks/useCSChat.ts:57-59`、`hooks/useSSE.ts:124-127`
- `addStreamEvent` 无条件归约：`isCurrentSession` 只保护了 thinking/todo/usage，**deltaText/currentStatus/nodeLabels 不受保护**；`csChat.addStreamEvent` 的 `sessionId` 形参从未使用 → 切换会话不 abort 旧流时内容互串。
- `useSSE`/`useCSChat` 的 finally **无条件** `setLoading(false); setCurrentRequestId(null)`：stop A 后立即发 B，A 的 AbortError 异步到达清掉 B 的状态 → B 的「停止生成」发不出（后端跑完整轮烧 token）、loading 误消失。
**修复**：store 记 `activeRequestId`，不匹配的 SSE 事件直接丢弃；finally 改为闭包比对 `if (store.currentRequestId === requestId)` 才清态。
