# 企业 RAG 标准化改造

## 目标

将现有 RAG 摄取与检索链路按用户给定的企业长期使用要求补齐：支持多格式解析、统一结构树、结构优先 Parent/Leaf 切分、分层元数据、可追溯质量门禁和安全发布。

## 范围

1. 检查并扩展统一 AST/结构归一化与原文定位契约。
2. 补齐 HTML、PPTX、JSON、XML 等格式的解析器，并贯通上传 MIME/扩展名白名单。
3. 将结构路由扩展至混合/嵌套内容，保留 FAQ、合同、表格和普通文档语义边界。
4. 补齐 Document / Section / Chunk / Index 元数据和 `content`、`embedding_text`、`search_text` 的责任边界。
5. 强化解析、表格、OCR、覆盖率、引用、权限与发布质量门禁；保留候选 generation 原子发布及现有授权事实源。
6. 补充格式矩阵、结构/溯源、索引文本、质量拒绝和授权边界的定向回归。
7. 按仓库要求重建受影响本机服务并确认健康状态。
8. 修复阻断本机重建的既有迁移目标重复登记，确保迁移在权威业务库执行。

## 不在范围

- 不改变现有业务入口、租户/权限事实源和发布状态机语义。
- 不默认引入外部付费解析服务。
- 不运行全量 pytest、真实 LLM 评测或共享数据库回归，除非定向证据显示必要。

## 验收

- 已登记格式均可解析为统一 AST；有损、超限或失败必须显式标记并阻止不完整版本发布。
- 节点/Chunk 能关联章节路径和可用源定位；FAQ 不拆问答，表格保留表头语义和行定位，混合文档局部路由。
- 正文、向量文本和关键词检索文本边界明确；权限/审核/版本字段仍由可信服务端状态提供。
- 质量门禁覆盖解析完整度、切分覆盖、Parent/Leaf 关系、引用定位和授权过滤。
- 定向 T0/T1/T2 验证通过；受影响服务 rebuild 后健康检查通过。未执行项明确标记。

## 停止条件

完成上述验收，交付 Diff、HEAD、测试与服务健康证据、未解决风险；不提交、不合并，等待用户明确后续 Git 操作。
