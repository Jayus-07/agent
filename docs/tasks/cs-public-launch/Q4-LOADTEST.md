# Q4 客服容量压测报告（2026-11-03）

> 结论先行：**只读链路在网关限流线内（≤8 RPS/用户）容量健康**——持续 8 RPS×180s 共 1441 请求 100% 成功，p50=42ms / p95=116ms / p99=241ms，无积压（发射=完成 8.0 rps）。网关限流桶（600 次/分/用户）行为与配置一致，25 RPS 时超额请求被 429 拒绝（网关层，无后端消耗）。**写路径/多坐席状态流转/WS 长连接场景未实测**（见「未覆盖与原因」），本报告不宣称这些场景的容量结论。

## 一、脚本修正（cs_dispatch_loadtest.py）

HANDOFF §7 判断属实，旧脚本不能证明目标 RPS 或错误率。修正项（均有单测）：

| 缺陷 | 修正 |
|---|---|
| 持续负载是串行请求（实际速率=1/延迟，20 RPS 目标形同虚设） | open-loop 定时发射（`run_sustained`），报告实际发射/完成速率 |
| 异常耗时与成功混在同一延迟列表 | 分位数只统计 2xx；错误按 status/异常类型独立计数分布 |
| 无错误率、无状态分布 | `total/success/success_ratio/errors` 结构化输出 |
| P95 索引小样本越界（`int(n*0.95)-1`） | ceil 索引 + 边界钳制 |
| 预检只挡 5xx，401/403 与限流冲突不区分 | 预检按 401/403/429/5xx 分类归因后中止 |
| 不支持认证 | `--header` 可重复注入（本链路需 JWT + X-API-Key 双凭据） |
| 默认路径 `/cs/conversations/stats` 网关 404（路由不存在） | 默认改 `/api/cs/customer-context`（真实只读端点，覆盖 gateway-auth+应用身份+DB 读） |

定向单测：`backend/tests/scripts/test_cs_dispatch_loadtest.py` 4 passed（错误不污染分位数、小样本不越界、open-loop 发射速率接近目标且远快于串行）。

## 二、实测数据（共享栈 APISIX :9080 → app → PG/business-mock）

测试身份：user 279（agent 角色 JWT + 会话闸键，短 TTL 签发，测后已清理）。时间 2026-11-02 20:41–20:46 UTC。原始 JSON：`docs/reports/cs-dispatch-loadtest-20261102T204138/204212/204537/204539.json`（随分支入库，SHA256 前 16 见 PROGRESS）。

| 场景 | 发射 | 成功 | 错误 | p50 | p95 | p99 | max |
|---|---|---:|---:|---:|---:|---:|---:|
| 突发 50 并发 | 50 | 50 | 0 | 8.53s | 9.36s | 9.44s | 9.44s |
| 突发 20 并发（随后） | 20 | 20 | 0 | 0.56s | 0.81s | 0.82s | 0.82s |
| 持续 8 RPS × 180s | 1441 | 1441 | 0 | **42ms** | **116ms** | 241ms | 405ms |
| 限流边界 25 RPS × 30s | 751 | 589 (78.4%) | 162×429 | 2.08s | 2.51s | 2.84s | 2.90s |

### 解读

1. **稳态读容量**：8 RPS（限流线 10 RPS 内）下 p95=116ms、零错误、零积压。按 600 次/分/用户的反滥用基线，单用户持续读流量上限就是 10 RPS——这是网关的**设计容量边界**，不是瓶颈。多用户并发时按 X-User-Id 分桶，单实例聚合容量受 4C8G 档位 DB 连接池约束（见下）。
2. **突发行为**：50 并发突发全部成功但 p50 恶化到 8.5s（请求排队）；随后 20 并发 p50 回落到 0.56s。突发排队未导致失败或超时（TIMEOUT 15s 内全部完成），说明 DB/上游池在排队而非拒绝——**可挂账观察项**：连接池峰值行为值得在隔离栈用 100/200 并发复测（对共享栈不执行该强度）。
3. **限流器行为与配置一致**：600/分桶在 25 RPS 下约 24s 后耗尽，超额 429 拒绝在网关层（延迟 ~0ms 级、不触后端），成功请求延迟因并发排队升至 p50 2.1s 但无一失败。压测脚本的 429 会体现在状态分布里，属预期语义。
4. **端点代表性**：`/api/cs/customer-context` 覆盖 gateway-auth（JWT 验签+会话闸 Redis 查询）→ 应用鉴权中间件（X-API-Key + 会话纵深）→ DB 读（账户+订单关联）。是客服读链路的代表性路径；**不含 LLM/RAG 调用**（那属于质量链路，受预算与模型吞吐约束，另行评估）。

## 四、瓶颈分级

| 项 | 级别 | 依据 |
|---|---|---|
| 网关限流 600/分/用户 | **设计边界（非缺陷）** | 容量规划按 ≥10 RPS/用户 × 并发用户数估算；放量前需产品确认目标并发用户规模是否超限 |
| DB/上游池突发排队（50 并发 p50 8.5s） | **可挂账** | 无失败；建议隔离栈复测 100/200 并发定位池配置（DB_POOL_MAX_CONN） |
| WS/写路径容量零数据 | **挂账（Q4 遗留）** | 需隔离栈；不阻塞 web 首期受控试用（首期流量远低于 8 RPS 持续） |
