# B2｜退款申请本机沙盒闭环

## 目标

沿用现有客服确认、业务守卫、Side Effect Idempotency 和统一案件事实源，完成退款草案修改/取消/重新确认、确认时资格复核、幂等登记与本人状态查询。登记退款申请不代表退款已到账。

## 范围

- 在现有客服案件 `customer_service.cs_case` 中持久化退款申请，申请 ID 与确认 ID 稳定关联；不把 `order.refunds` 当作退款申请表，也不新建平行执行账本。
- 仅显式本机 sandbox 模式可创建申请；HTTP 业务网关没有退款 API 时 fail-closed，不回退本地、不伪造外部成功。
- 重新确认前按可信 user/tenant 重验订单归属、资格、金额和政策版本。
- 允许修改退款说明；更新使用现有 Proposal Version CAS，旧版本确认必须失效。更换订单需取消草案后重新发起。
- 提供按认证 user/tenant 限定的申请状态列表/详情；人工案件状态不等同退款完成。
- 不修改 `frontend-admin/`、旅游代码或生产/共享数据库；不调用真实模型/Provider。

## 验收

1. 隔离 PostgreSQL 中确认后真实创建一条退款案件，查询得到稳定申请 ID 与状态。
2. 同确认重放/并发确认最多创建一条申请；结果不确定时保留 `verifying` 并能用稳定 ID 查询，不盲目重试。
3. 修改说明会递增版本；旧版本确认返回冲突；取消草案不创建申请。
4. 确认时若订单归属、可退资格、金额或政策版本变化则 fail-closed，不创建申请。
5. 跨 user/tenant 读申请返回等价 404；无退款网关的 HTTP 模式不写本地案件。
6. UI 明确说明“待处理/待审核”不代表已退款，并可查询本人申请。
7. 相关客服 T1/T2、隔离 PostgreSQL 测试、前端定向测试和类型检查通过；真实 Provider 与 APISIX/浏览器 T3 依赖另行标记。

## 停止条件

满足以上本地可验收项并推送以 PR #61 为 base 的 stacked PR；不合并 main。任何真实退款/付款 API、生产库、付费 Provider 或无法证明安全的状态变更均停止并记录阻断。
