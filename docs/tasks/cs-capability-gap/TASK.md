# 客服能力差距补齐任务

- **任务 ID**：`cs-capability-gap`
- **目标**：按生产可运营标准补齐客服能力；本阶段的业务写操作只进入可审计的 business-mock 或既有人工审核流程，不接真实支付、物流、税务等外部写接口。
- **状态事实源**：[PROGRESS.md](PROGRESS.md)；设计依据：[FINAL-PLAN.md](FINAL-PLAN.md)。每批的 PR、部署和验收必须以当前证据核对，不能从计划推断完成。

## 范围

- **B4**：支付流水查询、重复扣款识别；退款只登记退款申请并等待人工审核，不自动退款。
- **B5**：物流催办 mock 登记；不承诺承运方已受理或具体处理时效。
- **B6**：价保差额只进入 business-mock 演示钱包，默认关闭，不触达真实资金。
- **B7**：在途订单改地址；复核物流状态、用户确认后只登记 mock 请求，不改真实订单或通知承运方。
- **B8**：开票申请与状态使用 mock，不连接真实税务或开票渠道。
- **B9**：完成多模态能力立项与安全边界，不在本任务实现图像、音频或视频模型链路。

B0–B3 按 `PROGRESS.md` 中的提交、CI 和验收证据核对。真实业务渠道接入不属于本任务范围。

## 验收条件

1. 用户路径完成意图分流、必要信息补槽、资格与资源授权、提案、用户确认（如为写操作）、幂等执行或人工审核，以及持久化审计。
2. 用户身份和租户只取自服务端可信上下文；订单状态、金额、资格、归属或执行结果无法核实时 fail closed。
3. Mock 的模拟结果与真实业务结果清楚区分；不得声称真实资金、订单、承运方或税务状态已改变。
4. 新迁移登记在 `scripts/init_db.py` 与 RAG 路径分类；新客服测试纳入 `.github/workflows/rag_smoke.yml`。词表变化通过客服 Golden 与决策回放双门禁。
5. 按风险执行最小充分 T0–T2 验证；代码服务须从当前任务 worktree 重建并健康检查，浏览器/真机链路须有实际证据。未执行的验证标记为 `UNVERIFIED`。
6. 实现、测试和本地自查完成后展示 diff 与结果，等用户明确确认再提交任务分支；所有改动走 PR，未经确认不合并 main。

## 停止条件

出现真实外部资金或业务写入、绕过用户确认或退款人工审核、跨用户/租户访问、审计不能持久化、写入结果无法判定，或无法安全从当前 worktree 重建共享服务时，停止该批副作用操作，并在 `PROGRESS.md` 记录 `BLOCKED` 或 `UNVERIFIED` 与恢复条件。
