# 客服能力差距补齐任务

- **任务 ID**：`cs-capability-gap`
- **目标阶段**：生产可运营；业务写能力只接确定性 business-mock 或转人工，真实外部渠道留待后续单独决策。
- **状态事实源**：[PROGRESS.md](PROGRESS.md)；能力设计见 [FINAL-PLAN.md](FINAL-PLAN.md)。

## 目标与范围

完成客服能力清单 B4–B8 的最小可审计 mock 实现，并为 B9 建立多模态立项方案：

- **B4**：支付流水查询与重复扣款识别；符合严格条件且显式开启时，只对 business-mock 演示样本自动模拟退款并持久化审计；其余退款提案走既有用户确认与人工审核，不创建真实退款申请或触碰真实资金。
- **B5**：物流催办 mock 登记，不能承诺承运方已受理或具体时效。
- **B6**：价保差额只在 business-mock 演示账本登记，资金开关默认关闭，不触达真实资金。
- **B7**：在途订单改址需重新校验状态并由用户确认，只登记 mock 请求，不改真实订单地址、不通知承运方。
- **B8**：开票申请/记录使用 mock 服务，不连接真实税务或开票渠道。
- **B9**：完成多模态能力立项和安全边界，不在本任务实现图像/音视频模型链路。

B0–B3 为已完成批次；具体 PR、工作树和验收证据按 PROGRESS 记录核实，不能仅凭历史状态推断合并或部署完成。

- 不触发已过期的 B4 q3 会话 `b4-acc-q3`；退款提案不得由集成验收恢复、确认或提交。

## 必须满足的验收条件

每批能力在用户可见的客服路径中完成：意图区分 → 必要信息补槽 → 资格/权限核对 → 提案 → 用户确认（如有写操作）→ 幂等 mock 执行或人工审核 → 持久化动作审计。行为结果、错误和模拟状态必须诚实表达。

- 订单、申请和会话按服务端认证用户及租户隔离；权限、订单状态或业务事实无法核实时 fail closed。
- 写操作复用现有确认、幂等和 `agent_actions`/`audit_logs` 审计链；mock 重启导致演示状态清空时，不得声称其是生产业务记录。
- 新迁移登记进 `scripts/init_db.py` 与 RAG 路径分类；新增测试进入 `.github/workflows/rag_smoke.yml` 定向清单。
- 词表变化通过客服 Golden 和决策回放双门禁。按风险执行 T0–T2 定向验证；未实际重建、健康检查或真机验证不得标成已部署。
- 本地修改始终在独立任务 worktree；展示 diff 和证据后，等待用户确认提交。未经明确确认不得合并 main。

## 停止条件

出现真实支付/订单/物流/税务写入、真实退款绕过现有人工审核、要求确认的动作绕过用户确认、不可确认的副作用结果、审计不能持久化、租户隔离失败，或无法安全从当前 worktree 重建共享服务时，停止该批写操作并记录 `BLOCKED` 或 `UNVERIFIED` 及恢复条件。
