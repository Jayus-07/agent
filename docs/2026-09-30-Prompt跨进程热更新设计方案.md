# Prompt 跨进程热更新设计方案（推拉结合）

> 2026-09-30 ｜ 状态：待评审施工
> 解决的问题：管理端发布/回滚 prompt 后，app 进程即时生效，但 5 个 Celery worker 与 rag-service 的进程内快照冻结在启动态，必须重启才换版本——生产不可接受。
> 关联：M4（版本指针语义）、#5（请求级版本 pin）、M8（发布留痕）、治理台账 `docs/2026-09-30-企业级治理技术债修复台账.md`

---

## 1. 背景与问题（现状代码证据）

### 1.1 读路径：一切走进程内快照

`backend/prompts/service.py` 的三条读取路径，**快照全部最优先**：

| 路径 | 实现 | 快照 miss 时 |
|---|---|---|
| `get_template_sync(key)` (L178) | 只读 `_snapshot` → defaults | 直接 defaults，**不查 DB** |
| `render_sync(key)` (L158) | 同上 | 同上 |
| `get_active(key)` (L126, async) | `_snapshot` → Redis cache(TTL 300s) → DB | 快照覆盖了全部 DB active prompt，cache/DB 分支实际死代码 |

结论：**任何进程的 prompt 新鲜度 = 该进程最近一次 `refresh_snapshot()` 的时刻**。

### 1.2 快照刷新点：只有启动（+ seed）

全仓 `refresh_snapshot()` 调用点：

- `backend/app/server.py:194`（app 启动）
- `backend/tasks/celery_app.py:218`（`worker_process_init` 钩子，**每个 prefork 子进程**启动时）
- `backend/services/rag_server.py:170`（rag-service 启动）
- `service.py:444`（seed 路径）

### 1.3 发布/回滚：只刷新本进程

`PromptService.publish()`（rollback = publish(skip_workflow=True)，set_alias("production") 复用 publish）做了：DB 权威更新（active_version + production alias 同步 + 审计）→ cache 失效 → **本进程** `_snapshot[key]` 更新（epoch+1）→ 本进程 `_fire_hooks(key)`。

`_fire_hooks` / `register_reload_hook` 机制存在但**全仓零生产调用方**。无 Redis pub/sub、无 epoch 轮询、无周期任务。

### 1.4 影响矩阵

| 进程类 | 发布/回滚后 | 承载的业务 |
|---|---|---|
| app | ✅ 即时生效（发布方即本进程） | chat 主链路、主图、workflow 同步执行、planner/critique/supervisor |
| 5×Celery worker（prefork 子进程） | ❌ 冻结在启动态 | 异步任务内 LLM 调用（report/maintenance/metadata_shadow/rag_index）、断点续跑重执行 |
| rag-service | ❌ 冻结在启动态 | RAG 检索链内部 prompt（metadata_extract 等） |

trace 影响说明：#5 的版本 pin（`runner.py:393` / `task_executor.py:262` 调 `current_versions()` 读快照）语义是诚实的——trace 永远记录**当次实际用的版本**。worker/rag-service 的旧快照会如实显示旧版本号；本方案修的是「实际用的版本落后于 DB 权威」，修复后 trace 自然全对，**pin 语义本身零改动**。

## 2. 目标与非目标

### 目标

- **G1 免重启生效**：管理端发布/回滚后，所有进程在有限窗口内（pub/sub 在线：亚秒级；兜底：≤ `PROMPT_EPOCH_CHECK_TTL` + 刷新耗时）使用新版本
- **G2 正确性兜底**：pub/sub 丢消息（worker 重连窗口、broker 抖动）后，拉模式保证最终一致，**自愈、无需人工干预**
- **G3 失败不伤业务**：Redis 不可达 / 刷新异常时 fail-open 保持当前快照，零请求失败，告警可观测
- **G4 可观测可排障**：任一进程能回答「我当前 epoch 是多少、最后刷新时间、为什么还在用旧版」
- **G5 复用既有基建**：只用现有 Redis（db0）与 DB，不引入 Nacos/Apollo 等新组件（不引入未要求的依赖）

### 非目标

- 不做按 key 精准失效（全量重载 = 一个 `list_all` 查询 39 行，代价可忽略，精准失效不值得复杂度）
- 不做 staging 运行时消费（staging 指针不触发 bump、不进运行时读路径——M4 既定口径，Phase 2 灰度另案）
- 不改 in-flight 请求语义（请求级 pin 快照本来就对，发布不影响已开始请求）
- 不做灰度放量发布（canary 按 label 的发布属发布系统范畴，另案）

## 3. 总体设计

```
                    ┌─────────────── 写侧（唯一 bump 单点）───────────────┐
                    │  PromptService.publish / seed 成功后                │
                    │  → hot_reload.bump_prompt_epoch(key, actor)         │
                    │     ① Redis INCR  {prefix}prompt:epoch  （权威信号）│
                    │     ② Redis PUBLISH {prefix}prompt:changed （推送） │
                    └──────────────────────────┬─────────────────────────┘
                                               │
              ┌────────────────────────────────┼────────────────────────────────┐
              │ 推（时效，亚秒）                │ 拉兜底（正确性，≤TTL）          │
              ▼                                ▼                                ▼
   ┌─────────────────────┐        ┌─────────────────────┐         ┌─────────────────────┐
   │ app                 │        │ rag-service          │         │ 5×Celery worker     │
   │ 发布即本进程自更，   │        │ 启动起订阅线程        │         │ 子进程 init 起订阅线程│
   │ 无需额外接线（可选   │        │ + 请求入口 ensure_   │         │ + 任务入口 pin 前    │
   │ 也挂订阅保持一致）   │        │ fresh                │         │ ensure_fresh        │
   └─────────────────────┘        └─────────────────────┘         └─────────────────────┘
              │                                │                                │
              └──────────── 收到事件或发现 epoch 落后 → refresh_snapshot() ──────┘
                            （幂等全量重载，RLock 并发安全，进程内 2s 防抖去重）
```

**推拉职责划分（为何两者都要）**：推负责时效（sub 秒级）；拉负责正确性（pub/sub 是 fire-and-forget，worker 重连窗口会丢消息，epoch 比对保证落后必被追平）。这是 Nacos/Apollo 类配置中心的内核模式，只用了仓库已有的 Redis。

## 4. 详细设计

### 4.1 权威信号与键名

- **epoch 键**：`{REDIS_KEY_PREFIX}prompt:epoch`（即 `agent:prompt:epoch`），STRING，`INCR`，**不设 TTL**（权威计数必须永存；Redis 重启丢失 → 见 4.5 退化口径）
- **变更频道**：`{REDIS_KEY_PREFIX}prompt:changed`，payload JSON：`{"key": "<prompt.key>", "epoch": <int>, "actor": "...", "ts": <unix>}`（key 仅供日志与未来精准失效，刷新动作恒全量）
- **DB 兜底口径**（仅用于排障比对，不做运行时依赖）：`SELECT max(updated_at) FROM ai.prompt_versions`（018 迁移已含 updated_at）

### 4.2 写侧：唯一 bump 单点

新模块 `backend/prompts/hot_reload.py`：

```python
def bump_prompt_epoch(key: str, actor: str) -> None:
    """发布侧唯一入口：INCR epoch + PUBLISH 变更事件。软失败（发不出≠发布失败，
    只损失跨进程时效，拉兜底仍在 Redis 恢复后追平——但要在 app 侧记 warning）。"""
```

接线点（**只有一处业务调用**）：`service.py::publish()` 成功路径末尾（审计写入之后）。rollback / set_alias("production") 都收敛到 publish，自动覆盖；`seed` 路径（L444 已做本进程 refresh）后同样 bump。**set_alias("staging") 不 bump**（不影响运行时读路径，M4 口径）。

### 4.3 读侧：同一模块的三个能力

```python
def start_prompt_reload_listener() -> None   # 启动 daemon 订阅线程（每进程一个）
def ensure_prompt_snapshot_fresh() -> None   # 惰性核对（带进程内 TTL 缓存的拉检查）
def _do_refresh_if_stale(authoritative_epoch) -> None  # 内部：防抖 + 刷新
```

- **订阅线程**：`redis-py .pubsub().subscribe(channel)` 阻塞监听（`get_redis()` 直连 db0），收到消息 → 调 `_do_refresh_if_stale`（读消息里的 epoch）。断线自动重连循环（间隔 5s，重连成功立即做一次拉核对——补丢消息窗口）。
- **惰性核对**：进程内缓存「上次核对到的 epoch 值 + 上次核对时间」；距上次核对 ≥ `PROMPT_EPOCH_CHECK_TTL`（默认 10s）才真正 GET Redis，epoch 大于本地 `_epoch` → 刷新。**每次核对开销 = 命中缓存时零 IO**。
- **刷新执行**：复用 `prompt_service.refresh_snapshot()`（幂等全量；`_snapshot_lock` RLock 已并发安全）。
  - 常驻事件循环进程（rag-service）：订阅线程内 `asyncio.run(...)` 不行（线程内无 loop 但 asyncio.run 可用）——统一用 `asyncio.run(prompt_service.refresh_snapshot())`，与 worker 启动路径同款（celery_app.py:218 先例）。
  - Celery prefork 子进程：同款 `asyncio.run`（fresh fork 无 loop，既有先例已验证）。

### 4.4 接入点矩阵（全部真实落点）

| 进程 | 推（订阅） | 拉（ensure_fresh） | 接线位置 |
|---|---|---|---|
| app | 可选挂（保持机制统一，默认挂） | 不需要（发布自更） | `server.py` startup（L194 旁） |
| rag-service | ✅ | FastAPI 依赖/中间件（每请求，TTL 缓存后零 IO） | `rag_server.py` startup（L170 旁） |
| Celery 子进程 ×（5 worker + beat + cs-dispatcher×2） | ✅ | `runner.py:393` 与 `task_executor.py:262` 的 `current_versions()` **前一行**（与 #5 pin 同点，语义天然一致：核对后再 pin） | `celery_app.py::_on_worker_process_init`（L228，起订阅线程） |

### 4.5 失败语义（fail-open 三态）

| 故障 | 行为 | 观测 |
|---|---|---|
| 发布侧 Redis 不可达（bump 失败） | 不影响发布成功；损失跨进程时效，warning 日志 | `bump_prompt_epoch_failed` 计数 |
| 订阅/核对侧 Redis 不可达 | 保持当前快照继续服务，订阅线程 5s 退避重连；核对静默跳过（TTL 后再试） | `prompt_reload_listener_reconnect` 计数 |
| refresh_snapshot 失败（DB 抖动） | 保持当前快照（旧版本继续可用），告警 | `prompt_snapshot_refresh_total{result="error"}` |

**铁律：热更链路任何故障不得产生业务请求失败。** prompt 暂时旧版本可用性 > 热更失败放大。

### 4.6 防抖与并发

- 进程内 `threading.Lock` + `_last_refresh_at`：2s 内的重复触发合并为一次刷新（批量 seed、多 key 连发只刷一次）
- 刷新本身幂等，重复触发无害；跨进程各自独立刷新，不要求全局去重
- epoch 比对只在**取到比本地大的值**时刷新，回退的 epoch 值（理论上不该发生）忽略并告警

### 4.7 观测

- 结构化日志：`[PromptHotReload] refreshed epoch {local}→{authoritative} source={pubsub|poll} keys={n} cost_ms={ms}`（每进程可回答 G4）
- Prometheus：`prompt_snapshot_refresh_total{process, result=ok|error|skipped}`、`prompt_epoch_lag`（最近一次核对时 authoritative-local 的 gauge）、`prompt_reload_listener_reconnect_total`
- 告警（接既有 alerts.py 软降级）：`prompt_epoch_lag > 0` 持续 > 5min、`refresh error` 连续 ≥ 3 次

### 4.8 配置与开关

| 变量 | 默认 | 说明 |
|---|---|---|
| `PROMPT_HOT_RELOAD_ENABLED` | `true` | 总开关；**false = 完全退化为现状**（重启语义），是本功能自身的回滚手段 |
| `PROMPT_EPOCH_CHECK_TTL` | `10` | 拉核对的最小间隔秒（传播兜底上界 ≈ TTL + 刷新耗时） |
| `PROMPT_PUBSUB_CHANNEL` | `{prefix}prompt:changed` | 频道名（前缀随 REDIS_KEY_PREFIX） |

登记进 `backend/config` 既有配置注册表（M16 同款），不散落 os.getenv。

## 5. 测试计划

### 单测（`backend/tests/prompts/test_hot_reload.py` 新建）

- bump 单点：publish/rollback/set_alias(production) 后 epoch INCR + channel 收到消息；**staging 不 bump**
- ensure_fresh：TTL 内零 Redis 调用；过期后 GET；落后即刷新；fail-open（Redis 抛异常 → 快照不动、无异常外泄）
- 防抖：2s 内多次触发只刷一次
- 开关关闭：所有接线 no-op
- 既有语义回归：#5 pin 快照值不被热更影响（in-flight 断言）、staging 读路径不变

### 集成/实机验收（发布→不重启→验证）

1. 管理端 publish prompt X vN+1 → 3s 内 rag-service 日志出现 refreshed、`/prompts/{key}` active=N+1
2. 触发一条走 worker 的异步任务（metadata_shadow）→ 任务 trace `tags.prompt_versions` 中 X=N+1（不重启 worker）
3. **一键回滚** X 至 vN → 重复 1-2，两个进程都回到 vN，trace 同步
4. 停 Redis-broker（或断业务 redis）→ 发布成功、业务请求零失败、恢复后 ≤TTL+刷新耗时内追平
5. `PROMPT_HOT_RELOAD_ENABLED=false` 重建 → 行为与现状完全一致（对照）
6. 发布后跑 `python -m backend.scripts.gen_prompt_contract_lock` 留痕（既有门禁要求，写进 Runbook）

### SLO

- 传播延迟：pub/sub 在线 P99 < 3s；兜底路径 ≤ TTL + 刷新耗时（约 12s）
- fail-open 期间业务请求失败增量为 0

## 6. 风险与兼容

| 风险 | 评估 | 缓解 |
|---|---|---|
| 每个子进程多一条 Redis 连接（订阅长连） | worker 并发 2-4 × 8 进程 ≈ 20 条，db0 现连接池上限 20/进程量级，充裕 | 订阅线程独立连接，不复用请求池，互不干扰 |
| 刷新风暴（频繁发布） | 管理端人工操作频率极低 | 2s 进程内防抖已覆盖 |
| asyncio.run 在线程内创建 loop | 与 celery_app.py:218 启动路径同款先例，已验证 | 仅在刷新时短暂创建 |
| epoch 键因 Redis 数据清空回退 | 计数变小 → 比对「大于才刷」不会误刷 | 拉侧发现 epoch < 本地记录：告警 + 以 DB max(updated_at) 人工核对（Runbook 步骤） |
| 与未来配置中心冲突 | 无——模块边界即 hot_reload.py 单文件 | 若引入 Nacos/Apollo，仅替换该模块实现 |

## 8. Runbook（发布/回滚操作流程）

1. 管理端 `POST /prompts/{key}/drafts` → `transition`（校验）→ `publish`；或已发布版本直接 `POST /{key}/rollback`（一键，skip_workflow）
2. 发布/回滚成功即生效（本方案窗口内全进程追平）；trace 按请求开始时 pin 的版本如实记录
3. **留痕**：`python -m backend.scripts.gen_prompt_contract_lock` 重新生成 prompts.lock.json 随变更提交（漏了会被 `test_prompt_contract_lock` 与 CI 拦截）
4. 排障：各进程日志搜 `[PromptHotReload]`；`prompt_epoch_lag` gauge 定位落后进程；Redis GET `agent:prompt:epoch` 与本地日志比对
5. 功能自身回滚：`.env` 设 `PROMPT_HOT_RELOAD_ENABLED=false` 重建，即回到「重启生效」的现状语义
