# 2026-09-16 工作流高并发方案（100 并发请求场景）

> 状态：**草案 v0.1，待补充确认**（文末「七、待确认问题清单」为预留讨论区）

---

## 一、要解决的问题

一个任务编排/工作流调用多个 tool，当 **100 个用户同时请求该任务** 时，系统必须：
1. 不丢请求、不雪崩（下游 LLM / DB / 外部 API 是真正瓶颈）；
2. 用户立即得到受理反馈，并可查询进度与结果；
3. 公平（单个用户不能占满全部容量）；
4. 失败可控（重试不产生重复副作用，可降级）。

## 二、现状盘点（实测依据）

| 模块 | 位置 | 现状 | 结论 |
|---|---|---|---|
| Workflow 触发 | `backend/app/api/routes/workflows.py:84` | `await scheduler.run_now(...)` | ⚠️ HTTP 请求**同步挂住整个 workflow 全程**（注释写"异步执行"与实际不符） |
| Run 间并发控制 | `backend/orchestration/workflow/scheduler.py` | 无 Semaphore / 队列 | ⚠️ 100 个 trigger = 100 个 workflow 同时跑 |
| Run 内并行 | `backend/orchestration/workflow/executor.py` | DAG 分层 + `asyncio.gather`，per-step retry/timeout/on_error | ✅ 基础良好，无需重写 |
| Run 持久化 | `backend/orchestration/workflow/persistence.py` | SQLite `data/workflow_runs.db` | ✅ 可复用，需补 `queued` 状态 |
| Tool 层 | `backend/tools/` + `tool_registry` | 20 个 tool 注册，无 per-tool 限流 | ⚠️ 下游无保护 |
| 队列基建 | `docs/OPTIMIZATION_P3_ASYNC_QUEUE_ARCHITECTURE.md` | 已为上传链路设计 RQ + Redis，Redis 已部署运行 | ✅ 技术选型可沿用 |
| 降级 | `backend/orchestration/supervisor/degradation.py` | 已有雏形 | ✅ 熔断挂这里 |

## 三、总体架构

```
                ┌──────────────────────────────────────────────┐
 100 个请求 ──▶ │ FastAPI POST /workflows/{name}/trigger       │
                │  ① 建 run 记录(queued) ② 入队 ③ 立即返回 run_id │
                └──────────────┬───────────────────────────────┘
                               ▼
                    ┌─────────────────────┐
                    │  Redis Queue (RQ)   │  ◀── 队列深度/等待时间指标
                    └──────────┬──────────┘
                               ▼
              ┌────────────────────────────────┐
              │ Worker 池（全局并发 W=8~20）      │
              │  · 每用户并发上限 U=2~3          │
              │  · 每队列深度上限，超出→429       │
              └──────┬─────────────────────────┘
                     ▼
        ┌──────────────────────────────┐
        │ WorkflowExecutor（现有，不动）  │
        │  DAG 分层并行 + retry/timeout  │
        └──────┬───────────────────────┘
               ▼
   ┌───────────────────────────────────────┐
   │ Tool 调用层（新增资源信号量）             │
   │  · LLM: RPM/并发上限   · DB: 连接池      │
   │  · 外部 API: 各自配额   · 结果缓存命中即跳过│
   └───────────────────────────────────────┘
               ▼
   前端：GET /runs/{run_id} 轮询 或 SSE 订阅进度
```

## 四、分层设计

### 1. 入口层：受理 ≠ 执行（改动最小、收益最大）
- `trigger_workflow` 改为：校验 → 创建 run（status=`queued`）→ 任务入队 → **立即返回** `{run_id, status: "queued", queue_position}`；
- 队列满或预估等待超阈值 → `429 Too Many Requests` + `retry_after`；
- 修正现有注释与行为不一致的问题（当前 `await executor.run` 会挂住请求整个执行期）。

### 2. 调度层：全局并发阀门
- **全局 worker 并发 W**：同时运行的 workflow 实例数（建议初始 8，压测后调）；
- **每用户并发上限 U**：同一 user_id 最多 U 个 run 同时执行（建议 2~3），超出排队；
- **公平性**：多队列或轮询出队，避免先来大任务阻塞后面小任务；
- 容量估算（单 workflow ≈30s）：W=8 → 100 请求约 6~7 分钟消化完；W=20 → 约 2.5 分钟。

### 3. 执行层：现有 Executor 保留，只做两件事
- run 状态机补全：`queued → running → succeeded / failed / cancelled`，persistence 增加 `queued_at / started_at / queue_wait_ms`；
- step 结果回调写入进度（`当前第 n/m 步：step_name`），供前端展示。

### 4. Tool 层：下游保护（雪崩防线）
- **资源信号量**（`asyncio.Semaphore` 或 token bucket）：
  - LLM 调用：全局并发上限 + RPM 限流（最贵、最先崩的一环）；
  - 外部 API（地图/爬虫/web）：每域名独立配额 + 指数退避；
  - DB：复用连接池上限，不额外开；
- **结果缓存**：tool 结果按 `(tool_name, 输入哈希)` 缓存（Redis，TTL 按工具性质定）。100 个相似请求的真实计算量往往只有个位数；
- **幂等**：幂等键 = `run_id + step_name`，重试不产生重复副作用（写操作类 tool 必须实现）。

### 5. 可靠性
- 熔断：连续 N 次失败的 tool 自动熔断，run 走 `supervisor/degradation.py` 的降级路径；
- 死信：重试耗尽的 run 进死信记录，可人工重放；
- 取消：支持 `POST /runs/{run_id}/cancel`（queued 直接出队，running 发协程取消信号）。

### 6. 可观测
- 新指标（Prometheus 已接入）：`workflow_queue_depth`、`workflow_queue_wait_ms`、`workflow_running`、`tool_call_total{tool,status}`、`tool_cache_hit_ratio`；
- 告警：队列深度持续 > 阈值、平均等待超 SLA。

## 五、实施分期

| 阶段 | 内容 | 改动面 |
|---|---|---|
| **P0 最小可用**（建议先做） | trigger 异步化 + in-process `asyncio.Queue` + 全局 Semaphore + run 补 `queued` 状态 + 进度查询 | 只动 `workflows.py` / `scheduler.py` / `persistence.py`，单进程内解决，一天内可交付 |
| **P1 队列外置** | 换 RQ + Redis，worker 独立进程（可横向扩容），沿用 P3 文档选型 | 新增 worker 进程与配置 |
| **P2 防线完善** | tool 信号量 + 结果缓存 + 幂等键 + 熔断接入 + 死信重放 | tool 层与 supervisor |
| **P3 体验** | SSE/WebSocket 进度推送、取消接口、每用户配额管理界面 | API + 前端 |

> P0 的价值：单进程内 100 并发就已经从「雪崩」变成「排队有序消化」；P1 再解决多进程与横向扩容。两步可独立验收。

## 六、技术决策记录

- **队列选 RQ 不选 Celery**：沿用 P3 文档结论（轻量、FastAPI 集成好、团队已有 Redis 运维经验）；
- **不动 WorkflowExecutor**：DAG 并行 + retry/timeout 已达标，重写只会引入风险；
- **缓存放 tool 层而非 workflow 层**：tool 结果复用粒度更细，跨 workflow 也受益。

## 七、待确认问题清单（请你补充）

1. **容量预期**：100 并发是峰值常态还是偶发？单 workflow 预期时长/step 数？
2. **实时性要求**：排队几分钟可接受，还是必须秒级返回结果（那要谈预计算/预热）？
3. **公平策略**：按用户限流是否合适？有没有 VIP/付费用户优先级需求？
4. **Tool 幂等现状**：20 个 tool 里有哪些是写操作（下单/发邮件/写库）？这决定幂等改造范围；
5. **部署形态**：单机 docker compose 还是规划多机？决定 P1 worker 扩容方式；
6. **前端现状**：进度展示用轮询还是可以上 SSE？
7. **成本红线**：LLM 并发上限愿意给到多少（直接决定 W 的上限）？

## 附录 A：Temporal 选型评估（2026-09-16 调研）

### 内存占用（自托管，Docker Compose 实测口径）

| 组件 | 最低 | 推荐 |
|---|---|---|
| Temporal Server（Frontend/History/Matching 合一） | 512 MB | 2 GB |
| 持久化 PostgreSQL（必需，工作流状态全存这里） | 256 MB | 1 GB |
| Web UI | ~100 MB | — |
| **Postgres-only 最小栈合计** | **~1 GB** | **~2 GB（机器建议 4 GB）** |
| Elasticsearch（高级可视化，可选） | +1 GB | +2~4 GB（最吃内存，可不上） |
| Python Worker（跑你们业务代码的进程） | ~100-300 MB | 随并发涨 |

> 对比：本方案 P0（in-process 队列）额外内存 ≈ 0；P1（RQ）≈ 一个 worker 进程几十 MB + 已有 Redis。**Temporal 最小栈比 RQ 方案多常驻 1~1.5 GB。** 单节点吞吐可达 ~100 wf/s，100 并发请求场景性能绰绰有余——瓶颈不在性能，在改造与运维成本。

### 优势（真实的）
- **持久执行（durable execution）**：进程崩溃/重启后 workflow 从断点自动恢复，状态像事务一样可靠；
- 重试/超时/定时/信号（signal）开箱即用，自带 Web UI 与完整执行历史；
- **人工审批场景天然契合**：signal/queue 机制正好匹配项目已有的 `approvals.py` 人工介入流；
- 长时任务（分钟~天级）是其主场。

### 代价（也是真实的）
1. **编程模型迁移是重写不是改造**：workflow 函数必须确定性（可重放），每个 tool 调用要改写成 Activity；现有 `WorkflowExecutor`（DAG 分层 + gather）、registry、persistence **全部被替换**，且与 LangGraph 状态机不好混用；
2. **多一个有状态组件**：PostgreSQL schema 管理、版本升级、备份（工作流历史全在 PG 里）、生产环境还要 mTLS；
3. 团队/会话协作复杂度：SDK 学习成本 + 事件历史调试心智模型。

### 结论
- **不建议为解决"100 并发"整体迁移 Temporal**——这个问题的正解是排队 + 并发阀（P0/P1 就够，成本≈0），Temporal 在这里是高射炮打蚊子；
- **建议路径**：
  1. 先按本方案 P0 → P1 上线，验证排队模型够不够用；
  2. 若后续出现以下任一信号，再做 **Temporal 增量试点**（不迁移存量）：workflow 时长进入分钟/小时级、需要断点恢复、人工审批流变多、多机部署需求；
  3. 试点时选 1 个新 workflow 用 Temporal 重写（每个 tool = Activity），存量 workflow 继续走现有 executor，两套并存，验证收益后再决定是否扩大；
  4. 若只想要"轻量版持久执行"，可评估 **DBOS**（Python 原生、复用 Postgres、无独立 server）作为中间选项。
