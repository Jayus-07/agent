# 旅游规划域设计

本文记录旅游域的产品目标、稳定契约和开发边界。具体运行行为以 [旅游代码](../backend/travel/)、[Travel v2 代码](../backend/travel_v2/) 及对应测试为准；若实现与本文冲突，先核实契约，再同步修正文档或实现。

## 1. 产品目标与边界

为个人旅行者生成可编辑、可解释的逐日行程，并支持围绕行程继续问答。计划应兼顾时间、地理、体力和预算约束，并区分实时事实、缓存、知识库内容、示例数据与估算结果。

平台不代替景区、交通或住宿供应商的权威信息和交易系统。未接入或无法核实的能力应明确披露，不编造价格、营业时间、库存或预订结果。

## 2. 用户流程

1. 用户从表单或对话提交目的地、日期、人数、节奏、偏好及必去项。
2. 系统澄清缺失信息，检索地点、天气和知识资料，并标记证据来源与时效。
3. 规划与优化服务安排逐日活动，校验约束；冲突时解释并请求用户决策。
4. 用户查看行程、依据和提醒，可修改并生成新版本。
5. 用户可对当前行程追问；涉及预订或其他写操作时走显式确认与治理流程。

入口、页面和接口以当前前端与 API 路由为准；本文不记录各入口的上线状态。

## 3. 执行进度

进度事件只能反映真实执行阶段，不得使用虚构百分比或报告尚未发生的成功状态。优先复用平台 SSE 事件协议；新增事件时同步更新后端事件 Schema、前端解析器和流式契约测试。普通同步请求不得因增加进度展示而改变既有响应契约。

## 4. 结果呈现

行程结果应便于快速查看：

- **概览**：目的地、日期、行程要点、预算和地图信息。
- **每日行程**：按日期展示活动、时刻、交通和费用信息。
- **依据与提醒**：展示关键事实的来源、核实时点、有效期、估算/示例属性和校验警告。

日期、费用和路线可为估算时必须如实标注；版本差异应能说明用户修改对计划造成的影响。

## 5. 行程问答

问答仅基于当前行程状态及可引用的 Evidence。答案应附可追溯的事实标识；缺少依据时明确表示未知，不从模型常识补造当前价格、营业时间或天气。预设问题应限于现有数据可回答的内容。

## 6. 预约与时效提醒

预约规则应来自带来源和核实时点的知识条目或经接入的权威数据源。没有可靠条目时不展示猜测性提醒。提醒在结果视图中与已确认的行程事实分开，并按来源类型和时效显示可信程度。

## 7. 偏好与记忆

偏好、会话摘要和规划恢复数据属于横向能力，不是 Agent。记忆读写失败不得阻断主要规划流程；偏好注入应可控、可追踪，且不得覆盖用户本轮明确表达的要求。

## 8. 导出

支持与行程用途匹配的日历、文本或地图链接等导出形式。导出字段与源行程保持一致，时间及地点信息需有明确含义；PDF、图片等新格式只有在依赖、安全和维护成本评估后再增加。

## 9. 架构边界

旅游域沿用平台既有分层：

`Supervisor → Domain Agent → Service / Tool → Provider`

- Router / Supervisor 负责意图、阶段和执行治理，不直接承载外部数据访问细节。
- Agent 通过共享状态和显式输入输出契约协作，不互相直接调用。
- Service 组织领域规则；Tool 封装原子能力；Provider 适配外部数据源。
- validator、repair 和 reporter 分别承担校验、有限修复和结果呈现，不绕过领域服务直接执行交易。
- 拓扑以代码为准；调整节点前核对共享状态、事件、超时、恢复及业务调用方测试。

## 10. 逻辑职责

| 职责 | 责任范围 |
|---|---|
| Supervisor | 判定规划、修改、查询或交易意图；推进阶段、处理超时和跨轮状态。 |
| Requirement | 将用户表达转为结构化旅行需求；信息不足时追问。 |
| Research | 获取地点、天气、知识和风险资料，并为事实附 Evidence。 |
| Planning | 分配必去项并生成行程骨架；不得静默删除用户指定地点。 |
| Optimization | 调整路线、时刻和预算；改变必去项前必须进入明确的冲突处理。 |
| Commerce | 集中处理比价、下单、取消和确认等交易能力。 |
| Travel Assistant | 回答当前行程问题，只使用有依据的状态和 Evidence。 |

这是逻辑职责划分，不表示运行时必须使用相同数量的图节点。实际节点和开关以当前代码为准。

## 11. 校验与修复

- 校验覆盖时间、地理、体力、预算、数据可信度和用户约束等关键维度。
- validator 应保持确定性，不执行外部 I/O 或隐藏的模型调用。
- repair 必须有轮数上限并避免反复震荡；不能通过丢弃必去项或降低校验标准来伪造通过。
- 每次修复保留可解释的差异或警告；仍有冲突时交由用户决策。

具体校验项和错误码以实现及测试为准。

## 12. Tool 治理

Tool 按副作用划分为 `READ`、`COMPUTE`、`WRITE`、`TRANSACTION`。Agent 仅能调用其显式允许的 Tool；写入和交易能力应集中在相应业务边界，并接入平台的授权、确认/审批及幂等机制。新增 Tool 时更新声明式注册、输出契约和失败路径测试。

## 13. Evidence 契约

Evidence 的模型定义位于 `backend/travel/core/contracts.py`，当前字段为 `fact_id`、`value`、`source`、`source_type`、`confidence`、`verified_at`、`expire_at`。字段或序列化格式变更需同步核对 API、前端消费方和测试。

来源类型及置信度上限：

| 来源类型 | 基线置信度 |
|---|---:|
| `live` | 0.95 |
| `cache` | 0.85 |
| `rag` | 0.70 |
| `seed` | 0.50 |
| `estimate` | 0.50 |

没有 `verified_at` 的事实置信度上限为 0.50。实际值不得高于来源基线；过期缓存和无核实点数据应降低可信度或明确标注。

统一呈现规则：未过期实时事实可正常陈述；缓存或过期事实需提示可能变化；种子、估算或低置信事实需标为示例/估算/待确认。不得把一个字段的实时来源当作同一对象其他字段的证据，例如不能用 POI 坐标的来源为占位票价背书。

## 14. 确认、审批与幂等

凡会创建或改变订单、预订、退款或其他外部状态的操作，都必须遵循现有治理流程。用户确认应绑定目标、金额或计划版本及有效期；重复请求需幂等。审批、确认和业务执行结果必须分别表达，不得将“已提交”描述成“已完成”。

## 15. 外部数据与可靠性

- Agent 声明需要的能力，不自行选择或拼装 Provider。
- Provider 链路应定义主源、回退、缓存和最终失败行为；每次降级保留来源与可信度变化。
- 为外部调用设置明确超时、预算和错误分类；外部失败不得吞掉或伪造成功。
- 缓存 TTL 按数据类型配置；实时状态或交易结果不能仅凭旧缓存作出确定性承诺。
- 新增数据源时核实授权、限额、隐私和商业许可，并测试不可用、超时、空结果及过期数据路径。

## 16. 开发验收

涉及规划契约的修改至少核对必去项、用户确认、跨轮状态及相关 API；涉及 Evidence 的修改核对缺来源、缺核实时点、过期和混合数据；涉及 Provider 或交易的修改核对超时、失败、降级及幂等路径。验证范围按 [AGENTS.md](../AGENTS.md) 选择，不以文档中的固定测试数量代替实际结果。
