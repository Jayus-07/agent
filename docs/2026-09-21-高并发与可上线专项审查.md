## 总判断

**当前不可直接上线。** 安全边界与观测底子好于预期（8000 绑回环+信任头、PG/Redis/Chroma/Kafka 全落卷、60+ Prometheus 指标 + 40+ 告警规则、checkpoint 强制 PgSaver），但有 **6 个上线硬阻塞**需先修复；高并发能力按默认配置仅 **~12-16 路 SSE 并发**，到 100 路需一轮约 8 项的改造（无架构重写）。

## 🔴 上线硬阻塞（6 项）

### B1. Redis `allkeys-lru` 会静默吃掉任务消息与已吊销 token — `docker-compose.yml:584`
单实例同扛 Celery broker(db1)+result(db2)+会话/pubsub(db0)+网关 token 黑名单，`maxmemory 512mb --maxmemory-policy allkeys-lru` 且无 AOF：内存压力下未 ack 任务消息、结果、登录会话、**已吊销 JWT 黑名单键**均可被逐出 → 任务丢失 + 被吊销 token 复活（安全事件）。
**修复**：`noeviction + appendonly yes + requirepass`；broker 与缓存拆实例；加 maxmemory 告警。

### B2. 全新部署 schema 不完整，登录与派单首启即挂 — `docker/init-dbs.sh:28-70`
首启只执行到 027，缺 021/022/023_auth_sessions/024/028_cs_dispatch；alembic（alembic.ini 双库）在 compose/Dockerfile/部署脚本中**零调用点**，app 启动也无 create_all。新卷部署后 /auth/refresh 与 cs-dispatcher 启动即报错。
**修复**：init-dbs.sh 补齐缺失 migration 或首启强制 `alembic upgrade head`；收敛 sql/migrations 与 alembic 双轨（建议 alembic 唯一权威）。**需在干净环境做一次「空卷 → compose up → 登录+派单冒烟」验证。**

### B3. PG 零备份 — 全仓
PG 是任务状态/checkpoint/记忆库唯一权威（单机 pg_data 卷），无任何自动备份（仅手工 pg_dump 命令散在文档）。磁盘损坏 = 全量丢失。
**修复**：每日 pg_dump + WAL 归档 + 保留策略 + 恢复演练纳入发布验收。

### B4. 告警只响不给 — `docker/prometheus-alert-rules.yml`（40+ 规则）+ `backend/observability/alerts.py:75`
无 Alertmanager 服务、`ALERT_WEBHOOK_URL` 默认空且 compose 未配置。队列堆积/LLM 全熔断/PG 挂掉时告警只躺在 Prometheus UI，无人值守即静默。
**修复**：compose 加 alertmanager（钉钉/企微 receiver）或强制注入 webhook；同时补 PG 连接饱和告警（现只有 `PostgresDown` up==0，池打满 up 仍为 1）。

### B5. 僵尸 RUNNING 任务无法收尸 — `backend/models/task.py:39-41` + `tasks/task_manager.py:112-124`
`resumable()` 不含 RUNNING，worker 崩溃后（消息丢失/visibility timeout 未重投）任务永久卡 RUNNING，连 admin retry 都被拒。
**修复**：定时 reconcile（heartbeat/started_at 超阈值 → FAILED 或重投）；RUNNING 纳入管理端强制取消范围。

### B6. 优雅停机缺口 — compose 全文无 `stop_grace_period`；`Dockerfile:74` uvicorn 无 `--timeout-graceful-shutdown`
docker stop 默认 10s 后 SIGKILL：分钟级 SSE 必被硬断；Celery worker 被杀后依赖 visibility_timeout（1h）才重投。
**修复**：app/rag `stop_grace_period: 700s` + `--timeout-graceful-shutdown 600`；worker 置硬超时+60s。

## 高并发容量链（默认配置量化）

| 环节 | 当前上限 | 依据 |
|---|---|---|
| APISIX | 单用户 3 并发流 + 30 req/min，read 600s | apisix.yaml L42-50, L95-112 |

| SSE 生产者 | 专用池 cpu×2=**16 路**，第 17 路排队无准入超时 | chat.py L47-51, L249 |
| SSE 消费者 | `run_in_executor(None, q.get)` 占默认池，min(32,c+4)=**~12 流**后开始饿死（最先打满） | chat.py L270 |
| LLM | **无 in-flight 信号量**，本地 100QPS 桶+Redis 桶；429 仅重试 1 次/0.5s；熔断进程内单例全局半径 | proxy.py L457-493；circuit_breaker.py L52 |
| rerank | rag-service 独立进程，但 bge-reranker CPU 推理 GIL 锁 → **1-3 并发**即延迟陡增 | rag_server.py L169 |
| PG | 未设 max_connections（默认 100）；async 池 20+10 + pgvector 池 10 + quota/usage/trace **每次 LLM 调用新建 2-3 条裸连接**；Celery 4 子进程各自建池 → 峰值需求 >100 | database/memory.py L37-38、rag.py L278-282、quota.py L287-292 |

**打满顺序**：消费者线程池(~12) → SSE 生产者(16) → rerank CPU → LLM 供应商限流（本地无闸）→ PG 连接（突发即爆）。

## 100 并发 SSE 最小改造清单（约 6-8 个文件，无架构重写）

1. `chat.py` 队列桥接去线程化：producer 改 `call_soon_threadsafe` 写 asyncio.Queue，consumer 纯 await（~30 行，解除最大瓶颈）
2. uvicorn `--workers 4` + 三处进程内状态 Redis 化：abort 注册表（chat.py:53）、require_rate_limit（rate_limiter.py:141 → 已有 distributed_rate_limiter）、熔断器计数
3. `CHAT_SSE_MAX_WORKERS=64`（I/O 为主可承受）
4. PG `max_connections=300` + quota/usage/trace 收口共享池（pgvector_store.py L68 有现成范式）或 pgbouncer
5. rag-service ×2 副本 + rerank 信号量（或 GPU）
6. LLM 全局 in-flight 信号量（32-128）+ 429 退避改 3-5 次指数+抖动（现 1 次/0.5s 过激）
7. Redis 拆 broker 实例（与 B1 合并做）
8. Celery 拆 rag_index 独立 worker（-Q rag_index -c 2）
9. 此后再扩容走队列化执行（/chat/stream → task + Redis pubsub 推流），彻底解除线程/连接与进程耦合
