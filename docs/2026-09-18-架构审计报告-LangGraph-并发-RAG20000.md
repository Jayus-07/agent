## 1. 目标与成功标准

### 1.1 目标

把当前系统从“单实例可运行、RAG 架构具备但未完成 20k 实证”提升为：

1. 多租户数据隔离可证明，任意查询在排序前完成租户、权限和版本过滤。
2. API、RAG 查询、异步索引和调度职责分离，可在多副本下保持一致行为。
3. 20,000 文档可以增量索引，不依赖全量重建的进程内 BM25 文件。
4. LangGraph 并行状态合并、跨副本取消、审批、幂等和 checkpoint 策略均有明确一致性边界。
5. 以可复现的 20k 数据集、500 条黄金查询、负载测试和故障演练证明质量、性能、可靠性和回滚能力。

## 2. 范围边界

### 2.1 本规划要做

- 补齐 RAG 全链路 `tenant_id`，并把租户、权限、版本过滤下推到向量与稀疏检索排序之前。
- 把 API、只读 RAG 查询服务、RAG 索引写入者、Agent Worker、调度器拆成清晰的运行单元。
- 以 PostgreSQL 原生全文检索替换文件型 BM25 作为推荐主路径，并保留影子比对、灰度和回滚。
- 将进程内取消、上传进度路由、审批降级、checkpoint 降级改为跨副本一致且生产失败关闭。
- 修复 LangGraph 并行分支的 `alerts` 状态合并契约。
- 建立 20k 语料、500 条黄金查询、质量评估、容量测试、故障演练和发布门禁。
- 用实测结果决定 pgvector 参数、分区、`halfvec`、MMR、截断长度、引用阈值和语义切分，不凭推测启用。
- 更新与实现一致的架构文档、SLO、值班手册、恢复手册和多副本就绪清单。

### 2.2 本规划不做

- 不在本次规划中修改任何业务代码、测试、数据库、配置或部署环境。
- 不改变主图 8 个核心节点的名称、顺序和声明式自动发现机制。
- 不新增业务域图、Skill、Capability、Workflow 或 MCP Server。
- 不默认迁移到 Milvus、Elasticsearch/OpenSearch；外部搜索引擎只在 PostgreSQL 稀疏检索连续两轮调优仍未达标时进入替代方案评审。
- 不默认增加 PPT/PPTX/HTML 解析；只有确认的生产语料包含这些格式时才进入实施范围。
- 不默认开启 HyDE、MMR、语义切分或增大文本截断；只有黄金集归因证明至少 2% 查询受对应问题影响，才允许做单变量实验。
- 不重构与本目标无关的前端页面、业务领域逻辑或用户现有未提交改动。
- 不把单主机 Docker Compose 描述为高可用部署。

### 2.3 停止与回滚条件

任一条件成立，当前阶段立即停止；不得用降低验收门槛的方式继续：

| 条件 | 动作 | 恢复条件 |
|---|---|---|
| 未取得合法、脱敏、可复现的 20k 语料 | 停止容量与质量验收。 | 数据负责人签署语料清单和使用授权。 |
| 任一跨租户或越权泄漏 | 停止灰度，回滚到无流量版本并保留证据。 | 根因修复后，隔离测试全量 0 泄漏且安全负责人签字。 |

## 3. 审计结论校正

原会话审计的方向成立，但仓库复核后需按下表修正优先级，避免重复建设或把未验证假设当成缺陷。

| 原结论 | 仓库复核 | 规划处理 |
|---|---|---|
| P1：主图 checkpointer 默认关闭且失败降级 | 属实，但主图每轮 `thread_id` 唯一；checkpoint 当前主要承担单轮故障恢复，不等同于跨轮记忆。 | 先冻结业务语义：生产明确选择“关闭且无恢复承诺”或“PostgreSQL 池化、失败即启动失败”；禁止静默 MemorySaver。 |
| P2：取消、审批、单进程阻碍多副本 | 属实；`_active_stops` 与审批后备为进程内状态。 | 取消迁 Redis；审批生产失败关闭；API 至少 2 副本验证。 |

| P9：副作用写操作重试无幂等 | 原报告已过期。仓库已有 Redis claim + PostgreSQL 结果存储，副作用工具已接入，并有 20 并发唯一赢家测试。 | 不重做；列为强制回归门，补多副本与故障恢复测试。 |

| 原报告未识别：应用 `/health` 不是严格 readiness | 健康接口可返回 `status=ok` 而关键依赖未就绪。 | 分离 liveness/readiness，readiness 覆盖发布契约中的关键依赖。 |

## 4. 总体做法

### 4.1 方案比较

| 方案 | 做法 | 优点 | 硬缺点 | 决策 |
|---|---|---|---|---|
| A：保留 pickle BM25 | 用 Redis/PG 分布式锁限制单写者，服务端定期检查版本并重载。 | 变更最少，可在阶段 1 快速止血。 | 增删仍是 O(N) 全量重建；服务重载复杂；文件分发和崩溃恢复仍是单独问题。 | 只作为阶段 1 临时措施和回滚路径。 |
| B：PostgreSQL 向量 + 原生稀疏检索 | 在 `rag_vectors` 或等价规范化表中保存预分词文本/`tsvector`，GIN 检索；向量与稀疏均在 SQL 中前置租户、权限和版本过滤。 | 单一数据平面、增量事务写入、跨副本立即可见、20k 运维成本最低。 | `ts_rank_cd` 不是 BM25；中文分词和排序质量必须影子验证。 | **推荐主方案。** |
| C：OpenSearch/Elasticsearch + pgvector | 专用搜索引擎负责 BM25/中文分析，PostgreSQL 负责向量和权威元数据。 | 稀疏检索能力和扩展性强。 | 新增集群、双写一致性、备份、监控和成本；20k 规模可能过度设计。 | 仅当方案 B 连续两轮调优仍未达标时启动 ADR。 |

### 4.2 推荐目标拓扑

```text
客户端
  │
APISIX（认证、限流、追踪、上游健康）
  ├─ API × 2+（无本地权威状态，不运行 scheduler，不执行 RAG 索引）
  │    ├─ LangGraph 主图
  │    ├─ Redis：取消、进度、限流、幂等 claim
  │    └─ PostgreSQL：任务、审批、checkpoint（若启用）
  ├─ RAG Query × 2+（只读启动，不同步、不回填、不重建）
  │    └─ PostgreSQL/pgvector：注册表、向量、稀疏索引、ACL/版本过滤
  ├─ Agent Worker × N（只消费 agent）
  ├─ RAG Index Worker × 1（初始单写者，只消费 rag_index）
  └─ Scheduler × 1（独立进程/服务）

对象存储：原始文档与可再生成中间产物
Prometheus/Grafana/日志/Trace：全链路可观测
```

### 4.3 数据与发布策略

1. **单一权威**：文档注册表和任务终态在 PostgreSQL；Redis 只保存可重建的短期协调状态；原始文档在对象存储。
2. **前置过滤**：`tenant_id` 为必填等值条件；权限、有效版本、有效期在 SQL 排序前过滤。禁止先召回再靠 Python 删除越权结果。
3. **单写者起步**：稀疏迁移完成前，`rag_index` concurrency 固定为 1；确认事务和唯一键能处理不同文档并发后，再用测试决定是否提高。
4. **扩展—回填—验证—切换—收缩**：数据库迁移不直接删除旧字段/旧索引；新旧路径并存并对账，完成灰度后保留 7 天回滚窗口。
5. **影子评估**：新稀疏检索先只记录候选重合率、质量与延迟，不影响用户答案；达标后按 5%/25%/50%/100% 切流。
6. **参数实证**：向量候选数、`ef_search`、halfvec、分区、切分和引用阈值都必须在同一冻结数据集上单变量比较。
