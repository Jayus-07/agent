# 企业助手、客服、旅游的 Docker 拆分评估

## 当前结构

- 当前 Compose 项目 `agent` 运行 18 个容器。主机检查时可用内存约 3.5 GiB；另有独立验收数据库容器，不应将其误算成第二套完整产品栈。
- 三个前端已分开：用户门户 `frontend`、管理端 `frontend-admin`、客服坐席端 `frontend-cs`。
- 后端仍是一个 FastAPI `app` 容器。企业助手、客服和旅游 API/Runtime 在同一进程注册；`CS_ENABLED`、`TRAVEL_ENABLED` 是功能开关，不是独立服务边界。
- 数据库、Redis、认证 Redis、任务 broker、APISIX 和部分 worker 共用。已有 `cs-dispatcher`、RAG/MCP/agent 等专用运行容器，但它们不能说明客服或旅游 API 已独立部署。

## 建议

**先保留一套共享基础设施，再按产品拆应用进程；不要复制三套完整 Compose 和数据库。** 当前单机和单店试点下，多套 PG/Redis 会增加内存、迁移、备份和数据一致性成本，并发运行也容易争抢 4 核资源。

后续需要独立发布、故障隔离或不同扩容节奏时，可从同一应用镜像增加 `app-enterprise`、`app-customer-service`、`app-travel` 三个运行目标，由 APISIX 按路由转发；PostgreSQL、认证、核心 Redis/broker 仍共享。通过 Compose profiles 或小型覆盖文件选择启动哪些应用，避免每个产品重复声明整套基础设施。

## 拆分前必须补齐的边界

1. 后端按产品明确挂载路由和 Runtime；不能只复制 `app` 服务并改容器名，否则三个容器仍暴露同一组 API。
2. 把跨产品共享能力明确为内部接口，例如登录/会话、RAG、SQL、Trace 和审计；校验可信用户、租户与产品权限，不依赖前端隐藏入口。
3. 标清各产品 worker 的队列、任务所有者、幂等键和故障恢复责任；一个产品的 API 停止时，不能误收或丢弃另一个产品的任务。
4. 核对共享 schema 与迁移所有者。只有出现法规隔离、不同备份恢复目标或明确性能瓶颈时，再评估数据库/Redis 独立实例；不能把“产品分容器”直接等同于“产品分数据库”。
5. 补齐 APISIX 上游、容器健康检查、资源预算、监控归属、发布回滚和本地开发脚本，再做逐产品切流验证。

## 当前结论

现阶段不拆容器、不改 Compose。先让企业助手和 ERP 试点稳定运行；待三个产品的路由/Runtime/任务边界及本机内存预算有证据后，再按“同镜像、不同服务目标、共享基础设施”拆应用层。此评估未停止、重建或修改任何共享容器。
