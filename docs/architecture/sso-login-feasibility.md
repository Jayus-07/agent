# 企业扫码登录与 RBAC 接入评估

评估日期：2026-11-19
状态：可行性已确认；尚未接入任何外部身份提供方。

## 结论

飞书、企业微信和钉钉都能为网页应用提供扫码/授权登录能力，接入本项目在技术上可行。推荐把它们作为**外部身份认证入口**：平台验证扫码身份后，查找已绑定的本地用户，再走现有登录准入、RBAC、JWT、会话和 Cookie 流程。外部平台只证明“是谁”，不能直接决定用户在本项目能做什么。

目前不应直接开放“扫码即注册并登录”。本项目是多租户系统，尚无统一的外部身份绑定与企业映射表；若按姓名、手机号或邮箱自动匹配，会有账号串租户、冒领管理员账号和重复身份等风险。未知身份应拒绝登录，由管理员预先绑定或由已登录用户完成受控绑定。

## 当前项目身份与权限边界

- `backend/app/api/routes/auth_local.py` 是登录权威入口：当前通过 `X-Tenant-ID` 定位租户内的 `auth.users`，校验本地账号状态和凭据，然后按 `client_app` 检查 web、admin、cs 的端口准入。
- 本地用户角色保存在 `auth.users.role`；平台权限由 `backend/security/authorization.py` 中的角色权限表推导。客服端角色另从 `customer_service.cs_agents` 查询。
- 登录成功后，系统创建 `auth.sessions` 与刷新令牌，签发本项目 JWT；web、admin、cs 使用不同的 refresh Cookie。退出、刷新、强制下线和审计都依赖这套本地会话。
- `backend/security/authorization.py` 当前说明 `data_scope` 是 SQL 行级数据范围的表达位，尚不构成门店级行权限。SSO 接入不会自动补上门店授权。

## 三个平台的接入条件

| 平台 | 网页登录能力 | 主要前置条件 | 项目侧要处理的身份 |
| --- | --- | --- | --- |
| 飞书 | 网页扫码登录基于 OAuth 2.0；回调后由服务端换取身份并建立本地会话 | 创建网页应用、配置应用权限和严格匹配的回调地址；保管 App 凭据 | 飞书企业/租户标识和用户唯一标识，不能只依赖姓名或邮箱 |
| 企业微信 | 企业微信扫码授权可以为网站返回成员身份；自建应用和服务商应用的适用范围不同 | 配置企业应用、扫码登录能力、可信回调域及企业信息。单个客户自建应用适合该客户；面向多家客户时要确认服务商授权模式 | 企业 ID 与成员 UserID；企业 ID 必须映射到平台租户 |
| 钉钉 | 开放平台提供第三方网站扫码登录，也提供钉钉客户端内微应用免登；二者是不同入口 | 创建并发布对应网页/企业应用，配置回调地址、应用权限和凭据；按目标场景选择网站扫码或客户端内免登 | 钉钉企业标识与用户稳定标识；不把部门名称当平台角色 |

## 与现有项目的冲突和处理方法

| 冲突点 | 直接接入的风险 | 建议处理 |
| --- | --- | --- |
| 登录必须先有内部租户；OAuth 回调由外部平台发起 | 从浏览器传入租户头会让用户伪造归属 | OAuth 开始时生成一次性 `state` 并在服务端保存；回调只用 `state` 恢复登录端和发起上下文，再用平台返回的企业标识查平台租户映射。不得信任回调 URL、请求体或浏览器自带的 `X-Tenant-ID` 作为租户归属。 |
| `auth.users` 没有外部身份绑定契约 | 用 email/手机号猜本地账号可能串租户或绑定错人 | 新增唯一映射，例如 `(provider, external_org_id, external_subject_id) → (tenant_id, user_id)`；同时设置外键、唯一约束、启停和审计字段。首次绑定只能由管理员预置，或用户完成现有账号重新认证后确认。 |
| 本地角色、客服角色与平台端口准入在登录路径内 | 直接采信 IdP 的“管理员/部门”字段会绕过本地 RBAC 与客服坐席绑定 | 绑定后按本地 `auth.users.status/role/tenant_id` 重查，并复用 `_portal_admission_error`；客服端仍须命中已启用的 `cs_agents`。外部角色/部门只作为身份资料，不能写成平台角色。 |
| 当前凭据登录直接创建平台 session/JWT | 单独实现 SSO token 会绕开会话轮换、强制下线、logout 和三端 Cookie 隔离 | 把“已验证本地用户”收敛到共享的本地登录签发服务；密码登录与各 SSO callback 都调用同一服务创建 session、refresh token、JWT 和对应端 Cookie。 |
| 多租户应用注册和回调域各不相同 | 多客户共用单一 `client_id/secret` 或宽泛回调地址会导致串企业/错误回调 | Provider 配置按平台租户隔离，密钥加密保存，不进前端与日志；回调 URL 固定 allowlist，`state` 一次性且绑定 Provider、tenant mapping、portal、浏览器会话。 |
| 同一自然人可能在三个平台上有不同账号 | 用户切换平台后产生重复本地账号、不同 RBAC 或审计身份分裂 | 用显式身份绑定把多个 Provider subject 关联到同一个 `auth.users.id`；业务和审计始终以本地 user ID 为主体。解绑/更换身份要二次验证并留下审计记录。 |
| 未来要做门店级权限 | 企业通讯录中的部门不等于门店授权；按部门自动给门店数据范围会越权 | 另建本地门店成员/数据范围授权，并在 SQL 运行前强制注入；SSO 只建立用户身份，不推导可见门店。 |

## 推荐实现顺序

1. 先确定部署方式（单企业私有部署或多租户 SaaS）、试点租户、首个扫码平台，以及三个端是否都需要 SSO；公司实际使用哪个套件目前尚未由项目证据确认。
2. 设计并迁移租户级 Provider 配置与外部身份映射表；设置唯一键、审计、禁用和解绑规则。密钥使用服务端密钥管理/现有加密能力。
3. 抽出可被本地密码登录与 OAuth callback 共用的“本地用户签发会话”服务，避免复制 refresh/JWT/RBAC 逻辑。
4. 按平台实现独立 OAuth adapter：授权 URL、一次性 state、code 换身份、企业标识校验、错误回调处理；优先只请求身份识别必需的最小权限。
5. 先在一个试点租户接入一个平台；验证普通用户、管理员、客服坐席、未绑定用户、禁用用户、错误企业、切换 web/admin/cs 端和退出/刷新/强制下线，再扩展其余 Provider。
6. 外部真实登录验收需要客户创建并发布的应用、HTTPS 回调域、测试账号和相应 scope。缺少这些条件时只能完成离线契约测试，不能宣称扫码登录已验收。

## 验收停止条件

评估阶段到此完成。实现阶段只有在以下证据齐备后才可标记通过：身份绑定不能跨租户；Provider 回调不能自选角色；禁用/解绑账号不能继续登录；三个客户端的准入和 Cookie 隔离保持原样；退出、刷新、强制下线有效；真实扫码回调在获授权的客户环境走通。没有应用凭据或业务确认的 Provider 标记为“受阻/未验证”，不以模拟身份冒充真实登录。
