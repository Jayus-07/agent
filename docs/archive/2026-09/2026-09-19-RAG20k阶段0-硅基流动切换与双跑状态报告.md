### 3. 双跑的直接阻塞：doc 级向量库覆盖缺口（2026-09-19 13:15 实测）

清库（TRUNCATE 三表）后按预期只重建了 chunk 级与注册表，**doc 级向量（collection=doc_db）未按注册表 doc_id 重建**，而评测门禁（`runners/rag.py:229-320`）恰好读 doc_db 的 kb_id 元数据：

```
注册表 rag_eval_kb active : 96
doc_db  rag_eval_kb 文档  : 58 条，但 doc_id 与注册表 96 个 active 全部对不上（96/96 缺失）
chunk 级 chroma rag_eval_kb: 426 条（正常）
```

结论：doc_db 里那 58 条是索引器恢复路径写入的 hash doc_id 残留，**不是**注册表 slug 行的 doc 级向量。评测跑起来会在第一个 case 就抛
`评测 KB='rag_eval_kb' 不在 doc_db 中 (available=['policy_general','rag_100_docs','rag_test_kb'])，拒绝回退 default`，169 case 全部 1ms error（本日 12:18 那次双跑实测即此）。

**修复路径（未执行，按用户指示停止）**：
1. 重新完整入库（`ingest_eval_fixtures.py --fixture-set expanded_100`）直到 `slug 行注册` 与 doc 级向量都齐全；或
2. 单独触发 doc 级重建，使其 doc_id 与注册表一致；
3. 校验 SQL（就绪判据）：
   ```sql
   SELECT count(*) FROM doc_registry dr WHERE dr.kb_id='rag_eval_kb' AND dr.status='active'
     AND NOT EXISTS (SELECT 1 FROM rag_vectors rv WHERE rv.collection='doc_db' AND rv.metadata->>'doc_id'=dr.doc_id);
   -- 期望 0
   ```
4. 之后再执行 §二.1 的双跑命令链。
