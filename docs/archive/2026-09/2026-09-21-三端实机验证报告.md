## 二、发现并已修复的缺陷（本轮提交）

### F1 网关 /api/cs 角色闸误伤用户侧抽屉（P0）— 提交 `9190247`
普通用户（viewer）调 `/api/cs/conversations/{id}/handoff` 等抽屉端点被昨日新加的
any_of 角色闸拦截 → 403 role-insufficient，**客服抽屉转人工全断**。
修复：`gateway-auth.lua` 新增 `ROLE_GATE_EXEMPT_PATTERNS` 用户侧豁免
（/confirm、/conversations/my*、/{id}/handoff、/{id}/rating），坐席端点仍受闸拦截。

### F2 接单/拒单/重派 500（P0）— 提交 `9190247`
`require_agent` 与端点共用同一 get_session 实例，身份查询令事务 autobegin，
服务层再 `session.begin()` 抛 `InvalidRequestError` → 三条路径必现 500。
修复：`offers.py` 新增 `_txn` 助手（已开事务则复用，全新 session 才显式 begin）。

### F3 接单成功后立即发消息被 409（P1）— 提交 `a9cbd2a`
`get_session` 的 commit 在依赖 teardown（**响应已发出之后**）才执行：
accept 返回 200 但事务未提交，坐席紧接着发消息读到旧状态 `agent_offered`
→ 误报 409 "claim it first"（实测 65ms 内必现）。
修复：accept/decline/reassign 三处在返回前显式 `await session.commit()`。

## 三、遗留缺陷 / 待改进（未在本轮修）

### D1 问答页多轮追问无上下文继承（用户核心诉求）
实测：第 1 轮「我想去云南旅游…」正常回答；第 2 轮追问「那当地有什么特色美食？」
被**原句**直接丢给知识库检索——「当地」脱离语境无法解析，检索空 → EvidenceGate
拒答模板「未能找到相关信息」。第 3 轮同理。**不是"只能追问一轮"，而是追问轮完全
不继承上一轮语境**。
改进方向（建议单独排期）：
1. 会话内维护 rolling context（实体槽位：目的地/日期/人数），追问时做 query 改写
   （"那当地…" → "云南的美食…"）再进检索；
2. 追问命中改写失败时降级为引导式反问（引导式追问的产品形态：
   「您是想问云南的美食、交通还是住宿？」），而非直接拒答；
3. 拒答模板前先检查上一轮答案是否已包含可引用内容。

### D2 记忆检索报 pgvector 操作符错误（P2，日志持续出现）
`[MemoryService] start_session 失败: operator does not exist: bytea <=> unknown`
—— `memory_records.embedding` 按原值比较时被判为 bytea（疑似部分行/列类型未迁移为
vector(1024)），记忆召回静默失败。聊天主流程有降级不受阻，但记忆能力实际失效。

### D3 并发回归测试预存失败（与本次改动无关，基线复现）
`test_p3_concurrency_pg.py::test_handoff_claim_has_one_success_under_twenty_concurrent_agents`
报检查约束 `ck_cs_assignment_active_handoff_required` 冲突，在改动前基线同样失败。

## 四、管理端设计建议（本轮只出方案，不动代码）

### 4.1 导航重排：8 组 38 页 → 5 组

现状「运营总览/知识运营/业务分析/可观测/成本治理/质量与配置/审批与安全/自动化」
层级过多且粒度不均（质量与配置 7 项、自动化仅 1 项）。建议按「角色动线」合并：

| 新分组 | 收纳 | 动线 |
|---|---|---|
| **总览** | 首页仪表盘 | 所有人 |
| **知识库** | 文档入库、待复核、词库、评测结果、反馈候选 | 知识运营 |
| **业务分析** | 竞品监控、选品漏斗、选品决策、报告中心 | 业务方 |
| **运维监控** | 任务中心、问答追踪、可观测 4 页、网关安全、安全运营、告警中心、定时任务 | 值班/排障 |
| **平台管理** | Prompt/Agent 节点/能力技能、预算策略、模型单价、模型供应商、工具审批、访问控制、Token 用量 | 平台管理员 |

要点：①「自动化」单页并入运维监控；②「成本治理」2 页并入平台管理（预算是治理动作
不是观测）；③ 安全相关（网关安全/安全运营）与可观测同组，排障动线不再跨组。

### 4.2 /settings/access 对标主流 RBAC 用户管理

现状：仅两个页签——用户列表（搜索/分页/改平台角色+客服角色）、审计日志。
**缺**：新建用户（现在只能靠自助注册或脚本插库）、禁用/启用、重置密码、强制下线
（目前孤悬在 /security 页）、用户详情（最近登录/在线会话/归属）。

主流 RBAC 用户管理功能清单（对标）：
| 能力 | 主流做法 | 现状 |
|---|---|---|
| 用户 CRUD | 列表/新建/禁用/删除（软删） | ❌ 缺新建/禁用 |
| 角色分配 | 单角色或角色组勾选，改后审计 | ✅（有审计） |
| 凭据管理 | 重置密码、强制下线、会话列表 | ❌（强下线在 /security） |
| 审计 | 变更历史可回溯 | ✅ |
| 组织/租户 | 部门/租户归属展示 | 部分（多租户已埋点） |

建议（企业做法，不引入新模式）：`/settings/access` 扩为三页签
**用户 / 角色 / 审计**——用户页签补「新建用户（admin 邮箱或表单直建，走既有
hash_password）、启用/禁用（status 字段已有）、重置密码、强制下线（复用 /security
的吊销接口，把入口收拢过来）」；角色页签先只读展示三平台角色+客服角色的权限说明
（权限矩阵固化后可编辑）。原 then /security 的会话列表保留（那是监控视角，非管理动作）。
