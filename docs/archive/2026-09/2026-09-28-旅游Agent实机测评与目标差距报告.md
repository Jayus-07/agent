# 旅游 Agent 实机测评与目标差距报告

> 日期：2026-09-28 ｜ 环境：本机全栈（docker app:8000 + APISIX:9080 + PG 5433）｜ 模式：**第三方 API 全 mock**
> 方法：经网关真实登录（JWT）→ `/api/chat/stream` SSE 20 轮 + REST 四件套 + 前端 `/travel` 页实机走查，对照「理想旅游 Agent 八层能力」逐层评分。
> 结论速览：**骨架与工程治理远超 demo 水准，但「实时信息」与「预订执行」两大核心空洞 + 4 个实测缺陷，使整体距目标约 45~50%**。MVP 七项里 4 项达标、2 项残缺、1 项缺失。

## 一、总评分表（八层能力）

| # | 能力层 | 得分 | 等级 | 一句话判定 |
|---|---|---|---|---|
| 1 | 需求理解与澄清 | 70% | B- | 槽位/追问/分级/记忆齐全，但口语抽取漏「2个大人」「慢一点」 |
| 2 | 实时信息检索与验证 | 25% | D | 来源披露体系优秀；实际数据=3 城 31 个种子点，天气无 mock 即不可用 |
| 3 | 行程生成与优化 | 65% | B- | 可解释性是真实亮点；无 Plan B，路线优化停在贪心 |
| 4 | 预算与预订执行 | 30% | D+ | 幂等账本/状态机工程质量高；只支持酒店/机票且聊天端两跳必断 |
| 5 | 动态调整与异常处理 | 45% | C | 多轮改单实测全过；取消指令漏识别；监控式重规划为零 |
| 6 | 输出与协作 | 40% | C- | ICS 导出实测 500（输出链路实际是断的）；无 PDF/分享/协作 |
| 7 | 交互与多模态 | 50% | C | 双通路（聊天+表单）流畅、地图打点可用；语音/图像/AR 全无 |
| 8 | 技术支撑能力 | 75% | B | 纯规则全链可测+金标+e2e+指标；LLM 缺席是表达力上限 |

**加权观感（对照目标的完整闭环「理解→检索→行程→预订→监控→重规划」）**：前段（理解+生成）可用，中段（实时数据）塌方，后段（预订+监控+重规划）只有脚手架。

## 三、实测确认的能力（亮点，对照目标属实）

1. **澄清与分级追问**：模糊问句「帮我规划一个旅游行程」→ 只追问两个必填（城市/天数），附可规划城市清单与个性化推荐；只答「福州」→ 精准追问剩余天数（A1/A2）。
2. **防幻觉立场**：「东京5天攻略」→ 明确回答「东京暂时无法规划（还没有当地的地点数据）」并给替代城市，不编造（C 轮）。
3. **可解释行程单**：逐日时刻轴+通勤耗时/距离/车费+闭馆日预警（「固定闭馆日：周一」）+开门等候预警（「09:00 才开放，需等候 30 分钟」）+未排入候选披露+数据来源段（`seed:local — 本地示例数据（未经实时校验）`）+置信度脚注（0.75「由约束通过度与数据完备度计算，非模型自评」）。
4. **跨轮改单闭环**：同一会话「必须去三坊七巷，不想去鼓山，重新排」→ 必去置顶+避雷消失+候选回填+「上一版行程作废」披露；「改成 5 天」→ 全量重排、住宿/餐饮按天伸缩（A4/A5）。需求版本链（需求 v3→v5）与指纹重排机制实测有效。
5. **偏好记忆**：A 会话说的「对海鲜过敏」与表单页的「亲子」已落 `travel_preferences` 表；新会话行程单自动带出既有偏好标签；模糊问句的推荐按偏好打分（A1「贴合你的自然偏好」）。
6. **前端表单通路**：未登录可直接用 `/travel`，填表→秒级出行程→时间轴+静态地图打点+费用拆分+👍/👎反馈，「必去灵隐寺」从其他要求字段生效置顶第 1 天。
7. **工程可测性**：32 个测试文件+34 条金标评测+5 个 e2e 驱动+Prometheus 质量指标，validator 五轴纯规则零 LLM，符合仓库 G1~G4 治理。

## 四、实测暴露的缺陷台账（按优先级）

| # | 级别 | 缺陷 | 复现 | 根因定位 |
|---|---|---|---|---|
| D1 | **P1** | **ICS 导出 500，中文目的地必现** | `POST /api/travel/export/ics` 500；UI 点「导出日历 (ICS)」红字报错 | `app/api/routes/travel.py:202`：`Content-Disposition` 头直接内嵌中文目的地（`travel-杭州.ics`），HTTP 头 latin-1 编码 → `UnicodeEncodeError`。三个支持城市全中文=100% 复现。修法：RFC 6266 `filename*=UTF-8''` + ASCII fallback |
| D2 | **P1** | **预订流对话式两跳必断** | 「帮我订一间福州的酒店」→ 域内正确反问日期；答「10月20日入住…」→ **掉出预订域**，被主路由 plan 模式接住（向量路由甚至误配到 `travel.poi_search`） | `booking_prefilter.py` 按单条消息正则判定，无域内挂起恢复（旅游域有 TravelPendingResolver，预订/商务域没有）。既有 STOP L E2E 全靠「一句话说全」（帮我预订大阪10月3日到5日的酒店）绕开了该场景 |
| D3 | **P1** | **旅游域口语说法漏路由** | 「再去福州玩两天」→ RAG 兜底「未能找到相关信息」；「福州两天游」→ 同样掉坑；「不用了，取消吧」（同会话刚改完单）→ 通用澄清兜底 | `travel_prefilter.py:27-35` 词表有「一日游」无「N天游/玩N天」类模式；且域完成后无常驻语义，取消/后续改单必须每条消息重新命中 prefilter |
| D4 | P2 | 人数口语漏抓 | 「2个大人」「2大1小」两次实测均排成「人数 1 人」 | `travel/slot_filler.py:113-117`：只认「XX人/XX个人/XX位/一家三口/带爸妈」类模式 |
| D5 | P2 | 节奏口语漏抓 | 「节奏慢一点」→ 行程单仍显示「节奏 适中（每天最多 5 地点）」 | `travel/models/brief.py:46-47`：relaxed 词表有「慢慢/放慢/慢节奏」无「慢一点/节奏慢」 |
| D6 | P2 | 无天气块时免责声明失真 | mock 关天气后行程单仍写「行程使用的天气预报为规划时点的预报」 | `experts/risk.py` 免责为静态文案，未按天气 provider 实际状态裁剪 |
| D7 | P2 | /travel 页无鉴墙 | 未登录浏览器直接可用全部功能（plan/导出/反馈） | `resolve_identity` 允许匿名会话身份。便利 vs 安全取舍需拍板（至少 feedback/导出应登录） |

## 五、八层逐层差距分析（目标 → 现状 → 差距）

### L1 需求理解与澄清（70%）
**目标**：全槽位收集+兴趣/约束识别+主动追问+必须/可选分级+用户历史偏好。
**现状**：TravelBrief 14 字段、必填仅 2、追问一次列全（最多 6 问）、必去/avoid/忌口/节奏/预算/日期均入模，偏好表跨会话预填。
**差距**：①口语抽取召回率低（D3/D4/D5 是同一族问题：纯规则词表的表达力上限）；②出发地「从上海」只记录不排程（跨城交通 P2 未做，实测偏好表 origin 也未回写）；③签证/无障碍/老人儿童/宠物等约束无模型；④「必须满足 vs 可选」只有必填/必去两级，无权重。
**补齐建议**：短平快=D3/D4/D5 词表+正则补齐（半天）；中期=travel prefilter 命中后加一层 LLM 槽位抽取兜底（与「无模型发挥」设计立场冲突，需拍板：建议限定在 slot_filler 的抽取环节，排程仍纯规则）。

### L2 实时信息检索与验证（25%）
**目标**：景点/餐厅/交通/住宿/天气/汇率/签证实时数据+来源与更新时间。
**现状**：字段体系完备（observed_at/verified/fallback_reason/来源披露段），这是好底子；但数据面=3 城 31 POI 种子（坐标自认示例值）、交通=启发式估算、天气=live-only（无 mock，本次关闭后行程单无天气块）、门票/餐厅/酒店价格全无、汇率/签证/活动/安全预警零。
**差距**：这一层是「写攻略」与「可执行行程」的分水岭，当前基本塌方。免责声明诚实，但目标要求的「实时性」未达成。
**补齐建议**：①天气补 mock 实现（哪怕确定性回放），使天气链路在测试环境常开；②腾讯 LBS 已有 key，`TRAVEL_USE_LIVE_MAP` 打开即得真实路况/POI resolve，但 POI **候选检索** live 实现缺失（腾讯不支持城市级候选→需要另接来源或自建爬库）；③票价/开放时间接景区官方或票务聚合源（P1）。

### L3 行程生成与优化（65%）
**目标**：按天时段生成+路线优化+多目标平衡+备选方案+可解释。
**现状**：骨架分配（必去置顶+地理均衡）+最近邻时刻排程+午餐插入+天气替换（live 时）+五轴校验+删除式修复+修复轮上限+完整可解释。
**差距**：①路线优化是「均衡+贪心」，无 TSP/少折返最优化（实测 day3 出现 33 分钟/11.8km 折返）；②**Plan B 完全没有**（雨天版/深度版/亲子版备选，代码层 grep 为零）；③多目标只有预算/体力硬校验，兴趣只影响推荐不影响取舍；④repair 只能删不能换序/替换。
**补齐建议**：①Plan B 用规则版可做：每个户外 POI 预挂同城室内备选，输出「雨天版」附页（1~2 天工作量）；②2-opt 就地优化相邻日顺序（纯函数，可单测）。

### L4 预算与预订执行（30%）
**目标**：分类估算+多币种+实时价+预订机票酒店门票餐厅+订单管理+发票合规。
**现状**：分类估算可×（门票/餐饮/住宿/通勤+超支校验）；预订域图（resolver→executor）+幂等账本+canonical_amount+8 态状态机+webhook 验签+对账/恢复扫描全部就位——但 provider 只有 fake，品类只有酒店/机票，且聊天端两跳必断（D2），无真实支付、无用户侧订单管理/取消入口（store 层有实现无 API/节点）、无门票/餐厅/保险、无多币种。
**差距**：脚手架完整、通路不通、数据为假。「协助预订」这一环当前用户实际用不到。
**补齐建议**：①先修 D2（把 TravelPendingResolver 模式移植给 booking/commerce 域）——已有现成模式，工作量可控；②订单查询/取消 REST+节点补齐；③真实供应商按 STOP J 七态契约逐步接入（无真实供应商前保持 fail-closed 是正确姿势）。

### L5 动态调整与异常处理（45%）
**目标**：多轮修改+监控变化自动重规划+紧急支持。
**现状**：同会话多轮改单（换景点/改天数/加避雷/重排）实测全过且版本链透明；但取消指令漏识别（D3 族）、环境监控自动重规划零实现（天气只在规划时点查一次，grep 无 monitor/watch/cron）、紧急支持零。
**差距**：目标里「明天下雨，已把户外改成博物馆」的自动化闭环完全没有——这是与「合格旅游 Agent」差距最形象的一环。
**补齐建议**：出发前 T-1 校验的 cron 任务（beat 已有基建）：对已交付行程重查天气→生成 patch 建议→推给用户确认。天气 mock 补齐后即可在测试环境打通。

### L6 输出与协作（40%）
**目标**：PDF/日历/地图收藏/导航/分享协作/多端同步/离线。
**现状**：Markdown 行程单（可复制发同行人）+ICS 导出（**坏了，D1**）+静态地图+👍/👎反馈。无 PDF、无分享链接、无协作编辑/投票、无多端同步/离线、无导航路线导出。
**补齐建议**：D1 是半小时级修复，修完「日历导出」即达 MVP 线；PDF 可由 Markdown 服务端渲染；分享（只读链接）价值高成本低。

### L7 交互与多模态（50%）
**目标**：对话+语音+图像+地图时间轴看板拖拽+主动提醒+AR。
**现状**：聊天流式（SSE 20/20 正常）+表单双通路+时间轴+地图打点（真实瓦片）+ICS/反馈按钮。无拖拽调整、无看板视图、无语音/图像/拍照翻译、无 AR/伴游、无主动提醒（值机/预约）。
**补齐建议**：时间轴卡片加「删除/替换」微交互是规则域图天然支持的改单入口，优先级高于新模态。

### L8 技术支撑（75%）
**目标**：LLM 理解生成+工具查数据+规划引擎+记忆画像+评估指标。
**现状**：反其道而行——**全程零 LLM**，换来 32 测试文件全绿可测、五轴校验确定性、34 条金标门禁、Prometheus 指标+trace 贯穿。记忆=travel_preferences 单表（忌口/节奏/标签/出发地），无过敏 severity、无同行人画像。评估指标（行程可行性/满意度/预算准确率/重规划速度/转化率）只有工程侧埋点，无业务指标闭环。
**判定**：方向本身成立（规则保底+确定性可验收），但要达「合格」目标需在两个点引入 LLM/数据：槽位抽取兜底（L1）与最终行程润色/解释（可选）。供应商生态与业务评估指标是两块真短板。

## 六、MVP 七项对照（用户口径逐条）

| MVP 项 | 判定 | 依据 |
|---|---|---|
| 需求澄清 | ✅ 达标（带缺陷） | L1 实测通过，D3/D4/D5 扣分 |
| 行程生成 | ✅ 达标 | 全链路可用、可解释、可改单 |
| 地图路线 | ⚠️ 半达标 | 静态地图打点有；导航路线/少折返优化无 |
| 预算估算 | ✅ 达标 | 分类估算+超支校验（非实时价） |
| 多轮修改 | ✅ 达标（取消除外） | A4/A5 全过；D3 取消掉坑 |
| 导出 | ⚠️ 半达标 | ICS 500（D1）；无 PDF |
| 实时信息 | ❌ 缺失 | 种子数据+天气不可用；live 默认关 |

第二阶段四项：预订支付 ⚠️（fake+通路断）、天气监控 ❌、协作分享 ❌、记忆画像 ⚠️（偏好单表）。

**总体：MVP 七项 4✅ 2⚠️ 1❌ —— 距「MVP 完整」差一口气，差距集中在实时数据与导出缺陷，均为可修项。**

## 七、建议路线（按投入产出排序）

1. **第一批（半天~1 天，全是小改动）**：修 D1（ICS filename*）、D3/D4/D5（prefilter 词表加「玩N天/N天游/N日游/取消/不排了」+人数/节奏口语正则）、D6（免责文案按 provider 状态裁剪）。
2. **第二批（1~2 天）**：修 D2（booking/commerce 域移植 TravelPendingResolver 挂起恢复）；booking 订单查询/取消最小 REST；天气 mock provider（确定性回放），让天气替换链路在测试环境常开可测。
3. **第三批（数据面，决定产品上限）**：`TRAVEL_USE_LIVE_MAP=true` 打开腾讯路况实测；补 POI 候选检索数据源（自建爬库或第三方聚合）；票价/开放时间接真实源后，行程单才从「示例数据」变「可执行」。
