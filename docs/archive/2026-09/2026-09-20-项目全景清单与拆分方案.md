## 0. 结论先行

**这个仓库不是「一个项目」，而是三条独立演进线糊在一起：**

| 线 | 内容 | 演进驱动力 | 当前状态 |
|---|---|---|---|
| **A. Agent 平台底座** | 编排 / RAG / Skill / Tool / MCP / 网关 / 可观测 | 跟框架版本、跟企业级规范 | 通用能力强，可复用给任何业务域 |
| **B. 电商业务域** | 客服 / 旅游 / 选品 / 竞品 / 库存 / 报表 / 调研 | 跟业务需求、跟运营节奏 | 已落 2 个域图 + 4 个 workflow |
| **C. Java 业务系统** | Spring Boot + SCG（客服 OA 侧） | 独立团队 | **已分离**（compose 已移出，Kafka 进 `java-loop` profile） |

**建议拆分线选 A/B**，不是前后端、也不是 Python/Java（后者已完成）。
**但不要拆 git 仓库** —— 理由与代价见 §4。

### 2.3 核心能力链路

**主链路**：`POST /chat/stream` → Input Guard 门禁 → `memory.start_session` → `graph.stream`

```
START → router ─┬─ 客服预过滤命中 ──→ cs_graph_node → END
                ├─ 旅游预过滤命中 ──→ travel_graph_node → END
                └─ 三层 Router（rule→vector→LLM）→ route_selector
                      ├─ direct   → skill_executor → reporter → END
                      ├─ workflow → workflow_executor → reporter → END
                      └─ plan     → planner → critique → supervisor(Send 并行) → reporter → END
```

**RAG 子链路**：改写 → MultiQuery → 混合检索（向量 + BM25）→ 同文档扩展 → Rerank → **EvidenceGate** → 带引用生成 → META 尾拒答判定

**SQL 子系统**：`SQLSkill → SQLAgent → Router → Generator → Validator(6 层) → RowSecurity → Executor(连接池) → PostgreSQL`
6 层安全：①SELECT 校验 ②表名白名单 ③敏感列拒绝 ④函数黑名单 ⑤LIMIT 强制 ⑥agent_readonly 只读角色

**客服子图**：`state_loader → pending_handler → cs_supervisor（handoff 拦截/循环上限/LLM 兜底）→ 5 专家 → 回 supervisor → cs_reporter`

**旅游子图**：`travel_slot_filler → travel_supervisor（纯规则）→ poi/transit/budget/risk 专家 → travel_validator →（未通过）travel_repair → 回 supervisor → travel_reporter`
> `travel_validator` = 旅游域的 Evidence Gate：纯规则、零 LLM、零 IO，四轴判定（时间/地理/体力/预算）

## 4. 拆分成两个项目的方案

### 4.1 三种切法对比

| 方案 | 切分线 | 收益 | 代价 | 结论 |
|---|---|---|---|---|
| **甲** | **平台底座 / 业务应用** | 两条演进线解耦；平台可版本化复用给新业务域；业务侧独立交付给不同团队 | 需改造域图/Skill 自注册机制（见 4.3） | ✅ **推荐** |
| 乙 | 后端 / 前端 | CI 独立、部署独立 | 前后端已分别有 package.json，收益有限 | 🔸 可顺手做 |
| 丙 | Python / Java | 技术栈彻底隔离 | **已完成**：compose 已移除 Java 服务，Kafka 进 `java-loop` profile | ⏹ 无需重复 |

### 4.2 方案甲的具体切分

**A 项目 — Agent 平台底座**（`agent-platform`，可独立发版）


**B 项目 — 电商业务域**（`agent-domains`，依赖 A）

```
customer_service/   客服域图（5 专家 + handoff）

```

### 4.3 ⚠️ 拆分的真实风险（必须处理）

**风险 1：域图自注册机制依赖同仓相对 import**

现状是 `domains/__init__.py` → `<domain>/register.py` → builder 自动布线，**不改 builder.py**。
拆成两个 package 后，`register.py` 的自动发现会失效 —— **域永不触发，且不报错**（静默失能）。

**处理**：改为 Python `entry_points` 插件发现，或显式配置 `DOMAINS_ENABLED=['customer_service','travel']` 名单 + import path。**必须配一条"域已加载"的启动断言**，否则拆完就是静默降级。

**风险 2：Skill 注册表是集中式**

`skills/registry.py::_instances` 是硬编码列表。业务 Skill（`competitor_analysis` / `travel_poi`）拆出去后，平台侧会缺项 → `capabilities.yaml` ↔ registry 双向校验测试（`test_registry_consistency.py`）**必然失败**。

**处理**：`capabilities.yaml` 也要按 A/B 拆成"平台能力"+"业务能力"两份 manifest，或改为外部可追加。

**风险 3：四层铁律的适用边界要重写**

`docs/2026-09-16-Agent-Skill-Tool-MCP四层设计规范.md` 的 G1~G4 铁律 + `test_layer_consistency.py` 的 10 条机器守护规则，都是按"单仓单容器"设计。拆包后：
- G3「谁定义谁注册，禁止集中代注册」在跨包场景下语义变了
- `scan_repo_declared_tools()` 的 AST 扫仓库判据会跨包失效

**处理**：拆包前先扩规范 §4 例外台账，明确"跨包注册"的合规形态。

**风险 4：数据库与迁移归属不清**

`agent_business` 的 7 schema 18 表同时服务平台（tasks / approvals / checkpoints）和业务（order / product / inventory）。**拆成两个项目必须先把 schema 切成两个 library 或两个 database**，否则谁跑 migration 都说不清。

### 4.4 建议路径（务实版）

**不要现在拆 git 仓库。** 分三步：

| 步 | 动作 | 收益 |
|---|---|---|
| **1** | **同仓内目录级分区**：`backend/` 拆成 `backend/platform/` + `backend/domains/`，只改 import 路径，不动注册机制 | 边界清晰、可测；零功能风险 |
| **2** | **注册机制插件化**：域图/Skill 改为 entry_point 或显式名单 + 启动断言；`capabilities.yaml` 拆两份 | 具备物理拆分的前置条件 |
| **3** | **schema 与部署单元分离**：`agent_business` 按域切 library；compose 里业务 worker 独立 service 定义 | 可独立交付、独立扩容 |

**第 3 步完成后**再评估是否拆 git 仓库 —— 那时拆分成本最低，且已有回归网兜底。

### 4.5 拆分的阻塞前置

- ⚠️ **当前工作区有 40+ 未提交改动**（模型配置治理）。任何结构性重组都必须在这批改动落定后开始，否则 diff 混入无关文件、无法回滚。
- ⚠️ **`backend/tests/` 460 文件 / 74k 行**依赖现有目录结构与 import 路径。目录级重组会大面积触动测试 import，需要一次性机械替换 + 全量回归（~11.5 min）。
- ⚠️ **并发会话在跑全量 pytest 时不得改 `backend/**` 或动容器**（13 个容器当前在运行）。
