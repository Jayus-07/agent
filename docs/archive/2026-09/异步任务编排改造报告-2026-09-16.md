## 二、架构变化

```
FastAPI /tasks ──► task_manager ──► Celery(broker: redis /1, queue: agent)
                                        │ payload 仅 task_id
                                   Agent Worker (celery prefork)
                                        │
                              TaskGraphExecutor ◄── 复用 build_graph() 主图
                                        │
              ┌─────────────────────────┼──────────────────────┐
        PostgresSaver            agent_memory.tasks       Redis pub/sub
      （LangGraph 完整状态）      （任务状态权威）          ──► SSE /stream
        thread_id=task-{uuid}    agent_checkpoints（节点历史）
```

关键设计：
1. **Celery 与 LangGraph 解耦**：Celery 只传 task_id；Agent 状态完全由 PostgresSaver checkpoint（thread_id 落库）+ tasks 表承载。
2. **恢复不重跑**：重试/恢复/宕机回队时 `graph.stream(None, config)` 从最近 checkpoint 续跑；resume 注入的用户输入经 `update_state` 合入。
3. **暂停/等待用户**：节点主动返回 `state["needs_user_input"]`（或 LangGraph 原生 interrupt）→ WAITING_USER，checkpoint 已自动保存；也可经 `POST /pause` 在节点边界暂停。
4. **取消/暂停信号**：Redis 标志位（TTL 1h），Worker 在节点边界轮询；未开跑任务额外 revoke。
5. **Skill 层零感知**：tasks/ 不被 skills/domains 引用；执行器不 import Celery（TaskGraphExecutor 可被任意运行时调用）。
6. **多用户隔离**：tasks 绑定 user_id+tenant_id；服务层强制过滤，API 层 404 不区分存在性（防枚举）。

## 三、API 文档（经 APISIX 网关加 `/api` 前缀）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/tasks` | body `{query, user_id?, tenant_id?}` → 202 `{task_id, status:"PENDING"}`（立即返回） |
| GET | `/api/tasks/{task_id}` | → `{task_id, status, progress, current_node, result, ...}` |
| GET | `/api/tasks?status=&limit=` | 用户任务历史 |
| POST | `/api/tasks/{task_id}/cancel` | 取消（节点边界生效，排队中直接 revoke） |
| POST | `/api/tasks/{task_id}/pause` | 暂停（节点边界生效 → PAUSED） |
| POST | `/api/tasks/{task_id}/resume` | body `{user_input?}`，恢复 WAITING_USER/PAUSED/FAILED |
| GET | `/api/tasks/{task_id}/stream` | SSE：`snapshot/node_start/node_finish/waiting_user/completed/failed/cancelled/ping` |

SSE 事件示例：`event: node_start` + `data: {"event":"node_start","node":"planner"}`

## 四、数据库迁移说明

- 目标库：`agent_memory`（与主图 checkpointer 同库）
- 方式 A（推荐）：**零操作**——task_service.ensure_schema() 首次调用自动执行幂等 DDL（测试已验证建表成功）

## 六、Kubernetes Worker 横向扩展方案

1. **Worker Deployment**（镜像复用 app 镜像，改 command）：
   ```yaml
   command: ["celery", "-A", "backend.workers.agent_worker", "worker",
             "--loglevel=info", "-c", "4", "-Q", "agent", "-n", "worker@%h"]
   ```
   副本数即吞吐（prefetch=1 保证公平分发）；HPA 按 Redis 队列深度（`LLEN agent`，KEDA）或 CPU 扩缩。
2. **无状态保障**：状态全在 PG/Redis，Worker 可随时杀；`task_reject_on_worker_lost` 让未 ack 任务自动回队。
3. **API 无需变更**：APISIX → app Deployment 不变；Worker 独立伸缩。
4. **依赖**：镜像需含 celery（已加入 requirements-lock.txt，下次镜像构建生效）；HPA 需 KEDA + Redis scaler。
5. **监控**：flower（已装）或 celery-exporter → Prometheus（现有 agent-prometheus 可直接接）。

## 七、已知边界（如实说明）

- 容器内已 `docker cp` 新代码 + root 安装 celery 用于验证；**运行中的 app 进程与容器 FS 在镜像重建后会还原**——正式生效需重建镜像（`docker compose build app`，由用户择机执行，本会话未动容器）。
- Worker 进程尚未启动（属运行态操作）；启动命令见 `backend/workers/agent_worker.py` 文档字符串。
- `MAIN_GRAPH_CHECKPOINTER_ENABLED` 全局开关与任务模式无关：任务执行器强制挂 PostgresSaver（MemorySaver 降级会破坏恢复语义，直接硬失败）。
- 任务模式不走会话记忆（MemoryService），一次性执行语义；多轮对话仍走 `/chat`。
