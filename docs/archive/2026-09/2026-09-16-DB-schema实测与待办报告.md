## 二、已完成（有实证）

### 2.1 空卷首启实测：定位 P0 — 建库脚本从未成功执行

**结论**：`docker/init-dbs.sh` **从未成功执行过一次**。这是"为什么必须手工补库"的真正根因。

此前（含我自己的初判）认为原因是"数据卷已存在、`docker-entrypoint-initdb.d` 不会重跑"。**该解释不成立**——真实原因是脚本自身执行失败。

证据链（4 条，逐级加强）：

1. **行尾**：`head -c 30 docker/init-dbs.sh | od -c` → shebang 实为 `#!/bin/bash\r`
2. **git 视角**：`git ls-files --eol` → `i/lf w/crlf`（索引 LF、工作区 CRLF）；`core.autocrlf=true`；仓库**无 `.gitattributes`**
3. **复现（决定性）**：起独立探针容器（新建 volume + bind mount 真实脚本 + 镜像 `pgvector/pgvector:pg16`，与生产同镜像）→ 容器 **`Exited (127)`**，日志明确：
   ```
   docker-entrypoint.sh: running /docker-entrypoint-initdb.d/10-init-dbs.sh
   /docker-entrypoint-initdb.d/10-init-dbs.sh: cannot execute: required file not found
   ```
4. **反证**：换用 `tr -d '\r'` 生成的 LF 副本，同一流程**一次通过**（`[init-dbs] 1/3 … 3/3 … 完成`）→ 归因确凿

> **严重度评估**：`docker-entrypoint-initdb.d` 中脚本执行失败会让 **postgres 容器直接退出**。即在**空卷首启**场景下，整个容器栈起不来——而现有环境因为卷里早有数据（且已手工补过），一直掩盖了这个问题。

### 2.2 纠正我自己的两个错误推断（静态推断被实测证伪）

我在此前的静态分析中提出过两个"疑似缺口"，实测后**均不成立**，如实收回：

| 原推断 | 实测结论 |
|---|---|
| `ai.tool_approval_requests` 表缺失 → 工具审批功能是坏的 | **表确实不存在，但这不是缺陷**。`backend/security/tool_approval.py:119 _ensure_table()` 会 `CREATE TABLE IF NOT EXISTS` 幂等自愈；且它用的是 `BUSINESS_DB_CONFIG`（**主连接**，非只读角色），有建表权限。表不存在只说明该功能尚未被首次调用 |
| `006_customer_service.sql` 从未执行 → 客服域缺表 | **孤儿文件**。`customer_service` 实测在 `agent_memory` 库**存在**，由 alembic memory `0003/0004/0005` 覆盖。业务库没有该 schema 属预期 |

对 `006`/`007` 两个 SQL 做全仓 `grep`：`007` 仅出现在 `tool_approval.py:120` 的一句注释里（"生产仍以 migrations/007_tool_approval.sql 为准"），**二者都不被任何脚本执行**。

> **结论**：它们是**冗余**，不是缺口。**不要把它们当缺陷去"修"**，否则会与懒建表/alembic 形成第三处重复定义。

### 2.3 两个附带发现

**（1）`docker/entrypoint.sh` 是零引用的死文件**

- `Dockerfile` 中**没有** `COPY docker/`，启动命令是第 71 行 `CMD ["python","-m","uvicorn","backend.app.server:app","--host","0.0.0.0","--port","8000"]`
- `docker-compose.yml` 的 app 服务也没有 `entrypoint:`，`command:` 只出现在 rag-service(224) / mcp(269) / redis(405)
- 全仓引用**只出现在**自动生成的 `.qoder/repowiki` 文档里

> 因此我此前"schema 管理四轨并行"的判断应修正为：**两轨（`init-dbs.sh` + 手动 alembic/rebuild_pg.py）+ 两个死文件（`entrypoint.sh`、孤儿 SQL）**。`entrypoint.sh` 里"每次启动裸跑 memory 迁移"的逻辑**从未发生过**。

**（2）宿主 PG ≠ 容器 PG（两个独立实例）**

- 宿主 `0.0.0.0:5432` 有**原生 PostgreSQL**（PID 5608）在监听
- `agent-postgres-1` 容器**未映射 5432**（compose 里 ports 被注释）
- `.env` 为 `PGHOST=localhost` / `PGPORT=5432`

→ **在宿主机跑 pytest 连的是宿主 PG，容器栈用的是容器内 PG，两者互不相通**。排查任何"库里没有表/角色/schema"的问题前，必须先确认在问哪一个实例。
