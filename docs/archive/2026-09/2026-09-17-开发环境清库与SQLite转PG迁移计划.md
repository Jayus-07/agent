# 开发环境清库 + SQLite→PostgreSQL 迁移计划

> 2026-09-17 · 范围：**仅开发环境**（dev 数据可丢弃，不做数据搬迁，只迁 schema + 代码）
> 状态：待评审

## 0. 背景与现状

- `agent-app-1` / `agent-worker-1` / `agent-rag-service-1` 三个容器**共享同一个** named volume `agent_app_data`（→ `/app/data`），SQLite 多进程并发读写是已知痛点（WAL + busy_timeout 只是缓解）。
- PG 基础设施已就绪：
  - `pgvector/pgvector:pg16` 双库：`agent_memory`（Agent 自身元数据）+ `agent_business`（业务数仓，`docker/init-dbs.sh` 首次建）
  - 连接层：`backend/sql/executor.py`（psycopg2 `ThreadedConnectionPool`，统一 `execute_sql`）
  - 迁移：`backend/sql/migrations/001~011` 编号 SQL；`docker/init-dbs.sh` 仅在空卷首启时执行
  - **参考实现**：doc_registry 双后端（`doc_registry.py` 按 `DOC_REGISTRY_BACKEND=postgres` 分发到 `doc_registry_pg.py`，`_init_db` 幂等建表，010/011 为权威 schema）
- 已知缺口：010/011 未纳入 `init-dbs.sh`（新空卷不会预建 doc_registry PG 表，目前靠应用侧幂等建表兜底）——本计划 P1 顺手补齐。
- `OBS_BACKEND=postgres` 目前只是 analytics_store.py 里的注释预留，方言层并未实现，观测族需真写 PG 实现。

## 2. 通用规范（所有批次遵守）

1. **双实现 + env 分发**，照抄 doc_registry 模式：SQLite 实现保留（单测用 tmp 路径 + 回滚兜底），PG 实现放同级 `*_pg.py`，工厂按 `"<STORE>_BACKEND=postgres"` 分发。
2. **幂等建表**：PG 实现 `_init_db` 用 `CREATE TABLE IF NOT EXISTS`；迁移 SQL 文件作为权威 schema 记录，与应用供建表语句保持一字不差。
3. **时间列保持 TEXT**，写入 `to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI:SS')`（010 先例）——与 SQLite 文本时间戳排序语义一致，`list_since`（Evidence Gate 反向驱动在用）零改动。
4. **连接统一走 `backend/sql/executor.py` 连接池**，store 内不自建 pool。
5. **库归属（两库制，按"Agent 自身元数据 vs 业务数据"划线）**：
   - **agent_memory**（Agent 私人账本，跟随 010 先例）：trace_store、analytics（含 llm_usage）、doc_registry、chunk_store、keyword_rules、doc_operation_log、workflow_runs——与 chat/memory/checkpoints 同层，是 Agent 自身运行状态，**绝不暴露给 NL2SQL**；
   - **agent_business**（平台的生意数据）：selection、selection_decision、market_research、competitor、feedback、inventory_alerts——`agent_readonly`（NL2SQL 执行身份）已挂在该库上，业务表转进来即对 SQL Agent 天然可查；该库当前为空壳，正好启用；
   - 成本：`executor.py` 单例连接池需支持双 DSN（一处基建小改）；迁移文件头标注目标库；跨库不 JOIN（现状跨 SQLite/PG/Chroma 本就无 JOIN，全靠 id 引用，无回归）。
6. env 开关与 `.env` 样例、compose `environment` 同步更新；dev 默认值在 P3 切换时统一起效。

## 4. P3 清库与重建（一次性操作，需协调窗口）

**前置检查（硬性）**：
- `git status` 确认无其他会话未提交的实施；确认无并行 pytest/评测在跑（全量 pytest ≈ 20 分钟，跑期间不动 backend）；
- 向用户确认：将 `docker compose down` 并删除三个卷，影响所有正在运行的服务。

步骤：
1. 提交所有批次代码；
2. `docker compose down`；
3. `docker volume rm agent_app_data agent_pg_data`（= "把库都清了"：SQLite 全删 + PG 全重置）；`agent_app_cache`（embedding 模型缓存）保留；
4. `.env` 将各 `*_BACKEND` 默认置 `postgres`；
5. `docker compose up -d --build`——init-dbs.sh 重建双库并应用 001~020；各 store `_init_db` 幂等补表；
6. 重灌 R3 fixtures（100 份）重建 RAG 索引（doc_registry/chunk_store/keyword_rules 在 PG 全新写入）；主语料目录 docker cp 进卷后由 rag-service 重启触发的索引同步自动补齐；
7. 跑 §5 验收清单。

> **执行结果（2026-09-17，✅ 全部完成）**：见 §5 验收注记。清库重建额外暴露 5 个"仅存在于旧卷存量、不在任何迁移中"的缺口，均已补齐迁移并进 init-dbs.sh 首启链路：
> ① prompts 三表（018）；② ai.gateway_access_logs（019，对应 Alembic 0008）；③ customer_service schema + 工具审批 + 评分（006/014_cs_rating/007 历史遗漏未进 init-dbs.sh）；④ Alembic 0003/0004/0005/0007 手写化 + chat_sessions.title ORM 漂移列（020）；⑤ agent_readonly 对 public/ai schema 的 SELECT 授权（004 修订）。

## 6. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 某批次 PG 实现有缺陷 | env 开关切回 `sqlite` + 重建卷即回滚（SQLite 实现全程保留） |
| 时间戳语义偏差（UTC vs local） | 全部走 010 的 UTC 文本约定；`list_since` 有测试覆盖 |
| 清库打断并行会话 | §4 前置检查；窗口期避开全量 pytest |
| init-dbs.sh 与应用建表语句漂移 | 迁移文件为权威源，两处语句 CI 比对（后续可加 lint） |
| Chroma/.cache 卷被误删导致重嵌模型重下 | `agent_app_cache` 删除前确认磁盘/网络可接受，或保留该卷只清 `agent_app_data`+`agent_pg_data`（评审时定） |
