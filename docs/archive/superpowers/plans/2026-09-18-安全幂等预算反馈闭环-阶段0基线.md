## 0.4 反馈、Trace 与评测数据流

```text
客户端 POST /feedback
  -> backend/app/api/routes/feedback.py
  -> backend/feedback/pg.py
  -> agent_business.feedback（session_id/msg_id/vote/reason 等）
  -> 仅 record_feedback() 指标

线上 Trace
  -> TraceCollector / trace_store_pg（agent_memory.trace_store）
  -> /evaluation/cases/from-trace
  -> evaluation.trace_bridge.build_test_case_from_trace()
  -> evaluation.curator.append_case()
  -> backend/evaluation/datasets/<module>/cases.jsonl
```

当前事实：

1. `feedback` 表只有 `session_id/msg_id/question/answer_preview/vote/reason/created_at`，没有 `trace_id/user_id/tenant_id/review_status/correction_text/expected_answer`。
2. `/feedback` 没有调用 `resolve_identity()` 或 `require_identity()`，也没有从服务端校验 Trace/消息归属。
3. `/evaluation/cases/from-trace` 直接调用 `append_case()`，没有 pending/approved/rejected/promoted 状态机；`curator.append_case()` 是直接原子写 JSONL，只有 trace_id/case_id 去重。
4. Trace `TraceRecord` 有 `request_id/session_id/tags/metadata`，PG `trace_store` 的索引字段没有 `tenant_id`，需要在阶段 5 先定义租户归属来源和查询条件，再开放反馈关联。
5. 管理端目前有 Trace 详情和 “Add to Eval” 入口，但未发现与反馈审核状态机对应的管理 API；现有 `/evaluation` 是评测集/运行 API，不等价于反馈审核 API。

## 0.6 四类契约冻结草案

### 统一失败 JSON Schema（草案）

```json
{
  "type": "object",
  "required": ["code", "retryable", "handoff_available", "message", "trace_id"],
  "properties": {
    "code": {"enum": ["INVALID_PARAM", "PERMISSION_DENIED", "NOT_FOUND", "TIMEOUT", "UPSTREAM_UNAVAILABLE", "RATE_LIMITED", "IDEMPOTENCY_CONFLICT", "BUDGET_EXCEEDED", "INTERNAL_ERROR"]},
    "retryable": {"type": "boolean"},
    "handoff_available": {"type": "boolean"},
    "message": {"type": "string"},
    "trace_id": {"type": "string"},
    "source": {"type": "string"},
    "details": {"type": "object"}
  },
  "additionalProperties": true
}
```

兼容策略：旧 HTTP/SSE/反馈客户端暂保留 `error/detail` 或既有成功字段；新字段追加在同一响应/错误帧内。生产消息禁止异常类名、堆栈、本地路径和数据库连接细节。成功响应不在工作包 1 中改写。

### 幂等状态机（草案）

```text
缺失 --claim--> running --complete--> succeeded
                   |                     |
                   +--fail-------------> failed
                   +--lease 过期--------> recoverable/running

同 key + 同请求指纹：返回 running 或历史结果
同 key + 不同请求指纹：IDEMPOTENCY_CONFLICT，不执行副作用
Redis/PG 任一关键存储不可用：副作用默认拒绝，不回退进程内存放行
```

幂等范围至少包含 `tenant + actor + operation + client_key`；请求体用规范化 JSON 哈希。外部系统无法回查成功状态时，重试不得自动再次产生副作用，应转人工。

### 预算继承草案

```text
用户覆盖 > 租户覆盖 > 系统默认
```

请求级独立计数：调用数、总 token、成本、重试次数、fallback 次数。每次 primary/retry/fallback 前检查；用户/租户日/月配额采用 Redis 原子预占 + PG 结算。当前因 `tenant_id` 未进入权威 RequestContext、Q4/Q8 未冻结，暂不启用生产硬阻断。

### 反馈状态机草案

```text
pending --人工批准--> approved --promotion--> promoted
pending --人工拒绝--> rejected
approved --重复 promotion--> 原结果（幂等，不生成重复用例）
其他状态跳转：拒绝
```

负反馈或存在纠错内容才生成一个 pending 候选；正反馈且无纠错不生成候选。Trace、用户和租户归属必须由服务端认证上下文解析，客户端不能覆盖。
