## 一、竞品分析功能可行性评估

### 1.1 四维评估

#### ① 技术实现难度：★★★☆☆（中等）

| 组件 | 现状复用 | 需新建 |
|---|---|---|
| 数据抓取 | `web_crawl` Skill（已注册）+ `data_collection` 5 阶段 Pipeline | 多源适配器（官网/电商页/新闻 RSS/社媒 API）、代理池 |
| 数据存储 | PostgreSQL + `data_collection` 存储 | `competitor` schema（竞品/价格快照/变更历史表） |
| 信息抽取 | LLM 调用链（MiniMax-M3 / DeepSeek，OpenAI 兼容） | 抽取 Prompt 模板、字段校验规则 |
| 对比分析 | Multi-Agent 编排（Planner→Supervisor）+ `business_analysis` Skill | 优劣分析 Agent、竞品拆解 Agent |
| 报告输出 | `report` Skill（Jinja2 沙箱 + matplotlib 图表）+ `email` Skill | 竞品报告模板 3-5 套 |
| 调度 | Workflow 引擎（APScheduler，已有 daily_report / inventory_alert 两实例） | `competitor_monitor` workflow 实例 |

**判断**：约 70% 能力可复用，新建部分集中在**数据源适配器**和**抽取准确率调优**——这是真正的难点，而非架构。

#### ② 所需资源

| 类别 | 需求 | 说明 |
|---|---|---|
| **人力** | 2.5-3.5 人 × 12 周 | 后端/Agent 1 人、数据工程 1 人、前端 0.5、分析业务 0.5、QA/DevOps 0.5 |
| **基础设施** | 代理 IP 池（1-3 万/月）、对象存储（页面快照）、PG 扩 schema | 均为轻量增量，无需新购服务器 |
| **数据来源** | 竞品官网、电商详情页、新闻/RSS、社媒公开 API、公开数据库 | 可选补充：第三方电商数据 API（如逐步接入合规商业数据源） |
| **LLM 成本** | 约 1-3 万/月 | 日抓 500-2000 页 × 抽取/分析调用；MiniMax/DeepSeek 价格低，可控 |

#### ③ 时间成本

- **MVP（8 周）**：3-5 家竞品 × 2 类数据源，价格/促销监控 + 周报自动生成
- **完整版（12 周）**：多源扩展、优劣分析、实时告警、前端看板、人工审校闭环

#### ④ 潜在风险

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| **数据获取合规性** | 中 | 法律投诉/纠纷 | 只抓公开数据、遵守 robots.txt、不破反爬、不抓登录态数据；上线前法务过审 |
| **数据源不稳定**（改版/反爬升级） | 高 | 抓取中断 | 适配器配置化 + 成功率监控告警 + 多源互备 |
| **抽取准确率不足** | 中 | 报告误导决策 | LLM+规则混合抽取、价格等关键字段 95% 准确率门槛、置信度标注、人工抽检 |
| **成本超支** | 中低 | 预算失控 | 抓取量→LLM 调用量联动配额；批处理合并抽取调用；Token 用量走现有 Trace 埋点监控 |
| **与方案 3 抢资源** | 中 | 双线受阻 | 按既定节奏：竞品分析优先，方案 3 只做数据基座预研 |

### 1.2 结论：✅ 建议实施

**核心依据**：
1. **复用度最高**——9 个已注册 Skill 中 6 个直接参与（web_crawl / data_collection / sql / report / email / business_analysis），是所有候选功能里与现有架构最匹配的。
2. **风险隔离好**——纯离线分析，不碰交易链路，失败不影响 GMV。
3. **已有详细落地计划**——与 2026-08-21 方案 4 实施计划完全一致，可直接执行（本文档不重复展开，里程碑见该计划）。

### 1.3 分阶段实施建议与功能边界

| 阶段 | 周期 | 范围 | **明确不做** |
|---|---|---|---|
| **P1：MVP** | W1-8 | 价格/促销监控、周报、邮件推送 | 不做社媒舆情、不做自动策略执行 |
| **P2：分析深化** | W9-12 | 优劣分析、变更告警、看板 | 不做跨行业对标 |
| **P3：运营闭环**（后续） | W13+ | 人工审校、报告 API 化、与推荐联动 | — |

**硬边界（合规底线）**：
- ❌ 不抓取需登录/付费墙后的数据
- ❌ 不绕过反爬机制（验证码、频率限制）
- ❌ 不做「自动降价跟竞」等自动执行类动作（只做建议，人来决策）

### 1.4 可扩展性与可维护性保障

**集成方式（严格遵循现有架构）**：
```
新增 CompetitorAnalysisSkill
  → backend/skills/competitor/skill.py（Skill 类）
  → registry.py 注册
  → Planner 自动发现，Capability DAG 即可用
数据：PG 新增 competitor schema（与现有 7 schema 同级规范）
调度：Workflow 引擎挂 competitor_monitor 实例（复用 @workflow/@step）
观测：Trace 记录每次抓取/抽取的 latency、token、成功率
```

**迭代兼容性设计**：
- **数据源适配器模式**：每类源一个 Adapter 类（统一 `fetch() → RawPage[]` 接口），新增数据源不改核心代码
- **抽取字段 Schema 版本化**：字段定义带版本号，历史数据可回溯
- **报告模板独立演进**：Jinja2 模板文件独立于代码，运营可自行改版式

### 1.5 多路径对比与推荐

| 路径 | 说明 | 优势 | 劣势 | 成本 |
|---|---|---|---|---|
| **A：自建爬虫 + LLM 抽取（推荐）** | 复用 web_crawl/data_collection，LLM 做非结构化抽取 | 覆盖面广、字段自定义、可控 | 需维护适配器、合规自担 | 中 |
| B：第三方数据 API 为主 | 采购商业竞品数据服务 | 数据稳定、合规无忧 | 字段固定、按年订阅贵（5-20 万/年）、覆盖竞品受限 | 高 |
| C：人工 + Agent 辅助半自动 | 分析师手动粘贴资料，Agent 做结构化和报告 | 零合规风险 | 人力密集，失去自动化价值 | 低（但价值低） |

**推荐：A 为主，B 按需补充**——核心竞品价格用 A 自建保证字段自由度；社媒声量等难抓数据可后期按需接 B。

## 二、图片生成功能模块可行性评估

### 2.1 场景拆解：先看清「图片生成」到底在生成什么

| 场景 | 真实需求 | 纯文生图 API 能力 | 差距 |
|---|---|---|---|
| **营销海报** | 精确中文文案排版、品牌色/Logo、价格/促销信息、多尺寸适配 | ❌ 文字渲染错误率高（尤其中文）、品牌元素无法精确控制 | **致命差距** |
| **产品图合成** | 产品主体**不能变形**，仅替换背景/场景 | ❌ 扩散模型会改变产品形态（电商场景不可接受） | 需 ControlNet/inpainting 或模板合成 |
| **背景/素材生成** | 创意性背景图、节日氛围素材 | ✅ 文生图擅长 | 无差距 |

**关键洞察**：海报场景 90% 的工作量是**确定性排版**（文字/价格/Logo 精确落位），只有 10% 是创意生成。用生成式模型做排版是用错了工具。

### 2.2 四维评估

#### ① 技术实现难度：取决于路径（详见 2.6 路径对比）

- **模板合成路径**：★★☆☆☆——Pillow/HTML+截图引擎即可，matplotlib 图表生成经验已具备
- **文生图 API 路径**：★★☆☆☆（接入易）——但**产出不可用于海报主流程**
- **本地 SDXL + ControlNet**：★★★★☆——需 GPU 运维、模型调优、LoRA 训练

#### ② 所需资源

| 类别 | 模板混合路径（推荐） | 本地部署路径 |
|---|---|---|
| 人力 | 1.5-2 人 × 8-10 周 | 2.5-3 人 × 12-14 周 |
| 基础设施 | 对象存储 + 现有服务器即可 | GPU 服务器（A10/4090 级，采购 3-8 万或月租 3-5 千） |
| API 成本 | 文生图按张计费约 0.05-0.3 元/张（背景素材，量小） | 无按张费用，但固定 GPU 成本 |
| 模板资产 | 需设计 5-10 套品牌模板（可与运营共创） | 需训练品牌 LoRA |

#### ③ 时间成本（推荐路径）

- **MVP（4 周）**：5 套海报模板 + LLM 文案生成 + Pillow 合成 + 前端预览下载
- **完整版（8-10 周）**：产品抠图+背景替换、AIGC 背景素材、批量生成、A/B 素材管理

#### ④ 潜在风险

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| **生成质量不稳定/品牌失控** | 高（纯文生图） | 海报不可用 | 模板合成锁定品牌元素；AIGC 只产出背景素材 |
| **广告法合规** | 中 | 违规文案（「最低价」「第一」等极限词） | 复用现有 RAG guardrails 思路：文案生成后过敏感词校验（已有 risk_filter 可扩展） |
| **API 依赖与成本** | 中 | 服务中断/费用增长 | 渲染接口抽象化，可切换厂商；素材预生成+缓存 |
| **GPU 运维负担**（本地路径） | 中 | 团队精力被占用 | 推荐 Phase 3 才考虑本地部署 |
| **与 Phase 3 平台化抢资源** | 中 | 鉴权/RBAC 延期 | 图片生成鉴权依赖低，用独立 API Key 先行 |

### 2.3 结论：🟡 需调整后实施

**核心依据**：
1. **原始设想（接文生图 API 直接生成海报）不可行**——中文文字渲染错误率、品牌元素失控、产品变形三座大山，是当前所有文生图模型的共性短板，非选型可解决。
2. **调整后（模板合成 + AIGC 素材混合架构）高度可行**——用 20% 的成本覆盖 90% 的海报需求，且与现有 Jinja2 模板 + matplotlib 的技术栈同构，学习成本几乎为零。
3. **条件**：需投入模板设计资源（与运营共创 5-10 套），这是前置条件而非技术风险。

### 2.4 分阶段实施建议与功能边界

| 阶段 | 周期 | 范围 | **明确不做** |
|---|---|---|---|
| **P1：模板海报 MVP** | W1-4 | 5-10 套模板、LLM 文案（含敏感词过滤）、Pillow 合成、预览/下载/导出 | 不做自定义模板编辑器、不做视频 |
| **P2：智能合成** | W5-8 | 产品抠图（rembg）+ 背景替换、文生图 API 生成背景素材、批量任务 | 不做实时生图（保持异步任务队列模式） |
| **P3：进阶**（可选） | W9+ | 品牌规范自动校验、A/B 素材效果追踪、本地 SDXL 评估 | 不做用户自训模型 |

**功能边界（与竞品分析联动）**：
- 海报文案输入支持手动 + 从竞品分析报告提取卖点（跨模块联动点）
- ❌ 不做设计工具（Canva 类），定位是「运营效率工具」

### 2.5 可扩展性与可维护性保障

**集成方式**：
```
新增 ImageGenSkill（三步注册，与竞品分析同规范）
  ├── Renderer 抽象接口（可插拔）
  │     ├── TemplateRenderer   — Jinja2-HTML + 截图引擎 / Pillow
  │     ├── ApiRenderer        — 第三方文生图（adapter 模式，可换厂商）
  │     └── LocalDiffusionRenderer — 本地 SDXL（Phase 3 预留）
  ├── 产物：对象存储 + PG 元数据（模板版本/参数/成本）
  └── 观测：Trace 记录每张图的生成参数、耗时、API 费用
前端：新增「素材中心」页面，走现有 Next.js 路由 + SSE 任务进度
```

**迭代兼容性设计**：
- **渲染后端可替换**：所有调用方只依赖 `ImageRenderer.render(spec) → url` 接口，换 API 厂商/上本地模型只动 Adapter
- **海报 Spec Schema 化**：海报以结构化 JSON 描述（模板 id + 文案字段 + 图层参数），与渲染实现解耦，未来换渲染引擎历史 Spec 仍可复用
- **模板版本管理**：模板带版本号，旧海报可回溯当时模板渲染

### 2.6 多路径对比与推荐

| 维度 | 路径 A：文生图 API 直出 | 路径 B：本地 SDXL + ControlNet + LoRA | **路径 C：模板合成 + AIGC 素材（推荐）** |
|---|---|---|---|
| 文字精确度 | ❌ 差 | ⚠️ 中（ControlNet 辅助） | ✅ 精确（代码排版） |
| 品牌一致性 | ❌ 不可控 | ⚠️ LoRA 需训练 | ✅ 模板锁定 |
| 产品保真 | ❌ 会变形 | ✅ ControlNet 可保 | ✅ 原图抠图合成 |
| 实施周期 | 2 周（但产出不可用） | 12-14 周 | **4-8 周** |
| 成本 | 按张计费 | GPU 3-8 万 + 运维 | **最低（素材生成量小）** |
| 创意上限 | 高 | 高 | 受模板约束（可通过素材库扩充） |
| 技术栈契合 | 中 | 低（引入新体系） | **高（与 Jinja2/matplotlib 同构）** |

**推荐：路径 C**，理由：
1. 海报需求的本质是「确定性排版 + 少量创意」，路径 C 精确匹配这一需求结构；
2. 与现有 Jinja2 模板 + matplotlib 技术栈同构，团队零新概念学习；
3. 留好升级口：Renderer 抽象接口下，路径 B 可作为 Phase 3 的一个新 Renderer 无缝插入，不推翻架构。

## 三、两项功能组合落地建议

### 3.1 节奏与资源错峰

```
W1-W4    竞品分析 P1（数据源+抓取）          [后端1 + 数据1]
W5-W8    竞品分析 P1 收尾 | 图片生成 P1 并行   [+前端0.5+后端1]
W9-W12   竞品分析 P2 | 图片生成 P2
W13+     联动：竞品卖点 → 海报文案自动填充
```

峰值人力约 4 人，与单独做竞品分析（3.5 人）错峰可控。

### 3.2 联动价值（1+1>2）

- 竞品分析输出的「差异化卖点」「价格带」可直接注入海报文案生成 Prompt；
- 后续可打通「竞品降价 → 自动生成我方促销海报草稿（人工确认）」的半自动运营流。

### 3.3 与现有 Roadmap 的关系

| Roadmap 项 | 竞品分析 | 图片生成 |
|---|---|---|
| 鉴权/RBAC（P0） | 依赖低（内部工具） | 依赖低（API Key 先行） |
| SQLite→PG 迁移（P0） | 中依赖（新数据直接建 PG schema） | 低依赖 |
| 结论 | **不阻塞 Phase 3，可先行** | **不阻塞，可先行** |
