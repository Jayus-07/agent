**版本化管理设计口径（三问三答，2026-09-30 拍板）**：
1. **提示词版本化**：唯一事实源 = PG（prompts.key 唯一 + prompt_versions 不可变追加 + active_version 指针）；语义层 = change_kind(major/minor/patch)；指针层 = prompt_aliases（production 恒=active_version，切它=完整发布语义含工作流校验/审计/快照刷新；staging 只动指针不影响运行时）；仓库镜像 = prompts.lock.json（发布原子提交纪律）；评测关联 = eval_run_records.prompt_snapshot（PG 权威口径）+ #4a 反查。
2. **发布时 in-flight 流程**：**请求级快照（pin）语义**——请求/任务开始时把 {key: version} 定格进 AgentState.prompt_versions 与 trace.tags，发布不影响已快照的值（记录保证可追溯）。执行分层：同步 chat（秒级）请求内天然一致；Celery 长任务 prompt_versions 随 checkpoint 持久化，**断点续跑的恢复时点重新快照**（恢复用恢复时点版本，旧 execution 的 trace 与新 execution 对照可发现中途换版）；多轮对话每轮重新快照（轮次间读最新——修复能及时生效，轮内一致由请求级 pin 保证）。已知窗口：跨进程生效仍需重启（M4 尾项 15s 轮询未做）——同进程发布即时，worker/rag-server 最长滞后到下次重启，期间 trace 里的版本串是判别依据。
3. **任务状态与版本绑定**：任务状态权威 = PG `agent_memory.tasks`（状态机/thread_id/checkpoint_id/trace_id）+ LangGraph checkpoint（PG postgres 优先）；**绑定方式 = state.prompt_versions 随 checkpoint 持久化 + tasks.trace_id → trace.tags.prompt_versions 双向可查**——刻意不给 tasks 表加版本列（Phase2 异步运行时 FROZEN 禁重构），trace 是任务↔版本的关联平面。

## D1（M1）Tool 契约快照 lock + 变更分类

**为什么/解决什么**：34 个 Tool 的契约（args_schema、output_type、封套）无快照无 hash，7 组守卫测试 CI 全 disabled，破坏性变更只能靠人记得跑测试；事后无法回答「哪个构建改了什么契约」。

**修改模块**：新增 `backend/scripts/gen_tool_contract_lock.py`（生成/比对/分类）+ `backend/tool_contracts.lock.json`（派生快照，进版本库）+ `backend/tests/test_tool_contract_lock.py`；后续接 release.sh 与 CI（属 D1 第二步，随 M8 一起接）。

**契约条款（每 Tool）**：`name / module(相对路径) / args_schema(canonical JSON: 参数名→类型，必填与否) / output_type(skill 声明侧，可空) / envelope(若该 tool 被 map/_base 封套约束) / capabilities(引用它的 capability 列表) / content_hash(sha256[:16])`；顶层 `generated_at / git_sha / lock_hash / tool_count`。

**变更分类规则（diff 自动判定）**：
- BREAKING：删除 Tool、删除参数、参数类型变更、可选→必填
- DEGRADED：新增必填参数、output_type 变化、structured↔text 翻转
- COMPATIBLE：新增可选参数、描述变化、新增 Tool、capability 归属变化

**不影响已有功能**：纯派生脚本+快照文件，零运行时依赖；registry 不变。

**验收门**：① 生成 lock 与 tool_registry 实时派生一致（count=34）；② 单测覆盖三种分类各至少 1 例；③ `--check` 在 lock 被人为篡改时 exit 1 且输出分类；④ 一致性三件套回归绿。
