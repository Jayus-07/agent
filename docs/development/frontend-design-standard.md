# 前端 UI/UX 设计规范（跨三端）

> **状态：现行设计规范（约束后续新增/修改页面，不代表旧页面已全部达标）。** 适用于 `frontend/` 用户端、`frontend-admin/` 管理端、`frontend-cs/` 客服端。目标是统一设计质量、减少页面风格漂移和返工，**不以此发起全站视觉重构**。
>
> **职责边界：** 本文是**视觉、交互和可用性**的主规范；[frontend-guide.md](frontend-guide.md) 是 Next.js / API / SSE / Auth / 状态一致性的工程主规范；[testing-guide.md](testing-guide.md) 是唯一测试分级规范。旅游 V2 的正式行程生命周期与业务交互以 [产品总设计书](../domains/travel-v2/product-design.md) 为准，本文不改写业务契约。

## 1. 设计原则和事实源

1. **清晰优先：** 一屏只有一个主要任务和一个突出主操作；用层级、间距、分组表达关系，不依赖大量色块、渐变、阴影、闪动徽章。
2. **少即是多：** 同类页面优先复用既有布局、导航、表单、状态、卡片和图标；只在存在明确领域差异时新增变体。不要再创建并行设计系统或新 UI 框架。
3. **状态真实：** 页面成功、保存成功、数据来源、工具进度必须来自实际业务结果。不得把 HTTP 200、SSE 流结束、Mock 或乐观展示当作正式保存证明。
4. **先任务流后装饰：** 先画清入口 → 操作 → 成功/失败 → 返回/恢复路径，再调整颜色、动效、图片。
5. **渐进一致：** 对本次实际改动范围应用本规范；已有非目标页面的 UI 缺口记录为后续事项，不因文档新增而强制重做。

**代码事实源：** 三端的 `src/app/globals.css`、现有 Tailwind 配置与 `src/components/` 组件；具体 CSS 变量以实际代码为准。当前三端 CSS 均可找到 `--accent`、`--bg-root`、`--bg-surface`、`--text-primary`、`--text-secondary`、`--border-subtle` 等变量；旅游 V2 有领域页面级样式。不要把文档示例当作新的运行时 Token 定义。

## 2. 视觉系统：一致性和信息层级

| 元素 | 新增/改动页面的规范 | 不应出现 |
| --- | --- | --- |
| 主色与语义色 | 采用当前应用已使用的 Token/组件变体；主色用于主要 CTA、选中和链接；错误/警告/成功有清楚文字 | 同屏多个抢注意力的主色；仅靠颜色表达状态 |
| 背景与卡片 | 页面背景、主要表面、边框按已有主题层级；有限阴影，优先用留白和分隔组织 | 大量渐变、装饰性高饱和卡片、层层套卡片 |
| 字体与层级 | 页面标题 → 模块标题 → 主内容 → 辅助信息，形成可辨顺序；正文优先 14–16px，辅助文字优先 12–14px | 承担业务含义的 8–10px 文字；过多字号 |
| 间距与密度 | 优先基于 4/8px 的可重复间距规律；同级卡片一致；管理端可更紧凑 | 相同模块任意间距、无意义的大量留白 |
| 圆角与图标 | 复用当前应用圆角体系与 lucide 图标；同类控件尺寸一致 | 不同图标库随意混用；为装饰重复图标 |
| 文案与标签 | 短句、明确动作、说明操作后果；单一主操作；重要风险用状态文本 | 按钮只写“确定”；“成功”“已保存”无服务端证据 |

以上文字尺寸是**新设计的可读性目标**，并非声称已有页面达标；若旧的微型标签被本次修改且承载关键业务信息，应同步提高可读性。表格密度较高时可合理压缩，但不得牺牲关键字段可辨性。

## 3. 页面布局与导航

- **用户端**：聊天、行程/卡片和地图以当前任务为中心，次要功能用渐进展开；重要操作和状态应在用户正在操作的区域出现。
- **管理端**：列表/筛选/详情/审批路径一致；危险操作应与普通编辑视觉区分；表格先处理列宽、溢出和空态再增加装饰。
- **客服端**：队列、会话、客户信息与人工操作有明确边界；重要业务状态（待确认、转人工、失败）优先于次要统计。
- 主导航的名称、当前位置、链接目标和返回路径必须一致；不能把“浏览全部”指向单个详情或空路由。
- 固定顶栏/底栏/侧栏不能遮挡内容、输入框、确认按钮；移动端适配 `env(safe-area-inset-*)`。页面跳转、浏览器返回与刷新后仍保持正确上下文。
- PC 多栏的使用前提是阅读和操作空间足够；窄屏时变为单列、Tab 或抽屉，**不得把桌面三栏等比缩小到手机**。
- 宽表、代码、引用和地图可在自己的内容容器滚动，不能使整页产生不可控的横向溢出。

## 4. 组件与交互状态

每个核心页面/组件至少明确自身实际适用的状态，不必强行展示不存在的业务状态：

| 类别 | 要处理的用户可见状态 |
| --- | --- |
| 只读查询/列表 | 首次加载、空、成功、无结果、网络错误/服务不可用、重试、切换/取消 |
| 表单 | 默认、聚焦、校验错误、提交中、已验证成功、可修正失败、不可编辑/禁用原因 |
| 正式写操作 | 保存中、服务端确认成功、409 冲突、422 不合法、结果未知、重试/查证 |
| AI/工具任务 | 准备、运行中、工具结果、部分降级、需要追问/确认、失败、业务终态 |
| 多页面实体（Trip/会话/工单） | 切换实体、迟到响应、刷新恢复、导航离开与返回、权限/资源不存在 |

- 只读请求可以取消；有副作用请求即使页面离开，也不能把客户端 Abort 当作服务端取消成功。对未知提交结果使用准确提示，具体技术契约见 [frontend-guide.md](frontend-guide.md)。
- 成功 Toast/徽章必须对应服务端已确认结果；已取消、已失败、未知、部分成功各有独立语义。错误提示应提供可执行的下一步，禁止无限 Spinner。
- 加载时用不跳布局的占位或清晰的状态提示；完成后工具活动记录不留下永远“查询中”的旧事件。
- 搜索、筛选、Tab、弹窗、日期/人数输入等采用既有组件；新增变体要有复用价值和具体使用场景。

## 5. 表单、对话和 AI 工作流体验

- 输入标签要描述用户需要填什么，给出格式/约束；必填、错误原因和修复方向应在输入附近可读。禁用时说明原因，不靠灰色按钮猜测。
- **优先减少追问轮数**：已提供的信息不重复询问；每轮最多突出一个当前最重要的问题，并明确可选答案（是否支持由领域契约决定）。
- AI 对话区将“用户消息”“生成回答”“检索证据”“Tool 调用进度”“正式业务状态”清楚分组；不把内部思维过程或敏感工具参数作为默认面向用户内容。
- 修改已有正式业务数据时，清楚区分“建议/草案”和“正式结果”。是否自动保存、是否需要确认、是否允许恢复，**由领域产品与服务端契约决定**，不得用一套 UI 假设覆盖所有领域。
- 动作后给明确反馈：发生了什么、保存到哪里、是否可撤销、需要用户做什么；Provider 的价格/营业状态/车次须展示来源、时间和可信度，不编造实时事实。
- 同一实体多个入口（聊天、表单、搜索面板、卡片）使用一致的业务名称和状态口径。

## 6. 响应式与无障碍

- **基准验收视口（桌面浏览器模拟）**：1280×900、1440×900、390×844、375×667；复杂窄屏或大字体需求增加实际相关场景。这些是最低设计回归视口，不等于已做真实设备验收。
- 正文、主要操作与重要反馈不可被移动端固定导航、系统安全区或软键盘遮挡；地图、列表与聊天有合理滚动边界。
- 触控主要操作优先提供约 44×44 CSS px 的易点击区域；密集控件遵循实际 WCAG 目标尺寸与间距，不用微小图标承担唯一操作。
- 可见焦点、键盘 Tab 顺序、Enter/Escape、表单标签、语义 HTML、`aria-current`/`aria-expanded`/`role=alert|status` 按场景合理使用。弹窗/抽屉需考虑焦点进入、退出和返回触发器。
- 文本对比度以 WCAG AA 为目标（普通文字至少 4.5:1，大字至少 3:1）；颜色不能是唯一信息通道。尊重 `prefers-reduced-motion`；动画用于反馈，不妨碍阅读和操作。
- 不因“页面过于花哨”而简单缩小字体或隐藏重要内容；先减视觉装饰、合并冗余信息，再考虑渐进展示。

## 7. 性能、图片与稳定性

- 避免为一个列表同时渲染大量重资源地图/图表；长列表按现有分页、懒加载或虚拟化能力处理。没有完整分页契约时只显示“已加载数量”，不可声称“全部”。
- 尽量使用项目已有图片组件/策略和经过验证的图片源，提供明确尺寸或稳定容器，避免布局跳动；图片失败仍保留可理解的文本与占位。
- 不在常规页面新增高频轮询、持续重动画或无必要的同步计算；SSE/WS 按对应工程规范释放资源。
- 视觉调整不能引入未经授权的 API、密钥暴露、全局状态框架、独立版本系统或对其他业务端的破坏性依赖。

## 8. 落地与验收（面向 Codex / Zcode）

**动手前：** 只读取本规范、[frontend-guide.md](frontend-guide.md)、受影响领域文档和实际源码；识别已有组件和 Token。写清 REUSE / FIX / BUILD / BLOCKED。确认页面任务流程与改动边界，避免重做已有能力。

**完成后按风险分层验证：**

| 检查 | 最小验收证据 |
| --- | --- |
| 视觉一致性 | 主次操作明显；同类控件颜色/间距/字体一致；没有新增杂乱色块/卡片 |
| 页面可用性 | 导航、刷新、返回、空/错/加载、按钮禁用说明、弹窗关闭都可用 |
| 桌面与手机 | 在受影响视口检查溢出、固定栏遮挡、滚动、焦点；浏览器模拟与真实设备分开标注 |
| 服务端语义 | 200 但业务失败不假成功；正式保存/未知结果与实际服务端一致；权限拒绝不泄漏 |
| AI/Provider | Tool 终态不长时间悬挂、来源/更新时间可信；降级与阻断不被包装成成功 |
| 回归与性能 | 受影响 Vitest、TypeScript、`git diff --check`，必要的浏览器回放；不以此代替发布全链路验收 |

报告 **PASS / FAIL / BLOCKED / NOT_RUN**，附实际运行命令、用例数、耗时、测试环境与截图或 Trace；不能用 Mock、静态编译或截图替代真实业务验收。测试范围按 [testing-guide.md](testing-guide.md)；Git/发布遵循 [release-quality.md](../operations/release-quality.md)。

## 9. 规范边界与维护

- 本文件只管 UI/UX 和设计验收，不复制 API 错误枚举、权限、SSE 事件模式、Travel Revision 或具体业务协议。
- 颜色、Token、组件 API 更改时，以**当前代码**为事实源，同 PR 更新本规范受影响规则；普通修 Bug 不例行修改文档。
- 三端可以有不同信息密度与业务导航，不要求外观完全一致；必须共享可解释、可信和可访问的体验原则。
- 现有旅游 V2 的 FE-1B 等进行中 PR 自行评估本规范与本批范围的差距；**文档合并不构成要求重开已批准批次或自动追溯重构所有旧页面**。
