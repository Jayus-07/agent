### 2.2 核心能力链路

**主链路**：`POST /chat/stream` → Input Guard 门禁 → `memory.start_session` → `graph.stream`

```
START → router ─┬─ 客服预过滤命中 ──→ cs_graph_node → END
                ├─ 旅游预过滤命中 ──→ travel_graph_node → END
                └─ 三层 Router（rule→vector→LLM）→ route_selector
                      ├─ direct   → skill_executor → reporter → END
                      ├─ workflow → workflow_executor → reporter → END
                      └─ plan     → planner → critique → supervisor(Send 并行) → reporter → END
```

| 子系统 | 链路 | 亮点 |
|---|---|---|
| **RAG** | 改写 → MultiQuery → 混合检索（向量 + BM25）→ 同文档扩展 → Rerank → **EvidenceGate** → 带引用生成 → META 尾拒答判定 | 三层拒答 + Self-Correction，无证据拒绝输出而非幻觉补全 |
| **SQL** | SQLSkill → SQLAgent → Router → Generator → Validator(6 层) → RowSecurity → Executor(连接池) → PostgreSQL | 6 层安全：①SELECT 校验 ②表名白名单 ③敏感列拒绝 ④函数黑名单 ⑤LIMIT 强制 ⑥`agent_readonly` 只读角色 |
| **记忆** | L1 短期窗口 / L2 会话（PG）/ L3 长期（PG + pgvector） | Token 裁剪 + 会话摘要 |
| **客服域图** | `state_loader → pending_handler → cs_supervisor（handoff 拦截/循环上限/LLM 兜底）→ 5 专家 → 回 supervisor → cs_reporter` | 9 节点；动作类走 资格检查→确认卡→幂等执行 |
| **旅游域图** | `travel_slot_filler → travel_supervisor（纯规则）→ poi/transit/budget/risk 专家 → travel_validator →（未通过）travel_repair → 回 supervisor → travel_reporter` | validator = 旅游域 Evidence Gate：纯规则、零 LLM、零 IO，四轴判定（时间/地理/体力/预算） |

## 3. 调优点清单

> 分三类：**3.1 已落地成果**（可直接写成"我做了什么、改善了什么"，简历主力）；**3.2 攻坚型**（有排查过程，面试最能讲）；**3.3 在推/已设计**（可写"主导设计/技术选型"）。

### 3.1 已落地成果（成果可量化）

| # | 调优点 | 做法与效果 |
|---|---|---|
| 1 | **同名 registry 消歧** | `orchestration/tool_registry.py` → `capability_registry.py`，35 处 import 同步；旧路径仅留 DeprecationWarning shim + 守护测试防回退 |
| 2 | **跨 event loop 资源泄漏** | `builder._make_sync` 改线程本地 loop 复用，定规则「Skill 禁止持有绑定单次调用的全局 async 资源」（aiohttp session 跨 loop 会炸） |
| 3 | **路由缓存正确性** | 缓存键纳入上下文位 `Router.route(query, context=)`，加 `_ROUTE_CACHE_CONTEXT_VERSION` 支持整体失效 |
| 4 | **Plan 深度失控** | `MAX_PLAN_DEPTH=8` + `plan_depth`，critique 规则 5 + `_depth_backstop` 拒绝超限计划（空 plan 直达 Reporter） |
| 5 | **导入链惰性化** | `config/llm.py` / `rag/chain.py` / `infra/llm/*` / `rag/reranker.py` 惰性化，消除 torch ~8s、sentence_transformers ~17s 的连带启动开销 |
| 6 | **RAG 评测基线重定** | 发现旧口径 0.9697 含 **RD-031 权限泄漏的虚假命中**，重定为 **Recall@5 0.9394 / MRR 0.9242 / Top-1 0.9667 / 36 通过** |
| 7 | **模型栈切换** | 切硅基流动：LLM `Qwen3-32B`、Embedding `bge-m3`(1024)、Rerank `bge-reranker-v2-m3`；索引删库重建 + 指纹校验（`60eb4b2ebe593be7`） |
| 8 | **元数据级联灰度** | 级联路由 + 影子 worker + 灰度百分比 + 独立队列故障域 |
| 9 | **统一理解层 CSUnderstanding** | 纯规则零 LLM，复用 `normalize_query` 与 `INTENT_PROFILES` 单一事实源；**200 实体样本精确匹配 ≥0.95、形近错别字 0 改写**；`decision_layer` 入 Trace |
| 10 | **Guard 边界收敛** | 注入/SQL 归一全局 RuleGuard，CSInputGuard 只留业务校验表；**100 攻击样本拦截 100/100、转人工与确认文本 0 误拦截** |
| 11 | **状态权威收口** | ConfirmationStore / HandoffStore 改为 DB 成功后才更新 L1；**并发 20 请求确认仅 1 个认领成功，坐席认领 20 并仅 1 成功、19 个 409** |
| 12 | **事件补偿链路** | PG 落库异常转 Redis Stream outbox；补偿 Worker 先接管 pending、PG 成功后再 ACK；`event_id` 复用唯一约束幂等；含 `XPENDING + XCLAIM` 降级接管 + 连续 20 次 ACK 前中断恢复测试 |
| 13 | **WS 真实链路验收** | 修正 APISIX `cs-ws` 路由缺失 `enable_websocket: true` 导致的 401/404；**100 次 ticket→WS→瞬态事件→断开，失败 0、事件 ID 重复 0、连接残留 0** |
| 14 | **前端流式滚动抖动** | ResizeObserver 内容高度 + `userScrolling` 4 秒防打断 + raf 节流，替代"依赖数组 + smooth scroll 排队"方案 |
| 15 | **前端渲染性能** | MessageBubble memo + 组件级订阅，流式期间仅最后一条气泡重渲，避免 N 条历史气泡全量重渲 + Markdown 重复解析 |
| 16 | **人工接管时延** | 客户转人工→坐席队列可见 **≈1468ms**（目标 ≤2s 达标）；坐席认领原子化（`already_claimed=false`） |
| 17 | **CS 域 B/C 剧本缺陷修复** | 三段缺陷链：①缺槽位 `"latest"` 字面匹配 → 退款确认卡永不可达 ②订单号正则 `\b[A-Za-z]{2,10}-\d{2,12}\b` 对两段式订单号截断（`ORD-20260915-0042` → `ORD-20260915`）③资格拒绝异常裸抛 → 通用报错。逐段修复 + 补齐回归测试（55 + 26 passed） |
| 18 | **网关伪头剥离 + 身份注入** | JWT HS512 验签 + Redis 黑名单 + 4 个伪头无条件剥离；12/12 场景矩阵 + Redis 故障 fail-closed |

### 3.2 攻坚型（排查过程完整，面试可展开）

| # | 问题 | 关键过程 |
|---|---|---|
| 1 | **trace_writer 死循环** | 只在全量 pytest 下暴露（单模块跑永远绿）；定位后修复，全量才跑得完 |
| 2 | **测试自污染** | 现象"首轮绿、之后全红"；根因是测试触发 embedding 缓存 → 定规则「测试触 embedding 缓存必须在 fixture 关 `RAG_EMBED_CACHE_ENABLED`」 |
| 3 | **RAG 指标虚高** | 评测 Recall 0.9697 异常偏高，追到 RD-031 权限泄漏造成虚假命中 → 修正口径并重定基线 |
| 4 | **推荐/路由静默失能** | 域图靠 `domains/__init__.py` 自动发现，漏注册时**域永不触发且不报错**；定位后补启动断言 |
| 5 | **多副本阻断项系统性识别** | 逐一排查出进程内状态：`_active_stops`（取消）、审批后备存储、`_celery_routed`（上传路由）、每 API 进程独立 scheduler；形成 8 条 P0 调优清单 |
| 6 | **BM25 全量重建风险** | 识别出增删均 O(N) 重建全局 pickle，且 `agent` 与 `rag_index` 共用 `concurrency=4` Worker → 不同文档可并发重建同一文件；给出 PG `tsvector` + GIN（Jieba 预分词）替代方案 |
| 7 | **LangGraph 并行合并不确定** | `alerts` 无 reducer，`Send` 并行分支合并顺序不确定 → 设计显式 reducer + 稳定排序 + 业务键去重，配"20 分支 1000 次结果一致"验收 |
| 8 | **容器化开发环境约束** | 无代码卷 → 改码必须 `docker compose build` 重建；`.gitattributes` 强制被 Linux 容器执行的脚本 eol=lf（否则 CRLF 复发致 `init-dbs.sh` Exited 127） |

## 4. 拆成两个项目的三种切法

| 方案 | 项目一 | 项目二 | 区分度 | 评价 |
|---|---|---|---|---|
| **甲** | 企业级 RAG 知识库问答系统 | Multi-Agent 编排平台 + 业务域落地 | **高**（一个偏检索/AI 工程，一个偏架构/工程化） | **推荐** |
| 乙 | Agent 平台底座 | 电商业务域应用 | 中（两个项目共享同一套底座，易写重） | 可用 |
| 丙 | Python AI 平台 | Java 微服务网关 / 认证体系 | 高（技术栈完全不重叠） | 需确认 Java 项目是否也算你的产出 |

### 4.1 方案甲的两个项目（推荐）

**项目一：企业级 RAG 知识库问答系统**
- 技术标签：FastAPI / pgvector / bge-m3 + bge-reranker-v2-m3 / BM25 混合检索 / Celery / PostgreSQL 16
- 核心内容：6 段检索流水线、三层 EvidenceGate 拒答、引用生成与定位、多租户与权限下推、20k 容量验收体系、评测驱动优化（Recall@5 / MRR / NDCG@10 / Top-1）
- 可量化亮点：评测基线 **Recall@5 0.9394 / MRR 0.9242 / Top-1 0.9667**；识别并修正权限泄漏导致的指标虚高；索引重建 + 指纹校验

**项目二：Multi-Agent 智能体编排平台（含客服/旅游业务域落地）**
- 技术标签：LangGraph / LangChain / 自研四层架构（Agent-Skill-Tool-MCP）/ APISIX / Redis / Celery / Next.js 14
- 核心内容：主图 8 节点 + `Send[]` 并行 + 三级路由；12 Skill / 34 Tool / 4 Workflow / 2 域图；声明式注册与 fail-fast；网关迁移 B0→B4；SSE 十类事件流式协议；管理后台 41 页
- 可量化亮点：~560 端点 / 40 路由模块；网关认证矩阵 12/12、回滚 10.8s；客服域 9 节点子图、人工接管队列可见 1468ms；并发确认 20→1 唯一赢家；100 攻击样本拦截 100/100

### 4.2 三个项目都能写的话

素材足够再拆出**项目三：AI 应用管理后台与可观测体系**（Next.js 14 + Zustand + TanStack Query，41 页；Trace/Prometheus/Grafana/Langfuse 全链路可观测；成本治理与提示词 Playground）。
