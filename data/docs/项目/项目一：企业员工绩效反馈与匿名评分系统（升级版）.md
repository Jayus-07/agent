# 企业员工绩效反馈与匿名评分系统（升级版）——项目架构设计

## 1. 项目背景与目标

本系统是在原有匿名员工评分系统的基础上，重构为完整的绩效管理平台。旨在解决以下问题：

- 原系统单体架构，扩展性差，难以支持多部门、多角色复杂业务；
- 评分高峰期数据库压力大，统计报表生成缓慢；
- 匿名性保障不足，存在刷分漏洞；
- 缺乏消息通知、权限管理等企业级功能。

**升级目标**：

- 采用微服务架构，支持高并发、可扩展；
- 引入消息中间件实现异步解耦，提升响应速度；
- 完善权限模型，支持多角色分级管理；
- 提供实时报表与数据可视化，支持导出；
- 保障匿名评分的公平性与防刷机制。

## 2. 整体架构设计

系统采用前后端分离，后端基于SpringCloud微服务架构，服务注册与配置中心使用Nacos，网关采用Spring Cloud Gateway，服务间通信通过OpenFeign，消息中间件使用RocketMQ，缓存使用Redis，数据库为MySQL（分库分表准备），持久层框架为Mybatis-Plus。

### 4.2 评分任务管理

- **核心实体**：task（任务）、dimension（评分维度）、task_participant（参评人员）、task_target（被评人）。
- **流程**：
  1. HR创建任务，填写任务名称、评分周期（开始/结束时间）、选择维度（可多选）；
  2. 指定参评人员（员工列表）和被评人（通常是员工本人或所有人）；
  3. 任务状态为“待开始”，到达开始时间自动变为“进行中”，到达结束时间自动变为“已结束”（可用定时任务或RocketMQ延时消息实现）；
  4. 任务开始后，员工可在前端看到待评任务列表。
- **分布式事务**：创建任务时，需要同时初始化多个表，并发送通知。使用RocketMQ事务消息保证：先预提交任务，发送half消息，若任务创建成功则commit消息，通知服务消费后发送通知；若失败则rollback，保证最终一致。

### 4.3 匿名评分提交与防刷

- **匿名机制**：
  - 前端提交评分时，不携带用户ID，只携带任务ID和被评人ID。
  - 后端根据当前登录token解析用户ID，但匿名处理：评分表中只记录用户ID的哈希值（加盐），无法直接关联具体用户，但可防重复评分。
- **防刷策略**：
  1. **频率限制**：对同一用户（IP+UserAgent）的提交接口做限流（Guava RateLimiter或Redis计数器），例如每分钟最多10次。
  2. **评分间隔**：同一用户对同一被评人同一维度，只能评分一次（由唯一索引保证：task_id + target_user_id + dimension_id + user_hash）。
  3. **IP限制**：同一IP一天内最多提交50次。
  4. **时间校验**：评分时间必须在任务有效期内，后端严格校验。
  5. **行为分析**：若短时间内评分模式异常（如全打满分），触发人工审核标记。

### 4.4 评分结果统计与报表生成

- **实时统计**：
  - 评分提交后，通过RocketMQ发送消息到statistic-service，异步更新统计结果。
  - 统计结果存入Redis（如task_id:target_user_id:avg_score），同时异步写入MySQL统计表作为持久化。
  - 热门统计（如部门平均分、个人排名）直接查询Redis，减少数据库压力。
- **报表生成**：
  - 支持按任务、部门、个人维度生成图表（柱状图、雷达图）。
  - 导出Excel/PDF：使用EasyExcel或POI，异步生成后上传OSS，通过消息通知用户下载。
- **缓存更新策略**：
  - 设置Redis过期时间（如任务结束后7天），若任务重新计算则主动更新。
  - 使用Redisson分布式锁防止缓存击穿。

### 4.5 消息通知

- **触发时机**：任务开始、任务即将结束、任务结束、评分结果公布、异常告警。
- **消息类型**：站内信（存入数据库）、邮件（调用邮件服务）、企业微信机器人（Webhook）。
- **可靠性**：RocketMQ普通消息，保证至少一次投递。消费端做幂等（如根据消息ID去重）。
- **失败重试**：消费失败进入重试队列，超过次数进入死信队列人工处理。

## 5. 技术亮点深入剖析

### 5.1 匿名性与防刷设计

- **挑战**：既要保证匿名性（管理者无法追查谁打了低分），又要防止恶意刷分破坏公平性。
- **解决方案**：
  - 用户ID哈希存储，不可逆，保证匿名。
  - 唯一索引（task_id+target_user_id+dimension_id+user_hash）防止重复评分。
  - 结合限流、IP限制、时间校验等多维度风控。
  - 若发现异常评分，可由管理员标记无效，重新计算统计。

### 5.2 高并发评分处理

- **挑战**：评分高峰期（如月底考核）可能有数千人同时提交，直接写入数据库会导致锁竞争、响应慢。
- **解决方案**：
  - 评分请求先写入Redis（list或set），返回“提交成功”给用户。
  - 后台定时任务批量刷盘到MySQL，或使用RocketMQ异步写入。
  - 采用RocketMQ顺序消息保证同一任务的评分按顺序处理，避免统计偏差。
  - 数据库层面使用批量插入，减少连接开销。

### 5.3 实时报表缓存

- **挑战**：统计结果需要实时更新，且可能被大量用户同时查看（如部门经理查看下属得分）。
- **解决方案**：
  - 采用“写后失效”策略：评分提交后，删除相关统计缓存，查询时重新计算并缓存。
  - 使用Redis的Hash结构存储维度得分，如 `stat:task:123:user:456` 存各个维度得分。
  - 热点数据设置较短过期时间（如10分钟），避免冷数据长期占用内存。

### 5.4 微服务拆分与分布式事务

- **挑战**：创建任务涉及多个服务（任务表初始化、通知发送），需要保证数据一致性。
- **解决方案**：
  - 使用RocketMQ事务消息：任务服务先发送half消息，然后执行本地事务（写入任务表），若成功则commit消息，通知服务消费；若失败则rollback。
  - 对于跨服务的数据查询，采用最终一致性设计，允许短暂不一致。
  - 引入Seata分布式事务框架作为备选，但考虑到性能，优先使用事务消息。

### 5.5 性能优化

- **数据库优化**：
  - 分表：按任务ID分表（如rating_0~15），减轻单表压力。
  - 索引：针对查询场景建立联合索引（task_id, target_user_id, dimension_id）。
  - 读写分离：主库负责写，从库负责统计查询。
- **缓存优化**：
  - 缓存用户权限、任务基本信息、热门统计结果。
  - 使用Redis pipeline批量操作，减少网络开销。
- **限流熔断**：
  - Gateway层配置Sentinel限流，防止突发流量压垮服务。
  - 服务间调用配置Hystrix或Resilience4j熔断降级。

## 6. 部署方案

- **环境**：Docker + Kubernetes（或简单docker-compose）。
- **服务实例**：核心服务（user、task、rating）部署2个以上实例，statistic服务可根据压力动态扩容。
- **中间件**：MySQL主从（1主2从），Redis哨兵/集群，RocketMQ集群（2主2从）。
- **监控**：Prometheus + Grafana监控各服务指标，ELK收集日志。

本系统通过对原有匿名评分系统的微服务化改造，引入了分布式架构、消息中间件、缓存等技术，解决了高并发、数据一致性和匿名防刷等核心问题。同时，完善的权限管理和报表功能使其成为一个成熟的企业级绩效平台。项目不仅体现了对SpringCloud生态的掌握，还深入实践了分布式事务、异步处理、缓存设计等高级技术，是展示个人能力的优质项目。

## 项目二：分布式电商秒杀系统

**背景**：电商领域常见项目，能充分展示你对高并发、缓存、消息队列的理解。即使没有真实上线经验，作为技术研究或内部项目也可以。

**技术栈**
SpringBoot + SpringCloud + Mybatis-Plus + MySQL + Redis + RocketMQ + Docker

**核心模块**

- 秒杀商品管理（后台配置秒杀活动、库存、时间）
- 秒杀接口暴露（前端获取动态秒杀地址）
- 用户秒杀下单（高并发下库存扣减、订单生成）
- 订单异步处理（RocketMQ削峰，最终写入数据库）
- 支付模拟与超时处理（MQ延时消息取消未支付订单）

**技术亮点与难点**

- **Redis预减库存**：秒杀请求先操作Redis库存，减少数据库压力，结合Lua脚本保证原子性。
- **分布式锁**：使用Redisson实现Redis分布式锁，防止超卖。
- **RocketMQ事务消息**：解决扣减库存与创建订单的分布式事务问题，保证数据最终一致。
- **接口限流**：基于Sentinel或Guava RateLimiter对秒杀接口进行限流，防止恶意请求。
- **动静分离**：秒杀页面静态化，CDN加速，减轻服务器压力。

**技术亮点与难点**

- **WebSocket长连接管理**：维护用户连接，心跳保活，连接断开自动清理。
- **消息可靠送达**：客户端ACK确认，服务端重试机制，消息持久化到MySQL。
- **离线消息处理**：用户离线时消息存入Redis，上线后拉取。
- **消息有序性**：使用RocketMQ顺序消息保证同一会话的消息顺序。
- **多端同步**：通过消息版本号或拉取方式实现多端消息同步。
